# ── ① 需要 PostgreSQL —— ✅ 已清空 (2026-08-10) ──────────────────────────────
# 曾有 22 个文件, 全部 `OSError: Connect call failed 127.0.0.1:5432` (149 errors)。
#
# 真因**不是**「缺 PG」, 而是: 这些文件里 18 个**本来就写着**
#     if not settings.postgres_url:
#         pytest.skip("No Postgres configured")
# 而 `Settings.postgres_url` 是拼出来的字符串(f"postgresql://{u}:{p}@{h}:{port}/{db}",
# 各字段都有默认值) → **永远非空**。那个守卫是结构性的死代码, 从来没生效过一次。
# 于是「没有 PG」这个状态被表达成了 149 个 error, 整组被挂上台账好几个月。
#
# 判据: **写「没配就跳过」的守卫时, 要确认「没配」这个状态真的表达得出来。**
#       一个恒为真的表达式后面跟着 skip, 和没写守卫是一回事。
#
# 修法在 tests/conftest.py: 会话开始时探一次可达性, 连不上就把 postgres_url 置空,
# 让那些守卫按作者本来的意图生效。不改生产语义。
# ⚠️ 探针本身也踩了一次同形状的坑: 第一版用 socket.create_connection 判「端口通」,
#    而本机那个端口上确实有东西 accept 但不是可用的 PG(握手后即断,
#    ConnectionResetError WinError 64) → 探针判定「可达」并放行, 什么都没改善。
#    改成真的 connect + `SELECT 1` 才对。
#    判据: **判别式要验「只有真东西才有的特征」, 不能验代理指标。**
#
# ⛔ 这不增加覆盖: 22 个文件里 146 个用例仍然是 skip, 只是从「伪装成错误」变成
#    「如实报告」。但同组另外 **61 个用例本来就不需要真库**, 它们此前被整文件排除,
#    现在真正进了门禁 —— 这部分是净增的守护。

# ── ② event loop 取法过时 —— ✅ 已清空 (2026-08-01) ──────────────────────────
# 曾有 5 个文件, 全部 `RuntimeError: There is no current event loop in thread 'MainThread'`。
# ⚠️ 我本机 (py3.11) 见到它时判断成「本机 py 版本差异, CI 的 py3.10 应该没事」——
#    **这个判断被 CI 证伪了**: py3.10 上同样 192 次。是真问题, 不是环境差异。
# 根因: 这 5 个文件用 `asyncio.get_event_loop().run_until_complete(coro)` 跑协程。
#    新版 pytest-asyncio (1.3.0) 在每个 async 用例后清掉本线程的 loop, 于是这些**同步**
#    用例只要**排在任何一个 async 用例之后**就拿不到 loop。所以它们单独跑全绿、
#    进套件才炸 —— 是顺序依赖, 不是文件本身坏。
# 修法: 11 处全部改成 `asyncio.run(coro)` (都是一次性协程 + 假 pool, 无跨调用 loop 态)。
# 判据: `pytest smartbi/services/restaurant/tests/ smartbi/gold/tests/test_clean_display_name.py
#        smartbi/gold/tests/test_gold_reads_restaurant.py
#        smartbi/gold/tests/test_review_connected_contract.py`
#        —— 改前 41 failed / 406 passed, 改后 447 passed。

#   prod venv 实测 polars 1.43.0 / pandas 1.5.3 / **pyarrow 缺席**, requirements
#   也只声明 polars。而全仓 grep `from_pandas` / `to_polars`, **非测试代码里一次
