## ⛔ 硬约束（八条，执行项，不是提醒）

下面八条**不是**用来识别问题的形态，是每次都要照做的动作。
它们各自都已经先以「形态」的身份写进过本文件，然后**在写进去之后又被踩了一次** ——
所以升级成硬约束。**读到形态会点头，读到硬约束才会动手。**

### 硬约束 1：诊断输出一律落文件再查，禁止管道直接 `head` / `tail`

```bash
#  ❌ 报错正好在被截掉的那一段里
./scripts/deploy/release-cretas.sh ... 2>&1 | tail -30

#  ✅ 全量落盘, 再让「我看了多少」变成显式的数
./scripts/deploy/release-cretas.sh ... > /tmp/deploy.log 2>&1; echo "EXIT=$?"
wc -l /tmp/deploy.log
grep -n -E "ERROR|FAIL|拒绝" /tmp/deploy.log
```

**为什么是硬约束**：同一天栽了**四次**，其中第三、第四次发生在把
「形态 A⁗ 我看到的是全部吗」写进本文件**之后**：
`sorted(v.keys())[:9]` / `grep "^DUMP"`（pytest 进度点粘在行首） /
逐意图遍历同一句问句 / **部署命令尾部的 `| tail -30` 把失败原因整段吃掉** ——
最后那次代价是一次 3 分 29 秒的白构建加一轮误诊。

🔴 **第二个理由（2026-08-13 新增）：管道还会替换退出码。**
`cmd | tail -3` 的退出码是 **tail 的**，而 tail 几乎永远成功。

```bash
#  ❌ rc 是 tail 的, 永远 0 —— 失败被读成成功
python -m probe | tail -3; echo "rc=$?"
#  ✅ 直接取, 要看输出就先落盘
python -m probe > /tmp/probe.log 2>&1; rc=$?; echo "rc=$rc"; tail -3 /tmp/probe.log
```

⚠️ 这比截断更阴：**截断至少你知道自己没看全，退出码被替换是无声的。**

🔴 **第三个理由（2026-08-13 新增）：多步流水线用 `&&` 串，不要用 `;`。**

```bash
#  ❌ 闸拒绝了 commit, 后面照跑, 建出一个空 PR
./scripts/safe-commit.sh "..." files; git push; gh pr create ...
#  ✅ 前一条失败就停
./scripts/safe-commit.sh "..." files && git push && gh pr create ...
```

实测：硬约束 7 那道闸**正确地拒绝了提交**，而我串在后面的 `gh pr create` 照跑，
留下一个空壳 PR。**闸拦住一步，不代表流水线后面的步骤知道它被拦了。**
与「管道会替换退出码」同源：`;` 让后一条无视前一条的成败。
实测：验证对账闸的变异对照时，我拿到 `rc=0` 就以为闸没红，
而那个 0 是 tail 的。

### 硬约束 6：含转义字符的内容，**从产生到落盘全程不经过 shell**

**做法**：用能**直接落盘**的工具写（Write / Edit 这类）。
非要经过 shell，就用 `chr(92)` 这种**显式构造**，不要依赖转义写法。

```
X ssh host "python - <<'EOF' ... EOF"     两层解释, 转义在中间被吃掉
X cat > script.py <<'EOF' ... EOF         「落文件」了, 但落盘那一步仍过 shell
O 用 Write/Edit 直接写文件 -> 语法检查 -> 跑
O 非过 shell 不可时: BS = chr(92); pattern = BS + "x1f"
```

**为什么是硬约束**：转义在 heredoc 里**连栽三次**，
而且**症状不是报错，是行为不对** —— `s.count(pattern)` 返回 0，
看起来像「代码里没有这个模式」，实际是模式被吃掉了一层反斜杠。

🔴 **「落文件」不是终点，「不经过 shell」才是。**
第一版这条约束写的是「一律落文件再跑」，照做之后**仍然中招** ——
因为那个文件本身是用 heredoc 写出来的，转义在**写入时**又被吃了一层，
落盘的脚本直接是语法错的。

⚠️ 本条最好的证据是它自己：这段说明第一次写进规则时，示例里的转义
**被吃成了空串**，规则正文里躺着两个空引号和一个真正的 0x1F 字节 ——
一条讲「转义会被吃掉」的规则，自己的例子被转义吃掉了。

⚠️ **这是本节第三次「落文件」成为解法** —— 与硬约束 1（诊断输出落文件）同一个形状：

> **不要在管道或内联里做需要精确字符的事。**
> 管道会截断你要看的字符，内联会吃掉你要写的字符。
> 两者都**不报错**，只是给你一个错的读数或一个错的脚本。

### 硬约束 2：部署判据是「在运行中的东西里找到这次改动的标记」

`DEPLOY_EXIT=0` **不是**判据。`RELEASE_FINAL_STATUS=deployed` 也不是。

```bash
# 每次部署后必做, 二选一或都做:
#  a) 进程启动时间 晚于 制品/代码 mtime
ssh <host> "ps -o lstart= -p \$(systemctl show -p MainPID --value <svc>); stat -c '%y' <artifact>"
#  b) 在运行中的制品里 grep 到这次改动的标记
ssh <host> "unzip -p <jar> '<class>' | strings | grep -c '<标记>'"
```

**为什么是硬约束**：`release-cretas.sh` **只发 Java + web-admin**，
纯 Python 的 PR 合完跑它会得到 `DEPLOY_EXIT=0` / `RELEASE_FINAL_STATUS=deployed`
而**东西根本没上线**（Python 走 `deploy-smartbi-python.sh --env prod`）。
所有判据全绿，改动没上 —— 实测踩过。
另有一次 `RELEASE_FINAL_STATUS=no-op` 被误读成「部署了」，靠比进程启动时间才认出来。

### 硬约束 3：跨样本批量读数，开跑前清缓存并**贴出清了哪几个**

```python
# 模块自带 helper 就用 helper —— 拼错的属性名不会报错, 只会让清理静默失效
for fn in ("clear_semantic_plan_cache", "clear_route_cache", "clear_tenant_gate_cache"):
    getattr(ri, fn)()      # ⛔ 不要 getattr(..., None) 然后 if callable
```

并且**参数化遍历要断言被参数化的那一维真的不同**（例：`intent` 列逐行不同），
否则「N 次全绿」可能只是同一个样本跑了 N 遍。

**为什么是硬约束**：三次实测。①`_PLAN_CACHE` 是个不存在的名字，`getattr` 默认
`None` 静默 no-op，同时漏清 `_ROUTE_CACHE` → 读数 25/13 修正后是 29/9；
②19 个意图同一句问句 → 路由缓存 replay 18 次，两个读数全作废；
③更早一次：r2 有 59/85 命中 r1 刚写进去的计划缓存，「两轮完全一致」是构造出来的。

### 硬约束 4：定时跑批的退出码是**三态**，不是两态

```
rc=0  没问题
rc=1  有问题（读数有效，且指向缺陷）
rc=2  这次没量到东西 —— 阳性对照没通过 / 样本 0 条 / 仪器起不来
```

`rc=2` **必须单独告警**，用与 `rc=1` 不同的措辞。

```bash
if [ "$rc" -eq 2 ]; then
    echo "XXX INSTRUMENT DEAD $(date '+%F %T') — 阳性对照未通过, 本次读数作废" >> "$ALERTS"
elif [ "$rc" -ne 0 ]; then
    echo "XXX DRIFT $(date '+%F %T') — 有条目不再等价" >> "$ALERTS"
fi
```

**为什么是硬约束**：两态跑批把「没量到」折叠进「没问题」。
一个连不上库 / 阳性对照为 0 的跑批会**安静地天天绿**，而它一个样本都没看过 ——
本仓已有先例：52 断言的回归电池随租户收敛一起死了 4 天，每天报一次没人处理。

⛔ **`rc=2` 那一态要主动构造一次**（例：把库名指到不存在的库、把样本源清空），
   确认它真的到得了。三态的价值全在第三态，而第三态平时永远不会自然发生 ——
   不构造就不知道它能不能到达。**与「让闸红一次」是同一条判据。**

### 硬约束 5：变异 / 改写脚本一律**文本模式 + `newline=''`**，禁止 `bytes` 字面量

```python
#  ❌ 中文注释进 bytes 字面量 → SyntaxError: bytes can only contain ASCII
d = open(p, 'rb').read()
d = d.replace(b'old', b'new  # 说明')

#  ✅ 文本模式 + newline='' —— 不做任何行尾转换（与二进制 IO 同样不污染 CRLF），
#     又能处理非 ASCII
s = open(p, 'r', encoding='utf-8', newline='').read()
open(p, 'w', encoding='utf-8', newline='').write(s.replace('old', 'new  # 说明'))
```

**为什么是硬约束**：`bytes` 字面量只能含 ASCII，写中文注释当场 `SyntaxError` ——
**同一天栽了四次**。它最初是为了躲 CRLF 污染（`pathlib.write_text` 在 Windows
把整文件转 CRLF，两个 PR 因此被打回）而选的，但 `newline=''` 同样不转换行尾，
**而且没有 ASCII 限制**。源码改写不需要字节精度。

⇒ 换成 `newline=''` 之后，「中文不能进 bytes」这个坑**从物理上消失**，不靠记得。

### 硬约束 7：squash 合并之后，本地分支必须**重开**

merge 完立刻做，**不做这一步别写下一行代码**：

```bash
git fetch origin main
git worktree add -b codex/claude-<task>-<n> ../cretas-<task>-<n> origin/main
git cherry-pick <已经写好的那个 commit>     # 如果改动已提交在旧分支上
```

**为什么**：squash 合并把整个分支压成 main 上的**一个新 commit**，
原分支的 commit **不再是 main 的祖先**。在原分支上继续追加再开 PR，
`gh pr merge` 直接报冲突：

```
Run the following to resolve the merge conflicts locally:
  gh pr checkout 2564 && git fetch origin main && git merge origin/main
```

2026-08-13 一晚踩两次（#2564、#2566 双双作废，两轮 CI 白跑）。

⛔ **不要用 `git merge origin/main` 去救旧分支** —— 那会把已经被 squash 进 main
的改动再合一遍，PR diff 变脏。cherry-pick 到干净的 origin/main 分支更省事，
也正是「worktree 永远 off origin/main」那条规则的本意。

判据是机械的，不需要判断：**只要刚 squash 合并过，下一批改动就开新分支。**

**机械触发点（2026-08-13 加）**：光有机械判据不够，**触发点也不能靠记得** ——
写下这条规则之后我当天又犯了两次。所以放进 `scripts/safe-commit.sh`：

```bash
gh pr view "$branch" --json state --jq .state   # MERGED → 拒绝提交
```

⛔ 不能按 commit hash 检测（squash 让 hash 对不上），按 **PR 状态**能绕开。
⚠️ 拿不到状态（离线 / 未登录 / 没开过 PR）一律**放行** —— 防手滑的闸不该在断网时把人挡死。

### 硬约束 8：改共享结构前先数，改完再数，两个数必须相等

```bash
# 改之前, 把这个数写下来
git grep -c '<那个结构的标志串>' -- <文件>      # BEFORE_COUNT=N
# 改完再数一次: 已改处 + 显式登记「故意不改」处 == N
```

**为什么是硬约束**：同一晚**三次**踩同一个形状 ——

| # | 共享结构 | 有几处 | 我改了几处 | 症状 |
|---|---|---|---|---|
| 1 | `_RESOLVER_DIMENSIONS` 子集比较 | 3 | 1 | 拒答从一道闸**挪到下一道**，读数像「还没修好」 |
| 2 | 毛利 / 毛利率同口径 | 2 | 1 | 毛利对上了，**毛利率还是两个数** |
| 3 | `resolve_gross_margin` 的 meta 出口 | 4(+1) | 1 | 对账闸读不到，连报 rc=2 |

⛔ 「故意不改」的那些要**显式登记并写理由**（与 `DELIBERATELY_NOT_PROJECTED`
同一条纪律：登记是留痕，不是豁免）。不登记就分不清「漏了」和「有意跳过」。

⚠️ 它挂在**形态 D** 下面，不独立成条 —— D 说「两份会漂」，
这条说**漂是怎么造出来的**：每次「只改一处」就现场制造一份漂移。

🔴 **数之前先确认你数的是不是那个东西**：第 3 次我数出「meta 有 4 处」并据此
下了诊断，而真因是**探针自己没传 role**（RBAC 把金额抹了），根本不在那 4 处里。
⇒ 闸报「没量到」时，**先查仪器自己的调用参数**，再去查被测对象。

**两层，都要**（这是第一次出现「机械约束正确执行了，但瞄错了方向」）：

| 层 | 保证什么 | 靠什么 |
|---|---|---|
| 机械约束（本条） | **你不会忘了数** | 触发点（`safe-commit` / 固定动作） |
| 形态 A | **你数对了东西** | 「我想知道 X ／ 我实际在量 Y」并排读一遍 |

⛔ 上面那次两层都在、第一层过了、第二层没做：`BEFORE=4 / AFTER=4` 完全正确，
而我想知道的 X 是「闸为什么读不到 resolver」，实际量的 Y 是「meta 有几处构造点」。
**机械约束不会替你想「这是不是那个数」。**

## 形态 A：我量的这个数，不是我真正想知道的那个数

**判据（动手前做，一次）**: 把这两句并排写下来读一遍 ——

```
我想知道的是 X：______
我实际在量的是 Y：______
```

X ≠ Y 就停下重新设计仪器。这一步花 30 秒，省下的是整轮读数。

### 实例

| # | 我想知道 X | 我实际量的 Y | 后果 |
|---|---|---|---|
| 1 | 存量晋升计划还能不能用 | plan spec 字段异同 | 量成了「契约演进」——存的 plan_json 里根本没有 `aggregation` 键 |
| 2 | 餐饮租户的数据 | `smartbi_db`(测试库)的数据 | 四张表全 0 行，我写成「不是 RLS，是真的有问题」 |
| 3 | 建厂缺了哪些配置 | 「真实工厂有多少行」 | 三条 TENS 级里两条不是缺陷（0 行合法） |
| 4 | 租户能算哪些指标 | 表有多少行 | 把 fill rate=0 的「税额/实收」承诺给了店长 |
| 5 | 窄路径有没有人走 | `Branch:TieredFirst` 计数 | 那是「委派成功」，不是「走了窄路径」 |
| 6 | **正文里的数有没有出处** | **我的正则切出来的东西有没有出处** | 见下方「A‴」——中位命中率 5.6% |

### A‴：判据能实时开火，不是事后总结（本套判据的第一次实战）

数字出处闸（`number_provenance.py`）自带一条判据：
**「上线前先量命中率分布，近 0% 或近 100% 都是仪器问题，不是产品结论」**。

第一次量：**中位命中率 5.6%**。按这条判据没有去写「产品在编数字」，而是先查仪器，
当场揪出两个我自己的缺陷：

- 正则把 `2026-07-14` 切成 `2026` / `-07` / `-14` **三个"数字"**，全判无出处
- 源池常年为 0 —— 我只喂了 `kpis`，没喂完整执行产出

修完（剔日期 + 喂全产出）重量：**中位 52.7%**（min 15.4% / max 100%，两端都不退化）。

⚠️ 值得单独记一笔的是：**这个缺陷是被判据本身抓住的，不是事后复盘想起来的**。
所以这一条不是「写下来好看」的规则，它会在你手上开火。**把它当成会响的东西用。**

### A⁗：我看到的是全部吗

**截断、分页、`head`、`[:N]`、少写一个锚点** —— 都会把「没有」变成「我没看到」。
这和「0 次没有阳性对照就没有意义」是**同一条判据的两面**：
前者问「我的读数覆盖全了吗」，后者问「我的仪器活着吗」。

实测（2026-08-12～13，一天之内三次，全在我自己的读取工具上）：

| # | 长相 | 差点导致的错误结论 |
|---|---|---|
| 1 | 探针打印写 `sorted(v.keys())[:9]`，而 `rows` 排在第 9 位之后 | 「我改的那层不在这条路上」——差点去改别的层 |
| 2 | `grep -a "^DUMP"`，而 pytest 的进度点粘在行首成了 `.DUMP …` | 「19 个意图只跑了 1 个」 |
| 3 | 逐意图遍历用**同一句问句**，路由缓存把第一次的结果 replay 给后面 18 次 | 「19 次全绿」——那条断言是恒真式，只测了 1 个意图 |
| 4 | 部署命令尾部 `| tail -30`，把失败原因整段吃掉 | 「构建成功了怎么没部署」——报错就在被截掉的那 30 行外 |
| 5 | 推导钉子用**文本 grep** 数调用点，把 docstring 里**提到**函数名的那行也数上 | 「调用点变成 3 处」——仪器自己造了个假读数。改用 **AST 数真正的 `Call` 节点** |
| 6 | 对账命令尾部 **无条件** `echo "(空=零新增)"` | 明明列出了两条新增失败，下一行还在打「空」—— **内容对，标签假** |

前五例的共同点是**「没看全」**：读取工具把「没有」变成了「我没看到」，
或者把「提到」变成了「调用」。

🔴 **第 6 例是新形状，而且更危险**：内容是对的（那两行失败确实打出来了），
**是标签在说谎** —— 工具把结论**硬编码**了。「没看全」至少不会主动断言一个错误结论；
这一种会。

**判据**：任何「（空=X）」「（0=没问题）」这类**结论标签必须由实际值算出来**，
不能无条件打印。

```bash
#  ❌ 结论写死, 与实际输出无关
comm -23 <(sort a) <(sort b); echo "(空=零新增)"

#  ✅ 结论由实际值算出来
comm -23 <(sort a) <(sort b) | tee /tmp/new.txt
echo -n "新增条数: "; wc -l < /tmp/new.txt
```

以上六例，缺陷都不在被测的东西上，在量它的那把尺子上。

判据：**读数出来之后，先证明它在变**。参数化遍历要断言「被参数化的那一维真的不同」
（例：`intent` 列逐行不同），否则一次全绿可能只是同一个样本跑了 N 遍。

### A⁵：一个原因解释两个症状时，逐个验证机制对每个症状都成立

实测（2026-08-13，owner 侧）：同一台机器上两个症状 ——
① Chrome 打不开自家官网 `ERR_ADDRESS_INVALID`（DNS 被劫持成 `198.18.2.x`）；
② 发布时 SSH 到 `10.66.66.1` 那一跳在 key exchange 前被关闭。
`198.18.0.0/15` 是代理 fake-IP 段，看起来一个原因解释了两者。

**但机制对第二个症状不成立**：`10.66.66.1` 是字面 IP，SSH 根本不过 DNS ——
那一跳走的是 TUN 路由，不是 DNS 劫持。两个不同机制被并成了一个。
同一条推理还捎带出第二个错误：「`ssh 47.100` 正常是因为物理直连放行」也不对，
实测那条连接的本地地址同样是 `198.18.0.1`（走同一个代理）。

判据：**一个原因解释 N 个症状时，逐个验证那个机制对每个症状都成立**。
「能解释」不等于「就是它」——尤其当 N 个症状分属不同协议层时。

### 变体 A⁶：仪器自己的**会话上下文**，可能不是你以为的那个

2026-08-13 实测，本轮**最贵**的一次错读。

我逐租户量覆盖率，每个租户前面写了：

```python
await conn.execute("SELECT set_config('app.factory_id', $1, true)", fid)   # ← true = 事务级
await conn.fetchrow(coverage_sql, fid)
```

asyncpg 是**自动提交**的：`set_config(..., true)` 只在那一条语句自己的隐式事务里
有效，下一条 `fetchrow` 已经没有它了。于是 RLS 用的是
`bootstrap_probe("MOCK_REST")` 在**会话级**设的那个值，而我的 SQL 又写着
`WHERE factory_id = $1` —— 两个条件求交，**除 MOCK_REST 外每一家都恒为 0**。

我据此报出「21 家真实餐饮租户一行数据都没有」，owner 拿它做了方向判断。
用会话级（`false`）+ 每租户独立连接重测，真相是：**其中三家有数据，
一家 616,887 笔、数据到昨天、覆盖率 49%**。

判据：
- **RLS / 会话变量下量多租户，每个租户用独立会话，并断言上下文真的生效**
  （查一次 `current_setting('app.factory_id')` 贴出来）
- ⚠️ 「查询有 `WHERE factory_id = $1` 就够了」是错的 —— RLS 是**再加一层**，
  两层不一致时结果恒空，而且**不报错**
- 🔴 阳性对照要**跨样本**：我当时有阳性对照（MOCK_REST 读出 234,306 行），
  但它恰好是会话里那个租户 —— **一个只在某一个样本上成立的阳性对照，
  证明不了仪器在别的样本上活着。**

### 变体 A′：问活进程要真相 —— 不止 environ

「配置文件/jar 里的默认值」和「这个进程实际在用的值」是两回事。
默认值恰恰指向测试库。要问就问 `/proc/<pid>/`：

| 问什么 | 去哪问 | ⚠️ 坑 |
|---|---|---|
| 用哪个库/密钥 | `environ` | `.env.prod` 不含 `POSTGRES_DB`，只有 systemd unit 里有 |
| 日志真的写到哪 | `fd/` | `cretas-prod.log` 只收到 stdout banner，真日志在 `fd/6` → `logs/cretas-backend.log` |
| 相对路径相对谁 | `cwd` | |
| **用哪个解释器/可执行文件** | **`cmdline`** | 🔴 **`exe` 会说谎** —— 它把 symlink 解析掉：本轮 `exe` 指向 `/usr/bin/python3.11`，而 `cmdline` 显示真正在跑的是 `venv-current/bin/python`。照 `exe` 跑，第一行 `from __future__` 就 SyntaxError，且 `httpx`/`pandas` 全 import 不到（丢掉的正是 venv 那一层，site-packages 就挂在那儿） |

### 变体 A″：日志取数的窗口

daily rotate 7 + copytruncate，logback 另有 rolling。
**第二天 grep 活文件只数得到第二天**。用 `zgrep` 覆盖 `.gz`，
或每天固定时间累加。**每次把文件清单和字节数一起贴出来** ——
否则「0 次」分不清是「没发生」还是「我只看了 20 分钟的窗口」。

## 形态 B：机制在，只是没接上

代码里那个函数写得好好的，测试也绿 —— 但**生产上没人调它**。
单测对这一类是盲的：它直接调被测函数，绕过了「谁调它」。

**判据（每个 PR）**:
1. 至少一条断言跑在**产品真实入口**上（真实例、真数据结构，只桩掉外部 IO）
2. 新增抑制开关 / 闸 / 清洗时，能回答一句：**「生产上谁保证它被调用？」**
   答不上来就是没接上。
3. 🔴 **「产出端有了」≠「消费端收得到」——中间每层单独确认。**
   每层留一个可观测点，**二分定位**，不要一次改三层然后看结果。
   （实测代价：有一次修完第一层仍是 `None`、修完第二层还是 `None`、第三层才通。）

### 实例（七例）

| # | 机制 | 断在哪 |
|---|---|---|
| 1 | `sanitize` 清洗黑话 | 生产那条路径根本没调它；源码闸绿是因为它在断言里**自己模拟**了 sanitize |
| 2 | `awaitingClarification` 抑制发现块 | 接的是错的信号，首轮拒答漏网 |
| 3 | 载体闸 | 闸的形态变了，闸本身没跟着变 |
| 4 | 前端 reveal 动效 | 把元素裁成 0 宽 → IntersectionObserver 恒不相交 → 9 个眉题从来没显形 |
| 5 | `_unsupported_requirement_question` 的 `available` 列表 | 三个调用点都 guard 在 `not supported_requested_metrics`，`available` 恒为 `[]` |
| 6 | `gold_reads.py` 的 `kind` | Python 改对了，但这一路**根本不透传** `kind`，Java 永远走默认分支 |
| 7 | **`rows` 投影** | `generic_answer.py:413` 明明返回了 `"rows": [r.rows for r in results]`，而最终响应的键是 `['delegate','charts','kpis','code',…]`——**没有 rows**。数据在产出端，消费端找的是 `kpis`/`charts`，中间某层把它丢了。表现：正文印着 5 行表格，机器可读侧 `kpis: []` / `charts: 0` |
| 8 | **默认窗口没接到回放路径** | 「只缺时间就补默认」修在 T3 产出处（`tier == "llm"`），而**晋升路由回放走的是另一条路**，够不着。实测：同一句「折扣力度多大」，LLM 路直接答、回放路反问。⚠️ 这一条是我在**自己刚写完的修复**上踩的 —— 修复也会有「机制在、没接上」 |

**第 7 例是这一形态的典型长相**：不是数据缺失，是**投影丢失**。
判断依据是「产出端有 / 消费端没有」，而不是「查不到数」——
两者的修法完全不同（前者接线，后者补数据），搞混会去补一份根本不缺的数据。

### B′：断言本身可能是恒真式

本轮实测两次：
- 「按钮没出现」——`findingService` 是 mock 没打桩，`refusalFollowup` 在 findings 为空时一律返回 null，**无论走哪条路都没按钮**。变异时那条断言纹丝不动。
- 「自洽闸」——左右两边来源相同，一次都红不了。

判据：**每条正向断言配一条能让它红的对照**。让它红不了，它就没在守任何东西。
阴性断言（「X 不该出现」）额外要求：**先证明 X 在别的路径上出得来**。

### B‴：桩的形状，要能在生产上出现

B′ 是「断言不会红」。这一条不同：**断言会红，但它守的场景在生产上永远不发生。**

2026-08-13 实测。我给打烊日结设计了三态，注释写着：

> 营收算不出来是 `None`，分不清「没营业」和「执行链没跑通」；
> **订单数分得清（`0` vs `None`）**。

**订单数分不清。** `orders` 是 `COUNT(...)`，**空集上返回 0 而不是 NULL**。
三态里的 `no_data` 在生产上**永远到不了**。

单测是绿的，而且带变异对照——因为 `_FakeConn` 直接喂了 `{"orders": None}`，
一个**真实 SQL 永不产出**的形状。桩的自由度让我可以构造任何输入，
**包括被测系统的真实上游永远不会给出的输入**。

判据（写桩数据时，每个值问一次）：**真实那一侧，真的会给出这个形状吗？**

- 聚合函数尤其要当心：`COUNT` 空集给 **0**，`SUM`/`AVG`/`MAX` 空集给 **NULL**。
  混着用会得出**相反**的结论。
- 最硬的一步只要 30 秒：**拿一个必然为空的真实输入去跑**（不存在的租户、
  未来的日期），看它落到哪一态。我就是这么发现的。
- 再往下一层：**数据里根本不存在的区分，写多少代码都造不出来**。
  「今天没营业」和「今天数据没落库」在事实表上是同一个长相（都是没有行），
  要分清必须有外部信号（营业日历 / ETL 水位）。先确认信息在不在。

## 形态 C：变异要打在**被守的行为**上，不是某一行实现上

**判据**: 问「这条断言在守什么行为？」然后**破坏那个行为**，而不是随手改一行代码。

### 实例

| # | 我打的 | 应该打的 | 结果 |
|---|---|---|---|
| 1 | 只改 `assert entry.category` | 整个校验块 | 相邻的 `assert category in CATEGORIES` 仍在空串上触发 → 假绿 |
| 2 | 只改 `record_row` | 也要驱动 `_run_case` | 断言没覆盖真入口 |
| 3 | 把 `unavailable` 塞进 `isClarification` | ✅ 对 | 但先得让按钮**能出得来**（见 B′） |

### C′：`失败就 continue` 会丢掉信息量最大的样本

实测：D 探针第二版写了「(a) 执行失败就 continue」，
于是 34 条环境失败被静默跳过，**活下来的 6 条恰好全是不走执行链的问题** ——
唯一能暴露「我的探针起不来执行链」的对照被我自己跳过了。

判据：失败要**计数并逐条贴**，不许 continue。三分类里「执行失败」那一类
按 plan-spec 比对完全看不见，恰恰是最该量出来的。

### C″：变异不红时，先证明**变异真的生效了**，再下「断言没用」的结论

🔴 **同一个观察，两个相反的结论：**

```
断言没用   → 变异后不红 → 断言在守空气
变异没生效 → 变异后不红 → 断言可能好好的, 是变异没打进去
```

⚠️ 这条不是新增一句提醒 —— 它给我们之前**所有**「变异全绿所以断言没用」的判断
开了一个**可能翻案的口子**。那些结论都该复查一遍。

**做法**：让被变异的值**可观测**，确认变异到达之后，不红才是结论。

```python
# 变异之后, 先断言「变异确实到达了被测代码」
monkeypatch.setattr(reg, "METRICS", patched)
assert "wastage_qty" in unlocked_split_by_column()[column]["direct"], (
    "变异没打进反查 —— 后面那条断言无论红不红都没有意义")
# 到这里才轮到看正文变没变
```

**实测（2026-08-13，一天之内两种成因都遇到）**：

| # | 变异后不红 | 真正的原因 |
|---|---|---|
| 1 | 改 `Metric.requires` 而开价纹丝不动 | `fill_offers` 用 `from ... import METRICS` 把名字**绑死在自己模块上**，`monkeypatch.setattr(reg, "METRICS", ...)` 够不着它 —— **变异没生效** |
| 2 | 改 `requires` 而**产品正文**纹丝不动 | 那一列的**闭包非空**，正文只说闭包解锁的指标，直接命中的变化根本不出现在文案里 —— 变异打在了**正文看不见的地方** |
| 3 | 「按钮没出现」变异后纹丝不动 | 协作者 mock 没打桩，无论走哪条路按钮都出不来 —— **这一条才是真的「断言在守空气」** |

前两条改的是**变异**，第三条改的是**断言**。分不清就会去改错那一头。

⚠️ **这条规则推上去当天就开火了一次**（2026-08-13）：T2 开价改成「直接命中 /
闭包命中分开说」之后，产品入口那条变异**不红了** —— 因为它打在
`fact_pos_item.qty` 上，而那一列**闭包非空**，正文只说闭包解锁的指标，
直接命中的变化根本不出现在文案里。按本条先查「变异有没有到达正文」，
换成闭包为空的 `tax_amount` 才恢复可见。**不是断言没用，是变异打在了看不见的地方。**

### C⁶：修复要按**最不显眼的那个**验收，不是最显眼的那个

2026-08-13 实测。毛利口径修复：分子换成实收，分母忘了换。

```
毛利   475,623.83  两条路一致   ← 最显眼的那个数, 已经对上了
毛利率 63.5% vs 66.3%           ← 派生出来的那个, 还是两个数
```

**修复的进度会掩盖修复的缺口**，掩盖方式是**让最容易被检查的那个先对上**。
人看到毛利一致就会停下来。

判据：**毛利对了不算，毛利率对了才算；营收对了不算，派生指标对了才算。**

⚠️ 这条和「判据必须递归」（本文件 C″ 附近那个 `gross_margin` 的例子）
是同一件事的两面：**递归是怎么找到最不显眼的那个，这条是为什么要找它。**

### C‴：断言可能守着一个**我们已经不想要**的行为

`assert "决定系数" in question` **不是**恒真式（它真会红），也**不是**变异没生效 ——
它好好地守着一个行为，只不过那个行为现在被判定为**缺陷**（黑话漏给店长）。
于是它从保护变成了阻挡。

**三者的症状不一样，第三个最容易被读错：**

| | 变异后 | 真相 |
|---|---|---|
| B′ 恒真式 | **不红** | 断言在守空气 |
| C″ 变异没生效 | **不红** | 断言可能好好的，是变异没打进去 |
| **C‴ 守着旧行为** | **红** | 断言好好的，是**需求变了** |

🔴 前两个的症状都是「不红」；这一个的症状是**红得理直气壮** ——
最容易被读成「我改错了」然后**把改动回退掉**。

**判据**：改产品行为被断言拦住时，先问一句
**「这条断言守的是需求，还是历史？」** 是历史就改断言，是需求就改方案。

**⛔ 改断言最容易滑成删断言。** 正确的改法是**把守的东西从「字面」抬到「性质」**，
并补一条阴性对照：

```python
#  ❌ 守字面 —— 而这个字面正是要消灭的东西
assert "决定系数" in question

#  ✅ 守性质 + 阴性对照
assert "答不了" in question, "没有明确拒答"
assert "没画出来的图" in question, "没守住「不谎报成功」"
assert "决定系数" not in question      # ← 阴性对照: 黑话不许回来
```

⚠️ **克制也是判据的一部分**：同一次改动里另有两处措辞（「价格变动」
「对照门店或对照时段」）被既有断言钉着，但它们**本身不是黑话** ——
那两处保持原样。**去黑话只动黑话**，顺手改措辞只会白白弄红既有断言。

### C⁗：变异脚本本身会造缺陷

- `pathlib.write_text` 在 Windows 把整文件转 CRLF → PR diff 从 1680/17 膨胀成 2763/1100，两个 PR 被打回。**一律二进制 IO**。
  判据：`git diff --stat` 与 `git diff --ignore-all-space --stat` 对不上就去查（对不上不一定是污染，但一定要查）。
- `mv` 恢复备份带回**旧 mtime** → 源码比 `.class` 还老 → maven 增量编译跳过重编，跑的还是变异后的字节码。
- 变异串尾部加注释会把闭括号注释掉 —— `PROV_MEASURED  # MUTATION` 让 `)` 失效，报的是 SyntaxError 不是断言失败。

### C⁵：清缓存要用模块自己的 helper，别拼名字

实测：探针里写 `for name in ("_SEMANTIC_PLAN_CACHE", "_PLAN_CACHE")`。
`_PLAN_CACHE` **根本不存在**（`getattr` 默认 `None` → 静默 no-op，不报错），
而真正存在的 `_ROUTE_CACHE` 一次都没清。模块自己提供了
`clear_semantic_plan_cache()` / `clear_route_cache()` / `clear_tenant_gate_cache()`。

判据：**拼错的属性名不会报错，只会让你的清理静默失效**。有 helper 就用 helper。

## 形态 D：同一个东西有两份，它一定会漂

**症状比形态 B 更隐蔽** —— 它能跑，只是跑的是旧的那份。不报错、不变红、不缺功能。
B 是「机制在、没接上」，你至少会发现它没生效；D 是「机制在、接上了、接的是过期的那份」。

**判据**：发现自己在复制粘贴时问一句 **「哪一份是真的？」**
答不上来就该抽成一份。抽不动（比如跨语言、跨仓、跨运行时）就要有**一道闸钉住两份必须一致**。

⛔ 与硬约束 5 同一个思路：**不是提醒你别漂，是让它漂不起来。**

### 实例

| # | 两份是什么 | 漂成什么样 |
|---|---|---|
| 1 | `restaurant_ops_router` 里**三处**手写限定语 | 第三处措辞已经漂成「未覆盖成本的**部分**」，另两处是「**菜品**」——同一个口径两种说法 |
| 2 | 探针自举配方**复制粘贴在两个脚本头部** | 写第三个探针时没继承，40 条里 34 条报「餐饮执行链暂时不可用」，整轮 D 读数作废 |
| 3 | 等价性探针**两处副本**（探针树根目录 / 部署树 `smartbi/scripts/`） | `ModuleNotFoundError` —— 这次是**报错**了才发现；下次它可能只是跑了旧的那份 |
| 4 | `RELEASE_BACKEND_TREE_PATH` 常量**只改一半调用点** | 同时长出**两种相反**的坏法 |
| 5 | 「不要塞进 `conversionRates`」这句警告写在 spec 的 YAML 注释里 | 而**模型从来不读 spec** —— 正确结论写在了另一份上，执行者看不到 |

### D′：抽不成一份时，闸要钉的是「两份一致」，不是「各自都对」

各自都对是两条独立断言，它们同时绿也不排除两份内容不同。
钉一致性的形状是：**一份是源，另一份从它生成或对它校验**。

## 形态 E：闸的**完备性**和闸的**存活**是矛盾的

**判据：宁可让闸窄而可信，不要宽而被关掉。**

一道天天误报的闸，最终结局是被加 `noqa`、被注掉、或者被人默认忽略 ——
**那时它的覆盖率归零**。而一道窄的闸至少那一小块是真的。

### 实测（2026-08-13，黑话闸）

把闸从「只扫 1 个模块」扩到「扫全部模块」之后，报出 9 条。逐条读：

| 类型 | 条数 | 是不是真违例 |
|---|---|---|
| 给**模型**的 prompt（「你是能力登记审核员…」）| 1 | ❌ |
| SQL 串 | 2 | ❌ |
| 正则 | 1 | ❌ |
| 开发者断言消息 | 1 | ❌ |
| **真的会发给店长的** | **3** | ✅ |

**9 条里 6 条是误报。** 而误报正是让人把闸关掉的那个东西。

⚠️ 同一次扩面还暴露了反方向：`prod` 上**天天在发**的那句
「查询维度超出计划 resolver 的能力范围」**仍然不在清单里** ——
因为它没有中文标点，被「面向用户」的启发式当成键名跳过了。

🔴 **两个方向同时失效，根因是同一个**：没有「面向用户」这个判定，
用「有没有中文标点」当**代理**，而这个代理同时造出假阳性和假阴性。

### 判据：代理判据要标出来，并且要能被替换

**静态分析判不出「这个串会走到用户面前」。** 要判对只有一条路：
**把面向用户的串收敛到一处定义，闸扫那一处。**

在那之前：
1. 闸**只报不拦**（具名常量 `ENFORCE_JARGON_GATE = False`，不要写 `if False`）
2. 在闸自己的注释里**写明它用的是代理判据、看不见什么**
3. ⛔ **不要靠不断加启发式去逼近**「面向用户」—— 那会做出一个更复杂、
   误报更多、仍然漏 f-string 的东西。

## 报数时同时报口径（形态 A 的变体）

**两个数相同不代表是同一件事。**

实测（2026-08-13）：两轮都报「9 条」，而它们是**两个完全不同的集合** ——
前一轮的口径是「未扫模块里、**经 sanitize 之后**仍含黑话的串」，
后一轮是「全部模块里、**源码字面串**含黑话的」。数字巧合相同，
如果只报「9 → 9」，会被读成「没变化」。

这不是形态 A 的「量错了对象」，是**没说清量的是什么** ——
读数本身没错，错在它不带口径就被并排放在一起比。

**判据：报一个数的时候，把「这个数是怎么来的」一起报。**
尤其在两轮之间改过仪器时 —— 那时数字可比性为零，除非口径写出来。

## 改 `.claude/` 之前

```bash
git diff --stat HEAD origin/main
```

确认自己不在一个落后的分支上。实测过两次：项目根目录先后停在落后 **1251 / 1303 个 commit**
的分支，整晚加载的 rules/skills 全是旧版，据此给出两个自洽但错误的根因。

⚠️ **新增一条规则文件之后，必须同时把它登记进 `CLAUDE.md` 的常驻清单** ——
那份清单是**手工维护**的，文件放进 `.claude/rules/` 并不会自动加载。
本文件自己差点就是形态 B 的第八例。
