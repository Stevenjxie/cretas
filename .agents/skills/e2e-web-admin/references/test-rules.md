# E2E 测试执行规范

> 整合自: TestDino Playwright Skill, firstloophq/claude-code-test-runner,
> Playwright Test Agents (Planner/Healer), lackeyjb/playwright-skill

## 执行行为准则

**在测试执行期间，严格遵守以下指令:**

1. **不要偏离测试计划。不要询问跟进问题。** 遇到歧义时做最合理的决定并继续，在证据区块中报告歧义。
2. **优先使用 `browser_snapshot` 而非 `browser_take_screenshot`。** Snapshot 提供结构化 DOM 数据，token 消耗更低。
3. **每个模块最多 20 次工具交互。** 超过限制标记为 TIMEOUT。
4. **测试前检查数据前置条件。** 如果测试需要特定数据（原料有单价、产品有 BOM、客户有地址），先检查是否存在，不存在就先创建。不允许因"测试数据不完整"导致测试跳过。
5. **提交失败必须补全重试。** 如果表单提交失败（缺字段、验证不通过），必须补全缺失字段后重新提交，直到成功或确认是代码 bug。不允许"报告失败就结束"。

## 绝对禁止 (违反则整个测试无效)

1. **禁止用 curl/API 调用代替前端操作。** 所有 CRUD 测试必须通过 Playwright 浏览器执行（打开页面→点按钮→填表单→点提交）。curl 只允许用于健康检查和数据前置条件准备，不允许用于替代 L2/L3/L4 的任何测试步骤。
2. **禁止无证据 PASS。** 没有 evidence 区块的 PASS 标记为 ⚠️ UNVERIFIED。
3. **多角色登录测试也必须走前端。** 必须 Playwright 打开登录页→输入账号密码→点登录→验证首页加载。不允许只用 curl 调 login API。

## 硬性规则 (违反则单项测试无效)

1. **必须实际填写并提交表单** — 报告必须有 `filled:` 证据行，列出每个填写字段的具体值
2. **必须记录提交反馈** — 报告必须有 `toast:` 证据行，记录确切的 toast 文本（不能只说"success toast appeared"）
3. **必须验证数据持久化** — 报告必须有 `list after:` 证据行，刷新页面后确认数据在列表中可见
4. **跨模块必须验证下拉列表** — 报告必须有 `下拉列表:` 证据行，列出实际看到的选项
5. **必须验证前后端校验一致** — 检查带星号(*)的前端必填字段 = 后端 @NotNull/@NotBlank 字段
6. **提交失败不算完成** — 如果提交返回错误，必须分析原因、补全字段、重试。只有提交成功或确认是 KNOWN_BUG 才算测试完成

**强制证据模板 (必须逐项填写，不能省略):**

```
### [模块名] — [操作]
  action: [点击了什么按钮，打开了什么弹窗]
  evidence:
    - filled: 字段A=值1, 字段B=值2, 字段C=值3
    - toast: "确切的toast文本内容"
    - API: HTTP [状态码], success=[true/false], message="..."
    - list after: [数据在列表中可见/不可见，具体行内容]
    - validation: 前端必填标记与后端一致=[YES/NO]
  result: ✅ PASS / ❌ FAIL / ❌ KNOWN_BUG [原因]
```

不允许用"filled form with data"、"success toast appeared"这类模糊描述代替具体值。

## 前后端校验一致性检查

**必须检查每个创建/编辑表单的字段校验:**

| 检查项 | 方法 | 失败标记 |
|--------|------|---------|
| 前端有星号 → 后端有 @NotNull | 对比 formRules 和 DTO 注解 | ⚠️ VALIDATION_MISMATCH |
| 后端有 @NotNull → 前端有星号 | 反向对比 | ⚠️ VALIDATION_MISMATCH |
| body vs query param | 检查前端 post(url, body) vs 后端 @RequestParam | ❌ PARAM_MISMATCH |
| HTTP method | 前端 put/post/delete vs 后端 @PutMapping/@PostMapping | ❌ METHOD_MISMATCH |

常见失败模式 (本项目已发现 4 次):
- 前端 POST body 传参，后端 `@RequestParam` 期望 query param
- 前端调 PUT，后端只有 POST (405 Method Not Allowed)
- 后端必填字段前端没标星号，用户不填就 500

## Healer 模式 (--fix)

来自 Playwright Test Agents 的自愈模式:

```
运行测试 → 失败 → snapshot 页面 → 分析根因 → 修复代码 → 重跑 → 重复直到通过
```

**关键逃生舱:** 如果错误持续存在且你有高置信度认为测试是正确的（应用本身有 bug），标记为 `KNOWN_BUG` 并附注释解释实际行为 vs 预期行为。不要无限循环试图"修复"应用。

```
result: ❌ KNOWN_BUG
  expected: 点击"创建"后显示成功 toast
  actual: 500 系统异常 (后端缺少 orderDate 校验)
  action: 需要修复后端 CreatePurchaseOrderRequest DTO
```

## Layer 5: 业务正确性校验 (2026-04-04 新增)

> **教训**: 六扇门客户反馈中的15个 bug 全部通过了 L1-L4 测试。
> 原因: L2 只验证"操作能完成"，不验证"结果是否正确"。
> 此 Layer 弥补这一致命盲区。

### 5.1 UUID 检测 (必须)

**规则**: 任何面向用户的显示字段如果值匹配 UUID 格式，标记为 ❌ UUID_DISPLAY_BUG。

```javascript
const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;
// 白名单: 以下列头含这些关键词的列不检查
const ID_WHITELIST = ['编号', 'ID', 'code', '编码', '追踪码', '批次号', '工厂', 'factoryId', '参考号'];
```

**检测范围**: 详情页 descriptions-item 的值 + 表格名称/人员类列

**snapshot 执行方法**:
```
1. browser_snapshot → 获取所有 cell / descriptions-item
2. 过滤: 排除列头含 ID_WHITELIST 关键词的列
3. 对剩余每个值: UUID_RE.test(value.trim()) → true 则 FAIL
```

**必须检查的字段**: 销售/客户列, 采购/供应商列, 详情页外键关联字段(客户/供应商/创建人/审批人)

**证据模板**:
```
uuid_check:
  - 销售订单列表/客户列: "上海海壹佰米..." ✅ (非UUID)
  - ❌ 采购订单详情/供应商: "ab1c7d45-ebe8-..." → UUID_DISPLAY_BUG
```

### 5.2 关键字段非空检测 (必须)

**规则**: 详情页的核心业务字段不能为空/"-"。

| 模块 | 必须非空的字段 |
|------|--------------|
| 销售订单详情 | 客户名称, 订单编号, 下单日期, 总金额 |
| 销售订单行项目 | 产品名称, 数量, 单位, 单价 |
| 采购订单详情 | 供应商, 订单编号, 下单日期 |
| 采购订单行项目 | 原材料名称, 数量, 单位 |
| 研发样品 | 样品编码, 样品名称, 产品状态 |

**证据模板**:
```
field_check:
  - 采购行项目/原材料名称: "大豆油" ✅
  - ❌ 采购行项目/原材料名称: "" → EMPTY_FIELD_BUG
```

### 5.3 重复提交检测 (必须)

**两种重复，语义不同：**

| 类型 | 场景 | 期望结果 |
|------|------|---------|
| **A. 实体内去重** | 同一订单内添加同一产品两次 | ❌ 应拒绝 "不能重复" |
| **B. 独立实体重复** | 创建两个内容相同的独立订单 | ✅ 应允许（不同订单号） |

**类型A必须测试的模块** (同实体内唯一性):
- 销售订单: 同一订单内重复添加同一产品 → 被拦截
- 员工管理: 重复用户名 → 被拦截
- 客户管理: 重复客户编码 → 被拦截

**类型B必须测试的模块** (连续创建不报错):
- 采购订单: 连续创建两笔 → 两次都成功，订单号递增
- 销售订单: 连续创建两笔 → 两次都成功

| 结果 | 判定 |
|------|------|
| 类型A: 第二次被拒绝 | ✅ PASS |
| 类型A: 第二次成功(产生重复) | ❌ DUPLICATE_BUG |
| 类型B: 第二次成功 | ✅ PASS |
| 类型B: 第二次返回500 | ❌ RACE_CONDITION_BUG |

### 5.4 字段类型校验 (必须)

**规则**: 下拉字段必须是 `<select>` / `el-select`，不能是 `<input type="text">`。

**必须检查的字段**:
| 模块 | 字段 | 期望类型 |
|------|------|---------|
| 研发样品/新建 | 产品级别 | el-select (A/B/C/D) |
| 研发样品/新建 | 储存方式 | el-select (冷冻/冷藏/常温) |
| 销售订单/新建 | 客户 | el-select |
| 采购订单/新建 | 供应商 | el-select |

**证据模板**:
```
field_type:
  - 研发样品/产品级别: el-select ✅ options=[A,B,C,D]
  - ❌ 研发样品/产品级别: el-input → WRONG_FIELD_TYPE
```

### 5.5 列完整性校验 (建议)

**规则**: 核心模块的表格列必须包含期望的业务字段。

| 模块 | 期望列 |
|------|--------|
| 销售订单列表 | 订单编号, 客户, 业务员, 下单日期, 总金额, 状态 |
| 销售订单行项目 | 产品名, 规格, 数量, 单位, 箱数, 单价, 小计 |
| 采购订单列表 | 订单编号, 供应商, 类型, 下单日期, 总金额, 状态 |
| 采购订单行项目 | 原料名, 规格, 数量, 单位, 箱数, 单价, 小计 |
| 研发样品列表 | 样品编码, 样品名称, 客户名称, 规格, 产品级别, 业务员, 储存方式, 产品状态 |

检查方法: `browser_snapshot` 后检查 `columnheader` 节点是否包含期望列名。

### 5.6 状态标签校验 (建议)

**规则**: 状态字段必须显示中文标签，不能显示英文枚举值。

```
status_check:
  - 研发样品/APPROVED: "样品通过" ✅
  - ❌ 研发样品/APPROVED: "APPROVED" → RAW_ENUM_BUG
```

## L2 CRUD 硬性升级 (2026-04-04)

**每次 L2 创建测试必须附带 L5 必须检查 (5.1-5.4, 5.7-5.10)。** 建议检查 (5.5, 5.6, 5.11) 按需执行。

> L5 不是独立执行阶段，而是嵌入 L2/L3/L4 的质量增强。运行 `/e2e-web crud` 时自动包含 L5 必须项。
> 测试应可独立运行、任意顺序。每个测试自行检查+创建所需前置数据。

### 5.7 自动计算字段 (必须)

**规则**: 有依赖关系的字段必须自动计算正确，且支持手动覆盖。

| 模块 | 字段 | 公式 | 验证方法 |
|------|------|------|---------|
| 销售订单行 | 箱数 | 数量 / 产品.箱系数 | 选产品→输数量→snapshot→箱数正确 |
| 销售订单行 | 小计 | 数量 × 单价 × (1-折扣率) | 详情页核对 |
| 采购订单行 | 小计 | 数量 × 单价 | 详情页核对 |

**前置数据**: 需要一个已配置 `boxConversionCoefficient` 的产品。如环境中无此产品，先到系统管理→产品管理编辑任意产品，设置箱系数=10。或通过 API: `PUT /{factoryId}/product-types/{id}` body: `{"boxConversionCoefficient": 10}`

**测试步骤**: 选产品(箱系数=10) → 输数量50 → 箱数应=5.00 → 手动改6 → 提交 → 详情页箱数=6(手动值保留)

**snapshot 验证**:
```
// 填数量后 snapshot 表单 → 找箱数 input → 值=5.00
// 手动改为6 → 提交 → 详情页 snapshot → 箱数列=6
```

### 5.8 只读/自动填充字段 (必须)

**规则**: 系统管理字段必须 `disabled=true` 且值正确。

| 模块 | 字段 | 期望值 | disabled |
|------|------|--------|---------|
| 追踪记录 | 日期 | 今天日期 | true |
| 追踪记录 | 记录员 | 当前登录用户名 | true |

**snapshot 验证**:
```
// snapshot 弹窗 → 找 label="日期" 的 input
// 检查: 值=YYYY-MM-DD(今天), 且 node 包含 disabled 属性
// 找 label="记录员" 的 input → 值=当前用户名, disabled
```

### 5.9 订单号单调递增 (必须)

**规则**: 连续创建同类型订单，订单号必须严格递增。

> **交互预算**: 此规则需要创建两笔订单(~16次交互)，超出单模块20次限制。与该模块的L2 CRUD测试合并执行：第一笔为CRUD创建测试，第二笔为5.9递增验证，共享交互预算上限提升至30次。

**测试步骤**:
```
1. 创建采购订单 #1 → 记录号 PO-YYYYMMDD-XXXX
2. 立即创建 #2 → 记录号
3. 提取序号部分: parseInt(#2序号) > parseInt(#1序号) → PASS
4. #2序号 <= #1序号 → ❌ ORDER_NUMBER_BUG (COUNT vs MAX 问题)
```

### 5.10 搜索/筛选结果验证 (必须)

**规则**: 筛选后结果必须全部满足筛选条件。

**测试步骤**:
```
1. 确保列表有 ≥2 条数据且状态不同
2. 选状态筛选="研发中" → 点搜索
3. snapshot 表格 → 遍历所有行状态列 → 全部="研发中" → PASS
4. 如有非"研发中"的行 → ❌ FILTER_BUG
5. 点"重置" → 数据恢复原始数量
```

### 5.11 条件按钮/字段显隐 (建议)

**规则**: 操作按钮根据记录状态正确显示/隐藏。

| 模块 | 状态 | 应有按钮 | 不应有按钮 |
|------|------|---------|----------|
| 研发样品 | 研发中 | 追踪记录, 提交审核 | 提交报价申请 |
| 研发样品 | 样品通过 | 追踪记录, 提交报价申请 | 提交审核 |
| 销售订单 | 草稿 | 编辑, 确认, 取消 | 出库, 开票 |
| 销售订单 | 已确认 | 出库, 取消, 开票 | 编辑 |

**snapshot 验证**:
```
// 找到目标行 → snapshot 操作列
// 检查 button 文本列表 vs 期望列表
// 多余按钮或缺失按钮 → ❌ BUTTON_VISIBILITY_BUG
```

## 业务旅程测试

> 从真实用户角色视角定义完整业务闭环。每步不仅测"能不能做"，还测"结果对不对"。

### 旅程 A: 销售员接单（销售全链路）

```
角色: 销售业务员
1. 查客户列表 → 客户名称非UUID ✓
2. 新建销售订单:
   - 选客户(下拉显示名称) → 选业务员
   - 添加产品A: 规格自动填充, 输数量50, 箱数自动计算, 填单价
   - 添加产品B
   - ⚠️ 再加产品A → 被拦截"不能重复"
   - 创建成功
3. 查看订单: 列表客户名=真名(非UUID), 详情有规格+箱数, 产品名非空
4. 确认 → 状态变"已确认"
5. 发货 → 已发货数量更新
能发现: UUID显示, SKU重复, 规格箱数缺失, 空字段
```

### 旅程 B: 采购员补货（采购全链路）

```
角色: 采购/仓储
1. 新建PO#1: 选供应商(名称非UUID), 加原料(名称自动填入非空白), 填规格+箱数+单价 → 成功
2. 立即新建PO#2: 不同内容 → 成功, 订单号递增(不报错)
3. 查看: 列表供应商=真名, 详情原料名称完整, 有规格+箱数列
4. 审批 → 状态变化
5. 收货 → 库存增加
能发现: 供应商UUID, 原材料空白, 二次创建报错, 规格箱数缺失
```

### 旅程 C: 研发经理管样品（研发全链路）

```
角色: 研发/运营经理
1. 新建研发需求: 客户+联系方式+需求+紧急度 → 成功
2. 新建样品:
   - 填客户名称(手动), 选业务员(下拉)
   - 产品级别 → 必须是下拉(A/B/C/D)
   - 储存方式 → 必须是下拉
   - 创建成功
3. 查看列表:
   - 有搜索栏(名称+客户+状态), 用状态筛选→结果正确
   - 表头有客户名称/产品级别/储存方式, 无主原料/等级
   - 状态="研发中"(非IN_PROGRESS)
4. 追踪记录: 日期=今天且不可编辑, 记录员=当前用户且不可编辑
5. 提交审核 → 通过 → "提交报价申请"按钮出现
能发现: 字段类型错, 旧列残留, 搜索失效, 自动填充失效, 按钮条件错
```

### 旅程 D: 财务对账（数据完整性）

```
角色: 财务经理
1. 销售订单列表: 全部客户名=中文(无UUID), 金额>0, 业务员非空
2. 详情页: 行项目有规格+箱数列, 产品名非空, 成本单价存在
3. 财务状态: 开票状态=中文标签, 收款金额格式正确
4. 采购订单: 供应商=真名, 原材料完整, 单价×数量=小计
能发现: UUID残留, 字段缺失, 计算错误, 标签英文
```

### 旅程 E: 新人易错（错误路径）

```
角色: 新入职操作员
1. 不选客户提交 → 前端拦截"请选择客户"
2. 不加产品提交 → 拦截
3. 同订单内加重复产品 → 拦截
4. 两次创建一样的订单 → 第二次应成功(不同订单允许相同内容)
5. 提交失败后弹窗保持, 修正后再提交 → 成功
能发现: 前端校验缺失, 错误处理不友好, 表单状态丢失
```

## 防偷懒执行规则 (2026-04-05 新增)

> **教训**: 6轮测试迭代中每轮都被用户追问发现缺口。根因: API代替UI、WARN当可接受、只测L1声称全覆盖。

### 绝对禁止 (违反则整轮无效)

1. **禁止 fetch()/API 调用做 CRUD** — 测试脚本中不允许用 `fetch` 创建订单/样品/客户。只允许用于获取 login token 和查询前置数据ID。**发现任何 `api('/xxx', {method:'POST'})` 用于创建业务数据 = 立即标记为 INVALID_TEST**
2. **禁止 WARN 存在于最终报告** — WARN = 没通过 = 必须修。不接受"timing问题"/"数据问题"等解释。exit code: WARN>0 则返回1
3. **禁止声称"全覆盖"但跳过模块** — 运行前打印覆盖矩阵(16模块×CRUD)，运行后标记实际执行的，未执行自动 FAIL

### 测试函数强制结构

每个模块的 CRUD 测试必须包含以下步骤，缺任何一步 = 不合格:

```javascript
async function testModule(page, moduleName) {
  // === CREATE ===
  // 1. 导航到列表页 (Playwright go)
  // 2. 点"新建"按钮 (Playwright click)
  // 3. 填每个字段 → log('filled: 字段=值')
  // 4. 点"提交" → log('toast: xxx')
  // 5. 刷新列表 → 验证新行可见 → log('list after: xxx')
  // 6. 点"详情" → 逐项核对 → log('detail check: xxx')
  // 7. UUID扫描 → log('uuid scan: 0 found')
  // 8. 截图 → log('screenshot: xxx.png')

  // === EDIT === (同上结构)
  // === DELETE/CANCEL === (操作+验证状态变化)
}
```

### 证据完整性检查

每个测试结尾必须调用:
```javascript
function assertEvidence(testName, evidence) {
  const required = ['filled', 'toast', 'list_after', 'detail_check'];
  const missing = required.filter(k => !evidence[k]);
  if (missing.length > 0) FAIL(`${testName}: 缺证据 [${missing}]`);
}
```

## 元素定位优先级

来自 TestDino 的 locator 最佳实践。用 MCP 工具操作时，优先用高层级方式标识元素:

| 优先级 | 方式 | 示例 | 使用场景 |
|--------|------|------|---------|
| 1 | Role | `button[name="提交"]` | 始终首选 |
| 2 | Label | `label "用户名"` 关联的 input | 表单字段 |
| 3 | Text | 包含 "创建成功" 的元素 | 非交互内容 |
| 4 | Placeholder | `input[placeholder="请输入"]` | 搜索框 |
| 5 | TestID | `[data-testid="xxx"]` | 最后的语义选项 |
| 6 | CSS | `.el-select-dropdown__item` | 最后手段 |

在 `browser_click` 的 `ref` 参数中，使用 `browser_snapshot` 返回的 ref 值，不要猜 CSS 选择器。

## 失败分类

来自 TestDino 的 flakiness taxonomy:

| 类别 | 诊断方式 | 修复 |
|------|---------|------|
| **时序/异步** | 本地重复跑 20 次有时失败 | 用 auto-retry assertion 替代 waitForTimeout |
| **测试隔离** | 单独跑通过，一起跑失败 | 共享可变状态/数据冲突 |
| **环境** | 只在 CI/远程失败 | viewport/字体/慢机器 |
| **应用 Bug** | 稳定复现 | 标记 KNOWN_BUG，修后端/前端 |

## Element Plus 操作模式

```
# 选下拉 (el-select)
1. browser_snapshot → 找到 label "客户" 旁的 el-select
2. browser_click → 点击 el-select 打开下拉
3. browser_snapshot → 找到下拉选项
4. browser_click → 点击目标选项

# 填表单 (el-input)
1. browser_snapshot → 找到 label "批次号" 旁的 input
2. browser_fill_form → 填入值

# 检查 toast
1. browser_snapshot → 查找 .el-message--error 或 .el-message--success
2. 如果找到 error → 记录错误文本 → FAIL
3. 如果找到 success → 记录成功文本 → PASS

# 验证表格数据
1. browser_snapshot → 找到 .el-table
2. 检查 .el-table__row 数量 > 0
3. 检查第一行是否包含刚创建的数据
```

## 自然语言测试定义

来自 firstloophq/claude-code-test-runner。测试用结构化自然语言定义:

```
模块: 销售订单
操作: 创建
步骤:
  1. 导航到 /sales/orders
  2. 点击"新建销售订单"
  3. 选择客户: 任意可用客户
  4. 选择业务员: 任意下拉选项 (验证是下拉不是文本框)
  5. 添加商品: 选择任意产品, 数量=10, 单价=自动填充
  6. 点击"创建"
  7. 验证: 成功 toast 出现
  8. 验证: 列表中出现新创建的订单
```

每步骤必须标记: `PASS` / `FAIL` / `SKIPPED`，失败时附 error 详情。
