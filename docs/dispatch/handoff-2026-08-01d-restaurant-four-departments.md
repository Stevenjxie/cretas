## 三、本轮唯一的真代码缺口（已修并上 prod）

市场「最近30天哪家店业绩最好」——**两个租户都答不出**，落到澄清
「我识别到的问题对象与准备执行的分析范围不一致」。

### 逐层取证

```
t1 关键词       → RESTAURANT_OPS_SALES_SUMMARY
planned_intents → ('RESTAURANT_OPS_SALES_SUMMARY',)
LLM 选的 code   → RESTAURANT_OPS_STORE_MARGIN     ← 不在计划里
_detect_requested_metrics("…业绩最好") → ()        ← 根因
```

`code not in planned_intents` 本该由 contract-repair 修掉，但它要求
`_repair_backed_by_user_wording` 为真，而该函数拿 `_REQUEST_METRIC_RULES` 编译的
结果与修复指标求交集——**「业绩」不在表里 → 交集为空 → 修复通道拒绝介入**，
LLM 错的 resolver 一路走到澄清。

**对照句只换一个词就能答**：「最近30天哪家**门店营收**最高」实测
`planner_authority='llm_contract_repair'`。差别只在那一个词。

与表里 `requisition_cost` 那条注释是**同一形状**：指标编译不出来 → 修复条件永远为假。

⚠️ 症状是**不稳定而非恒错**：LLM 选对 resolver 时用不着 repair，选错时才暴露。
所以「生意怎么样」今天能答不代表它安全，只代表这一轮 LLM 选对了。

### 修复后 prod 实测

| | 修前 | 修后 |
|---|---|---|
| `_detect_requested_metrics` | `()` | `('revenue',)` |
| code | STORE_MARGIN | **SALES_SUMMARY** |
| clarification | True | **False** |
| authority | `llm` | **`llm_contract_repair`** |
| kind | 澄清 | **answer** |

答案：营收最高门店 ¥3,416,463.44 / 9419 单；10 家店合计 ¥33,931,057.47。
四部门复跑两轮一致，实质 12/18 → 13/18，**其余 17 条零退化**。

### ⛔ 刻意不收「生意」

第一版「业绩」「生意」一起加，**当场打挂 4 条既有用例，全部由「生意」引起**：
它是泛化经营词，会把 `asks_profitability`、`STAFFING_ADVICE` 一并吸走
（「生意有起色没，划算不划算」被吸成 revenue；时段经营问句被劫持成 TREND_ANALYSIS）。
而「生意怎么样」本来就能答，加它没有收益只有劫持。已加**反向断言**钉住这个决定。

## 五、🔴 判据类教训（本轮新增）

1. **审计分数不等于能力，先看答案正文。** 「诚实说没数据」被计成 OK 时，
   分数会系统性高估。判据：抽查答案里**有没有真排出排名/金额**。
2. **换个租户复跑，是分清「数据缺口 / 能力缺口」最省事的动作**，而且要**双向看**——
   本轮参考租户反过来把运营 6 条全打空，那也是信息。
3. **我的「实质」判据自己错了两次，两次都是被反例纠正的**：
   · 建议段的 `1. 2. 3.` 是行动项不是榜单 → 把空答案误判成实质（财务两条）
   · 金额可能没有小数位（`¥21,280,945`）→ 把真答案误判成空壳（市场堂食外卖占比）
   **凡是"我写个判据自动判"，都要先拿几条已知答案对一遍。**
4. **一次只改一个变量。** 「业绩」「生意」一起加，测试挂了 4 条；分开看才知道
   全是「生意」的锅、「业绩」零回归。
5. ⚠️ **`git reset --hard` 会丢弃未提交改动。** 本轮我在 commit 之前误跑了它，
   两个文件的改动全没了，只能照对话记录重做。**改完立刻 commit**（本仓
   concurrent-edit-safety 规则 1 就是这条，这次是我自己没守）。
