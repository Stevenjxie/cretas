## 1. 目标架构：一句话进来依次经过什么

```
                              ┌─ LLM ①：人话 → 一张表（唯一"理解"点）
一句话 ─► 前门 ─► ①记忆 ─► ②晋升 ─► ③翻译 ─► ④路由 ─► ⑤执行 ─► ⑥装修 ─► ⑦契约 ─► ⑧表达 ─► 答案
                  └零LLM┘ └零LLM┘          └───── 全部确定性代码 ─────┘      └─ LLM ②：结论 → 人话
                                                                                （仅归因类触发）
```

**LLM 在生产环境只出现两次；中间路由、查库、算数、判断，一个 token 都不烧。**

### 前门（Java）：只管「谁能做什么」

| | 今天 | 改完 |
|---|---|---|
| 写请求 | Java **自己理解**（645 条关键词，0/4）+ Java 执行 | Python 理解，**Java 只执行** |
| 读请求 | 转发 | 转发（不变） |
| 超时 | 15s（08-12 已改 60s 对齐 nginx，待合） | 不变 |

Java 只剩四件事，**一件都不涉及听懂人话**：权限 / 预览 / 确认 / 审计。

⚠️ Java 收到 Python 的结构化写意图后**不能信它** —— 必须自己再查：菜存在吗？属于该租户吗？
现在能下架吗？**LLM 的输出永远只是「建议做什么」，不是「可以做什么」。**

### ① 会话记忆：本地、确定性（新增）

今天：会话状态是 300 字符**文字摘要**，喂给 LLM 看。
改完：**存结构不存文字**。

```
会话状态 = {
   当前计划:   {指标:毛利, 对象:米饭, 时间:本月, 门店:全部}
   计划栈:     [前一个, 再前一个]        ← 只留 2-3 层
   已提及实体: {菜品:[…], 门店:[…]}
}
```

三级台阶，**能低就绝不高**：

| 情形 | 处理 | 成本 |
|---|---|---|
| 「本月全部门店米饭的毛利」（自足） | 整个换掉当前计划 | **零 LLM**，可晋升 |
| 「那毛利呢」「换成上个月」「徐汇店呢」 | 复制当前计划改一个槽 | **零 LLM** |
| 「回到刚才那个」 | 出栈 | **零 LLM** |
| 「那这样呢」「按你说的来」 | 说不清换哪个槽 → 下一层 | 走 LLM |

**今天这四种全走 LLM。**

⛔ 纪律：已提及实体**只用于补全，绝不用于覆盖**。用户明说「全部门店」，不许拿栈里的
「徐汇店」改它 —— 那是拿上下文顶替用户原话。**写成会红的断言。**

### ② 晋升路由：零 token 回放（已建好，停摆中）

原句与一条**人工审核过的自足句**逐字相同 → 直接拿出当年那张形状表，LLM 一次不调。

📌 **P0 已实测**：把 `_t3_llm_parse`（LLM 唯一入口）换成「一被调用就抛异常」的桩，
`_exact_shape_matches` 仍命中且未触发 → **零 LLM 成立**。
⚠️ 只证明了 4,000-token 的翻译调用被跳过；另有一次 407-token 小调用未验，
准确说法是「省 95%」不是「零」，端到端实测待补。

### ③ LLM 翻译：**唯一的"理解"点**

| | 今天 | 改完 |
|---|---|---|
| 输出 | `{intent:"RESTAURANT_OPS_GROSS_MARGIN", 指标:[毛利], …}` | `{指标:[毛利], 维度:菜品, 聚合:排名, 时间:本月}` |
| LLM 的任务 | **两件**：听懂 + 从 19 个意图名里挑一个 | **一件**：听懂 |
| prompt | 9,787 字符 | ≈ 8,300（**−15%**，去掉 19 个意图描述的 1,500 字符） |

⛔ 铁律不变：**LLM 只填表，不算数、不判断、不下结论。填完就被扔到一边。**

### ④ 形状路由：确定性查表（新）

```
拿到形状 {毛利 × 菜品 × 排名}
   ├─ 有 resolver 声明「我认领这个形状」？ → 用它
   └─ 没有                              → 通用执行器
```

**改的不是"后面怎么走"，是"谁来决定走哪条"**：今天路由键是 LLM 猜的 intent 名字，
改完是查表。**08-11 那个 bug 正是第二个决定错的** —— 它听懂了「亏钱卖」是毛利，
归类时却挑了 `DISH_SLOW`（销量榜）。**查表不会挑错。**

⚠️ 但它**不解决**「听错」：LLM 若把「亏钱卖」填成 `{指标:销量}`，照样答错。
**形状路由消灭的是"归类错"，不是"听错"。** 听错由第 3 节那四层兜。

### ⑤ 执行：确定性 SQL

- **resolver 路径**：它自己的手写 SQL（router 里有 68 处 `SELECT`）
- **通用执行器路径**：按登记表推导
  `SELECT {指标表达式} FROM {粒度} JOIN {维度} WHERE … GROUP BY … ORDER BY`
  推导不出来 → 抛 `UnsupportedCell` → 走 ⑦ 诚实拒答

### ⑥ 精装修：9 份模板，不是 3,168 份

决定答案长什么样的不是问题，是**聚合类型**：

| 聚合 | 模板 |
|---|---|
| rank / bottom | 榜单 + 柱状图 + 「第一名是第二名的 1.8 倍」 |
| trend | 折线 + 环比同比 + 拐点 |
| compare | 左右对比表 + 差额与百分比 |
| share | 占比条 + 「前三名占 71%」 |
| summary | 大数字 + 计算过程 + 范围声明 |
| **concentration** | 集中度 + 离群标注 ← **「正不正常」就是这个** |
| extremes / above_avg | 极值 + 均线位置 |

新增指标不写模板，自动继承全部 9 种展现。

### ⑦ 契约：两个出口 → 三个

```
今天:                        改完:
  ├─ 全覆盖 → 发出             ├─ 全覆盖   → 发出
  └─ 没覆盖 → 拒答             ├─ 部分覆盖 → 答能答的 + 列出缺什么   ★新增
                               └─ 没覆盖   → 拒答
```

「这个月赚钱了没有」：今天**拒答**；改完 ——

> 「按现在有的数据，**毛利 68 万，毛利率 67.7%**。要算净利润还差三样：
> **人工工资、房租、水电**。这些导进来我就能告诉你到底赚没赚。」

缺什么是**算出来的**（净利润 = 营收 − 食材 − 人工 − 租金 − 水电，逐项查库），不是手写文案。

⛔ 两条硬约束，**都要写成会红的断言**：
1. 部分答案里的每个数**必须是用户问的那个指标本身**，不许用"相关指标"顶
   —— 这条和「拿相邻指标顶替」只隔一层纸（2026-08-10 兜底事故：用营收数字回答「为什么」）
2. 不许出现「置信区间 / 因果效果 / 回归估计 / 显著性」这类黑话
   —— 现有 `buildRestaurantPriceElasticityGapResponse` 正是反面样本，一并改

### ⑧ 表达：LLM 第二次也是最后一次出场

**只对归因类触发**，且与走 resolver 还是通用执行器**无关**。

```
确定性算完：营收环比 −8.2%；门店维度 A 店 −32% 占降幅 61%（形状=集中）；
            菜品维度分散；拆解：订单数 −6%，客单价 −2%
LLM 只做一件事：写成人话 + 末尾反问事件（活动/换供应商/装修）
```

**谁是主因由算式定，不由 LLM 定。** LLM 拿到的是排好序的事实，没有编数字的机会。

## 3. 关键机制详解（对话中被反复追问的四处）

### 3.1 LLM 把「亏钱卖」填成销量怎么办 —— 四层兜，最后一层最硬

| 层 | 做法 | 硬度 |
|---|---|---|
| 同义词 | prompt 里指标本就带同义词表（`revenue(营收, 营业额/流水/收入/卖了多少钱)`），把「亏钱卖/赚不赚/挣不挣钱」挂到 `gross_margin` | 软，立刻见效 |
| 契约 | 用户问的指标答案里没有 → 不许发出。拦不住"填错"，拦得住"答非所问" | 中 |
| judge | 另一个模型判「答上老板问的了吗」→ 能**发现**你不知道的错 | 中 |
| 🔑 **晋升** | 人审一次 → 永久冻结成 `{指标:毛利}` → **这句话再也不经过 LLM，也就再也不会错** | **最硬** |

**飞轮不只是省钱，它是「把 LLM 理解对的那一次固化下来」的机制。**

### 3.2 3,168 个格子 —— 是覆盖地图，不是工作量

要建的只有三样：**9 份精装修模板** + **1 个通用执行器（已有）** + **给现有 18 个 resolver 各加一行形状声明**。

📌 **格子概念代码里已经存在**：`spec_to_cell()` 返回 `(指标, 维度, 聚合)` 三元组，
代码里就叫 `cell`；还有 `UnsupportedCell` 异常 —— 说明**有些格子会抛"不成立"**。

**要建的是「把这张表跑一遍、打印出来」**：哪些格子能出 SQL、哪些抛 `UnsupportedCell`、
哪些出了 SQL 但结果不对。**今天没人跑过，所以「我们能答哪些问题」这个问题没人答得上来。**

### 3.3 **更正**：语义层升级缩水成两项

我原本列三样，实测后诚实清点：

| 我原来列的 | 实际 |
|---|---|
| ~~join 路径~~ | ❌ **已经有了**。`GRAINS` 三种粒度各自带 JOIN，`item_cost` 是四层 LEFT JOIN（菜品→配方→成本表）。「红糖糍粑的成本」通用执行器**现在就能算**，我拿它当反例是错的 |
| **口径归属** | ✅ 真缺 |
| **数据可信度** | ✅ 真缺 |

**为什么这两项值得加（而且不花 token —— 确定性元数据，LLM 不读）**：

```python
"gross_margin": Derived(
    ...,
    caliber_by_grain = {                       # 口径归属
        "item":  "售价 − 食材成本",
        "store": "营收 − 已覆盖成本",
    },
    trust = {                                  # 数据可信度
        "coverage_expr": "有成本数据的营收 / 总营收",
        "freshness_from": "agg_restaurant_product_cost.updated_at",
    },
)
```

- **口径**：菜品层和门店层的「毛利」现在**没人对过它们一不一致** —— 一个在 resolver 里，一个在通用执行器里
- **可信度**：「成本覆盖率 100%」现在**手写在某个 resolver 的文案里**，所以走通用执行器时**说不出这句话**。同一个数字，一条路会声明可信度，另一条不会

**第三样（更多粒度：供应商链 / 损耗链）是增量不是架构** —— 用到就加。

### 3.4 **更正**：resolver 的定位

**resolver 不是为了快。** SQL 推导是拼字符串（微秒级），真正耗时的是数据库查询和 LLM 调用，
**两条路一模一样**。

| | 通用执行器 | resolver |
|---|---|---|
| SQL | 登记表**推导**出来 | **手写**（router 里 68 处 `SELECT`） |
| 输出 | 通用 `render()` + 9 份模板 | 手写文案：计算过程 / 图 / 建议动作 / 数据说明 |
| 覆盖 | 任意 (指标 × 维度 × 聚合) | 只有它认领的那个形状 |
| 何时值得 | 长尾 | ① 高频问题值得更好的话术 ② **登记表表达不出来的查询**（如「毛利谜题」要同时比销量分位和毛利分位，那不是一个格子能描述的） |

**「手写 resolver 会被 agent 打死」这话我说过头了。** 准确说法是：

> 死的是「**每来一种新问法就写一个 resolver**」这种做法，和「**用 resolver 当路由机制**」。
> **高频问题的 resolver 不会死**，它们一直值钱。
> 扩覆盖面应该靠**通用执行器 + 登记表**，不是靠加 resolver。

角色变化：**从「必经之路」降级成「某个形状的特供版」。**

### 3.5 **更正**：飞轮存什么、不存什么

> ❌ 误解：「飞轮是在丰富 resolver」

**飞轮和 resolver 是两个完全不同的层。** 表结构就是答案：

```sql
SELECT normalized_phrase,   -- 规范化后的整句话
       plan_json,           -- 形状（指标/维度/聚合/时间/对象/门店）
       routing_fingerprint  -- 当时的路由规则指纹
  FROM ai_promoted_routes
```

**只存三样：句子、形状、指纹。没有 resolver 名字，没有 SQL，没有数字，没有答案文本。**

```
② 晋升命中 → 直接拿出 plan_json         ← 省掉的是 ③ 的 4,000 token
③ LLM 翻译 ← 跳过
④ 形状路由 → 照跑
⑤ 执行     → 照跑（resolver 手写 SQL 或通用执行器推导，与没晋升时一模一样）
⑥⑦        → 照跑
```

**为什么只存形状**：

| 不存什么 | 理由 |
|---|---|
| 答案 / 数字 | 数据每天在变 |
| SQL | 是形状的确定性函数，存了等于存两份 |
| resolver 选择 | 也是确定性函数。**存了反而僵化** —— 以后给这个形状写了更好的 resolver，晋升表那条还指着老的 |

**只有「听懂」这一步又贵（4,000 token）又不确定（LLM 会错），所以只缓存它。**
后面几步又便宜又确定，重跑更好 —— **改进 resolver 或模板后，所有已晋升句子立刻受益，不用重审。**

**时间是相对的**：存 `{type: named, value: this_month}` 而不是具体日期。
回放走 `_replay_plan_spec`，**按今天重新编译日期再封章** —— 同一条路由 8 月问是 8 月，
9 月问是 9 月，永远新鲜。存具体日期的话第二个月就错了。

**指纹的作用**：它是当时那套「词 → 指标」映射规则的摘要。
规则一改（比如「流水」从 revenue 改成 actual_receive），指纹变，旧晋升自动失效回落 LLM
—— 防的是「规则变了旧形状还按老语义回放」。**现在 40 条全失效正是因为规则改过而没人重审。**

**完整闭环**：

```
① 真实老板问一句话
② 走完整链路，LLM 翻译出形状，答对了
③ 句子 + 形状 进入晋升候选池
④ 另一个模型独立复判：这句该翻译成这个形状吗？   ← promotion_llm_review
⑤ 人在 web-admin 审核台点通过                    ← 唯一人工环节
⑥ 写进 ai_promoted_routes，带当前指纹
⑦ 以后任何人说这句话 → 零 token，且永远翻译正确
```

**第 ⑦ 步「永远正确」比省 token 更值钱。**

## 4. 实施计划

### P-I 评估升级：子串断言 → LLM-judge 混合（**排第一**）

**为什么排第一**：不能用 84 条子串断言当仪器，去做「删 645 条 + 19 个意图」的手术。
删完跑一轮全绿，**分不清是真没坏还是断言看不见** —— 08-11 八张表格塌了、两轮 85/85 全绿，
就是同一个盲区。**评估先行，因为它是仪器不是目标。**

**混合，不是替换**：
```
确定性断言（留）: 数字必须 == 7,926,316.02        ← judge 判不了也不该判
LLM-judge（加）  : 答上老板问的了吗？
                   有没有黑话？
                   排版塌没塌？                    ← 子串断言永远看不见这三条
```

**成本**：一次 judge ≈ 1,500 token；85 题一轮 **+13 万 = 电池总成本 +10%~27%**。
**只在测试跑，生产零成本。**

**行业参照（2026）**：LLM-judge 与人类评审一致率约 85%，**高于两个人类之间的一致率**，
成本是人工的 1/500~1/5000，已是行业默认评估方式。

**具体步骤**：
1. 写 judge 评分卡：①答上问的了吗 ②有无黑话 ③排版是否可读 ④有无编造数字
2. 现有 84 题的 `contains` 断言里，**数字类保留**，措辞类删掉换 judge
3. 跑一轮，对比 judge 判定 vs 现有断言 —— **两者分歧的地方就是现在的盲区**

### P-C 形状路由 + 9 份精装修 —— **本质是把字符串边界从 ⑤ 挪到 ⑥**

> ⚠️ 2026-08-12 更正：本节原来写的是「9 份模板管展现」，**说小了**。
> P-I 停点查出黑话为什么会漏之后才看清，它真正的内容是下面这句。

**今天**：
```
⑤ 执行 ──► "本月毛利 68 万，覆盖率 100%，净利润缺费用税费…"   ← 字符串在这生成
⑥ 装修 ──► （对 18 个手写 resolver 而言不存在，它已经是成品文字了）
⑦ 契约 ──► 只能在字符串里 grep
```

**改完**：
```
⑤ 执行 ──► {指标:毛利, 行:[…], 单位:元, 缺:[人工,租金,水电]}    ← 结构
⑥ 装修 ──► render(结构) → 文案                                   ← 唯一文案作者
⑦ 契约 ──► 检查结构字段
```

**🔑 参照实现已经存在，不用发明**：通用执行器一直是这个形状 ——
```python
class CellResult:              # generic_executor.py
    metric_key, metric_label, dimension_key, aggregation_key, unit
    rows: List[Dict]
    missing_columns: Tuple     # 「缺数据」和「查出来是空的」分开
def render(result, window_label) -> str:    # generic_answer.py，文案是单独一步
```
它自己的注释写得最清楚：「`missing_columns` 非空时 `rows` 必须为空 ——
『缺数据』和『查出来是空的』是两件事，**混在一起会让上层无法如实措辞**。」

**要做的是把 18 个手写 resolver 迁到同一个形状**，不是造新东西。

**四个症状塌成同一个根**（都是「结构在 ⑤ 层就被压成了字符串」）：

| 症状 | 因为 |
|---|---|
| 黑话漏到店长面前（`维度`/`相邻分析`/`中位`…） | **resolver 在写文案**，而写它的人脑子里是「维度」「槽位」 |
| 84 条断言全是子串检查 | **答案只有字符串**，没有别的可断言 |
| 契约只能子串匹配 | 同上 |
| 清洗函数删掉 markdown 空行，8 张表全塌（#2475） | 一个**文本层**的洗涤剂，不知道自己在洗结构 |

**执行步骤**：
1. LLM 输出去掉 `intent` 字段，只填形状 → prompt −15%
2. 给 18 个 resolver 各加一行**形状声明**（认领哪些 指标×维度×聚合）
3. 路由改成查表：有认领用 resolver，没有走通用执行器
4. **把 18 个 resolver 的返回从 `answer_text` 字符串迁成 `CellResult` 式结构**
5. 按**聚合类型**写 9 份精装修模板 —— **⑥ 层是全系统唯一的文案作者**
6. **产出覆盖率表**：跑遍所有格子，打印「有 resolver / 走通用 / 抛 UnsupportedCell」三态

⛔ **模板文案的判据是「不懂技术的人读得懂」，由判据②（模型）守，不由词表守。**
9 份模板是**有限集合**，模型审得完 —— 这正是词表想做而做不到的事。

### P-K 黑话清洗层的退场（2026-08-12 新增）

**先说它为什么存在** —— `customer_text.py` 是一张 30+ 对的翻译表：

```
「叙述模型预算已用完」→「今天的智能分析次数已经用完」
「确定性多维分析」    →「按系统真实数据做的综合分析」
「本轮已纳入维度」    →「这次已经查看的方面」
「语义规划」          →「问题理解」
「实体槽位」          →「菜品、门店等条件」
```

**左边全是我们自己的架构术语。** 根因：**文案是在实现层写的** —— 写 resolver 的人
在写答案文字时脑子里是「语义规划」「维度」「槽位」，因为他此刻正在实现它们。
**文案继承了实现的词汇表**，然后有人加了一层翻译。
**这层翻译的存在，本身就是「文案作者是工程师」的证据。**

**而它自己造过一次更大的事故**：`d39adad726 fix(restaurant-ai): 空行是 markdown
的结构 —— 清洗函数把它删了，8 张表全被并成一坨 (#2475)`。一个为了洗黑话而存在的
文本层函数，造成了比黑话严重得多的排版事故，四个 PR + 两轮 85/85 + CI 全绿都没发现。

**它在架构上不在任何一层** —— 是散落在 10 处的 10 次调用，靠「谁记得谁调」。
> 没有一层负责「把话说成人话」，所以有人加了个洗涤剂，在他想得起来的地方各调一次。

**⛔ 2026-08-12 作废的一条指令**：organizer 一度让执行者「往词表补上实测漏出的
4 个词」。**那是错的** —— 词表 13 条只覆盖了 6 个实测漏出词里的 2 个
（`相近指标`/`相邻分析`/`中位`/`可验证结果` 都不在），补到 17 条只会等下一个
没想到的词。**这正是本仓记了四次的「手写清单不全，而清单错了没有任何东西会红」。**

**词表和模型的真差别：词表要求你先想到那个词，模型不要求。**
`相邻分析` 没人列过，词表就是瞎的；判据②（模型）会直接说「这句话店长读不懂」——
**它是唯一能发现你没想到的词的东西**。所以判据②**不是「词表缺口发现器」**
（那还是把词表当主体），**它就是主判据**；词表退成「已知必错词的快速通道」。

**退场三步（顺序不能跳）**：
1. **改源码里那批串**（并入 P-B④）—— 止血。三个变体 `相近指标`/`相邻指标`/`相邻分析`
   一起动；`可验证结果`/`维度` 一起改。改完**没有东西需要被清洗**
2. **P-C 把字符串边界挪到 ⑥ 层** —— 根治：resolver 不再产文案，黑话没有产生的地方
3. **删掉 `sanitize_customer_ai_text` + `INTERNAL_VOCAB`** —— 那时它们已无存在理由

⛔ **不能跳过 2 直接做 3**：resolver 还在自己写文案时撤掉洗涤剂，黑话直接出去。
📌 在 1→2 期间 `sanitize` 保留为兜底，但**只准缩小不准增长**。

**接线面的遗留**（P-I 停点查出，修法降级为兜底）：11 处构造 `answer_text` 只有 3 处

### P-D 归因 resolver

沿每个维度环比 → 算贡献占比 → **判分布形状** → 按形状说话 → 末尾反问事件。

| 形状 | 判据 | 说法 |
|---|---|---|
| 集中 | top1 > 50% | 「主要是 A 店，占降幅 61%」 |
| **分散** | top3 < 50% | **「没有集中原因，10 家店普遍下降 3-5%」** |
| 两极 | 有涨有跌抵消 | 「B 店涨 12%，但 A/C 跌得更多」 |
| 结构 | 总量没变构成变了 | 「营收持平，但高毛利菜占比 34%→21%」 |

**★ 分散那一行是关键**：普遍性下降恰恰最需要解释（大盘/季节/商圈），
而「挑最大的报」会把系统性问题误报成单点问题。
**宁可说「找不到集中原因」，也不许把最大的那个当主因。**

**共用现有登记表，不新增维度。** 反问在结论之后，⛔ 不能变成「我不知道，你告诉我」。

## 5. Token 账（全部实测）

| 档 | 每题 | 条件 |
|---|---:|---|
| 零 | 0 | 命中晋升路由（**当前 0 条可命中**） |
| 极低 | ~100 | 计划缓存命中（同句 6h 内） |
| 低 | ~1,800 | prompt 前缀缓存命中 97% |
| 标准 | ~4,600 | 冷启动（4,402 prompt + 217 completion） |
| 高 | 1.5–2 万 | 链头不健康，每次超时重试重发完整 prompt |
| 最高 | 3 万+ | 多轮链后续轮 |

**prompt 结构（实测 9,787 字符）**：19 意图描述 + 22 指标枚举 + 9 聚合 + 10 个 few-shot + 规则。
**变量全拼在最后** —— 公共前缀 9,648 字符 = 固定部分的 100%，**它是为缓存设计的**。

**因此不建议 RAG**：97% 已被前缀缓存吃掉；而 RAG 的代价是检索没召回某指标时，
LLM **不会说检索不到，会挑个相近的** —— 正是 `_drop_planner_invented_metrics` 在治的病。
⚠️ 但 97% 是单次读数，部署重启后归零。**先量一周真实平均命中率**，低于 60% 再重新考虑。

**一轮 85 题电池 = 47 万 ~ 130 万 token ≈ 一个模型一整份免费额度。**
区间宽度全部来自链头健不健康。

**改完后生产环境净变化：−15%**（prompt 去掉 19 个意图描述），
新增 LLM 调用仅在 P-I 的测试环节与 P-D 的归因表达步骤（后者仅归因类触发，
~800 prompt + 300 completion）。

### 会被冲掉的三样（都在计划里）

1. **19 意图 + 18 resolver 当路由** ← 垂直**救不了**：坏在「问法的宽度」不是 schema 宽度
2. **指标层 ≠ 语义层** ← 垂直**大部分能救**：补口径 + 可信度即可（P-J）
3. **子串断言** ← 垂直**救不了**：跟垂不垂直无关，是仪器精度（P-I）

### 未来形状


**agent 替换的是 planner，不是 executor。**
往「19 意图 + 手写 resolver」加东西会被冲掉；往「登记表 + 契约 + 飞轮」加，agent 来了更值钱。

## 7. 垂直行业的边界：不需要 vs 现在不需要

| | 类别 | 什么时候会需要 |
|---|---|---|
| 多 schema / 多数据源适配 | **永远不需要** | 你就一套 schema |
| 知识图谱本体建模 | **永远不需要** | 三种粒度 + 十几个维度够用 |
| RAG 检索指标定义 | **大概率永远不需要** | 除非缓存命中率实测低于 60% |
| **向量化近似匹配** | 现在不需要，**长期要** | 晋升表积累到几百条**真实**问句之后 |
| **agent 多步探索** | 现在不需要，**可能要** | 做完 P-D，看剩下 20% 是什么 |
| **更多粒度**（供应商/损耗链） | 现在不需要，**用到就加** | 有人问那个维度时 |
| **垂直模型训练** | 很久以后 | 晋升语料到几千条量级 |

**判据**：前三样是「架构上不需要」，后四样是「**证据还不够**」。
而攒证据的唯一办法是**有真实用户**。
