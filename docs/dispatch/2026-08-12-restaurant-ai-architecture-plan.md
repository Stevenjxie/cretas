## 1. 目标架构（to-be）

```
RN ──► Java（门）
        │  写操作：权限 → 预览 → 确认 → 执行 → 审计      ← 保留，这是 Java 的价值
        │  读操作：转发，自己一个字不答                    ← 645 条要删的就是这里
        ▼
      Python
        │
        ├─① 会话记忆（本地、确定性，零 LLM）
        │     自足句      → 换掉当前计划
        │     可确定槽位  → 复制当前计划改一个槽
        │     出栈        → 「回到刚才那个」
        │
        ├─② 晋升路由（零 LLM）
        │     原句 == 已审核自足句 → 直接回放计划
        │
        ├─③ LLM 翻译（上面两级都接不住才走）
        │     人话 → {指标, 维度, 聚合, 时间, 对象, 门店}
        │     ⛔ LLM 只填表，不算数、不判断
        │
        ├─④ 形状路由（确定性）
        │     有 resolver 声明这个形状？ → 精装修
        │     没有                      → 通用执行器
        │
        ├─⑤ 执行（确定性，SQL）
        │
        └─⑥ 契约把关
              全覆盖   → 发出
              部分覆盖 → 答能答的 + 列出缺什么       ← 要新增
              没覆盖   → 诚实拒答
```

### P-A2 把「理解」整体收到 Python —— 读写共用一套语义（owner 2026-08-12 拍板）

**现状的线画错了**：现在按「读/写」切 ——

```
读 → Python 理解 + Python 执行
写 → Java 理解(645 条关键词, 11 天 4 次决定 4 次全错) + Java 执行
```

**应该按「理解/执行」切** ——

```
理解 → Python  （一套语义, 读写共用）
执行 → 读走 Python; 写走 Java（权限/预览/确认/审计/事务）
```

Python 的 planner 除查询计划外, 增加**写计划**输出:
```json
{ "动作": "下架", "对象": "红糖糍粑", "范围": "全部门店" }
```
Java 收到结构化写意图, 照旧 权限 → 预览 → 确认 → 执行 → 审计。**Java 不再理解任何东西。**

**为什么执行仍须留在 Java（真理由, 非历史包袱）**：
1. 权限真相在 Java（用户表/角色/权限码/JWT）—— Python 自己判权限 = 复制一套, 必然打架
2. 业务实体不变量在 Java（JPA 校验/级联/触发器）—— Python 直写表会绕过全部
3. 审计链在 Java

⛔ 这三条只支持「执行留 Java」, **一条都不支持「理解留 Java」**。

**这样改之后, 08-11 那个缺陷结构上不存在**：「有没有菜在亏钱卖, 要不要下架」是**半读半写**
的句子, 它出事正因为掉在**两套理解之间**。理解只有一套, 这句话只会被理解一次。

**三个必须处理的风险（写比读高一个量级）**：

1. **Java 不能信 Python 传来的对象名** —— 必须自己再查一遍: 菜存在吗? 属于该租户吗?
   当前状态能下架吗? **LLM 的输出永远只是「建议执行什么」, 不是「可以执行什么」。**
2. **写的 fail-closed 方向与读不同** —— 读是「不答」, 写是「不做」。但 Python 挂了
   不能让用户**改不了东西**, 写路径必须有**非 AI 退路**（操作页表单）。
   「AI 理解不了」≠「功能不可用」。
3. 🔴 **晋升/缓存必须硬性排除写计划** —— 读计划可缓存可回放; **写计划重放 = 重复执行**。
   同一句「下架红糖糍粑」说第二次不能直接回放。**写成会红的断言, 不靠纪律。**

**对 P-A 删除范围的影响**：理解统一后, 601 条**全删**, 不必保留那 ~30 条写意图 ——
它们和另外 570 条是同一个东西: 一张 0/4 准确率的关键词表。

**分三步走, 每步有退路**：
1. 先删 570 条读的（P-A 原样, 风险低证据足）
2. 同时开小验证: 让 Python planner 对「下架红糖糍粑」这类句子**只输出写计划不执行**,
   跑一批看理解准不准
3. 那批数据好看, 再动 Java 那 30 条和执行接口

### P-B 契约「部分通过」+ 白话化

**现状**：契约只有过 / 不过两个出口，不过就整个拒答。

**改成三个出口**，第三个是：**答已覆盖的部分 + 结构化列出缺什么**。

缺口必须**算出来**，不是手写文案：
```
净利润 = 营收 − 食材成本 − 人工 − 租金 − 水电
         ✓      ✓          ✗      ✗      ✗
→ 「按现在有的数据，毛利 68 万，毛利率 67.7%。
    要算净利润还差三样：人工工资、房租、水电。」
```

**⛔ 硬约束（写成会红的断言，不是注释）**：部分答案里出现的每一个数，
必须是用户问的那个指标本身，**不许用"相关指标"顶替**。
理由：这条路和「拿相邻指标顶替」只隔一层纸——2026-08-10 兜底事故就是
用一个营收数字回答了「为什么」。

**⛔ 话术纪律**：不许出现「置信区间」「因果效果」「回归估计」「显著性」这类词。
（现有 `buildRestaurantPriceElasticityGapResponse` 正是反面样本，一并改。）

### P-C 形状路由 + 通用执行器精装修

**现状**（源码实测）：通用执行器**只在契约判失败时才启动**，
即「resolver 强制优先」。后果：resolver 接住了但答得烂（契约恰好过了）→
通用执行器永远没机会。而「答得烂」这件事契约根本判不了。

**改成**：
```
LLM 产出形状 {指标, 维度, 聚合, 时间}
  ├─ 有 resolver 声明处理这个形状 → 用它（精装修）
  └─ 没有                        → 通用执行器
```
关键：**resolver 自己声明处理哪些形状**，不再靠 LLM 猜一个 intent 名字。

**附带产出**：覆盖率表——22 指标 × 16 维度 × 9 聚合里，哪些格子有 resolver、
哪些落通用、哪些两个都接不住。**这张表现在不存在，所以没人说得清覆盖面。**

**精装修挂在「聚合类型」上，不挂在「问题」上**——9 份模板覆盖全部格子：

| 聚合 | 模板 |
|---|---|
| rank / bottom | 榜单 + 柱状图 + 倍数对比 |
| trend | 折线 + 环比同比 + 拐点 |
| compare | 左右对比表 + 差额与百分比 |
| share | 占比条 + 「前三名占 71%」 |
| summary | 大数字 + 计算过程 + 范围声明 |
| concentration | 集中度 + 离群标注（**顺带解决「正不正常」**） |
| extremes / above_avg | 极值 + 均线位置 |

新增指标不用写模板，自动继承全部 9 种展现。

### P-D 归因 resolver

**共用现有登记表**，不新增维度：
```
「为什么营收比上月低」
  → 沿每个维度各做一次环比（门店/菜品/渠道/餐段/时段…）
  → 算每个维度值对总降幅的贡献占比
  → 判分布形状 → 按形状说话
  → 末尾反问事件（活动/换供应商/装修…）
```

**⛔ 算法不输出「主因」，输出「分布形状」**：

| 形状 | 判据 | 说法 |
|---|---|---|
| 集中 | top1 > 50% | 「主要是 A 店，占降幅 61%」 |
| **分散** | top3 < 50% | **「没有集中原因，10 家店普遍下降 3-5%」** |
| 两极 | 有涨有跌抵消 | 「B 店涨 12%，但 A/C 跌得更多」 |
| 结构 | 总量没变构成变了 | 「营收持平，但高毛利菜占比 34%→21%」 |

**★ 分散那一行是关键**：普遍性下降恰恰最需要解释（大盘/季节/商圈），
而「挑最大的报」会把系统性问题误报成单点问题。
**宁可说「找不到集中原因」，也不许把最大的那个当主因。**

**LLM 的位置**：只在两端——入口把人话变成形状，出口把确定性结论写成人话。
**谁是主因由算式定，不由 LLM 定。**

**反问在结论之后，不代替结论**。⛔ 不能变成「我不知道，你告诉我」。

### P-E 会话记忆（本地、确定性）

**存结构，不存文字**：
```
会话状态 = {
   当前计划:   {指标, 对象, 时间, 门店}      ← 唯一焦点
   计划栈:     [前一个, 再前一个]            ← 只留 2-3 层
   已提及实体: {菜品:[…], 门店:[…], 时间:[…]}
}
```

三级台阶，**能在低台阶解决绝不上高台阶**：

| 级 | 情形 | 成本 |
|---|---|---|
| ① | 自足句 → 整个换掉当前计划 | 零 LLM，**且可晋升** |
| ② | 能确定要换哪个槽（那毛利呢 / 换成上个月 / 徐汇店呢） | 零 LLM |
| ③ | 说不清换哪个槽（那这样呢 / 按你说的来） | 走 LLM |

「回到刚才那个」= 出栈，零 LLM。

**⛔ 纪律**：已提及实体只用于**补全**，绝不用于**覆盖**。用户明确说了「全部门店」，
不许拿栈里的「徐汇店」改它。写成会红的断言——否则就是「拿上下文顶替用户原话」。

📌 现有 `smart_bi_chat_session.session_state_summary`（≤300 字符）是**给 LLM 看的
文字摘要**，要改成上面这套结构化计划栈。

## 4. Token 成本（实测）

| 档 | 每题 | 条件 |
|---|---:|---|
| 零 | 0 | 命中晋升路由（**当前 0 条可命中**） |
| 极低 | ~100 | 计划缓存命中（同句 6h 内） |
| 低 | ~1,800 | prompt 前缀缓存命中 97% |
| 标准 | ~4,600 | 冷启动（4,402 prompt + 217 completion） |
| 高 | 1.5–2 万 | 链头不健康，每次超时重试重发完整 4,000 prompt |
| 最高 | 3 万+ | 多轮链后续轮 |

**prompt 结构（实测 9,787 字符）**：19 意图描述 + 22 指标枚举 + 9 聚合 + 10 个
few-shot + 规则。**变量全拼在最后**——公共前缀 9,648 字符 = 固定部分的 100%，
**它是为缓存设计的**。

**因此不建议 RAG**：97% 已被前缀缓存吃掉，RAG 再省的是那 3%；
而代价是检索没召回某指标时，LLM **不会说检索不到，会挑个相近的**——
正是 `_drop_planner_invented_metrics` 在治的病。
⚠️ 但 97% 是单次读数，且部署重启后归零。**先量一周真实平均命中率**，
低于 60% 再重新考虑 RAG。

**一轮 85 题电池 = 47万 ~ 130万 token ≈ 一个模型一整份免费额度。**
区间宽度全部来自链头健不健康。

## 5. 长期：会不会被 agent 替代

**会被替代的**：19 个意图枚举 + 手写 resolver + Java 645 条——
这一层就是「把 agent 该做的事拆成人写的分支」。

**不会被替代的（真正的资产）**：
1. **LLM 碰不到算术**——会写 SQL 的 agent 可以把 join / 日期 / 去重写错，且自信地报出来
2. **每个答案背后是可存、可比、可回放的计划**——agent 的思考过程存不下也回放不了，
   而「越用越省」只有在有这张计划时才成立
3. **成本可预测**——agent 每题 5-10 次工具调用，10-50 倍
4. **失败方式可预测**——fail closed；agent 几乎总会产出某个东西，
   对要拿它做决策的老板，听起来合理的错答案比「我不知道」糟得多

**判断**：那张 `22 × 16 × 9` 登记表**不是"把 agent 拆开"，它就是 agent 需要的工具
schema**。未来 agent 替换的是 **planner**，不是 **executor**：

```
agent 规划（会探索、会追问、会换角度）
   ↓ 产出仍是那张计划
确定性层执行  ← 不变
契约把关      ← 不变
飞轮沉淀      ← 不变，且 agent 越贵它越值钱
```

**投资方向**：往「19 意图 + 手写 resolver」加东西会被冲掉；
往「登记表 + 契约 + 飞轮」加，agent 来了更值钱。

⚠️ 本节是判断不是实测，与本文其余部分性质不同。

---

### P-I 评估升级：子串断言 → LLM-judge 混合（**新增, 排第一**）

**为什么排第一**: 你不能用 84 条子串断言当仪器, 去做「删 645 条规则 + 19 个意图」
的手术。删完跑一轮全绿, **根本分不清是真没坏还是断言看不见** —— 2026-08-11
八张表格塌了、两轮 85/85 全绿没发现, 就是同一个仪器同一种盲区。

**评估先行, 因为它是仪器不是目标。**

**混合, 不是替换**:
```
确定性断言(留): 数字必须 == 7,926,316.02      ← judge 判不了也不该判
LLM-judge(加) : 答上老板问的了吗?
                有没有「置信区间」这类黑话?
                排版塌没塌?                    ← 子串断言永远看不见这三条
```

**成本**: 一次 judge ≈ 1,500 token(答案 ~1,000 + 评分规则 ~500);
85 题一轮 **+13 万 token = 电池总成本的 +10%~+27%**。**只在测试跑, 生产零成本。**

**行业参照(2026)**: LLM-judge 与人类评审一致率约 85% —— **高于两个人类之间的一致率**,
成本是人工的 1/500~1/5000。已是行业默认评估方式。

配套: P-G 的 20 题口语电池一起做 —— 它是目前唯一能低成本引入「外部视角」的动作。

---

### P-J 登记表: 指标层 → 语义层（**新增**）

给 agent / 通用执行器用的语义层必须比指标层伸得更远。补三样, **都是登记表加字段,
不是新系统, token 成本 0**（确定性元数据, LLM 不读）:

1. **实体关联(join 路径)**: 菜品 ─配方─ 食材 ─供应商─ 进价。
   声明出来后通用执行器能自己算「这道菜的成本」, 不必等人写 RECIPE_COST resolver
2. **口径归属**: 「毛利」在菜品层 = 售价−食材成本; 在门店层 = 营收−已覆盖成本。
   **现在这两个定义藏在两个 resolver 里, 谁也不知道它们不一样**
3. **数据可信度**: 每个指标带覆盖率 / 最后更新时间。
   已有一半 ——「成本覆盖率 100.0%」那句是手写在 resolver 里的, 不是登记表属性

## 6. 关于「会不会被 agent 替代」的审计结论（2026-08-12, 含业内数据）

**方向没错, 但担心有一半是真的 —— 位置不同。**

### 支持这条路的数据

| 场景 | 结果 |
|---|---|
| Spider 2.0（真实企业库） | o1-preview code-agent 只解决 **21.3%** |
| BEAVER（真实数仓） | GPT-4o 等端到端准确率**接近 0%** |
| Salesforce 生产 text-to-SQL | 上线 **~50%**, 靠「一问生成 10 条 SQL 投票」才到 ~80% |
| 走语义层的 NL2SQL | Spider2-snow **94.15%** |
| 表结构变动 | text-to-SQL 准确率掉最多 **24 个点** |

关键判断:「**真正的瓶颈是做 grounding 的语义模型, 不是 LLM 本身**」。
Gartner: **只靠 MCP 做 agentic analytics 的项目 60% 会因缺一致语义层而失败**。
2026 最佳实践原话:「**agent 当决策编排者, 确定性组件当执行者**」——逐字是本架构。

### 会被冲掉的三样（都在计划里了）

1. **19 意图 + 18 resolver** ← 垂直行业**救不了**它: 坏在「问法的宽度」不是 schema 宽度
2. **指标层 ≠ 语义层** ← 垂直**大部分能救**: 补 join 路径/口径/可信度即可（P-J）
3. **子串断言** ← 垂直**救不了**: 跟垂不垂直无关, 是仪器精度（P-I）

### 垂直行业够不够

**大部分够。** 杀死 text-to-SQL 的 benchmark 测的是异构企业库（几百张表、schema 会变、
跨域）; 你只有一个域、一套固定 schema、14 个指标、10 家门店 —— agent 的
「探索/适应」价值对你打很大折扣。

### 要不要上 agent

**现在不要。** agent 唯一多给的是**多步探索**, 而 **P-D 归因 resolver 用确定性方式
能拿到其中 80%**（沿所有维度环比找异常 = 多步探索的确定性版本, 更快更便宜可复现）。
**先做 P-D, 看剩下 20% 是什么, 再决定。** 不要现在就假设需要它。

### 🔴 最想让人听进去的一条（与架构无关）

**近 7 天 6169 条问句, 6046 条是电池自己问的, 真实老板 0 条。**
所有架构争论在「没有一个真实用户」面前都是次要的。现在全部判据（84 题/契约/晋升）
都是**自己写给自己的** —— 这不是架构问题, 是**证据基础问题**, 它会让上面所有讨论
建在沙子上。

## 7. 建议顺序（2026-08-12 定稿）

```
① P-I  评估升级 (judge 混合) + P-G 20 题口语   ← 先有仪器, 否则后面是蒙眼动刀
② P-A  删 570 条读兜底                          ← 有仪器了才敢删
③ P-C  形状路由 (顺带删掉 19 个意图)            ← prompt 反而 −15%, 不增 LLM 调用
④ P-B  契约部分通过 + 白话化
⑤ P-J  登记表扩语义层
⑥ P-D  归因 resolver
⑦ P-A2 写理解收到 Python
⑧ P-E  会话记忆结构化 / P-F 飞轮重启
⑨ P-H  向量化                                   ← 暂缓, 等语料与真实流量
```

**生产环境 token 净变化: −15%**（prompt 去掉 19 个意图描述）, 新增 LLM 调用仅在
① 的测试环节与 ⑥ 的归因表达步骤（后者仅归因类问题触发, ~800 prompt + 300 completion）。
