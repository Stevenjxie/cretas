## ⚠️ 一个要先纠正的前提

交办时的说法是「确保 **139** 的每日营业自动生成也有这部分缺少的数据」。

**139 的生成器并不缺这部分数据。** 模拟端世界模型里一直都有：

```
dish        10 条，带 cost_cents
ingredient  13 条，带 unit_price_cents
recipe      22 条
```

缺的是中间两段：**① 没有接口能把它们取走**（API 表面只有 `/order/list` 与三个
`/stock/*`）**② 47 侧没有 connector 导入**。

所以**不需要改生成器**。菜品/食材/配方是**静态主数据**，seed 一次即可（现实中配方
本来就不每天变），每分钟推进的循环产的是订单与库存流水 —— 这个设计是对的。

⚠️ 我一开始查 139 的 cron 与 timer，只看到 acme.sh 续证书，差点得出「139 上没有
生成器」的错误结论。真相是生成器是 `cretas-mock-platform` 服务里的**常驻 asyncio
循环**，不是定时任务。**判据：找不到定时任务 ≠ 没有定时行为，先看 systemd 服务本身。**

## 一、根因链（逐层实测，不是推断）

```
财务 3 条答成「毛利前 0 名」
  ← agg_restaurant_product_cost  0 行
    ← fact_restaurant_recipe_line 0 行      ❌
    ← dim_ingredient.unit_price   全 NULL   ❌
      ← 139 API 没有 menu 端点               ❌
      ← 47 没有 menu connector               ❌
```

`dim_product` 10 条是有的（POS 侧建的），所以表面看「菜都在」，只有查到配方那一层
才发现是空的。MOCK_REST 的工厂名就写着 **「模拟平台餐饮租户 (假 POS 数据接入验证)」**
—— 它当初就是按 POS 接入验证建的，从没给过菜单主数据。

**链路完全不必碰 Java 库**：`product_types` 虽是主路径，但 SmartBI 侧
`dim_restaurant_cost_product` 是等价映射（已有 7 个租户在用），写它就够了。

## 三、🔴 成本口径（Steve 拍板，会直接影响客户看到的毛利率）

模拟端有**两个互相独立的成本事实**，实测差 2.2 倍：

| | 合计 | 食材成本率 | 毛利率 |
|---|---|---|---|
| `dish.cost_cents` | ¥193.80 | **42.0%** | **58%** ← 权威 |
| 22 条配方逐行算出 | ¥87.41 | 19.0% | 81% |

配方每道菜只列 2–4 种主料（藤椒鸡 = 鸡腿肉 + 藤椒 + 菜籽油），**不是完整 BOM**，
没有配菜、调料、损耗。按它直接算毛利率会显示 81%，技术上答得出来但不真实。

**定案**：配方用量与食材单价都保持真实，`line_cost` 按各行原始占比摊到
`dish.cost_cents`，把主料以外的部分显式分摊进去。

⚠️ 代价是 `line_cost ≠ standard_qty × unit_price`。这是**有意的**，不是 bug。
想改回逐行自洽，就得先在 139 把配方补成完整 BOM。

⚠️ **参考租户 RES_3101_009 实测加权毛利率 85.1%，很可能是同一成因**（配方只有主料
而没做分摊）。未查证，单独记着。

## 四、🔴 差点造成成本翻倍的集成隐患（已修）

写 connector 时发现：seed 用的幂等键是 `mp_rec_001_001`，而 writer 用
`mp_dish_001__mp_ingr_001` —— **两套键**。connector 首跑会在同一批菜上写出
**第二套 22 行**，食材成本直接翻倍，而**两套行看起来都合法**。

修法不是迁就旧键，而是让 writer 拥有自己的命名空间并**剪除平台已不再报的行**
（作用域收紧到本次 dish 集合）。这本来就是主数据同步该有的**全量替换**语义 ——
平台删掉一条配方，库里那行若留着仍会被 ETL 计进成本，只增不减且没人察觉。

**prod 实证**：connector 首跑日志 `pruned_stale_lines: 22`，库里最终
`total=22 / new_key=22 / old_key=0`（不是 44）。

同时把 seed 重构成薄封装：分摊口径、幂等键、写库**全部委托 `menu_writer`**，
并加用例 `test_seed脚本与connector用同一份口径` 断言两者结果逐字相同。

## 七、🔴 判据类教训

1. **找不到定时任务 ≠ 没有定时行为。** 生成器是常驻服务里的 asyncio 循环，
   查 cron/timer 一无所获时差点误判「139 上没有生成器」。
2. **同一件事有两处实现时，最凶险的不是数字不一致而是"两套都合法"。**
   两套幂等键会让成本静默翻倍。判据：**第二个实现写完，先问它和第一个的
   幂等键/口径是不是逐字相同**，并写用例钉住。
3. **`set_config(..., is_local=true)` 只在事务内有效。** 我把它和 count 写成两条
   事务外语句，RLS 把刚写的 10 行全藏起来，报「0 行」——**与真的没写进去长得一模一样**。
   查 Gold 表恒返回 0 这个坑，本轮又踩了一次。
4. **两个独立的"事实"打架时，别自己挑一个然后继续。** 成本口径差 2.2 倍会直接改变
   客户看到的毛利率（58% vs 81%），这是产品决策不是实现细节。
5. ⚠️ **嵌套转义在 ssh + psql + heredoc 三层里必炸**，本轮两次。写文件再 `scp` 过去跑。
