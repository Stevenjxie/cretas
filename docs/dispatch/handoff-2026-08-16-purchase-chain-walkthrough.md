## 二、🔑 本轮最重要的事：一次走查 = 一个「功能完全用不了」

### 起因

上一轮结论是「采购 OA 零实例」。本轮先问「打磨它有什么影响」，实测把定性改了两次：

| 说法 | 实测 |
|---|---|
| 「采购链零流量，那 12 条任务改的是没人走的链」 | ❌ **F006 每个域都是个位数**：销售 12 / 原料 4 / 生产 2 / 报工 2 / 采购 1。采购不是被冷落，是**排在队尾的下一个** |
| 「F006 整个业务历史只有 7 天」 | ❌ 只对生产侧成立。**财务侧从 5 月就在用**（45 条付款记录、26 条付款申请，到 8-12） |
| 「零流量」 | ⇒ 更准确：**各段都有人用，但段与段之间的接缝从没被走过**。采购单→收货 0 次；收货→应付 0 次 |

⇒ 那 12 条在飞任务改的**正是接缝**，也就是风险最高、证据最少的那一部分。

### 走查结果（5 个接缝，4 通 1 断）

```
建单 ✅ → 提交/OA ✅ → 财务审批 ✅ → 仓储待收货 ✅ → 收货入库 🔴 → 应付自动挂账 ✅
```

后端这条链**比预期完整**：自动生成应付（`AP-…` / 账期 T+30 / `source_type=PURCHASE_RECEIVE`）、采购单自动 `COMPLETED`。

### 🔴 断的那一处：RN 扫码入库 100% 失败（#2717）

```
RN WHReceiptCreateScreen 的顺序:
  1. createReceive(草稿)
  2. confirmReceive          ← 后端要求此时已有凭证 → 409
  3. 抄码品落日志
  4. 上传照片到 PURCHASE_RECEIPT/{receive.id}   ← 抛异常后永远执行不到
```

| | |
|---|---|
| 后端闸 | `PurchaseServiceImpl:2040` **无条件**要求确认前已有凭证，无工厂级开关 |
| 何时引入 | **2026-07-22 `#1577`** |
| RN 的上传顺序 | **2026-05-17 `#794`** 起就是「确认后才传」 |
| ⇒ | 闸落地那天起必然 409，**用户拍没拍照都一样** |
| web-admin | ✅ 一直是对的（附件数为 0 时禁用确认按钮） |

**为什么 25 天没人发现**：这条链在生产上没人走 —— F006 在 8-15 前一张采购单都没有；库里 28 张收货单全是别的租户的**无来源**收货，`from_purchase_order = 0`。

▎ **一次走查（约 1 小时）找到 1 个用户完全用不了的功能。**
▎ **那 12 条在飞任务没有一条会碰到它 —— 它只在「真的按顺序走一遍」时现形。**

## 七、下一个人必须知道的（环境与方法）

### 环境

- **主工作目录曾落后 origin/main 1453 个 commit**，加载的 `measurement-and-wiring.md` 是 1169 行旧版（权威 1246 行，少了硬约束 9）。本轮已对齐 `.claude/rules/**` + `.claude/skills/**`（46 文件）+ `CLAUDE.md`。⛔ **`AGENTS.md` 未动** —— 它有未推送的「GitHub 封控期离线」一节，且在 `POLICY-CODEX-MODEL-ADVISORY-20260810` 的 scope 锁内。
- **主目录仍停在旧分支**，任何人在那儿 `git checkout` 都会把这几份打回旧版。真正的根治是把它切回 main。
- **对齐 skills 顺手清掉了 3 份 F001 死凭证表**（`f006_*` 账号统一 `123456`，仓里 6 月的审计文档有记）。
- **东京取件链路不通**（`10.66.66.1:22`），预热一律 `PREWARM=skipped`。逃生门是脚本自带的 `--no-prefer-ci-artifact`，⛔ 别去动 VPN/SSH。
- **`release-cretas.sh --tests` 不接受通配符**，要显式类名（`release-java-preflight.sh` 拿类名去解析源文件给改动背书）。这与 CI 的 `TARGET_TESTS` 通配选择器**语义不同**，混用会 `DEPLOY_EXIT=1`。
- **蓝绿槽位本轮从 10010 翻到 10020**。查服务健康前先读 `139:/www/server/panel/vhost/nginx/_upstream_cretas.conf`。
- **`/proc/<pid>/cmdline` 里的 jar 是相对路径**，相对谁要问 `/proc/<pid>/cwd`。

### 方法（本轮实际拦住我的）

1. **OTA 验收用中文标记全是 0** —— Hermes `.hbc` 不以 UTF-8 直存中文。阳性对照（一个必然存在的中文串也读 0）救了一次，否则会报「改动没进 bundle」去重推。⇒ **二进制制品的标记优先选 ASCII**。
2. **服务器 assets 里搜到 4 处「已删」的死路** —— 是 24h 保留期内的**旧 chunk**，不在本次构建里。⇒ **量对东西：只量本次构建的那些**。
3. **`Java prod: 000` 差点当成生产故障** —— 实为我这边直连受限；服务器本机 200、公网 200。⇒ **判服务健康前先问「现在在服务的是哪个实例」**。
4. **`head -75` 截断让我报出「没有仓储角色」** —— `warehouse_*` 排在 `quality_*` 后面。又一次「我看到的是全部吗」。
5. **变异抓出我自己写的阳性对照是松的** —— 正则不锚定收尾时 `/…finance-approve/` 会把 `finance-approve-XX` 也匹配上，端点改名它照样绿。⇒ 阴性断言的阳性对照**也要变异一次**。
6. **两次环境抖动**（`useReportWorkflow` 一次红、`node_modules` IO 错一次），都靠「单独跑 + 全量重跑 + 记录机器状态」分开了，没误判成代码问题。
