# 餐饮实时演示数据流 — 2026-08-05

## 一句话说明

2026-08-05 09:00–14:00（Asia/Singapore），`MOCK_REST` 演示租户每 10 秒接收一条明确标记的模拟预订事件；餐饮首页每 60 秒只读刷新一次，所以每次刷新都会看到订单、人数、分钟柱和最新接收时间继续增长。

这不是扫呗真实接口，也不写入 `RES_3101_009`、F006 或其他租户。现场应说“模拟扫呗等平台授权数据接入后的实时效果”，不能说“扫呗已经接通”。

## 同一条数据怎样往后走

1. `cretas_live_showcase_20260805` 生成门店、目标日期、餐段、桌数、人数、状态和来源更新时间完整的事件，`is_simulated=true`。
2. 事件按明天、下周、下月轮转，进入已有预订事实表；十秒时钟生成幂等外部引用，服务重启不会重复一单。
3. Python 预测 FactBook 每次读取当前预订与 7/30/365 天 POS、客流、人效证据，重新计算预测客流、预订覆盖、建议人数、现有人数、缺口和置信度。
4. Web 餐饮首页每 60 秒只读拉取，展示近 15 分钟事件柱、最近事件、当前预订订单、预测客流和人力建议。
5. 用户提问“明天怎么排班”“下周需要多少兼职”“下个月各店人效安排”时，既有 LLM 路由读取同一 FactBook；数字仍由 FactBook 渲染，LLM 只解释和给可调整建议。

## 现场演示（3 分钟）

1. 用餐饮演示账号打开 `https://admin.cretaceousfuture.com/dashboard`，停留在“餐饮 AI 实时经营指挥屏”。
2. 指出“最后接收”“60 秒后刷新”和“持续接收中”，不要先讲技术架构。
3. 等待一次自动刷新，观察“当前预订订单”“近 15 分钟新增”、分钟柱和最近事件发生变化；每条最近事件都显示“演示模拟”。
4. 点击预测排班，切换明天、下周、下月，说明三类时域共用同一事件链和 FactBook。
5. 回到 AI，依次问三句真实问题；强调人数和百分比来自 FactBook，不是大模型心算。

## 生产写入与自动停止

- 唯一允许写入：`factory_id=MOCK_REST`、`source=cretas_live_showcase_20260805`、`is_simulated=true`。
- 事件间隔：10 秒；时间窗口：09:00（含）至 14:00（不含）；理论上限：1800 行。
- 14:00 后生成器自行正常退出，systemd 不会因成功退出重启；日志保存在 `/www/wwwroot/cretas/logs/restaurant-demo-stream-20260805.log`。
- Timer、服务、源代码和生产写入计数必须分别验收；Web HTTP 200 不能代替数据确实增长。
- 如需回滚，只能按 `factory_id` 与 `source` 双条件先计数、再删除本次模拟行；本任务不自动清理，以便演示后保留审计证据。
