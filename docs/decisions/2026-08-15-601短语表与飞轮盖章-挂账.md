### 原来的证明方式作废

原方案是「跑一个观察窗，看 `[NarrowPath] gate=restaurantPhrase` 有没有人走」。
**这条路走不通**，两个原因都是实测的：

1. **可证明的窗口只有约 13 小时，不是三周。**
   埋点 #2543 合于 2026-08-12，但服务器上 jar 备份**只剩 4 个**，最早
   `bak.20260814_233141`。08-12→08-14 部署的 jar 已被覆盖，
   **那几天的日志里有没有这行，无法追认**。
   ⇒ 这条路依赖日志/制品保留期，而保留期我们控制不了。

2. **96% 的餐饮问句根本不经过那张表。**

   ```
   [Branch:TieredFirst]   14989 (96%)   ← 委派 Python 语义规划
   [Branch:ToolDirect]      271
   [Branch:Dynamic]          22
   [Branch:TieredDelegate]   12

   餐饮请求总数 18319，其中 intentCode=null 17640 (96.3%)
   ```

   ⇒ 观察窗即使跑满，量到的也主要是「没走 Java 这条路」，不是「这张表没用」。

### 换成结构性论证：**三个读点，不是两个**

| # | 读点 | 有埋点？ | 餐饮租户可达？ |
|---|---|---|---|
| 1 | `IntentKnowledgeBase.matchPhrase(input,"RESTAURANT")` :8710 | ✅ 埋点 3/3 | 可达，实测 **0 次命中** |
| 2 | 覆盖率计算 :9027-9036（对已匹配的 intentCode 逐条比对） | ❌ 无 | 可达，**未量** |

### 🔴 读点 3 是决定性的：那 601 条是**语义匹配的锚点**

`SemanticIntentMatcher` 启动时把餐饮短语表整份灌进 embedding 索引：

## 三 · `is_active`：「开一家真实门店」是**一行数据**

```
factories.is_active = false
  → ToolPrincipalPolicy:54            不发 AI 工具 principal
  → AuthenticatedToolPrincipalFactory:27  候选租户被过滤掉
  → FactoryCapabilityPackRoutingPolicy:64 blocked("factory-type-unavailable")
  → FactoryBusinessTypeResolver:25    业态解析过滤
  → FactoryRepository                 13 个查询方法带 isActive = true
```

⇒ **`is_active=false` = 整租户的 AI 能力关停。**
「开一家真实门店」不是一个模糊的产品决定，**就是把这一列置 true**。

⚠️ 青花椒（RES_3101_009）与 DEMO_REST 都是 `is_active=f` ——
所以这十天读它们的数据走的是 **Python 直连**，绕开了 Java 那道 principal 闸。

▎**红线「不激活任何租户」守的正是这个开关。**
