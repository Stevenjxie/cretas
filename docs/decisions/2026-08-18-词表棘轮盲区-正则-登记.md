## 🔴 实测：那道闸看不见它

`backend/python/tests/test_restaurant_wordlist_ratchet.py` 的判据是
`audit_restaurant_wordlists._cjk_seq` —— **中文字符串的序列字面量**。

拿三个样本喂给它：

```
① 手工词表   _FOO_TOKENS = ("有几家店", "门店数量", "几个门店", "多少家店")
             闸能看见  ✅

② 正则       _ASKS_STORE_DIST = re.compile(r"有几家店|门店数量|几个门店|多少家店")
             闸能看见  🔴 看不见

③ 内联 if    if any(t in query for t in ("有几家店", "门店数量", "几个门店")): ...
             闸能看见  ✅
```

⇒ **正则是一个字符串，不是序列字面量** ⇒ `_cjk_seq` 直接返回 `None`。

▎**这个盲区正好就是刚才那次的形状。** 闸建起来了，而它挡不住触发它的那一类。

## 修法（判据，⛔ 不是"多加个正则规则"）

把普查的判据从「**中文序列字面量**」扩成：

> **凡是【拿用户问句去匹配】的新增点，无论写成词表、正则、还是内联 if，
> 都要在 `REGISTRY` 里登记它属于哪一类（ENTITY / INTENT / SAFETY / LEXICAL）。**

具体新增两种识别：

```python
# a) 含中文的正则字面量
re.compile(r"...中文...")          # 赋值给具名常量 → 按名字登记
re.search(r"...中文...", query)    # 内联 → 计入 inline

# b) 单个中文字符串被用来匹配用户输入
"有几家店" in query
query.startswith("哪家")
```

### ⚠️ 边界：只在**与用户输入相关**时才算

⛔ 不能见正则就报。仓里大量正则是**别的用途**：

```
判产品自己输出的正文     answer_contract 那几张（已登记为 LEXICAL）
SQL / 日志 / 文件名解析   与用户语义无关
单位/日期的词法归一       LEXICAL, 本来就该留
```

⇒ 判定「与用户输入相关」的做法，**沿用现在这个脚本已经证明有效的那条纪律**：
**⛔ 不自动猜，只机械地数 + 打出消费点，分类走显式 `REGISTRY`。**

（第一版分类器就是因为想自动判「跟谁比」而漏判三个 —— 详见脚本头部注释。）

## 一 · 判据扩成什么（超出原卡的一条：**载体名**）

原卡说的两种识别都做了（含中文的正则字面量 / 单个中文串被拿去匹配用户输入）。
**实测逼出第三条原卡没写的**：

> 第一版点出 **18 个局部变量名**当登记键 —— `body` / `match` / `raw` /
> `values` / `headers` / `order` / `normalized` / `resolved` …

▎那种键**登记不了**：`body` 在多个文件里都有，登记一个等于豁免全部同名的。
▎**登记键必须能被唯一指认，否则「登记」本身就是个漏洞。**

⇒ 载体名改成「**模块级常量名** 或 **所在函数名**」。

🔴 这条不是洁癖，是**必须的**：触发本卡的那个实例
（`asks_about_store_distribution`）的正则是**内联在函数里、模式还是动态拼的** ——
只认具名常量的话，闸照样挡不住它。

⚠️ 还剩三个局部变量名（`available` / `headers` / `order`）——
它们走的是**存量**那条序列字面量路径（`census()` 里的 `ast.Assign`），
同一个形状、不同代码路径。📏 已核对：三个**本来就在基线 22 里**，
⛔ 本次不动（不在同一个 PR 里改两件事）。**下一棒可顺手收敛。**

## 二 · 重新冻结：**22 → 88**（每一步都是实测值）
