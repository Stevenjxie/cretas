## 〇 · 北极星与交付定义

**让一个餐饮老板打开它，能自己做出一个决定。**

取舍顺序（硬的，冲突时按此让路）：**能不能决定 > 数字准不准 > 覆盖得全不全**

五条交付定义，缺一条不算完成：
1. **答得上** —— 给答案，不是「我没敢算」
2. **说一件他没想到的事** —— 只念他问的数字不算
3. **追问接得住** —— 第二轮必须针对追问，⛔ 不能把上一轮原样再发
4. **该给表格就给表格** —— 排行/对比/构成
5. **答不了时说清三件事** —— 缺什么、怎么拿到、他自己要干什么

反目标（比做成什么更重要）：
- **一条误发的提示，烧掉的是「这东西说的话能信」。** 上新提示前问：排最前面那个命中，他去查会不会一无所获？
- ⛔ 不为只有种子数据支持的形状建检测器 —— 那是在建幻觉
- ⛔ 不替他做判断。产品给依据和判断，**决定是他的**

## 一 · 架构：三个角色，职责不重叠

> **只让 LLM 判断「他想要什么」。代码只做三件不需要懂中文的事：核对、算日期、执行。**
> **问过并审过的直接回放，越用越便宜、越快、越不抖。**

```
LLM     所有语义判断（意图/维度/指代/实体提名/时间概念）      ← 猜
数据库   所有存在性（是不是一道菜、一家店、有没有这个能力）    ← 查
代码     核对、日期算术、执行、格式                          ← 算
```

▎**关键划分不是「词表 vs LLM」，是「猜 vs 查」。**
▎实测：「那最差的呢」→ LLM 自己输出 `dish='最差'`。**LLM 和词表犯的是同一个错，因为它俩都在猜。**
▎⇒ 把词表换成 LLM 不解决问题；该换的对象是**查**，而那一层仍然是确定性代码。

### 事实怎么给 LLM —— 按「量」分三类，⛔ 不一律塞 prompt

```
闭集且小（19 个意图）              → 直接进 prompt
开集或大（门店/菜单/能力表）        → 检索召回几条再进 prompt
                                    理由: 上千家店/上千道菜时 prompt 会无限膨胀
上下文（最近 20 轮 + 会话摘要）     → 进 prompt
```

### 向量检索的岗位 = **实体模糊匹配**，⛔ 不是意图路由

人不会说全称，只记住能唯一区分的那几个字：
```
库里「山川蒙湖店」        → 人说「山川店」        实测子串匹配 = False 🔴
库里「鲜花椒大人二人套餐」 → 人说「青花椒二人套餐」 实测子串匹配 = False 🔴
库里「模拟·徐汇美罗城店」  → 人说「美罗城店」      实测 = True ✅（真子串）
```
⇒ 精确/子串匹配从原理上做不了，只能向量检索。
⚠️ 仓里已有整套 `entity_resolution/agents/{embedding,llm_arbitrator,transitive}.py`，**餐饮读路径一次都没 import 它**。

### ③ LLM 判断（唯一的语义判断，一次调用）
拿回：`intent / dimensions / dish / store / 时间概念 / comparison / confidence`

**⛔ 硬性要求：信息不足时必须输出 `clarify` + 候选维度，不许硬挑一个。**
实测今天没有这条 —— 所以「那最差的呢」时它挑了 `dish='最差'`。

### ④ 核对 —— 判据是「在不在【这次召回给它的候选集】里」

⛔ **不是**「在不在全量目录里」（那是废话，它就是从库里捞出来的）。
我们防的是「**它没从我给的候选里选，自己写了一个**」。

**只覆盖四类，⛔ 不是万能的第二道判断：**

| # | 情况 | 处理 | 拒答? |
|---|---|---|---|
| 1 | **归一**（最高频）：LLM 改写了名字导致查库查不到<br>召回「模拟·徐汇美罗城店」→ LLM 输出「徐汇美罗城店」 | **唯一匹配** → 代码直接归一，⛔ 不回 LLM；**抬头用全名**让老板看见<br>**多条/零条** → 回 LLM 或反问老板 | ❌ |
| 2 | **继承来的槽位没验过**：第 5 轮「那家店的毛利呢」句中无店名，不触发召回 | 按当前租户目录校一次 | ❌ |
| 3 | **跨租户污染**：`dish_catalogue_scope` 注释明写 contextvar 不复位会泄漏到别的租户 | 按当前租户目录挡住 | ❌ |
| 4 | **跑不跑得动**（能力核对） | **唯一会拦的** → 带原因丢回 ③ 重试一次 | ✅ |

**⚠️ 它抓不到的两类（诚实登记）：**
```
❌ 召回对了、LLM 从候选里挑错一条   → 靠确认式反问 / 抬头显示全名
❌ 意图能跑但不是他要的            → 靠答案契约 + 老板否定反馈
```

**冲突处理流程（⛔ 不是一个冲突就丢回去）：**
```
1. 把【全部】维度校对完, 收集【所有】冲突
2. 一次性丢回 ③, 带上每一条冲突的原因（⛔ 不是原样再问一遍）
3. 重试【只有一次】
4. 回来后 ⛔ 不再校对已确认的部分, 直接进 ⑤
```

**重试回来后三条出路：**
```
「我错了，代码是对的」 → 按修正后的走
「我缺信息」          → 反问（重试后仍允许反问）
「确实跑不了」        → 拒答, 并说明是哪一种原因
```

**冲突四象限：**

| | 代码说「通过」 | 代码说「不通过」 |
|---|---|---|
| **LLM 对** | ✅ 执行 | 🔴 **误拦**（目录陈旧/新菜刚上架）→ fail-open + **明说**「菜单里没查到『X』，是不是新菜？」⛔ 绝不静默丢掉 |
| **LLM 错** | 🔴 **漏网** → 唯一防线是答案契约 + 老板否定反馈 | ✅ 拦住并带原因重试 |

### ⑤ 概念 → 日期（纯算术，只有代码知道今天几号）
```
{相对, 月, 2} + 今天 8/18  →  本月 8/1~8/17 ＋ 上月同期 7/1~7/17
{命名, 上季度}             →  4/1 ~ 6/30
{绝对, ...}                →  仅当【用户原话里就有这个日期】才接受
```

### ⑥ 执行 —— **dimensions 必须传进执行器**
实测今天没传：`resolve_wastage_top` 签名里根本没有 `dimensions`，且 `resolver_kwargs` 出口 12 个键没有它，`resolve_by_code` 又按签名过滤 —— **两道都丢**。
后果：「哪家店最多」与「最近损耗怎么样」返回**逐字相同**的答案（md5 `bd1d6675`，1249 字）。

### ⑦ 答案契约（11 项）
`window_label · profitability_verdict · margin_value · store_name · dish_name ·
non_empty_answer · comparison · margin_integrity · request_coverage ·
execution_consistency · analysis_action`

⚠️ 要认「**因权限而缺**」一态（店长看不到金额 ≠ 算不出来）。
⚠️ 实测 24 问句 × 2 轮缺口 **0 次** —— 一道从不开火的闸，「通过」等于没说话，⛔ 晋升条件不能写成「通过全部闸」。

### ⑧ 记账 + 两条飞轮
```
写日志: query / intent / answer / 耗时
   ➕ query_embedding   [实测 0/9731 有值] 🔴
   ➕ history           [实测 0/9731 有值] 🔴
   ➕ user_feedback     [实测 0/9731 有值] 🔴
   ➕ 【纠正记录】: LLM 说 X, 我们用了 Y, 因为 Z   ← 「越用越准」唯一的免费燃料

                   用途: 更便宜 / 更快 / 不抖
飞轮 B（答不上）  → 按【拒答原因】归类 → 人工据此【补能力】
                   ⛔ 不进晋升（它现在还答不了，晋升进去就是固化一个错的）
                   闭环: 能力补完后, 把这批原句原封不动批量晋升进飞轮 A
拒答原因分类: 没有数据 · 没有维度 · 没有判定标准 · 信息不足(已反问) · 域外 · 其它

## 三 · 其余架构规则

### 反问
```
① 一次把【所有】缺的问全, ⛔ 不许一个一个问
② 能给按钮的给按钮（时间: 本月/上月/最近7天/最近30天）
③ 门店/菜品数量大 ⇒ ⛔ 不列举, 走检索（老板打「山川」召回「山川蒙湖店」）
④ 回答后 → 拼成【完整句子】从 ① 整句重走（「过去30天米饭卖得怎么样」）
   ⛔ 不只把「过去30天」片段传回去
   理由: 「哪些该重算」本身是新判断, 新判断就是新出错点。全量重走一次调用换掉一整类风险
⑤ 同一个问题最多反问【两轮】, 之后用默认值 + 明确声明
   ⚠️ 与「⛔ 不做『有默认值就压掉澄清』」不矛盾: 那条管第一轮, 这条管第三轮
⑥ 反问判据是【维度确定了没有】, ⛔ 不是「有没有具体名字」
     「那最差的呢」    没说是店/菜/时段 ⇒ 必须反问
     「最差的那家店」  明确说了是【店】 ⇒ 直接算, ⛔ 不反问
```

### 上下文 —— ⛔ 不强制合并，存 spec 栈不存对话
```
缺对象/时间时: 先从前文找 → 找到只作【建议】给 LLM:「上文在说 X，这句要接着 X 吗？」
                          → 找不到才反问
多轮继承: 拼【上一轮的 spec（结构化）】+ 上一轮结论摘要(1~2句) + 这一轮原句
          ⛔ 不拼问句文字, ⛔ 不塞整段答案
          理由: 上一轮答案里有 10 家店,「那毛利呢」多半问【这 10 家】不是【第一名】
下钻: 在同一个 spec 上【加一层】; 换维: 改一维
      ⇒ 无论问多细, 上下文永远是「一个 spec + 它的下钻路径」
```

### 实体有两种来源
```
说出来的  「徐汇美罗城店」          → 召回 + 核对
算出来的  「最差的那家店」          → 🔑 先执行一次计算得到具体店名, 再核对那家店, 再执行分析
```

### 指标集合由 LLM 决定，⛔ 不是固定清单
```
「哪道菜不赚钱」          → 给全套同族: 销售额/销量/成本/毛利/毛利率, 倒序
「为什么这道菜卖一份亏一份」→ 只要成本结构 + 毛利, ⛔ 销售额没关系
「哪家店卖得最好」        → 前 3~5 家 + 全套销售指标表, ⛔ 不只答一家店名
边界: 判断在前, 数据在后。⛔ 不能变成 6 列数字让他自己找
      任何一个指标算不出来, 要说清为什么
```

## 四 · 措辞规范（老板可读，⛔ 不许出现技术词）

```
没有数据      「当前系统里还没有库存数据，接上之后我才能回答缺货情况。」
没有维度      「当前库存只能【按食材】看。要不要先按食材看一下？」
              ⛔ 不说「该能力尚未支持，请联系工作人员」—— 给出路, 不认错
              ⛔ 不说「底层表没有门店这一列」—— 技术话不给老板
没有判定标准  先用默认算法算出来(历史用量/离群), 再声明:
              「本次按【默认判断标准】计算。您门店的缺货判定标准建议重新设置。」
              ⛔ 没标准 ≠ 不能算
窗口内 0 行   「这家店最后一条记录是 8/12，之后没有数据上来。麻烦排查一下 POS。」
              ⛔ 不猜「有没有开张」—— AI 判断不了现场
不支持的指标  「翻台率我算不了 —— 缺【台位数】和【每桌就餐时长】，补上来我就能算。
               眼下最接近的是每小时订单数和时段分布，要不要先看这个？」
部分能做      能做的先给 → 为什么另一半不能 → 老板要做什么 → 还能看什么
              ⛔ 不因为一半不行就整句作废
权限          店长只有一家店 ⇒ 直接限定到他那家；金额被剥零时只给率并说明,
              ⛔ 绝不说「我算不出来」(那是撒谎)
归因七步      ①总量差多少 ②拆成量×价 ③客流再拆(同比/环比) ④落到哪几家店/菜/时段
              ⑤🔑反问现实事件(商场活动/施工/周边变化) ⑥给排查方向 ⑦都排除不掉才落到运营问题
```

## 八 · 测量纪律（本仓反复踩出来的执行项）

```
1  会读出「全无」的仪器必须配【阳性对照】—— 否则分不清「真没有」和「钩子没挂上」

   clear_semantic_plan_cache / clear_route_cache / clear_tenant_gate_cache
