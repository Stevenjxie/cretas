# 报工幂等：用客户端请求号，不用时间窗去重

**日期**: 2026-08-17
**决策人**: 本 chat（Steve 授权范围内自裁）
**触发**: 对抗性审计第 1 轮，在生产上验证

---

## 事实（生产实测）

对 F006 提交**两次完全相同**的领用报工（间隔 37ms）：

```
第 1 次 → 200, reportId 23804
第 2 次 → 200, reportId 23805
库存    → consumed 0.00 → 1.00   ← 领了 0.5, 扣了 1.0
```

**双扣，无任何拦截。** 已冲销。

## 为什么现在才要紧

实时化之前，产出要等审批，重复提交至少产出侧不会立刻影响库存。
**改成提交即入账之后，重复提交 = 库存立刻被多扣。** 风险等级变了。

而防护**只在前端**（`disabled={submitting}`）——
网络超时重试、离线重发、进程被杀后重开、API 直调，全都绕得过去。

## 决策：用客户端请求号（`clientRequestId`），⛔ 不用时间窗去重

legacy 栈（`WorkReportingServiceImpl`）用的是 **5 分钟时间窗**
（`existsBy…AndCreatedAtAfter…`）。**⛔ 不照抄。**

| | 时间窗去重 | 客户端请求号 |
|---|---|---|
| 「重试同一个动作」 | ✅ 拦得住 | ✅ 拦得住 |
| **「真的要报第二笔」** | 🔴 **误拦** | ✅ 放行 |

报工恰恰是**合法高频**的动作：分段报工、领两批料、一道工序多人分别报。
用时间窗会把这些正当操作当成重复 —— 而**一道会误拦正当操作的闸，最后一定会被绕开或关掉**。

请求号能区分二者：**同一次点击的重试**带同一个号，**用户真的再报一笔**时前端重新生成号。

## 落地

- `production_reports` 加 `client_request_id` 列 + `(factory_id, client_request_id)` 唯一索引
  （与 `production_plans.client_request_id` 同一套模式，仓里已有先例）
- 后端：带号时先查，命中就返回**原来那条**的结果（幂等，不报错、不新建）
- RN：每次进入报工屏生成一个号；**提交失败重试沿用同一个号**；提交成功或用户改了内容才换新号

## 判据

- 同号提交两次 → 只产生一条报工、库存只扣一次、第二次返回第一次的 reportId
- **阴性对照**：不同号提交两次 → 正常产生两条（⛔ 不许把正当的第二笔拦掉）
- 不带号 → 保持现状（向后兼容，旧版 App 不会被挡）
- 变异：把唯一索引/查重去掉 → 第一条断言必须红
