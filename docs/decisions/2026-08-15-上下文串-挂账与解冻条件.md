## 二 · 方法学死路（为什么当前方法量不出发生率）

### 死因：计划缓存键不含 history

```python
def _semantic_plan_cache_key(factory_id: str, query: str) -> Tuple[str, str, str]
# → (factory_id, 归一化问句, plan_version)   ⛔ 不含 history / session
```

代码注释里明写这是**故意的**（"deliberately NOT on the session, so a sentence
answered once is answered free for everyone"）。

于是 A/B 探针「同一个 query，先跑不带 history、再跑带 history」：

```
第 1 次（不带）→ LLM 真编译，结果**写进缓存**
第 2 次（带）  → **命中第 1 次写的缓存**
⇒ 两侧是同一个东西，当然相等
```

### 实测读数（2026-08-15，MOCK_REST，prod）

**基线抖动**（8 问句 × 各 10 次，不带 history）：

```
最大抖动 1/10；而抖的**只有 source_tier** 一个字段：
  次数 [1]                        → {'source_tier': 'llm'}
  次数 [2,3,4,5,6,7,8,9,10]       → {'source_tier': 'plan_cache'}
```

**所有业务槽位**（intent / store_scope / dimensions / metrics /
date_range / window_label / analysis_action …）**零抖动**。
⇒ 那 1/10 不是噪声，是**缓存预热**，而且是确定性的。

**按有效比较重算**（18 个互不相同的多轮场景，各比一次）：

```
总样本 18   有效（两侧 source_tier 都是 llm）2   其中串 0
```

16 条无效，**无效原因完全一致**：`不带='llm'  带='plan_cache'`。

两条有效样本都是阳性对照，**都不是串**（「上个月呢」「罗氏虾呢」，
差异全部落在「槽位原本为空，继承是补全」和「问句含指代」上）。

### ⚠️ 一个被读数否掉的推断（owner，已认）

从注释 `CONVERSATION STATE DISQUALIFIES BOTH EXITS` 推出「带 history 就不吃缓存」。
**实测 16 条带 history 的全部命中缓存。**
那句注释说的是「**被上下文改写过的**问句」不吃 —— 而绝大多数轮次并没有被改写。

⇒ 见下面规则一。

## 三 · 耦合：凑样本会**改变被测对象**

这是最要命的一条，也是「再跑几轮就有样本了」这个想法的死结：

- 有效率实测 **2/18 ≈ 11%**
- 同一问句**只有第一次是冷的** ⇒ 重复 N 次是**假重复**
- 要凑 10 个有效样本 ⇒ 需要约 **90 个互不相同的问句**
- 而**换问句本身就换了被测对象** —— 问句变了，串不串本来就可能不同

⇒ **在不清缓存的前提下**，不存在「样本再多一点就能得出发生率」这条路。

⚠️ 订正（见第四节）：**清缓存这条路一直是通的**，只是我四轮都没走。
所以「结构性死路」只对**我当时那套探针**成立，不对这个量本身成立。

## 四 · 解冻条件

### 🔴 订正：a 不需要产品改动 —— 那个开关**已经存在**

本文档第一版把 a 写成「需要一个 bypass 计划缓存的开关（需产品改动）」。
**那是错的。** 复核时发现：

```python
smartbi/gold/restaurant/restaurant_intent.py:3133
    def clear_semantic_plan_cache() -> None
    # 邻居还有 clear_route_cache(2718) / clear_tenant_gate_cache(5094)
```

而且 `.claude/rules/measurement-and-wiring.md` 的**硬约束 3**
（「跨样本批量读数，开跑前清缓存并**贴出清了哪几个**」）
示例里逐字写着 `clear_semantic_plan_cache` —— **那条硬约束当时就在**。

⇒ 四轮里我一次都没调它。这不是「缺工具」，是**没照已有的硬约束做**。
成因见规则文件末尾的「载体教训（第三次）」：主工作目录停在落后 1424 个
commit 的分支上，那里的规则文件是一份 **199 行的旧草稿**，没有硬约束这一章。

### a. 开跑前 `clear_semantic_plan_cache()`（**可立即执行**）

每个样本前清一次 ⇒ 有效率从 11% 回到 100%，重复 N 次才是 N 个独立样本。
⚠️ 三个 helper 一起清（route / plan / tenant_gate），并**贴出清了哪几个**。

### b. 换一个**不需要 A/B** 的判据（更稳，推荐）

直接问「这个槽位的值在**问句里**，还是在**上一轮**里有依据吗」，
⛔ 而不是「跟不带 history 的编译比」。判据不涉及第二次编译 ⇒ 缓存无从污染。

PR #2654 的复验判据就是这个形状（见下），实测三租户全绿、阴性对照全红。

### ⚠️ 那为什么还是冻结？

**理由从「量不了」换成「优先级」** —— 见第六节：
客户那次对话还没发生，「打烊看一眼」这个形态本身尚未经真人验证。
⛔ 但**不要再说「这个量测不了」** —— 它测得了，代价是几十次带清缓存的采样。

## 五 · 冻结期间的纪律

⛔ **在解冻之前，任何关于「上下文串发生率」的数字一律不作数** ——
包括 15.8%、3/19、0/12，以及本文档里的 0/2。
它们全部只是「在当时那套仪器下读到的东西」，而那套仪器**没有清缓存**。

⛔ 重开这条线时，第一件事是**开跑前清三个缓存并贴出清了哪几个**
（硬约束 3），⛔ 不是「先跑一轮看看」。

✅ **允许**继续做的：消掉**具体一类**串（如 PR #2654 消掉「按钮继承方向」那一类），
只要那一类有自己的独立变异对照，不依赖发生率。

### 已放行的一类：按钮携带上下文（PR #2654，2026-08-15 已部署 prod）

按钮问句现在带上它长出来那一屏的**显式日期**：

```
question='最近30天（2026-07-17 至 2026-08-15）哪些菜没有成本卡'
```

**要修 ≠ 解冻。** 发生率照旧冻结（本文件第五节纪律不变），
本线三件做完回挂账。本节依据的正是第五节末尾那条允许：

问句 `全部门店最近30天报损情况严不严重`。**登记为「故意不改」，不是「已确认不是串」。**

| | |
