## 0 · 要解决的是什么

owner 定稿原话：

```
飞轮 A（答上了）  →  按频次审 Top-50  →  晋升 ledger  →  下次 0 token 命中
飞轮 B（答不上）  →  按【拒答原因】归类  →  人工看这张表去【补能力】
                     ⛔ 不进晋升 —— 它现在还答不了, 晋升进去就是固化一个错的
```

📏 今天飞轮 B 完全不存在：拒答只写进普通日志，没有分类、没有队列、没有人看。
实测（本轮，AST 判定，阳性对照已过）：`record_refusal` / `enqueue_refusal` /
`log_refusal_reason` 在读路径三个文件里**都不存在**。

## 1 · 三个选项与各自的代价

| | 方案 | 代价 |
|---|---|---|
| **A** | 新建 `ai_refusal_queue` 表 + Flyway/migration | 字段是一等公民、索引好加、类型强。**但**：DB 迁移是本仓的强制 PR 高风险路径（`worktree-and-main-only-deploy.md` 双轨表）；更重的是它**新造了第二套聚合口径** —— 飞轮 A 的三个聚合器（`aggregate_candidates` / `aggregate_misses` / `list_promotion_candidates`）全部读 `smart_bi_llm_fallback_log`，再开一张表就是形态 D：同一件事两份，一定会漂 |
| **B** | 复用 `smart_bi_llm_fallback_log` + `agg_meta.refusal_reason`（**飞轮 A 的形状**） | 零 migration；RLS GUC、fail-open、`log_template_hit` 写入、`GROUP BY trim(query)` 聚合全部沿用既有实现。代价是 `agg_meta` 是 JSONB，聚合谓词写成 `agg_meta->>'refusal_reason'`，没有函数索引；当前该表 9731 行，这个代价可以忽略，涨到百万行时再加索引 |
| **C** | repo-committed JSON 账本（飞轮 A 的 `LEDGER_FILE` 形状） | ⛔ **直接排除**。拒答是**运行时高频写**，而 Python 部署是 `rsync` 代码树 —— 活进程写到磁盘上的东西下次部署就被覆盖。`restaurant_intent_promotion` 的模块 docstring 第 1 点已经把这条写死了：只有「人审判断」这种低频、需要进 git 的东西才配走文件 |

## 2 · 裁定：**B**

理由三条，按权重：

1. **飞轮 A 的 miss 记录（`log_intent_miss`）就接在同一个函数里**
   （`gold_reads.py:1261`，`should_delegate` 为假的那一支）。飞轮 B 接在同一个
   函数的下一步，读同一张表、同一个 `agg_meta` 约定、同一个 RLS GUC helper。
   ⛔ 不另起一套 —— 任务卡的原话。
2. **零 migration ⇒ 零 DDL 风险**，也不占用「强制 PR + DB 审」的通道。
3. B 的缺点（JSONB 没索引）是**可以后补的**；A 的缺点（两套口径）是**结构性的**。

## 3 · 拒答原因分类：只用**结构性**信号，⛔ 不做文本匹配

任务卡硬要求：三态在 SQL/数据层上必须是结构性不同的信号。逐条给出它的来源：

| 分类 | 常量 | 结构性信号 | 来源 |
|---|---|---|---|
| **没有数据** | `no_data` | ① `result.meta.data_gap is True` —— `data_gaps.honest_gap_answer` **真查表**且 `count == 0` 才返回；② `spec.unsupported_requirements` 非空 —— `_UNSUPPORTED_REQUIREMENT_LABELS` 每一条括号里写的都是「缺少 &lt;字段&gt;」，缺的是**采集** | `data_gaps.py:102` / `restaurant_intent.py:813` |
| **没有维度** | `no_dimension` | `asked − supported` 非空。`asked = canonical_dimensions(spec.dimensions)`，`supported = _supported_dimensions(spec.planned_intents)` —— **读的是 `_supported_dimensions` 这唯一一处定义**，与 `_execution_mismatch` / `_dimension_gap_advice` 同源 | `restaurant_intent_service.py:545` |
| **没有判定标准** | `no_standard` | 🔴 **今天没有任何结构性产出点** —— 见下节「登记：判不了」 | — |
| **信息不足(已反问)** | `need_more_info` | `spec.clarification_needed is True` 且上面三条都不成立 | `restaurant_intent.py:317` |
| **域外** | `out_of_domain` | `result.code == "RESTAURANT_OPS_OUT_OF_DOMAIN"` | `restaurant_ops_router.py:644` |
| **其它** | `other` | 落到拒答形状但以上都判不出（典型：答案契约未过） | — |

### 🔴 登记：「没有判定标准」判不了

owner 举的例子是「缺货判定标准没设置 ⇒ 先用默认算法算 + 声明这是默认的」。
本轮全仓查过：读路径上**没有任何地方**会因为「标准没配」而拒答 ——
`plan_alert` 的 `threshold_value` 是**预警规则**（定时跑批），不是问答拒答；
`generic_executor` 的 `_threshold` 是**算出来的均值**，不是租户配的标准。

⇒ 按任务卡第 3 条：**想不出结构性信号就登记为「判不了」，⛔ 不拿文本匹配硬凑。**
常量 `REASON_NO_STANDARD` 保留在枚举里（它是 owner 定的分类），
但**当前没有任何代码写它**，并有一道闸（`test_no_standard_has_no_producer_yet`）
钉住这件事：等 owner 缺口清单第 5 项（能力表登记「为什么不能」三态）落地，
那里会给出结构性信号，届时这道闸会红，提醒把产出点接上。

⚠️ 这不是「先留个坑」——它是**显式登记**。不登记就分不清「漏了」和「有意跳过」。

### ⛔ 域外分一类，但不进飞轮 B 的待办表

缺口清单第 12 项：问天气/股票不是能力缺口。做法是
**照样落库**（分类是 `out_of_domain`，频次仍然可查），
但 `aggregate_refusals(include_out_of_domain=False)` 默认把它排除在待办表之外 ——
飞轮 B 那张表的定义是「人工看它去补能力」，域外条目在那张表上是纯噪音。

### ⛔ 系统故障（`kind == "unavailable"`）不是拒答

`restaurant_intent_service.py:1826 / 2580` 的 `kind="unavailable"` 是
「LLM 额度不可用 / 执行链挂了」。把它记成能力缺口会让**故障在指标上看起来像产品行为**
（那一处的注释自己就是这么写的）。⇒ `_REFUSAL_KINDS` 里没有它。

## 4 · 一个能让判据红的对照

任务卡要求「一个能让判据红的对照」。这里给**三个**，每个盯住一条不同的判据：

| # | 判据 | 对照（变异） | 期望 |
|---|---|---|---|
| 1 | **生产上真的有人调它** | 把 `gold_reads.py` 里那一行 `record_refusal(...)` 删掉 | `test_java_delegate_entry_records_refusal` 必须红 |
| 2 | **分类是结构性的，不是文本匹配** | 让 `classify_refusal` 读 `result["answer_text"]` 去判「维度」二字 | `test_classification_never_reads_answer_text`（AST，数 `Call`/`Subscript` 节点⛔不是字符串计数）必须红 |
| 3 | **不是恒真式**（它真的会分类，不是一律 `other`） | 把 `_supported_dimensions` 的返回改成「全维度」 | `test_dimension_gap_is_structural` 必须红（`no_dimension` 退化成 `need_more_info`） |

⚠️ 对照 3 是**阳性对照的对照**：没有它，「维度差非空 ⇒ no_dimension」
可能只是因为 `supported` 恒为空集（那时 `extra` 恒等于 `asked`，判据不可能红）。

## 5 · 闭环（补完能力后批量晋升）

owner：「开发把某个能力补完之后，把飞轮 B 里那批原句原封不动晋升进飞轮 A。」

`promotion_entries(rows, code=...)` 把 `aggregate_refusals` 的行翻成
`[{"query": ..., "code": ...}]` —— **恰好是 `apply_promotions` /
`apply_route_promotions` 已经接受的形状**。

⛔ 本模块**一个字都不写晋升账本**。与飞轮 A 同一条纪律：
写只发生在人跑 CLI `--apply` 的那一刻。`promotion_entries` 是纯函数，
产出的是一份**给人审的文件**，不是一次写入。
