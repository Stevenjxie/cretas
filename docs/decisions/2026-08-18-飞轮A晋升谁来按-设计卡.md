## 1 · 三个选项与各自的代价

| | 方案 | 代价 |
|---|---|---|
| **A 人工审台** | 新建一个 web 页面，运营人员点按钮审 Top-50 | 前端 + 后端 API 都要新写；`llm_fallback_admin.py`/`gold_reads.py` 是本任务禁碰的文件（另一线在改），新 API 端点若挂在这些文件上就撞了；且现有 CLI（`scripts/restaurant-intent-promote.py --list`）**已经就是**一张人审台（逐条打印「当时的真实回答」，见该脚本 2026-08-07 的 Steve 拍板），重新做一个 web 版是重复造轮子 |
| **B 定时跑批 + 阈值** | cron 按候选数/频次自动判断该不该提醒 | 若做成**自动 `--apply`**：⛔ 直接违反反目标——「晋升前必须有一道『这条当时答对了吗』的判据，不能只按频次」，自动化会把「审」这一步跳过，晋升进去就是固化一个错的；若做成**只告警不写**：零风险，且本仓已有三条同形态精确先例（`time-phrase-backlog-daily.sh` / `margin-parity-daily.sh` / `replay-equivalence-daily.sh`），照抄纪律成本很低 |
| **C 保持手动但给可读候选表** | 什么都不加，`--list` 已经存在 | 零工作量，**但正是今天的现状**——候选表存在，19 天以来（`smart_bi_llm_fallback_log` 最早的 restaurant_ops 记录到今天）从没人跑过 `--apply`。「表存在」不等于「有人会去看」 |

## 2 · 裁定：**B 的"只告警不写"半段 + C 的候选表半段，⛔ 不要 A**

理由：

1. **A 是重复造轮子**：`--list` 已经是一张功能完整的人审台——概览表 + 冲突标注 +
   「达标待审」逐条给出当时的真实回答（2026-08-07 Steve 原话：「我得看到根据我们
   的模型他的回复是什么，我得人审确定他回答没有错，我才补进去」）。还有
   `--llm-review` 做模型预审分堆。缺的从来不是「审的地方」，是「**记得去审**」。
2. **纯自动化（B 的全自动版本）被反目标直接排除**：`aggregate_candidates` 的
   `recommended` 标记本身就写着"仅供参考，⛔ 不能反过来当放行依据"（2026-08-07
   注释）。频次高不等于答对了——`answered_judgment` 是判定模型的结论，会错；
   置信度已经在 2026-08-07 被明确排除出判据（"连续的数、不可证伪"）。
3. **真正缺的那一步，机械化成本很低**：候选"攒了很久没人看"是一个**提醒问题**，
   不是一个**判断问题**。提醒可以自动化（cron+阈值），判断不能（人必须看
   `latest_answer`）。这正是"只告警"的边界。

⇒ 落地：`--counts`（机器可读一行）+ `restaurant-flywheel-promotion-backlog-daily.sh`
（三态告警，阈值默认 50——"每次审 Top-50"里的那个 50，不是随手挑的整数）。
`--apply` 本身**一个字都没改**：人审、人挑、人跑，与今天完全一样。

### 已有但容易被忽视：「这条当时答对了吗」的判据其实已经存在

`aggregate_candidates` 的行级过滤（第 (a) 层）里已经有：

```sql
AND (agg_meta->>'answered_judgment') = 'true'
```

这是 2026-08-09 加的——判定模型认为"答到了"才有资格进候选池。所以"晋升前必须
有一道回答对了吗的判据"这条硬约束，在**候选池的准入层**已经满足；真正还缺的是
**人工核对**这一层（判定模型也会错，这也是为什么 `--list` 坚持要打印
`latest_answer` 而不是只给一个分数）。⇒ 本卡不新增一道判据，只是把"人多久看一次
候选池"从"随缘"变成"有告警提醒"。

## 4 · 纠正记账（LLM 说 X，我们用了 Y，因为 Z）—— 结构性缺口，本轮未修

owner 定稿里"补 feedback/embedding/history 三列值"之外还有一句：

```
➕ 【纠正记录】: LLM 说 X, 我们用了 Y, 因为 Z    ← 「越用越准」唯一的免费燃料
```

### 4.1 已经存在的部分（探针实测）

`smart_bi_llm_fallback_log.agg_meta` 里已经有三个字段在记"纠正"，且**已经有数据**
（探针实测，跨租户 admin scope，11958 行里）：

```
contract_missing  非空 174 行   —— 答案契约算出的「缺什么」（确定性规则）
rejected_answer   非空 172 行   —— 被契约否决前引擎原本产出的文本
answered_missing  非空 979 行   —— 判定模型认为「没答到」时，缺的是什么
```

这三个字段合起来就是"LLM/引擎产出了 Y'，因为 Z（契约缺 X / 判定说没答到），
我们没用 Y'，改用了安全文案 Y"——**对"答案被驳回"这一类纠正，记账已经在发生**，
只是分散在三个 JSONB key 里，没被当作一件事看待、没有聚合视图。

### 4.2 缺的部分：静默的确定性层改写（真正的空白）

架构地图另有一条实测：「确定性层改写 LLM：intent 3/12、dims 3/12，逐条读 4/5
次改对」——这是 `_plan_requested_intents` / `_repair_backed_by_user_wording`
（`restaurant_intent.py`）在**不触发契约失败**的前提下，静默把 LLM 的原始输出
纠正成另一个值，**且答案照样送达用户**。这一类纠正**没有任何字段记录**：
`RestaurantQuerySpec`（`restaurant_intent.py:286`）只有编译后的最终值，没有
"LLM 原话 vs 编译后值"的 diff 字段——纠正发生的那一刻，原始值已经不可回溯。

⛔ **本轮没有修这一类**，原因是结构性的、不是偷懒：

1. 埋点必须打在纠正发生的那一刻（`_plan_requested_intents` 内部），而那个函数
   在 `restaurant_intent.py`——本任务的禁碰文件（另一线 `REST-AI-READ-PATH-20260812`
   当前就在改这个文件，最近一次提交 `2d9ee2b484`/#2841，就在今天）。
2. 尝试从**外部**（`restaurant_intent_service.py`）补这一类纠正记账做不到——
   `spec` 到达 `restaurant_intent_service.py` 时纠正已经发生完毕，原始 LLM 输出
   已经不在作用域里，没有东西可以"读出来再补记"（不同于 `history`：那个是调用方
   本来就持有、只是没传进去；这个是**产出方内部状态**，调用方从来拿不到）。

### 4.3 给下一棒的具体接线点

等 `REST-AI-READ-PATH-20260812` 收尾、`restaurant_intent.py` 解禁后：

```
埋点位置: _plan_requested_intents 每一处 "改写了 LLM 输出" 的分支
          （search: restaurant_intent.py 里改 spec.intent / spec.dimensions /
          spec.dish_slot 且右边不是 llm 原始值的赋值）
记什么:   {"corrected_field": "intent", "llm_said": <原始值>,
           "used": <编译后值>, "reason": <触发改写的规则名>}
写到哪:   agg_meta.corrections（数组，与 contract_missing 平级）
消费方:   scripts/restaurant-intent-promote.py --list 的人审台逐条多打一行
          "本轮纠正: intent LLM说X 用了Y 因为Z"——与 4.1 的三个既有字段
          合并成一张"纠正记账"视图，⛔ 不要再开第四个字段/第二套聚合口径
```
