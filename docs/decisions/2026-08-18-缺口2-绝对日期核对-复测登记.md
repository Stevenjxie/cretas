## 一 · 怎么测的（可复跑）

pipeline（避免被零 token 回放 / 计划缓存短路，那会测成「有没有绕过 LLM」

```python

```
clear_semantic_plan_cache / clear_route_cache /
clear_tenant_gate_cache / clear_promoted_routes_cache

和「它最终会变成的日期区间」两层读数。

## 三 · 判据核对（owner 的原话逐字过一遍）

> LLM 吐出的日期，在老板的原话里出现过吗？没出现过而它自己编了一个 ⇒ 复现。

- 「前天和昨天哪天好」本身不含任何绝对日期。
- 10 轮里，LLM **从未**输出任何形如 `YYYY-MM-DD` 的具体日期值——
  第 5/7 轮的 `start`/`end` 是字面词「前天」「昨天」，**不是日期**，
  连 ISO 格式校验都过不了，谈不上"编了一个日期"。
- ⇒ **没有一轮满足复现条件。**

## 四 · 副产品：一个相邻但不同的问题（登记，⛔ 不在本条判据范围内）

2/10 轮 LLM 把 `type` 判成 `"absolute"` 却没有给出实际日期，只是把用户
原话里的相对时间词抄进了本该放 ISO 日期的槽位。这是**类型选择不稳定**
（同一句话、同一个 prompt、8/10 轮选对 `relative`，2/10 轮选错
`absolute`），不是"编日期"：

- 不会污染成一个错误但看起来合法的日期（这正是 owner 担心的那种"最脏"的
  bug 形状——错但像真的）。
- 会导致这两轮 `_parse_t3_time_range` 返回空字符串，下游拿不到时间窗
  （生产管线里这会走向"解不出窗口"的后续分支，不是"算错了窗口"）。
- 20% 的类型误判率本身可能值得关注，但**这是 #2 判据要问的问题之外的
  另一件事**——#2 问的是"会不会编日期"，这里量到的是"会不会选错
  time_range 的 type"。不混进本条的判据，单独记在这里，留给下一棒决定
  要不要单独立卡。
