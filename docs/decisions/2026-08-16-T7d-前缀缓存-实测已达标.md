## 一 · 台账原本怎么写的

> **B1** T7-d：把「今天是 X」移出 system prompt 吃满 DeepSeek 前缀缓存

## 二 · 实测：那个前提不成立

### ① system prompt 里没有日期

`restaurant_intent.py:6287` 的 system 消息是一个**短常量**：

```python
{"role": "system", "content": "你只输出JSON格式的意图解析结果，不输出任何其他文字。"}
```

全仓 `今天是` 在 prompt 构造处**一处都没有**（仅有的两处命中：`attribution.py:124`
是给店长的正文、`replay_equivalence_probe.py:18` 是注释）。

### ② 变的东西**本来就排在最后**

拿两个不同问句各构造一次 T3 prompt，逐字比共同前缀：

```
两个不同问句     共同前缀 9645 / 9659 = 99.9%
不同 history     共同前缀 9689 / 9737 = 99.5%
无史 vs 有史     共同前缀 9638 / 9737 = 99.0%
不同门店列表     共同前缀 9638 / 9699 = 99.4%
```

共同前缀的结尾是：

```
..."clarification_options": ["营收和订单", "毛利", "损耗", "库存"]}

用户问题: "
```

第一处差异就是**用户那句话本身**，在 9659 字符的第 9645 位。

▎**这个 prompt 本来就是为前缀缓存排好的 —— 没有什么可以往后挪。**

## 三 · 为什么记这一条（而不是默默关掉）

台账那条描述**读起来完全合理**，而且带着一个具体数字（50 倍）。
如果照着做，我会去 system prompt 里找一个不存在的日期，找不到之后
很可能「顺手」重排 prompt —— 那会**打碎现在 99.9% 的前缀**，
把一件已经对的事做坏。

⚠️ 这是本条线**第三次**「照交接件/注释讲的历史下结论」。
判据仍然是那句：**引用一句描述来支撑动作之前，先跑一次让它自己说。**
这次跑了，花了两分钟。

## 四 · 顺带记一条我自己的错

第一次量 history 那几档时，我的夹具写的是 `{"question": ..., "answer": ...}`，
结果 prompt 里只插进了**表头**、内容是两个空行，两份不同 history 产出的
prompt **完全相同**。

我一度以为抓到了「history 没进 prompt」的大 bug。
真相是 **`ChatSessionService` 存的是 `{q, a_summary}`**，我造了一个
**生产永远不产出的形状**（`restaurant_intent.py:5308` 的注释就写着）。
换成真形状后，history 确实进了 prompt。

▎**桩数据里的每个键名，都要问一次「真实那一侧真的会给出这个吗」。**

## 五 · 什么时候需要重开这一条

前缀缓存的收益已经吃满，⛔ 除非出现下面任一：

- 有人往 T3 prompt 的**前部**插入随请求变化的内容（租户名、日期、门店列表位置上移）
- ⇒ 那时上面那组「共同前缀占比」的数会掉下来，重量一次就看得见
