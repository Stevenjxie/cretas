### 🔴 量这张表时踩的两个仪器缺陷（都被自己的输出抓住了）

「事实表是空的」，方向判断整个反掉。

**② 日期列选错。** `fact_pos_transaction` 同时有 `date`(营业日) 与 `created_at`(入库时刻)，
优先级表把 `created_at` 排前面 ⇒ 量的会是 ETL 时刻。

### 做得好的（要保住，⛔ 别在修别的时候弄坏）

- **定义 2「说一件他没想到的事」达标**：谜题象限点名到具体菜 ——
  「招牌青花椒鱼(2-3人份) 每份赚 ¥179.71，是 117 道菜里的高位（中位 ¥44.02）；
  近30天卖 39 份，低于中位 294 份 —— 最赚钱的菜没卖动」。**可点名、可核对。**
- **定义 4 表格达标**（能答的路径上）：菜品销量表、门店毛利排行、营收/成本/毛利三列。
- **定义 5 有一个满分样本**：「今天到现在卖了多少」→「今天没有可用数据。
  **没有用全部历史或其他日期替代**。请先确认营业流水已经同步，再按同一时间范围重试。」
- **毛利口径披露非常扎实**：覆盖率 48.4%、缺卡菜排除不按零成本算、
  13 个异常成本值已排除、计算过程逐项列出、「要更准得盘一次库」。
- **域外问题正确拒答**：「今天天气怎么样」→ 明说不在数据范围内 + 给了能问什么。

### 🔴 已验证的缺陷（每条都复现过，⛔ 不是一次读数）

#### D1 · 追问全断（0/5）—— 对「能不能决定」伤害最大
三条链第 2、3 轮全挂，两种长相：
- **(a) 归因/建议类**：「为什么」「它的问题出在哪」「那这个菜该怎么办」「那哪家店影响最大」
  → 一律回 *「这次没算出本轮要求的原因分析或优化动作…我不会拿别的数据凑」*（62 字）
- **(b) 指代被当实体名**：「别的店也有这个问题吗」→ *「**没有找到名为「别的店」的门店**」*

#### D2 · 疑问词／指代被当成门店名
「哪几家店在拖后腿」→ *「**没有找到名为「哪几家店」的门店**，不能计算该店的毛利…」*
措辞非常肯定，**老板会以为自己打错字了**。
⚠️ 阳性对照（真门店名「青花椒徐汇日月光店这个月生意怎么样」）**也失败了**
（落到维度兜底反问）⇒ ⛔ 不能断言「只是疑问词的问题」，**带门店名的问句本身也走不通**，
这一条要在修之前单独再验一次。

#### D3 · 同一句问题，两个结果（非确定性）
「哪家店最差」× 5，各自新 session：**4 次作答（1382 字，字字相同）+ 1 次反问（22 字）**。
两侧 `source` 都是 `restaurant_ops_gold`。
看 elapsed：0.4s 那几次是缓存命中，2.6/3.5s 是真编译，
而**反问那次也是 2.71s 真编译** ⇒ **非确定性在 LLM 编译那一步，不在缓存**。
⚠️ 我另一组「先问一句别的再问同一句」的读数**全部无效**（3 次都是 0.4s 缓存命中，
同一条目 replay）—— 我没清缓存，硬约束 3，我自己刚写进 prompt 又犯。

#### D4 · 该默认的不默认 —— 同一个产品两套时间策略
「哪家店卖得最好」「哪个菜不赚钱」**默认最近30天并披露**；
而「成本主要花在哪」「是客流少了还是客单价低了」「供应商价格有没有涨」
→ 一律反问 *「你想看哪个时间范围？」*（10~18 字）。
⚠️ 与昨天上线那条同族（交接里「默认窗口没接到回放路径」）。

#### D5 · 决策类问题被退回成看数请求
「明天我该干什么」「你有什么建议」「客户满意度怎么样」「帮我把米饭价格改成12块」
—— 四个**完全不同**的问题落到**同一句** *「你这次最想先看哪件事？」*（11 字）。
▎北极星是「让他自己做一个决定」，而他问「我该干什么」时产品反问「你想先看哪件事」。
⚠️「帮我改价格」是**写操作**被吞进看数兜底；而「哪些菜应该下架」却正确声明了
咨询模式/操作模式 —— **同一族两种处理**。

#### D6 · 维度兜底话术是开发者视角，且吃掉了「缺数据」这一类
*「你是想看某道菜、某家门店，还是全店合计？说一个就行，我不会拿别的数据凑」*
出现 5 次：员工排班 / 外卖堂食 / 最近损耗 / 有几家店亏钱 / 哪家店成本控制最差。
- 老板不知道「哪一层的数」是什么意思
- 「员工排班合理吗」**根本没有数据**（员工表 0 行），却按「维度不明」反问
  ⇒ **定义 5 失败**：没说缺什么数据、怎么拿到、他自己要干什么

#### D7 · 「一共有多少家店」把闭店算进去了
| 问法 | 产品答 | 真值 |
|---|---|---|
| 一共有多少家店 / 今天到现在 | **38** | `dim_store` 38（**含 5 家名字里写着「（闭店）」**） |
| 昨天 / 本月 / 最近30天 / 上半年 | **30** | 该窗口有交易 = 30 ✅ |
| （全历史有交易） | — | 33 |

⇒ **30 是对的，38 是档案全量。** 不是算错，是**口径没说清**。
但老板问「我有多少家店」得到 38，他会**按 38 家去分摊成本、排人力** ⇒ 实际伤害。

### 🟡 一条差点被我写成 Critical 的（记下来当教训）

我一度认定这是**跨租户泄漏**：以 `DEMO_REST` 登录，答案里 8 个门店名有 **7 个属于
`RES_3101_009`**（鲜行者/兄弟土菜馆/有滋有味/龍燕楼…），而 DEMO_REST 自己的 27 家
全叫「示范门店01-19」+「青花椒*」。

**真相**：`backend/python/smartbi/api/gold_reads.py:157` 有白名单
`DEMO_GOLD_TENANT_ALIASES = {"DEMO_REST": "RES_3101_009"}` ——
「公开免登录 demo 账号在 Java auth 里故意做得很轻，但 AI demo 需要完整的餐饮 Gold 数据集」。
**是有意的演示别名，不是泄漏。**

⚠️ 本仓反模式清单第 6 条原话：**「看到反常读数直接判缺陷。先问『写它的人怎么说』」**。

**但同一处代码露出一个真问题**：
`_resolve_tenant` 做别名重映射，`_resolve_tiered_tenant` **明确不做**，
其注释写着「tiered 路径直接读 DEMO_REST 自己 seed 的 restaurant-ops Gold 数据」。
而我的探针**就是走 tiered 路**（`ai-intents/execute`），回来的却是 RES_3101_009 的门店。
⇒ **设计意图与实际行为不一致**，且 Java 侧 `resolveGoldFactoryId` 的注释说
2026-08-05 删掉 Java 那侧的别名正是为了消除「divergent data visibility」。
⛔ 机制未验证（不从代码推），登记为 **D8**，修之前要单独跑一次定位。
