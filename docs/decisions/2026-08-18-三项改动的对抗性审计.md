# 三项改动的对抗性审计（PR #2805）

**日期** 2026-08-18 · **对象** [9] dimensions 到执行器 / [C1] 能力拒答不粘会话 / [1a] 标签服务不了时计划赢

⛔ 一个没被攻击过的设计不算设计。逐条列攻击 + 结构性回答**或诚实登记**。
⚠️ 「诚实登记」不是免罪符 —— 每条都写清楚**什么条件下它会咬人**。

## 攻击 1：[9] 只接了 18 个 resolver 里的 1 个

`_resolver_kwargs` 现在发 `dimensions` 了，但只有 `resolve_wastage_top` 消费它。
其余 17 个照旧：5 个带 `**kwargs` 的收到但不读，12 个被 `resolve_by_code` 按签名过滤掉。

**回答：诚实登记，并且⛔ 不许把这次说成「追问修好了」。**

📏 现在成立的是：**损耗这一条链**的追问按维度重组了。
「哪家店卖得最好 → 那毛利呢」这类仍然可能复读。

可执行的下一步（⛔ 不是「以后再说」）：对每个 resolver 量一次
「同一意图、不同 `dimensions`，产出指纹是否不同」，按问句频次排序补。
这个量法就是本轮 [9] 用的那个，成本是一次探针。

## 攻击 2：🔴 [9] 的首段在门店覆盖不全时会说谎

我加的首段是「按门店看：**X** 损耗最多，¥N；最少的是 Y ¥M。最高比最低高 P%」。
而 `_store_breakdown_block` 的 docstring 里记着一次真实事故：

```
抬头(30 天全部): ¥317,441.84
门店表合计:      ¥  6,828.07      ← 只有总额的 2%
成因: 存量行 store_id 全是 NULL, 聚合侧 WHERE store_id IS NOT NULL 排除了它们
▎老板会把这张表读成「各店几乎不损耗」——**每个数都对, 合起来是谎**
```

覆盖度提示在**表格下面**，而我的首段在**表格上面**。
▎**老板可能只读首段。**

**登记：本轮未做。** 首段在 `store_total < all_total * 0.995` 时应当带限定语
（例如「按已记门店的那部分看…」）。⛔ 不在这一轮顺手加 —— 它需要自己的
阴性对照（覆盖完整时不许出现那句限定语，否则又是一条误发的提示）。

⚠️ 触发条件很具体：**任何新接入的租户、任何一段没记门店的历史**都会命中。
MOCK_REST 当前覆盖完整，所以本轮 prod 验收**看不见**这个风险 ——
这正是「验收环境不含能让闸红的输入」那一类。

## 攻击 3：[C1] 摘掉 pending 之后，老板点按钮会不会失效

能力拒答的 spec 带 `clarification_options=['营收和订单','毛利','损耗','库存']`，
`_clarification_followups`（service:1421）会把它们渲染成 `{label, question}` 按钮。
摘掉 pending ⇒ 老板点「营收和订单」时不再走延续，而是当成一个**独立新问句**。

**回答：改动前那条路**本来就是坏的**。**

📏 pending 探针实测：挂着 pending 时，**任何**新问句（包括按钮文案）都会被拼进
`resolver_query_seed`，`table_turnover` 永不消失 ⇒ 拿到的还是那 129 字。
所以「点按钮能延续」在今天**并不成立**。

⚠️ 但「不更差」不等于「更好」：`营收和订单` 作为独立问句能不能答，
**我没有量过**。⇒ 部署后验收必须加这一条，⛔ 不许略过。

## 攻击 4：🔴 [1a] 让计划赢之后，答的可能不是老板问的那件事

「哪道菜毛利最高 → 哪个卖得最多」修复后 `code=GROSS_MARGIN`，
而老板问的是**销量**（`requested_metrics=('sales_volume',)`）。

**如果 GROSS_MARGIN 的答案只讲毛利不讲销量，那是「用错的数据回答」——
比拒答更糟。**

**回答：这是本轮最需要 prod 真跑确认的一条。** ⛔ 不许只看「不再拒答」就算过。
验收判据：读原文，确认里面**真的有销量**，且排序口径与老板问的一致。
不满足就回退这一支，把它降级成「拒答但说清差在哪」。

## 攻击 5：[1a] 旁路了两道有事故背景的 guard

`label_cannot_serve_dimensions` 让修复绕过了
`supported_requested_metrics` / `_repair_backed_by_user_wording` /
`_CONTRACT_REPAIRABLE_METRICS` 三条。而它们是 2026-07-30（采购）、07-31（盘点）
两次事故加上的。

**回答：形状不同，但⛔ 不能只靠「形状不同」这句话。**

那两次事故的形状是「**LLM 编出来的指标槽**推翻 planner」——
判据在指标的来源上。我的旁路条件是「**标签服务不了本轮维度**」，
那是一个与指标来源无关的结构性事实：保留标签 100% 以拒答收场。

⚠️ 而且 `repair_target_serves_dimensions` **留在 or 的外面** ——
两条正当性都必须满足「目标 resolver 服务得了本轮维度」，
所以旁路不会把「用错粒度回答」这一类放进来。

**但这仍然是推理，不是实测。** ⇒ 反事实实测（已加进回归）：
两条历史事故句在改动前后行为必须**逐字一致**：

```
全部门店最近30天采购花了多少钱
全部门店最近30天盘点亏了多少
```
