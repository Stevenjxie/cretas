## 〇 · 一句话

> **只让 LLM 判断「他想要什么」。代码只做三件不需要懂中文的事：核对、算日期、执行。**
> **问过并审过的直接回放，越用越便宜、越快、越不抖。**

---

## 一 · 三个角色，职责互不重叠

| 角色 | 只做这件事 | 判据 |
|---|---|---|
| **LLM** | 所有**语义判断**：意图、维度、指代、实体提名、时间概念 | 唯一能处理「你没想到的说法」的东西 |
| **数据库/事实表** | 所有**存在性**：这是不是一道菜、一家店、这个能力有没有 | 唯一事实来源，**自动跟着租户走** |
| **代码** | 所有**不需要懂中文**的事：核对、日期算术、执行、格式 | 问一句「这条规则要不要读懂中文？」要 → 它不该是代码 |

▎**关键划分不是「词表 vs LLM」，是「猜 vs 查」。**
▎📏 实测：「那最差的呢」→ LLM 输出 `dish='最差'`。**LLM 和词表犯的是同一个错，因为它俩都在猜。**
▎⇒ 把词表换成 LLM 不解决问题；该换的对象是**查**，而那一层仍然是确定性代码。

## 二 · 事实怎么给 LLM —— 按「量」分三类，⛔ 不是一律塞 prompt

| 类 | 内容 | 怎么给 | 为什么 |
|---|---|---|---|
| **闭集且小** | 19 个意图定义 | 直接进 prompt | 数量固定 |
| **开集或大** | 门店（可能上千家）<br>菜单（连锁上千道）<br>能力表（可能长成数千格矩阵） | **走检索，只把召回的几条进 prompt** | 全量塞 ⇒ prompt 无限膨胀，token 成本爆炸 |
| **上下文** | 最近 20 轮 + 会话摘要 | 进 prompt | 无法避免 |

📏 现状：门店是**全量塞 prompt** 的（prompt 原话「当前账号真实可选门店（只能从这里选择，禁止编造）」）。
今天 10 家店没问题，**上千家就不行**。⇒ 要改成检索。

## 三 · 向量检索的岗位 —— **实体模糊匹配**，⛔ 不是意图路由

**人不会说全称，他只记住能唯一区分的那几个字：**

```
库里叫「山川蒙湖店」        →  人说「山川店」
库里叫「鲜花椒大人二人套餐」 →  人说「青花椒二人套餐」
```

📏 实测现状（子串匹配）：

```
'山川店'        vs '山川蒙湖店'          → 匹配不上  🔴
'青花椒二人套餐' vs '鲜花椒大人二人套餐'   → 匹配不上  🔴
'美罗城店'      vs '模拟·徐汇美罗城店'    → 匹配上    ✅（真子串）
```

⇒ 精确/子串匹配**从原理上做不了**这件事，只能向量检索。

📖 仓里**已有整套 embedding 实体解析**（`entity_resolution/agents/{embedding,llm_arbitrator,transitive}.py`），
📏 **餐饮读路径一次都没 import 它** —— 又一个「机制在、没接上」。

## 四 · 完整八步

### ① 短路（三层记忆，命中任一跳到 ⑥）

| | 匹配 | 结果 | 代价 |
|---|---|---|---|
| 1a 已审句子 | 一字不差 | 拿现成计划 | 0 token，**永远同一结果** |
| 1b 会话缓存 | 一字不差（6h 内） | 拿现成计划 | 0 token |
| 1c 向量召回 | 意思相近 | **提名**一个计划，交 LLM 拍板 | 一个是非题 |

📏 现状：1a **0 条**（从没人晋升过）；1b 活着但 6h/500 条/进程内；1c 不在生产路径上。

### ② 加载事实（六样）

```
19 个意图定义     进 prompt
门店             ← 检索召回（现状：全量塞）
菜单             ← 检索召回（现状：完全没给）
能力表           ← 检索召回（现状：完全没给）
最近 20 轮对话    进 prompt
会话状态摘要      进 prompt
```

### ③ LLM 判断（唯一的语义判断，一次调用）

拿回：`intent` / `dimensions` / `dish` / `store` / `时间概念` / `comparison` / `confidence`

**⛔ 硬性要求：信息不足时必须输出 `clarify` + 候选维度，不许硬挑一个。**
📏 今天没有这条 —— 所以「那最差的呢」时它挑了 `dish='最差'`。

### ④ 核对 —— 它到底覆盖什么（owner 追问后收窄）

**判据不是「在不在全量目录里」，是「在不在【这次召回给它的候选集】里」。**
我们要防的不是「它说了个不存在的店」，是「**它没从我给的候选里选，自己写了一个**」。

**它只覆盖四种情况，⛔ 不是万能的第二道判断：**

| # | 情况 | 怎么处理 | 会不会拒答 |
|---|---|---|---|
| 1 | **归一**（最高频）：LLM 顺手改写了名字<br>召回「模拟·徐汇美罗城店」→ LLM 输出「徐汇美罗城店」→ 查库查不到 | **唯一匹配** → 代码直接归一，⛔ 不回 LLM；**抬头用全名**让老板看见<br>**多条/零条** → 回 LLM 或反问老板 | ❌ 不会 |
| 2 | **继承来的槽位没验过**：第 5 轮「那家店的毛利呢」句子里没店名，不触发召回，store 来自上下文 | 按当前租户目录校一次 | ❌ 不会 |
| 3 | **跨租户污染**：📖 `dish_catalogue_scope` 注释明写「contextvar 不复位会泄漏到同一 task 的后续代码 —— 一旦那里是另一个租户，就会拿错菜单去裁决」 | 按当前租户目录挡住 | ❌ 不会 |
| 4 | **跑不跑得动**（能力核对） | **唯一会拦住的一类** → 带原因丢回 ③ 重试一次 | ✅ 会 |

**⚠️ 它抓不到的两类（诚实登记）：**

```
❌ 召回对了、LLM 从候选里挑错了一条   → 核对通过, 无能为力 ⇒ 靠确认式反问 / 抬头显示全名
❌ 意图能跑, 但跑的不是他要的         → ⇒ 靠答案契约 + 老板的否定反馈
```

🔑 **所以核对没有「判决权」**：前三类只是**修正一个值 / 记一笔账**，老板完全无感；
只有第 4 类会拦，而拦住之后也是**丢回 LLM 重试**，⛔ 不是直接拒答。

### ④之二 · 核对的执行细则（⛔ 不再问 LLM，本地查，微秒级）

```
存在性:  dish / store    → 查目录
        绝对日期        → 查【用户原话】
能力性:  intent+dimensions → 查能力表
```

**⛔ 不是一个冲突就丢回去。** 流程是：

```
1. 把【全部】维度校对完, 收集【所有】冲突
2. 一次性丢回 ③, 带上每一条冲突的原因
3. 重试【只有一次】
4. 重试回来后 ⛔ 不再校对已确认的部分, 直接进 ⑤
```

### ⑤ 概念 → 日期（纯算术）
```
{相对, 月, 2} + 今天 8/18  →  本月 8/1~8/17 ＋ 上月同期 7/1~7/17
{命名, 上季度}             →  4/1 ~ 6/30
```

### ⑥ 执行 —— **dimensions 必须传进执行器**

📏 今天没传：`resolve_wastage_top` 的签名里根本没有 `dimensions`，
所以「哪家店最多」和「最近损耗怎么样」返回**逐字相同**的答案（指纹 `bd1d6675`）。

### ⑦ 答案契约（11 项）
`window_label · profitability_verdict · margin_value · store_name · dish_name ·
non_empty_answer · comparison · margin_integrity · request_coverage ·
execution_consistency · analysis_action`

📏 24 问句 × 2 轮，缺口 **0 次**。⚠️ 一道从不开火的闸，「通过」等于没说话 —— 晋升条件⛔ 不能写成「通过全部闸」。

### ⑧ 返回 + 记账 + 飞轮

```
写日志: query / intent / answer / 耗时
   ➕ query_embedding   📏 今天 0/9731 有值
   ➕ history           📏 今天 0/9731 有值
   ➕ 【纠正记录】: LLM 说 X, 我们用了 Y, 因为 Z      ← 「越用越准」唯一的免费燃料
离线: 按频次审 Top-50 → 晋升 → 回到 1a
```

📏 候选 176 条排队，晋升 0 条。Top-50 覆盖 49.2% 请求。

## 五 · 冲突处理：四象限（owner 补充）

| | **代码核对说「通过」** | **代码核对说「不通过」** |
|---|---|---|
| **LLM 判对了** | ✅ 正常执行 | 🔴 **误拦** —— 目录陈旧 / 新菜刚上架 / 新店刚开 |
| **LLM 判错了** | 🔴 **漏网** —— 只能靠答案契约兜底 | ✅ 拦住并修正（「最差」不是菜） |

**四种各自怎么办：**

1. **都对** → 执行。
2. **LLM 错 + 拦住** → 带原因丢回 LLM 重试一次。
3. **LLM 对 + 误拦**（目录陈旧）→ ⛔ **绝不静默丢掉**。
   fail-open + 明说：「菜单里没查到『X』，是不是新菜？要不要按这个名字先算一次？」
   ⚠️ 📖 现有纪律已经是 fail-open（目录没加载/为空时一律开放），要补的是**说出来**。
4. **都错** → 最危险，唯一防线是答案契约 + 老板自己看出来 ⇒ 所以第 ⑧ 步的反馈通道必须接上。

## 六 · 能力不足时对老板说什么（owner 定稿，⛔ 不许出现技术词）

| 情况 | ❌ 不许这么说 | ✅ 该这么说 |
|---|---|---|
| **没有这个数据** | — | 「当前系统里还没有库存数据，接上之后我才能回答缺货情况。」 |
| **没有这个维度** | ~~底层表里没有门店这一列，要支持得改表结构~~<br>~~该能力尚未支持，请联系工作人员优化能力~~ | 「当前库存只能**按食材**看。**要不要先按食材看一下？**」<br>（**给一条走得通的路**，⛔ 不是直白承认自己不行） |
| **没有判定标准** | ~~定了标准我才能算~~ | **先用默认算法算出来**（历史用量 / 方差离群），然后声明：<br>「本次按**默认判断标准**（相对历史用量的离群程度）计算。您门店的缺货判定标准建议重新设置。」 |

🔑 **第三条是 owner 的关键修正**：没有标准 ⛔ **不等于不能算**。
先用默认算法给出结果，**并声明这是默认的** —— 而不是把问题推回给老板。

🔑 **第二条的措辞原则（owner 定）**：能力不足时，**给出路，⛔ 不认错**。
「我做不到，请联系工作人员」把包袱丢回给老板；
「只能按食材看，要不要先按食材看一下？」让他这一轮就有东西可看。

⚠️ 同时这是一条**工程纪律**：「缺维度」这类应该在能力表里**提前登记并杜绝**，
⛔ 不该等到运行时才被老板撞见。

## 六之二 · 第二条飞轮：**答不上的也要进飞轮**（owner 新增）

飞轮不是只有一条。**答上的和答不上的，各进各的队列，用途完全不同。**

```
飞轮 A（答上了）  →  按频次审 Top-50  →  晋升 ledger  →  下次 0 token 命中
                     用途: 更便宜 / 更快 / 不抖

飞轮 B（答不上）  →  按【拒答原因】归类  →  人工看这张表去【补能力】
                     用途: 决定下一步开发什么
                     ⛔ 不进晋升 —— 它现在还答不了, 晋升进去就是固化一个错的
```

**飞轮 B 记什么**（每条拒答都要落）：

```
原句 / 拒答原因分类 / 缺的是什么 / 出现频次 / 首次与最近出现时间
拒答原因分类:  没有数据 · 没有维度 · 没有判定标准 · 信息不足(已反问) · 其它
```

**闭环**：开发把某个能力补完之后，**把飞轮 B 里那批原句原封不动晋升进飞轮 A**
—— 一次性做完，⛔ 不用等它们下次再被问到。

▎**这条把「拒答」从一个终点变成了产品待办的来源。**
▎📏 今天飞轮 B **完全不存在**：拒答只写进普通日志，没有分类、没有队列、没有人看。

## 七 · 反问规范

```
① 一次把【所有】缺的问全, ⛔ 不许一个一个问
② 能给按钮的给按钮（时间: 本月 / 上月 / 最近7天 / 最近30天）
③ 门店/菜品数量大 ⇒ ⛔ 不列举, 走检索（老板打「山川」就召回「山川蒙湖店」）
④ 反问被回答后 → 拼成【完整句子】从第 ① 步整句重走
     ✅「过去30天米饭卖得怎么样」
     ❌ 只把「过去30天」这个片段传回去
```

**为什么全量重走而不是部分重算**：「哪些该重算」本身是一个新判断，
而新判断就是新的出错点。全量重走一次调用，换掉一整类风险。

## 八 · 上下文怎么用 —— ⛔ 不强制合并

```
缺对象/时间时:
  先从前文找 → 找到了: 只作为【建议】丢给 LLM
                       「上文在说 X，这句要不要接着 X？」
                       ⛔ 不强制拼在一起（强制合并必然出错）
             → 找不到: 才反问
```
