# 缺口 #9 剩余三个：CHANNEL_MIX / GROSS_MARGIN / STAFFING_ADVICE

最后更新：2026-08-18

## 背景

`_dims_gap.py` 的静态判据（「签名里有没有 `dimensions`」）报出 3 个
「登记 ≥2 维度、执行器收不到」的 resolver：CHANNEL_MIX（channel、store）、
GROSS_MARGIN（dish、time）、STAFFING_ADVICE（store、time、meal_period）。

上一棒已经证伪了缺口 #9 的原始理由（「答案逐字相同」，见
`docs/decisions/2026-08-18-22项缺口清单-逐条重测.md` 行 36），改写成新判据：

> 哪些 resolver 因为收不到维度，导致老板问了某一维却拿不到**针对那一维、
> 直接说出来**的答案。

本卡记录对这 3 个的逐条判断，**判据是 prod 真跑读全文**（不是猜代码）。
探针：`smartbi/scripts/_dims2_direct_answer_probe.py`（跑完即删，不随本次改动提交）。

## 结论

| resolver | 登记维度 | 判定 | 依据 |
|---|---|---|---|
| CHANNEL_MIX | channel、store | ✅ 已经直接答，不改 | 见下 |
| GROSS_MARGIN | dish、time | ✅ 已经直接答，不改 | 见下 |
| STAFFING_ADVICE | store、time、meal_period | 🔴 store 维度是真缺口，已修 | 见下 |

### CHANNEL_MIX：不是缺口

📏 prod 实测（MOCK_REST）：「外卖和堂食各占多少」（dims=channel）与
「哪家店外卖占比最高」（dims=store、channel）拿到**几乎逐字相同**的答案
（正文长度 1023 vs 1021，唯一差异是末尾一句时间范围措辞）。

原因：`resolve_channel_mix` **无条件**（不看 `dimensions`，本来就没声明这个形参）
在 `len(per_store) >= 2` 时输出门店表 + 一句直接点名的收尾：

> 各门店的外卖占比：最高 **模拟·静安嘉里中心店** 28.5%、最低
> **模拟·长宁龙之梦店** 27.3%，相差 1.2 个百分点。

这句话本身就是「哪家店外卖占比最高」的直接答案，且**不需要知道用户问的是
不是门店**——channel 是这个 intent 的主轴（表本身），store 是无条件的第二轴。
⇒ 不存在「收不到维度导致答不出该维度」这件事。**不改。**

### GROSS_MARGIN：不是缺口

登记的两个维度各有独立于 `dimensions` 的传递通道，**都已经在工作**：

- `dish`：`resolve_gross_margin` 本来就把「按菜品拆」当默认输出（毛利前 N 名
  菜品是这个 resolver 存在的理由），另外还有 `dish_mention` / `dish_mentions`
  形参专门接具名菜品（`restaurant_intent_service.py` 2122-2126 行，`spec.dish_slot`
  单独路由进来，不经过通用 `dimensions`）。
- `time`：`trend_requested` 由 query 文本关键词（"趋势"/"走势"/"按月" 等）
  直接判断（第 4638 行），与 `dimensions` 无关，判定为真时会算月度毛利率
  趋势图（第 5500-5548 行）并在正文加「历史趋势按当前成本卡估算…」的说明。

📏 prod 实测：「毛利这几个月的走势怎么样」触发了 `trend_requested`
（正文含「历史趋势按当前成本卡估算，用于观察售价和销售结构变化」这句只在
`trend_requested=True` 时才会出现的说明），证实了这条判断确实在跑，且不依赖
`dimensions`。

⚠️ 探针另测了「毛利最低的菜品有哪些」，命中了一条与 dimensions 无关的
澄清（问门店/时间范围），这是缺口 #9 之外的另一件事——它发生在
`resolve_gross_margin` **之前**，与该 resolver 收不到 `dimensions` 无关，
不在本卡讨论范围（改它要碰 `restaurant_intent_service.py`，本轮文件范围
不含它）。**不改。**

### STAFFING_ADVICE：store 维度是真缺口，已修

📏 prod 实测（MOCK_REST，"明天" 视界）：「哪家店明天最缺人」
（dims=store）与「明天怎么排班」类通用问句拿到的答案**结构完全相同** ——
一份按缺口从大到小排序的 39 行「门店/时段」全量列表，**没有一句话点名**
缺口最大的是哪家店、哪个时段、缺几个人。用户必须自己扫一遍列表、
记住"排序是从大到小"这件事，才能读出答案排第一行。

这与 `_store_lead_sentence` 文档记的 WASTAGE_TOP 修复前的形状完全一致：
**数据在，答案不在**——判据是"他问的那件事有没有被直接说出来"，不是
"那个数在不在正文里"。

`resolve_staffing_advice` 此前**没有声明** `dimensions` 形参，
`resolve_by_code` 按签名过滤 kwargs，静默丢弃——判断不了"是不是按门店问"。

⚠️ meal_period 与 time 两个登记维度**不单独处理**，理由与
`resolve_daypart_performance`（登记维度同为 {meal_period, store, time}）
的既有先例一致：
- meal_period 是这个 resolver 输出的**基础轴**——每一行本来就带着
  daypart，不需要额外判断"问没问餐段"才决定要不要显示它。
- time（视界：明天/下周/下月）已经由 `horizon_from_question()` 独立解析，
  与 `dimensions` 无关。

⇒ 修法：只在 `asked_by_store(dimensions)` 为真时，用已经算好的
`rows`（`summary_rows` 按 `positive_gap` 降序排序后的结果，
`resolve_staffing_advice` 里本来就有）拼一句"点名"前导句，插在
`answer_text` 最前面：

```
按门店看：缺口最大的是**{store}**的**{daypart}**，预测客流 {guests} 人、
建议配 {recommended} 人、现有 {current} 人，还差 {gap} 人（置信度 {pct}%）。
```

若最大缺口是 0（全店都够人），改说"没有哪个门店 × 时段仍然缺人"，
不编一个不存在的缺口。

不问门店时（`dimensions=()` 或不含 `store`）**逐字不变**——有阴性对照钉着。

## 为什么不是全部三个都改

CHANNEL_MIX 和 GROSS_MARGIN 的登记维度都已经有独立于 `dimensions` 通用
kwarg 的传递路径在工作（无条件的门店表 + 点名句 / dish_mention +
query 文本关键词判断），**接上 `dimensions` 不会改变任何已观测到的产出**——
那是"为形参而形参"，brief 明确排除的情形。只有 STAFFING_ADVICE 的 store
维度是"登记了、真收不到、且答案里确实没有那句话"的三重叠加。

## 登记：没做完的

- GROSS_MARGIN 的澄清分支（"毛利最低的菜品有哪些"不带时间词时被拦成
  一条通用澄清）：发生在 `resolve_gross_margin` 之前，与本缺口无关，
  修它要碰 `restaurant_intent_service.py`，不在本轮文件范围内。留给
  处理该文件的那条线。
- STAFFING_ADVICE 的 meal_period 维度（"晚市要不要加人"时答案仍然是
  全量 39 行列表，未按餐段筛选/领先）：本轮判定为"基础轴，不特殊处理"，
  与 DAYPART_PERFORMANCE 先例一致。若后续数据分布变化（晚市不再天然
  排在缺口前列），可能需要重新评估——那时的修法会是"问了 meal_period
  时把该餐段的行提到最前"，同样只需要在 `resolve_staffing_advice` 里加
  一个 `asked_by_meal_period` 判断，不涉及 `staffing_forecast.py`。
