# 门店宇宙一致性：5 个 resolver 仍然「换个问法就换租户」

**日期** 2026-08-17 · **决策人** 本 chat（全权）· **状态** 已裁定并执行

---

## 一 · 实测（prod，⛔ 不是从代码推的）

`DEMO_REST` 账号下，各 resolver 实际读哪个租户：

```
SALES_SUMMARY / STORE_MARGIN / STORE_DIRECTORY / CHANNEL_MIX
    普通 = RES_3101_009      store_scoped = RES_3101_009      ✅ 一致

BUSINESS_OPTIMIZATION / STAFFING_ADVICE / WASTAGE_TOP
STOCK_SHORTAGE / REQUISITION_TREND
    普通 = DEMO_REST         store_scoped = RES_3101_009      🔴 换个问法就换租户
```

⇒ 老板问「最近损耗怎么样」和「哪家店损耗最多」，拿到的是**两个租户的数据**。

▎这与 PR #2773 修的是**同一个缺陷**，我当时只修了 CHANNEL_MIX 一个。

## 二 · 为什么不能「把 `store_scoped` 从判据里拿掉」

看起来最省事的修法是让租户只由 `_DEMO_GOLD_MAPPED_CODES` 决定。**不行** ——
`store_scoped` 有一个承重用途：

```python
demo_data_factory_for_code(None, factory_id, store_scoped=True)
# ↑ restaurant_intent.py:4806 / 4836，用来在 dim_store 里解析老板说的店名
```

**老板说的店名是在 gold 租户的目录里解析的。** 答案若读另一个租户，
那家「解析出来的店」在那边根本不存在 —— 会从「两批店」退化成「查无此店」。

## 三 · 三个选项

| | 做法 | 利 | 弊 |
|---|---|---|---|
| A | 把 5 个都并入 `_DEMO_GOLD_MAPPED_CODES` | 租户与店名目录**同源**，两种问法一致 | DEMO_REST 的后厨答案改读 RES_3101_009 —— 那边损耗只有 10 行、最后一条 2026-06-08（70 天前）⇒ **demo 变空** |
| B | `store_scoped` 只在 `code is None` 时生效 | 不动 demo 富度 | 🔴 店名在 gold 目录解析、答案读 DEMO_REST ⇒ **查无此店**，比现状更糟 |
| C | 维持现状，只登记 | 零改动 | 同一句话两种问法两套数 —— **信任问题**，且我已经为 CHANNEL_MIX 判过它是缺陷 |

## 四 · 裁定：**做 A**

**一致 > 富度。** 理由：

1. 那份「富度」是**假数据**（`seed_demo_rest_ops.py` 每天 1 条损耗），
   它的价值只是让演示不空；而不一致伤的是「这东西说的话能不能信」。
2. B 会把「两批店」换成「查无此店」，严格更糟。
3. C 是我自己在 #2773 已经判定为缺陷的形态，⛔ 不能同一个缺陷判两次不同的结果。

### 代价，写清楚

DEMO_REST 问「最近损耗怎么样」会从一张 214 行的表，变成

> 最近30天一条损耗记录都没有。你们最后一次录损耗是 2026-06-08，到今天 70 天。
> 这有两种可能：真的一件损耗都没发生，或者最近没人录。

⚠️ 那句话是**诚实且可行动**的（2026-08-17 当天刚做的），但演示确实变空。

⇒ **这恰好把「demo 后厨数据太薄」从一个抽象问题变成一个有具体症状的问题** ——
下一刀（demo seeder 门店感知 + 增量）有了明确的动机和验收标准。

## 五 · 闸要跟着扩

⇒ 扩成**遍历所有 store-capable resolver**：任何一个「问法不同就换租户」都要红。

⚠️ 这正是这次没被早点发现的原因：闸只钉了我当时修的那一个。
▎**修一个实例时，闸要钉那个形状，不是钉那个实例。**
