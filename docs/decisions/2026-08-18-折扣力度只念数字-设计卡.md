# 折扣力度多大 —— 交付定义② 的最后一条缺口

**日期**：2026-08-18　**缺口**：交付定义②「说一件他没想到的事」
**PR**：见文末

---

## 一句话

「折扣力度多大」只把他问的数念了一遍：占营收比、总额、一张构成表、
一句因果免责声明。表里其实已经有答案 —— 金额最高的前三种折扣合计占了
六成以上 —— 但没人会替他把表格前三行的百分比加起来。

## 三个选项

### 选项 A：渠道归属 —— 哪几种是平台抽走的、哪几种是自己发的

把折扣类型按名字分成「平台券」（美团/大众点评/抖音）与「自发促销」
（满减/首单/红包），说「平台渠道占了 X%，自己发的占 Y%」。

**代价**：这需要给每个 `discount_name` 分类，而分类规则只能靠**字符串猜测**
（名字里有没有「美团」「大众点评」「抖音」这类平台关键词）。三个风险：

1. 库里没有任何字段登记「这个折扣类型属于哪个渠道」——分类完全是**编出来的
   标签**，不是从 schema 里读出来的事实。与 DESCRIPTIVE only 的约束冲突
   （`resolve_discount_summary` docstring：「这个 schema 里没有任何东西能
   支撑那个因果/归属说法」，渠道归属是同一类无支撑声明）。
2. 只在 MOCK_REST 这批种子数据上命中率高（团购券名字带平台名是这批演示数据
   的巧合），换一个真实租户、换一种命名习惯（比如直接叫「38元套餐券」不带
   平台名）分类器就会全错或全漏 —— 典型的「只有种子数据支持的形状」
   （反目标第二条明文禁止）。
3. 分类错一条，「平台占 70%」就会变成一条编出来的、经不起查的断言 ——
   老板去核对不会得到平台账单印证的数字。

⛔ 否决。

### 选项 B：与营收占比对照 —— 4.5% 相对什么算高/低

「行业平均折扣率一般在 X%～Y%，你这 4.5% 偏低/正常/偏高」。

**代价**：库里没有任何行业基准数据，`X`、`Y` 只能是编的阈值。
本任务的硬纪律明文禁止（「不许拍一个阈值然后说偏高/偏低」）——
上一次这么做（门店极差阈值 `_STORE_SPREAD_WORTH_CHASING_PCT`）尚且是从
**同一份数据的内部对照**（最高店 vs 最低店）推出来的、有数据支撑的判据；
这里是拿一个**外部不存在的基准**去评判，性质完全不同。

⛔ 否决。

### 选项 C（选中）：集中度 —— 前几种占了多少

「金额最高的前三种合计占折扣总额的 X%，其余所有类型加起来只占 Y%」。

**为什么选它**：

| | 渠道归属（A） | 营收对照（B） | 集中度（C） |
|---|---|---|---|
| 数据来源 | 编的分类标签 | 编的外部基准 | `discount_summary` 已经返回的 `share_pct`，逐条来自 `agg_discount` |
| 需要新查询/新字段 | 是（渠道映射表） | 是（行业基准表，不存在） | 否 —— 表里已经有，只是加一步求和 |
| 跨租户是否稳健 | 否（依赖命名巧合） | 否（基准不存在） | 是 —— 任意租户任意命名都能求和 |
| 是否下判断 | 隐含"平台占太多" | 直接下"偏高/偏低"判断 | 只陈述分布形状，不下该不该的判断 |

集中度是**表里已经算好的数字换一种排列方式**给他看，不需要任何新的、
可能出错的输入。这正是交付定义②要的：「说一件他没想到的事」，而不是
「编一件他没问过的事」。

---

## 阴性对照：什么时候不说

`items` ≤ 3 种时「前三种」等于「全部」，「前三种占了 100%」是一句
不提供任何信息的废话 —— 违反反目标第一条（「排在最前面的命中要经得起
他去查」，一句废话经不起查）。守卫写在 `_discount_concentration_sentence`：

```python
if len(items) <= _DISCOUNT_CONCENTRATION_TOP_N:  # = 3
    return ""
```

`rest_pct` 用 `100 - top_pct` 而不是 `sum(items[3:])`：`items` 可能被
`discount_summary(top_n=10)` 截断，`share_pct` 的分母是**未截断的**折扣
总额，`100 - top_pct` 才是「除前几种外剩下全部」的真值。

百分比不按 `can_see_money` 拦（与「折扣占营收」同一条契约，两者都是比例，
不是绝对额）——非价格角色也能看到集中度这句话。

---

## 承重的判据

▎排在最前面的那个命中，他去查会不会一无所获。

集中度这句话**不是**一个新算出来的、可能错的数 —— 它就是构成表里已经
展示的 `share_pct` 加了个和。他往下翻构成表，能逐行核对：
21.1% + 20.3% + 20.2% = 61.6%，与这句话的数字完全对得上。
不存在"查了却查不到依据"的风险。

本地跑一遍改动后的 `resolve_discount_summary`（不经过部署，读的是本 PR
的代码 + 实测数据，是老板会看到的逐字原文）：

```

```

标记命中从 `{b_口径}` 变成 `{a_对比, b_口径}`（本次实测两次调用里

## 没做完的

1. **`DISCOUNT_CLOSING` 收尾句的 `b_口径` 命中不稳定**：三条轮换变体里
   有两条只含"不能"、一条含"不代表/做不了"，而探针 `_EXTRA_MARKS["b_口径"]`
   的正则不认"不能"。同一天两次调用（一次经完整管线、一次本地直调
   resolver，query 参数字面相同）分别命中了不同变体。**这是
   `phrasing.py` / `restaurant_delivery_definitions_probe.py` 的口径
   问题，本次改动范围（只碰 `restaurant_ops_router.py` + 测试）不含
   这两个文件，未修**。解冻条件：owner 决定要不要把"不能"加进
   `b_口径` 正则，或者收窄 `DISCOUNT_CLOSING` 三条变体都统一用"不代表"。
2. **选项 A（渠道归属）不是永久否决，是"现在数据不支撑"**：如果未来
   `dim_discount` 增加了真实的渠道字段（而不是靠名字猜），可以重新评估。
3. **`_DISCOUNT_CONCENTRATION_TOP_N = 3` 是拍的**，不是从数据反推的最优值。
   选 3 是因为"前三"是老板一眼扫过去就能数完的数量，超过这个数量注意力
   成本上升。如果后续观察到更多真实租户的折扣类型数分布，这个数字可以
   调整，但改动应该配一条新的实测依据，不能拍脑袋改。
