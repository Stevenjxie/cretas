——AST 扫描**确实抓到它**（`L9358`），证明扫描方法本身没漏东西。

## 二、14 个里，「窗口内 0 行」真的会发生的只有一部分

第 17 项要修的是**整个窗口在这张表上一行都没有**这一种语义，
不是「窗口有数据、但某个子维度/子过滤没有匹配」。两者混着改会把
「缺维度」错当成「缺数据」，产品措辞会失真。逐条分类：

| resolver | 命中的 no-data 分支 | 语义分类 | 是否本次改 |
|---|---|---|---|
| **resolve_sales_summary** | `bill_count <= 0` | 整窗口 0 行（`agg_daily`） | ✅ |
| **resolve_discount_summary** | `revenue <= 0` | 整窗口 0 行（`agg_daily`） | ✅ |
| **resolve_trend_analysis** | `if not monthly:` | 整窗口 0 行（`agg_daily`），且只在**给了明确 date_range** 时（否则是「全部历史都没有」，没有参照点） | ✅ |
| resolve_gross_margin | `if not pos_rows:`（无菜名/无排行分支） | 整窗口 0 行（`fact_pos_transaction`），**但**同一guard 下还叠了 dish-lookup-miss / ranking-miss 两种不同语义, 且函数长 1437 行 | ⛔ 见§五 |
| resolve_store_margin | `if not store_dish_rows:` | 整窗口 0 行（`fact_pos_transaction`）＋店维度 scoping，函数长 1921 行 | ⛔ 见§五 |
| resolve_channel_mix | `if not typed:` | **字段缺失**（订单存在，但没打堂食/外卖标签）——阳性对照本身 | ⛔ 不适用 |
| resolve_daypart_performance | `if not rows:` | **字段缺失**（订单存在，但没有下单时间） | ⛔ 不适用 |
| resolve_inventory_warning | `if not rows:` | **配置缺口**（没设安全库存），不是数据窗口 | ⛔ 不适用 |
| resolve_wastage_top | 「损耗成本明细未生成」 | **指标未实现**，没有「记录」这个概念可报最后一条 | ⛔ 不适用 |
| resolve_gross_margin（dish-name/ranking miss） | `if not matched_rows:` 等 | **过滤器未命中**（菜名找不到 / 排行为空），窗口本身有数据 | ⛔ 不适用 |
| resolve_store_margin（同上） | `if not ranked_rows:` 等 | 同上 | ⛔ 不适用 |
| resolve_supplier_price / resolve_discount_summary(构成) / resolve_by_code 等 | 各自的 no_data | 不同数据源缺失 / 对话状态缺失，非「整窗口 0 行」 | ⛔ 不适用 |

**为什么只改 3 个、不是全部整窗口 0 行的（还有 gross_margin / store_margin）**：

1. 三个入选的 resolver 共享**同一张日粒度表**（`agg_daily`）、**同一种
   查询形状**（`WHERE factory_id = $1`，日期做过滤），可以用**一个** helper
   覆盖，零重复 SQL（形态 D 的反面）。
2. `resolve_gross_margin` / `resolve_store_margin` 走的是
   `fact_pos_transaction` / `fact_pos_item`，且同一个 `if not X:` guard 下
   混了「整窗口 0 行」与「过滤器未命中」两种语义（比如
   `resolve_gross_margin` 的 `if not pos_rows:` 下面还分岔出
   dish_candidates / resolved_ranking_direction 两个完全不同的分支）。
   在 1400~1900 行的函数里做这种分岔判断，误改到过滤器未命中分支的
   风险远高于三个干净的 factory-wide resolver。
3. `resolve_store_margin` 的窗口起点在「近 N 天」相对窗口下是**只在
   SQL 里算出来的匿名值**（`anchor.end_date - days`），Python 层拿不到
   显式 `window_start` ——要接这个 hint 得再解一次 SQL 里的锚点逻辑，
   属于另一批改动。

⇒ 结论：**改 3 个，不是不知道还有别的，是知道还有别的、且明确写下了
为什么这次不动**（登记，不是漏改）。

## 三、三个选项

### 选项 1：每个 resolver 各写一遍「查 MAX(date)」SQL（不采用）

**代价**：本仓 `resolve_discount_summary` 已经有一处独立写的
`SELECT MAX(date) FROM agg_daily WHERE factory_id = $1`（用于算默认窗口，
不是本次的用途）。如果再各写一遍「最后一条记录」查询，三份 SQL 各自
维护，语义漂移只是时间问题（形态 D：「同一个东西有两份，它一定会漂」）。

### 选项 2：把 hint 挪到最外层的答案分发层，统一给所有 `no_data: True`
的答案追加（不采用）

**代价**：分发层不知道该查哪张表、哪个 `window_start`、要不要按 store_id
scope —— 这些信息只有 resolver 自己知道。而且分发层文件不在本次允许
改动的范围内（`restaurant_intent.py` / `answer_contract.py` /
`smartbi/api/chat.py` 明确红线禁碰）。

### 选项 3（裁定采用）：`_empty_window_last_record_date` 共享 helper +
`_empty_window_hint_sentence` 措辞函数，三处调用

```python
last_record = await _empty_window_last_record_date(
    smartbi_pool, factory_id, table="agg_daily", window_start=<该 resolver 的窗口起点>,
)
empty_window_hint = _empty_window_hint_sentence(last_record)
```

**核心设计**：helper 只在能诚实回答时才返回日期，三种情况一律 `None`
（调用方必须整句不说，见 docstring）：

1. `window_start is None`（没有可比较的窗口起点，例如「全部历史」查询）
2. 表里在 `window_start` 之前一条记录都没有（从未有过数据 —— 不是
   「停止上传」，是另一句话，这次不覆盖）
3. **`window_start` 之后（含当天）仍然有记录**（这段窗口是前后都有数据
   的孤立缺口 ——「之后没有数据上来」会是一句假话）

第 3 条是本设计卡里唯一容易漏掉的一条：如果只查
`MAX(date) WHERE date < window_start`，遇到「历史数据存在、只是中间挖了
一段」的情况会照样报出一个「最后一条记录」，但那句「之后没有数据上来」
是假的。所以查询同时带 `COUNT(*) FILTER (WHERE date >= window_start)`，
非零就整句噤声。

**代价（诚实登记）**：
- 任何查询异常（连接失败、mock 没实现 `fetchrow` 等）一律 `except
  Exception` 吞掉返回 `None` —— 这是一句锦上添花的提示，不能把主答案
  拖垮。代价是**如果 prod 上这条查询系统性失败，不会有任何报错**，
  只会安静地不出现这句话。已用 `logger.debug` 留痕；根据形态 E′
  的教训（「没喊」要分清「决定不喊」和「没能做决定」），后续如果要
  监控这条 hint 的命中率，应该在 `logger.debug` 之外单独加一个计数器，
  当前**未做**（见 §五）。
- `table` 参数拼进 f-string SQL —— 用 `_EMPTY_WINDOW_HINT_TABLES`
  allowlist 在拼接前做成员检查挡掉任意字符串；三处调用点的 `table=`
  实参都是硬编码常量 `"agg_daily"`，不经过任何用户输入。

## 四、一个能让判据红的对照

⛔ 不能只在「helper 单测」上验收——那是形态 B「测了 helper 没测接线」。
每个 resolver 的这句话必须在**产品入口**（`resolve_sales_summary` /
`resolve_discount_summary` / `resolve_trend_analysis` 本身）上验证。

**最硬的一条对照**：`test_returns_none_when_data_resumed_after_the_window_started`
——窗口起点之后其实还有数据（`rows_at_or_after=3`）。如果这条红了，
说明产品会说出「之后没有数据上来」这句假话，比不加这个 hint 更糟
（老板会去查一个其实一直在同步的 POS）。

### 变异对照（7 条，逐条实测；每条先证明变异到达了被测代码，再看断言）

| # | 变异 | 打红了 |
|---|---|---|
| M1 | 去掉「窗口起点后仍有记录就噤声」这道守卫 | `test_returns_none_when_data_resumed_after_the_window_started` |
| M2 | 去掉 `window_start is None` 提前返回 | `test_returns_none_without_querying_when_window_start_is_none` + `test_trend_analysis_full_history_empty_never_queries_for_a_hint`（用调用计数断言，不是只看返回值——否则「查询失败被吞」和「根本没查询」是同一个读数，见测试文件注释） |
| M3 | 去掉 table allowlist 检查 | `test_returns_none_without_querying_for_unlisted_table`（表现为 `KeyError`，因为该行在 `try` 块外，证明这道检查是真的在拦） |
| M4 | `except Exception` 收窄成 `except KeyError` | `test_query_failure_is_swallowed_not_propagated` + `test_sales_summary_empty_window_stays_silent_when_hint_unavailable` + `test_discount_summary_empty_window_stays_silent_when_hint_unavailable`（3 条，证明 fail-open 是被测的行为，不是没人管的默认值） |
| M5 | `resolve_sales_summary` 里把 `last_record` 硬改回 `None`（模拟机制没接线） | `test_sales_summary_empty_window_reports_last_record` |
| M6 | `resolve_trend_analysis` 同上 | `test_trend_analysis_empty_scoped_window_reports_last_record` |
| M7 | `resolve_discount_summary` 同上 | `test_discount_summary_empty_window_reports_last_record` |

7 条变异，每条命中的失败集合与预期**精确一致**（多一条少一条都记了下来，
没有出现「变异后无一条红」需要回头查变异是否生效的情况）。每次变异后
运行 `pytest smartbi/gold/tests/test_empty_window_last_record_hint.py`，
红了立即用 `git diff` 复核改动范围为空后 revert，确认改动是可逆的、
没有在仓库里留下残留（`git diff --stat` 收尾时为空）。

## 五、没做完的（登记 + 解冻条件）

| # | 没做 | 为什么 | 什么条件下再做 |
|---|---|---|---|
| 1 | `resolve_gross_margin` / `resolve_store_margin` 的整窗口 0 行分支没接这个 hint | 走 `fact_pos_transaction`（不是 `agg_daily`），且函数内同一 guard 混了「整窗口 0 行」与「过滤器未命中」两种语义，1400~1900 行的函数里做这种分岔风险更高；`resolve_store_margin` 的相对窗口起点只在 SQL 里算，Python 层没有显式 `window_start` | 单独一批改动：先把两个函数里「整窗口 0 行」与「过滤器未命中」的分支物理拆开（可测试的最小单元），再给 helper 加 `table="fact_pos_transaction"` 条目 + 可选 `store_id` scope 参数 |
| 2 | hint 查询失败没有可观测的计数/告警 | 当前只有 `logger.debug`，按形态 E′ 的标准（「没能做决定」要单独喊）应该有个计数器，本次范围内没有监控基础设施可挂 | 有 restaurant AI 的运行时指标通道时，给 `except Exception` 分支加一个失败计数，避免这条 hint 在 prod 上系统性失效却无人发现 |
| 3 | `resolve_channel_mix` / `resolve_daypart_performance` 的「字段缺失」分支没有被改造成「最后一条记录」话术 | 它们的语义是「订单存在但字段没打标签」，不是「窗口 0 行」——套用这句话反而会说谎（窗口明明有数据） | 不是「未做」，是这条判据本来就不适用；如果产品要给这两个 resolver 也加类似的「最后一条打了标签的记录是哪天」提示，需要单独设计（判据不同、话术也要不同） |
