# 环比问句被自己的 spec 拒答 —— 设计卡

**日期** 2026-08-17 · **决策人** 本 chat（全权）· **状态** 已裁定并实现（PR #2798）

## 〇 · 这张卡是怎么来的

owner 问的是：**「这种类似的问题是不是能解决一片、一类问题，而不是一个一个解决呢？」**

⇒ 先量这一类有多大，⛔ 不凭感觉说「能一片解决」。

第一个假设是**答案契约的元素缺口**（今晚手工补过两个）。量下来 **被推翻**：

```
24 问句 × 2 轮，钩 answer_contract.validate
契约缺口   0 次        ← 那一类已经关掉了
答上率     39/48
剩下 9 次拒答全部「契约调用 0 次」—— 被更早的东西拦下
```

⇒ 真正剩下的一片在**契约之前**。逐条打 spec 才看见它。

## 一 · 实测事实（MOCK_REST，每句 2–3 轮，全部稳定复现）

```
这个月比上个月好还是差   code=TREND_ANALYSIS  plan=(SALES_SUMMARY,)  → 拒答
这周比上周怎么样         code=TREND_ANALYSIS  plan=(SALES_SUMMARY,)  → 拒答
最近生意好还是差         无环比词 ⇒ code=SALES_SUMMARY 一致          → 正常答
这个月和上个月比营业额   有指标词 ⇒ 修复放行, authority=repair       → 正常答
```

▎触发条件是**「比」**：一带环比，spec 就自相矛盾。
▎而「比上个月好还是差」是餐饮老板问的**最基础的一件事**。

## 二 · 机制（逐条求值出来的，⛔ 不是从注释推的）

`_plan_requested_intents` 的 `elif comparison:` 分支排在
`selected_code == TREND_ANALYSIS` **之前** ⇒ 一带环比就无条件编译成
SALES_SUMMARY，**覆盖了 planner 的标签却没改那个标签**。
下游 `_execution_mismatch` 正是拿这个矛盾拒答。

本该消解矛盾的 contract-repair 被 `_repair_backed_by_user_wording` 挡住。
逐条求值五道 guard，**只有它是 False**：

| guard | 值 |
|---|---|
| `len(planned)==1` | True |
| `code not in planned` | True |
| `supported_requested_metrics` | True (`revenue`) |
| **用户措辞背书** | **False** ← 唯一挡住的 |
| 全部指标可修复 | True |

🔑 **它只会问一种证据 —— 指标。**「好还是差」里没有指标词，那个 `revenue`
是 LLM 填的，于是闸判定「模型的猜测推翻模型的判断」。**判得没错，问错了证据** ——
真正驱动这次覆盖的是 `comparison`，而「比上个月」明明就在用户嘴里。

⇒ 日志写着「保留 planner 的判断」，实际发生的是**拒答**。
⇒ **「放弃修复」与「拒答」成了同一件事。**

## 三 · 两种消解都跑出来读过，⛔ 没靠推理选

| | 老板问「好还是差」，他看到 |
|---|---|
| **计划赢 (SALES_SUMMARY)** | 「与上个月同期（2026-07-01 至 07-17）相比，营收低 **¥89,276.26（0.7%）**，订单数减少 208 单」⇒ **能直接做决定** |
| 标签赢 (TREND_ANALYSIS) | 「共 1 个月」「最高月 2026-08 / 最低月 2026-08」「**上月同期数据不足，本次不计算环比**」⇒ 他问的正是环比，这条路明说不算 |

⇒ **计划赢**，且不是勉强胜出 —— 标签赢那条实际上拒绝回答他问的那件事。

## 四 · 三个选项

| | 做法 | 利 | 弊 |
|---|---|---|---|
| **A** | `code ∉ planned` 时无条件让计划赢 | 一行，覆盖全类 | ⛔ **把 2026-07-30(采购) / 07-31(盘点) 两条事故重新打开**（实测这两句现在都正常答） |
| **B** | 再写一个「环比 → 放行」的手写补丁 | 窄、安全 | ⛔ `llm_contract_repair` 已经有**三个**手写补丁了。这正是 owner 问的「一个一个解决」 |
| **C** | **反事实归因**：把信号关掉重编译，计划变了 ⇒ 该信号是决定性的 | 对**未来任何用到该信号的新分支自动生效**；对两条事故句天然无效（它们没有环比词） | 多一次纯函数调用 |

## 五 · 裁定：**做 C**

`comparison` 由 `_detect_comparison(text)` **纯文本抽出**（「这个月」+「上个月」/
「比上周」/「同比」/「环比」），**零 LLM 参与** ⇒ 决定性 + 用户措辞 ⇒ 覆盖正当。

⛔ 不在 20 个分支里各记一份「我是被谁驱动的」—— 那正是**形态 D**
（同一个东西有两份，它一定会漂）。反事实只问结果，不需要分支配合。

## 六 · 验收

16 条断言，**两组阴性对照**：
1. 两条历史事故句无环比词 ⇒ 这道门对它们**关着**（少了它，放宽可能重开
   07-30/07-31 而没有任何断言会红）
2. 环比在 `wastage`/`requisition_cost`/`stocktaking_shortage` 上**不是**决定性的
   ⇒ 关掉计划不变（少了它，「有比字就放行」这种过宽实现同样能全绿）

变异对照两条，各自**精确红在所守的那条上**：

| 变异 | 红的那条 | 其余 |
|---|---|---|
| 拆掉 `or comparison_drove_the_plan` | 接线断言 | 15 条纹丝不动 |
| 归因降级成恒 `True` | 重编译断言 | 15 条纹丝不动 |

⚠️ 接线断言**第一次跑就红了，而且红得有用**：我写它时以为 contract-repair 在
`parse_restaurant_query` 里，实际在 `_build_spec`。
⇒ 接线断言不只守将来的回归，它当场纠正了我对代码位置的假设。
