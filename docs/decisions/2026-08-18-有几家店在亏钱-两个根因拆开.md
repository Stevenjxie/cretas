## 二 · owner 的五步排除法，机械跑出来的结论

判据直接写进探针，⛔ 不靠人事后回想：

```
② store_slot 是问句片段?      🔴 是 (A: 实体问题)
③ code ∉ plan 且 dims 非空?   否   (⛔ 不是 B —— code 和 plan 都是 GROSS_MARGIN)
④ dims == ()?                🔴 是 (覆盖洞)
```

⇒ **A 和 ④ 同时成立，B 不成立。**

### 🔑 拒答那句话是产品自己造的矛盾

`store_slot='有几家店'`（说「某家门店」）与 `store_scope='all'`（说「全店合计」）
—— 拒答理由念的正是这两格的矛盾，而它来自一个**根本不是门店名**的值。

## 三 · ✅ 已修（A）：归一 ≠ 核对

### 成因是 fallthrough

日志白纸黑字：

```
门店简称对不上, 走原路: '有几家店' (…)      ← 消解器**知道**它对不上
                                            ← 而这个结论被丢掉了
```

`_resolve_store_mentions` 消解不到时的分支是「走原路」，
而走原路就是**保留正则抽出来的原文**。

▎形态 A¹⁰：**兜底把「我不知道这是不是门店」翻译成「它就是门店」。**
▎owner 的原话：**归一 ≠ 核对** —— 归一是「简称 → 全名」，
▎而「有几家店」压根不是店名，归一必然失败；**失败之后走哪条路**才是缺陷。

### 修法：⛔ 不新写判据

复用 `_resolve_store_mentions` 用的同一个 `resolve_mention`
（它**不查库** —— 候选清单就是 `spec.store_options`，10 家）。
有 AST 断言钉着「必须调用 `resolve_mention`」+「判据里不许出现写死的门店字样」。

**接在两个来源上**（硬约束 8）：

```
① store_slots / extract_store_mentions(...)   ← 正则抽的
② spec.store_slot                             ← LLM 填的槽
```

⚠️ 这一条是**变异逼出来的**：断言的第一版只问「有没有调用」，
   变异 M6 只删掉来源①的接线、来源②还在 ⇒ **断言纹丝不动**。
   ▎硬约束 8 的原形：数的要是「这条路上有几处读同一份数据源」，
   ▎⛔ 不是「这个名字出现过几次」。

### ⚠️ fail-open 是既有纪律

目录为空 / 消解器抛异常 ⇒ **一律放行**。
▎判据坏了要退回「不拦」，⛔ 不能退回「拦住」——
▎后者会把能答的问题变成拒答，而那正是本次要修的病。

### 📏 净效果（prod 真跑，前后对比）

```
修之前  kind=clarification  n=67    「你问的是某家门店…我没敢算」
修之后  kind=answer         n=2368  一份真实的全店菜品毛利分析
```

⚠️ **这一句仍然没答对** —— 他问「有几家店在亏钱」，拿到的是菜品毛利分析。
   ⛔ 不假装修好了。第二半在下面的 ④。

**为什么这一半仍值得单独上**：假拒答是**产品在说一句关于「他自己说了什么」的
不实的话**，而他无从自证（他会想「我哪里问了某家门店？」）。
按反目标第一条，先把这一半修掉是改善。

## 四 · 🔵 登记不做（④）：contract-repair 在 `dims == ()` 时的覆盖洞

### 覆盖洞的确切位置

`restaurant_intent.py` 约 2601：

```python
if repair_candidate and dimensions:        # ← dims 为空 ⇒ 整段跳过
    repair_target_serves_dimensions = _resolver_serves_dimensions(...)
    if not repair_target_serves_dimensions:
        ...
        if code and _resolver_serves_dimensions(code, dimensions):
            planned_intents = (code,)      # ← 2636「标签赢」那一支
```

⇒ `dims == ()` 时，repair **无条件执行**：
`STORE_MARGIN`（LLM 判的，能按门店）被 `GROSS_MARGIN`（planner 从 metric 推的，
不能按门店）覆盖掉。

⚠️ 把 `and dimensions` 去掉**没用**：`_resolver_serves_dimensions(x, ())` 是
`set().issubset(...)` = **恒 True**。那不是漏写，是**结构上就保护不了**。

### 为什么现在不修

真正缺的判据是：**`STORE_MARGIN` 能不能算 `gross_margin`？**
（对照组实测**能** —— 那句「没有毛利为负的门店」就是它算的。）

📏 但仓里**没有 resolver → metric 的能力表**（只有 `_RESOLVER_DIMENSIONS` 维度表）。
造那张表是 20 个 resolver × N 个 metric 的工程，而仓里的既有纪律是
**「能力表写宽了下游会拿它当承诺」**。

⇒ 在这张表存在之前，任何「判 repair 该不该做」的下游修法都会退回**读句意**
（判「用户要不要按门店」），而那是已裁定退役的方向。

### 解冻条件（写死，⛔ 不靠记得）

满足**任一**即可动手：

1. 有了 resolver → metric 能力表（哪怕只覆盖毛利这一族），
   判据变成「LLM 选的 resolver 已能满足 planner 推出的全部指标 ⇒ ⛔ 不 repair」
   —— 那是**纯查表**，不读句意。
2. 实测出现**第二个**同形受害问句（`dims == ()` + LLM 与 planner 挑了不同
   resolver + 两者都能算那个指标）⇒ 说明它不是孤例，值得为它造表。
3. ⚠️ ⛔ **不要**用「问句里有没有『店』」这类判据去补 —— 那是关键词词语理解，
   2026-08-18 已撤回过一次。
