## 〇 · 先说这份文档跟上一版的差别

上一版（同日早些时候）提了一个「四级记忆飞轮」。**对抗性审计打掉了它的三个前提**：

| 我当时说 | 📏 实测 |
|---|---|
| 「候选池来自降级日志，可能偏向失败」 | ❌ 反了 —— `source=template ×9731`，是**成功应答**日志 |
| 「连向量都存好了，L2 几乎免费」 | ❌ `query_embedding` **0/9731 有值** |
| 「老板下一轮没否定 = 验证信号」 | ❌ `user_feedback` **0/9731 有值** |
| 「重复率 96.4%，L0 收益巨大」 | ⚠️ 那是**探针流量**（「今天天气怎么样」152 次，时间集中在 8-09~8-13），⛔ 不能外推 |

▎**底座的「列」都在，「值」全是空的。**
▎这是形态 B（机制在、没接上）长在**数据层**上 —— 比长在代码层更难发现，
▎因为 schema 看起来完全正常。

⇒ 于是有了本架构最重要的一条，它比任何一条具体设计都普适：

## ⛔ 第一原则：**任何被设计依赖的信号，必须先证明它非空**

```
❌ 「日志里有 user_feedback 这一列」        → 这是 schema
✅ 「SELECT count(*) WHERE user_feedback IS NOT NULL = 9731」 → 这才是信号
```

**落地形式**：每个「依赖某信号」的模块，配一条**非空断言**进 CI；
信号为空时**报 `rc=2`（没量到）而不是 `rc=0`（没问题）**——
与硬约束 4 的三态跑批同源。

## 二 · 架构：三条不变量 + 四级记忆

⛔ **不是流程提醒，是结构。** 本仓已经证明「决心不构成约束力」——
规则写下来第二天照犯。所以每条都必须由**一道能红的闸**兜住。

```
                       ┌─────────────────────────────────────┐
问句 ──────────────────▶│ L0  精确复用: 已审句子 → 回放计划     │ 0 token
                       │ L1  会话复用: 6h 内同句 → 回放         │ 0 token
                       │ L2  近似复用: 向量召回【已审句子】     │ 便宜
                       │ L3  冷编译:   LLM 完整判断             │ 贵
                       └──────────────┬──────────────────────┘
                                      ▼
                    ┌──── 不变量 ①  spec 必须自洽 ────┐
                    │   code ∈ planned_intents        │  ← 消灭 A
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌──── 不变量 ②  实体必须查得到 ────┐
                    │   dish/store ∈ 租户目录          │  ← 消灭 B
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌──── 不变量 ③  能力只有一张表 ────┐
                    │   只读 _RESOLVER_DIMENSIONS      │  ← 消灭 F
                    └──────────────┬──────────────────┘
                                   ▼
                              执行 → 答案契约
                                   ▼
              确定性层改写过 LLM?  ──是──▶ 写【纠正记录】 ← 消灭 C/D 的燃料
                                   ▼
                          人工审(⛔ 不自动毕业) → 晋升 → 回到 L0/L2
```

## 三 · 用今晚的真实案例走一遍

### 案例① 「这个月比上个月好还是差」— 不变量 ① 怎么救它

**📏 现在（修复前）：**

```
LLM 说         : TREND_ANALYSIS
确定性编译器算 : (SALES_SUMMARY,)      ← 因为句子里有「比上个月」
两者不一致     ⇒ 下游闸拒答
老板看到       : 「我准备算的东西跟你问的对不上，所以这次我没敢算。」
```

**⚠️ 注意这里的荒谬**：两条路**都算得出来**。产品不是不会算，是**自己跟自己没谈拢**。

**不变量①：交给执行的 spec 必须满足 `code ∈ planned_intents`。**
不满足就**必须当场消解**，⛔ 不许把矛盾留给下游当拒答理由。

消解规则用**反事实归因**：把 `comparison` 关掉重编译一次 ——
计划变了 ⇒ 这次选择是环比决定的；而「比上个月」是**用户自己说的**
（`_detect_comparison` 纯文本抽取，零 LLM）⇒ 覆盖正当。

**📏 修复后（prod 实测 2/2）：**

```
「与上个月同期（2026-07-01 至 07-17）相比，营收低 ¥89,276.26（0.7%），订单数减少 208 单」
```

⇒ 老板能直接做决定。

▎**这条为什么是「结构」而不是「补丁」**：它对**任何**用到 `comparison` 的
▎新分支自动生效。⛔ 不需要在 20 个分支里各记一份「我是被谁驱动的」。

---

### 案例② 「哪家店成本最高」— 同一条不变量，**方向相反**

**📏 现在（修复前）：**

```
LLM 说         : STORE_MARGIN    声明能按 ['dish','store']   ← 它能按门店
确定性编译器算 : (RECIPE_COST,)  声明只能按 ['dish']         ← 它不能
老板问的       : store
⇒ 又是 code ∉ plan ⇒ 拒答
```

代码里本来有一道 guard 做对了：目标服务不了这些维度就**跳过覆盖**，
并打日志「保留 planner 的判断」。

🔴 **那句日志是空话。** 跳过之后矛盾原样留着，下游照样拒答 ——
planner 的判断一个字都没保留下来。

▎**在代码里，「放弃修复」和「拒答」是同一件事。**

**修法**：跳过覆盖时，如果**标签自己**能服务这些维度，就把计划对齐到标签。

**📏 修复后（prod 实测 2/2）：** 答出「门店毛利对比（最近30天，10 家店）」。

▎**案例①和②是同一条不变量的两个方向** —— 一次计划赢、一次标签赢。
▎共同点：**⛔ 都不许把矛盾留着。** 这就是「一条不变量消灭一整类」的样子。

---

### 案例③ 「那最差的呢」— 不变量 ② 与「猜 vs 查」

老板先问「哪家店卖得最好」，产品答了。他追问「那最差的呢」：

**📏 现在：**

```
LLM 输出 dish='最差'          ← 🔑 是 LLM 自己判错的
_verbatim_entity 检查两件事:
   ① 在原句里吗?        ✅ 在
   ② 在手工黑名单里吗?  ❌ 不在（名单里有「这道菜」「哪家店」「门店」…没有「最差」）
⇒ 放行 ⇒ 去查一道叫「最差」的菜 ⇒ 维度从 store 翻成 dish ⇒ 拒答
```

**⛔ 修法不是补一个「最差」进名单。** 下次是「最好」「垫底的」「拖后腿那家」
「排第一的」「刚才那道」…… 每补一次测试都变绿、bug 都真的修好了，
**所以没有任何时刻会让人意识到自己在维护一张补不全的表**。

🔑 **关键的划分不是「词表 vs LLM」，是「猜 vs 查」：**

```
词表   用【词长什么样】猜        「最差」看着像名词 ⇒ 当菜名
LLM    用【语言模型】猜          「最差」在这位置像实体 ⇒ 当菜名
目录   【查】                    菜单里有没有「最差」这道菜 ⇒ 没有
```

▎**这次 LLM 和词表犯的是同一个错，因为它俩都在猜。**
▎⇒ 把词表换成 LLM **不解决问题**。该换的对象是**查**。

**不变量②：实体槽位必须在租户目录里查得到。**

📏 代价已经量过（MOCK_REST，菜单 10 条）：

```
dish 非空 5 次 → 在菜单 4（米饭/鲈鱼/水煮牛肉/罗氏虾，全该放行）
              → 不在 1（「最差」，正是那个 bug）
⇒ 零误伤
```

⚠️ 而且判据 `_catalogue_says_not_a_dish` **已经存在**（router:1342，
已被 router 内 3 处消费），只是没接到 dish 槽位上 —— 又一个形态 B。

⚠️ **门店那侧早就这么做了**（`_validated_llm_store_names` 对目录校验），
**菜品没照做** —— 硬约束 8 的原形：同一语义多处，只做对一处。

### 案例④ 「哪家店最多」（追问）— 为什么飞轮解决不了它

📏 实测（3/3 稳定复现）：

```
第1问 最近损耗怎么样   dims=('ingredient',)  正文指纹 bd1d6675  长度 1249
第2问 哪家店最多       dims=('store',)       正文指纹 bd1d6675  长度 1249
                                             ↑ 逐字相同
```

⚠️ 我第一次读它读错了两次，值得记：

1. 先报「4 条链 0 条接住追问」—— **说重了**。打开正文一看，
   那 1249 字里**确实有**「各门店损耗金额（10 家，从高到低）」表。
2. 再钩 resolver 想定位，结果**钩子把被测对象改坏了**（答案从 1249 字塌成 35 字）——
   因为 `resolve_by_code` 按**签名**过滤 kwargs，而我的 `spy(*a, **kw)` 签名是通配的。
   救我的是「之前量过 1249」这个偶然的阳性对照。

**真相**：`resolve_wastage_top` 的签名里**根本没有 `dimensions`** ——
规划器算出的维度**从来没传到 resolver**。三次调用它的产出长度全是 1137，
对「问的是哪一层」完全不敏感。

⇒ **这一类飞轮解决不了**，因为它不是「路由错了」，是**执行层收不到规划结果**。
⇒ 登记为独立项，⛔ 不塞进飞轮假装解决了。

## 四 · 对抗性审计：这套架构自己会怎么坏

⛔ 一个没被攻击过的设计不算设计。逐条列出攻击 + 结构性回答。

### 攻击 1：飞轮会把**错的**答案固化，而且让它更便宜到达

若一条错计划通过全部闸并被晋升，它就变成**持久 + 优先命中**的 ——
错误被放大而不是纠正。

**回答**：
- 晋升必须**人工审**（源码 spec 已明写「绝不静默自动毕业」，⛔ 不放宽）
- 每条晋升带**出处**（哪次请求、哪道闸判过、当时的 spec 全文）
- **必须有降级通道**：一条晋升可被撤回，且撤回后 L0/L2 立即失效

### 攻击 2：L0 消灭抖动，靠的是**冻结第一次的结果**

📏 「我要不要关掉最差的那家店」实测 1/2 ↔ 2/2 抖动。L0 命中后确实不抖了——
**但它冻结的是碰巧第一次出现的那个答案**。

**回答**：⚠️ **诚实地说，L0 给的是一致性，不是正确性。**
正确性只能来自人工审那一步。⛔ 不许把「不抖了」说成「准了」。

### 攻击 3：「全闸通过」是个弱信号

📏 契约缺口 24 问句 × 2 轮 = **0 次**，而同期仍有 6 次拒答。
一道从不开火的闸，「通过」等于没说话（形态 G）。

**回答**：晋升条件不能写成「通过全部闸」，必须写成
**「至少有一道闸对它做过实质判断，并指出是哪一道」**。
⛔ 说不出是哪道闸判的，就不算验证过。

### 攻击 4：纠正记录本身会变成第二份真相（形态 F）

**回答**：纠正记录必须是**派生的**，由闸在运行时产出，
⛔ 不许手写、不许人编辑。人只能**批准或拒绝**，不能修改内容。

### 攻击 5：目录校验会误伤真菜

菜单陈旧 / 同步延迟 / 新菜上架 ⇒ 真菜被判「不是菜」。

**回答**：**fail-open 已经是既有纪律**（源码明写：目录没加载 / 加载失败 /
菜单为空时**一律开放**，收紧会把该租户的菜品问答整片判死，那比误读更糟）。
再加一道：**目录条数骤降要告警**（三态，`rc=2`）。

### 攻击 6：人工审是瓶颈，而它从来没发生过

📏 176 条候选积压，晋升 0 条。

**回答**：这是**真的风险，且已经发生了**。⇒ 架构必须让审变便宜：
- 按**频次**排序（📏 Top-50 覆盖 49.2% 的请求 —— 审 50 条就够一半）
- 一次审的是「LLM 说 X、我们用了 Y、因为 Z」，⛔ 不是从零判一个 intent
- ⚠️ **若这一步仍然没人做，整套架构退化成「纯 LLM + 会话缓存」** —— 就是今天

### 攻击 7：我说「关键词已死」，样本只有一个租户、一条路径

📏 五处调用点 × 四个场景 = 0（阳性对照已过）。
但那是 **MOCK_REST + `semantic_first=True`** 这一条路径。

**回答**：⛔ 不许把它写成「关键词已经退役」。准确说法是
**「在这条路径、这个租户上实测为 0」**。别的入口要各自量。

### 攻击 8：「值域归一无弊端」—— 值域会变

📏 今天 `order_type` 只有 3 个值（`dine_in` / `takeaway` / `groupon`），
归一表 26 条全覆盖。但明天接入新渠道就是第 4 个。

**回答**：这一类**弊端可被机制消除**，因为输入是**可枚举的有限值域**：
配一道 `SELECT DISTINCT` 的闸，出现新值就告警。
⚠️ 今天那道闸**还没有**；现在靠的是「未知码原样返回」（显形不说谎）。

### 攻击 9：L2 冷启动 —— 已审句子是 0 条，向量召回无从召起

**回答**：用现有 62 条 `SAMPLE_QUERIES` 作种子，
但**必须标出处**（种子 / 实战晋升），否则又是「同一件事两份」。

### 攻击 10：这份架构自己会不会成为「描述过期」（形态 L）

**回答**：本文档所有 📏 数字都带**日期 + 租户 + 命令**。
⚠️ 且必须配一条纪律：**改动读路径时，grep 本文档的关键词**
（例：`code ∈ planned_intents`、`_catalogue_says_not_a_dish`），
描述过期比没有描述更糟 —— 它让下一个人跳过核实。

## 五 · 三条不变量各自的「能红」证明

⛔ 没红过的闸不算闸。每条不变量必须有阳性对照进 CI。

| 不变量 | 阳性对照 | 状态 |
|---|---|---|
| ① spec 自洽 | 拆掉 `or comparison_drove_the_plan` → 接线断言红；归因降级成恒 `True` → 重编译断言红 | ✅ 已做（#2798） |
| ① spec 自洽（方向二） | 只记日志不对齐 → 接线断言红；判据恒 `True` → **两条阴性对照同时红** | ✅ 已做（#2799） |
| ② 实体查得到 | 注入假词表 → 棘轮 exit 1 并点名；`census()` 返回空 → 3 条断言红 | 🟠 词表棘轮已做（#2801），**目录校验未接** |
| ③ 能力一张表 | `_resolver_serves_dimensions` 出现次数 == 2 且 `_build_spec` 内无手写 `issubset` | ✅ 已做（#2799） |
| ⛔ 信号非空 | 每个被依赖的信号一条 `count(*) > 0` 断言，为空报 `rc=2` | 🔴 **未做** |
