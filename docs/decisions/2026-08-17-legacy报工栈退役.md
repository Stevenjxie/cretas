⇒ **不存在数据合并问题。** 我列为「最棘手」的那一步，实际上是删死代码。

**从代码能推出一个自洽的故事，而否定它的东西在数据库里。**
判据：**说「两套并行」之前，先数两张表的行数**，十秒钟的事。

## 三、口径（Steve 授权自行决定）

### App 端审批屏 `WorkReportApprovalScreen`：**删掉，核对只在网页端做**

决定性理由不是偏好，是技术事实：

- 该屏调的是 **legacy 的 `approveReport`**；
- 而 2026-08-17 新做的**驳回回退库存**只接在 `process-work-reporting` 那条路上；
- ⇒ 留着它等于留一条**驳回不退库存**的审批路径，把当天修的东西从侧门绕过去。

加上业务流程本来就是「工人 App 报工 → 文员**网页端**检查」，两个审批面只会长成
本仓反复踩的「同一个问题两个答案」。

## 五、订正二：第 2 步不是「改指向」，是「先补端点」

写第四节时我假设 `process-work-reporting` 覆盖了 legacy 的只读能力。**没验。** 实测：

`process-work-reporting` 只有 6 个端点 ——
`pending-approval` / `{id}/approve` / `{id}/reject` / `batch-approve` /
`by-task/{taskId}` / `by-task/{taskId}/workers`。

| legacy 只读方法 | 替代 |
|---|---|
| `getReports`（带筛选的列表）| ❌ 只有 `pending-approval`（仅 PENDING）与 `by-task`（单任务）|
| `getReport`（按 id 单条）| ❌ 无 |
| `getSummary` | ❌ 无 |
| `getHistoricalAverage` | ❌ 无 |

⇒ 退役的真实成本比第四节写的高一档：**要先在 `process-work-reporting` 上补 3~4 个端点**
（列表 + 单条 + 汇总 + 历史均值），再谈改指向。

⚠️ **这是同一晚第四次同形**：从代码能推出一个自洽的计划，而否定它的东西
（端点清单 / 表行数）就在一条命令之外。前三次是
「自动盖章导致财审没输入」「产出静默不入库」「打卡两套并行要合数据」。

⇒ 判据升级：**写「改指向」这类计划步骤时，把替代面的端点清单贴出来逐条对**，
⛔ 不许只写「有对应实现」。
