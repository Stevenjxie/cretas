| 组 | 翻台率怎么样 | 营收趋势怎么样 | 毛利最低的菜品有哪些 |
|---|---|---|---|
| **A 共用一个 key**（= 生产入口的样子） | clar 129 字 `316dc92b` | clar 129 字 `316dc92b` | clar 129 字 `316dc92b` |
| **B 每句独立 key** | clar 129 字 `316dc92b` | **answer 511 字** `db9d5b1b` | **answer 2417 字** `7138e00f` |

`build_trusted_restaurant_session_key(fid, user_id, session_id)` ——
**同一个 sessionId 下所有轮次共用一个 key**，即 A 组。

### 逐轮读数（`session_key` 固定，每轮打印 pending 表 + spec）

```
第1句 翻台率怎么样
   spec.intent=''  unsupported=['table_turnover']
   clarification_question='你这次最想先看哪件事？'
   老板看到: 129 字「翻台率…现在算不出来 / 缺的是… / 我这儿有的是…」
   pending 落库: original_query='翻台率怎么样'

第2句 营收趋势怎么样
   spec.intent='RESTAURANT_OPS_TREND_ANALYSIS' dims=['time']      ← LLM 判对了
   clarification_question='你想看哪个时间范围的营收趋势？'          ← 也合理
   unsupported=['table_turnover']                                  ← 粘住了
   老板看到: 还是那 129 字
   pending 落库: original_query='翻台率怎么样 营收趋势怎么样'

第3句 毛利最低的菜品有哪些  → 同上, seed='翻台率怎么样 营收趋势怎么样 毛利最低的菜品有哪些'

```

▎**一次能力拒答之后，这个会话就废了** —— 后面每一句都拿到那 129 字，且串**无限增长**。

## 二 · 真因（两处，⛔ 不是一处）

```
① _parse_continuation:7400   concatenated = original_query + " " + answer
                             ⇒ 无条件强制拼接
② _semantic_spec_from_t3(parsed, concatenated, …)
   → _build_spec(effective_query=concatenated)
   → requested_metrics 从这个拼接串抽 → unsupported_requirements 含 table_turnover
   → service:1839 should_use_capability_refusal(...) 命中 → 能力拒答模板接管
```

🔑 **LLM 每一轮都判对了**（intent / clarification_question 逐轮不同且合理）。
错的是**消费端用错了输入** —— 形态 B 第 7 例（投影丢失）的又一实例。

⚠️ 架构对①已有裁定：
> 缺对象/时间时，前文只作为**建议**丢给 LLM，**⛔ 不强制拼在一起（强制合并必然出错）**
> 架构点 25：上下文存 **spec 栈**，⛔ 不存对话文字

⇒ 方向不需要重新讨论，只需要决定这一轮做到哪一步。

## 三 · 三个选项

| | 做法 | 代价 | 判据会不会漂 |
|---|---|---|---|
| **A** | 判「这句是不是在回答那个澄清」，不是就丢弃 pending | 判据是语义判断。写成词表/启发式必漂（形态 E 的代理判据）；交给 LLM 则要改 prompt + 新字段 + 回退分支 | 🔴 会 |
| **B**（选中） | **能力拒答 ⛔ 不注册 pending** | 只覆盖「能力拒答」这一类；真反问之后换话题仍会粘（登记未做） | ✅ 不会 —— 判据是既有的 `should_use_capability_refusal`，与 service 读同一个函数 |
| **C** | 完整实现架构点 25（上下文存 spec 栈） | 结构性正解，但是第二档大工程；这一轮做不完，而缺陷 100% 复现中 | ✅ 不会 |

### 裁定：**B**，理由是判据的**来源**

B 的判据不是我新发明的，它来自一个**已经存在的不一致**：

```
注册进 pending 的问题:  '你这次最想先看哪件事？'
老板实际看到的正文:      「翻台率…算不出来 / 缺的是… / 我这儿有的是…」
```

▎**注册的问题和发出去的话不是同一件事**（形态 D：同一件事两份，且已经漂了）。
▎`_maybe_register_pending` 的语义是「我问了你一个问题，等你回答」——
▎而能力拒答**根本没在问问题**，它在说「这个我算不了」。

⇒ 所以 B 不是「加一条规则去猜」，是**把一个本来就不该注册的东西不注册**。

⛔ 未做，显式登记：
- 真反问（缺时间/缺门店，老板确实看到了问题）之后换话题，仍然会拼接。
  归到架构点 25（选项 C），⛔ 不在这一轮用启发式凑。
- `resolver_query_seed` 无条件累积增长这一类没有解决。同上。

## 四 · 能让判据红的对照

| 类型 | 内容 | 期望 |
|---|---|---|
| **承重** | 能力拒答的 spec 过 `_maybe_register_pending` | `_pending_put` **不被调用** |
| **阴性** | 普通反问（`unsupported=()`，缺时间/门店）过同一函数 | `_pending_put` **照常被调用** —— ⛔ 不许把延续整个关掉 |
| **阴性** | `clarification_needed=False` 的正常 spec | 不注册（与改动前逐字相同） |
| **同源** | AST：`restaurant_intent` 与 `restaurant_intent_service` 引用**同一个** `should_use_capability_refusal`，且 `restaurant_intent` 里没有第二份手写判据 | 通过 |
| **变异 M1** | 把守卫条件删掉 | 承重断言红 |
| **变异 M2** | 把守卫改成无条件 `return`（谁都不注册） | **阴性对照红** —— 证明它红在「只拦能力拒答」这件事上，不是「拦一切」 |
| **prod 真跑** | 同一 session_key 连问「翻台率怎么样」→「营收趋势怎么样」 | 第二句 `is_clarification_continuation=False`，正文 ≠ `316dc92b` |
