# 设计卡：下钻回路（缺口 → 追问 → 归因 → 事件）

**2026-08-12** · 状态：待实施（本轮架构收口之后）
来源：`docs/dispatch/2026-08-12-内部方向讨论-日结主线-转录.md`
⚠️ 该转录三人全是内部人员，**不是需求验证**。本卡的取舍依据是「与已有实现的接口」，
不是「客户要求」。

---

## 一句话

把「缺口声明」「追问按钮」「归因止步」三件现在各自为政的事，合成一个能自我推进的回路。

转录里这三件事是**同一句话的三面**：

> `[32:38]`「先按照现在有的一些算一笔出来，但是会跟他提醒说现在还缺少哪些数据」
> `[36:37]`「你要不然你戳他就跳，你戳了他就跳，它有下钻引导」
> `[23:0x]`「原来这个菜今天卖的特别好，为什么卖的好，有降价吗，没降价吗，还是说他们推了，还是没推」

---

## 现状（实据，非推断）

| 环节 | 现在是什么 | 位置 |
|---|---|---|
| 缺口 | 「我这儿有的是 / 缺的是」—— **清单，不映射影响** | `capability_answer.py` |
| 追问 | **三个硬编码问句**，每个 scenario 都一样 | `GoldBackedRestaurantTool:457` `decisionFollowups()` |
| 归因 | 链条止于**数据维度**（客数/时段/客群） | `.ladder` 那套 |
| 事件标注 | **没有载体** | — |

现有的三个硬编码问句：

```java
followup("老板今天怎么用这张报表做决定？", …)
followup("哪些动作今天先不要做？", …)
followup("明天看哪三个数判断有没有效果？", …)
```

它们是**决策导向**的，与转录说的三种（汇整 / 偏重性 / 深究）不是同一套；
更关键的是它们**不可能知道这次答案缺了什么** —— 它只拿到一个 `scenario` 字符串。

---

## 目标形态

```
答案
 ├── 数字（带 provenance）
 ├── 限定语（由 provenance 生成，不手写）
 └── 追问按钮（有类型，不是自由文本）
      ├─ T1 下钻   → 沿当前指标往下一个维度
      ├─ T2 补数据 → 「补 X，能把 Y 从估变实 / 解锁 Z」    ← 缺口映射到影响
      ├─ T3 标事件 → 「这天有没有做活动？」                ← 归因止步时才出
      └─ T4 深究   → 预置分析框架（优先级最低，先不做）
```

---

## 四个类型的定义与生成规则

### T1 下钻 DRILL
- **何时出**：答案里有 ≥1 个还没用过的可细分维度
- **生成**：registry 反查「当前 metric × 未使用的 dimension」
- ⛔ 不手写。手写 = 每个 tool 各写各的，就是现在的样子

### T2 补数据 FILL —— 这条是「缺口映射到影响」的落点
- **何时出**：`CellResult.missing_columns` 非空，或 `provenance != MEASURED`
- **生成**：**registry 反查**。`Metric.requires` 形如
  `("fact_pos_transaction.net_amount", "fact_pos_item.amount")`，
  反转成 `column → [metric_key]` 即可知道「补这一列能解锁哪些指标」
- **两类文案，对应两种影响**：
  - 完全算不出 → 「补 {列的人话名}，能算出 {那些 metric 的 label}」
  - 精度降级（`provenance=ESTIMATED`）→ 「补 {basis 缺的那样}，{metric} 从估变实」
- ⛔ 「列的人话名」也必须在 registry 上，**不能手写映射表** ——
  与 `category` 同一条判据：手写映射一旦落地，新登记的列会悄悄落在表外而不报错

**为什么这条能自动产出而不用写文案**：只要反查做出来，
「补了能到什么程度」是算出来的，不是人编的。这也是它必须做成反查的全部理由。

### T3 标事件 ANNOTATE —— 归因止步时的出口
- **何时出**：归因链走到**无痕层**
- **判据**：当前归因维度的下一层在 registry 里**没有对应的 metric/dimension** → 无痕
- **有痕 / 无痕的实际分界**（已核）：

  | 要素 | 数据里有痕 | 能不能答 |
  |---|---|---|
  | 有降价吗 | ✅ 折扣额、折扣单数在 registry 里 | 能答 |
  | 做活动了吗 | ✅ 部分（促销/套餐能从订单看出） | 部分能 |
  | 他们推了没推 | ❌ 口头推荐不进 POS | 答不了 |
  | 天气 / 隔壁开店 | ❌ | 答不了 |

- **文案**：「{时间}{对象}{现象}，这天有没有做什么活动 / 是不是有人在推？」
- **用户答了** → 写入事件标注，`provenance = REPORTED_BY_USER`
- ⛔ **事件标注是主观数据，不能和实测数据混算**。它有自己的 provenance，
  否则下次归因会把「老板说那天做了活动」当成事实去推。
  这与 C 项那张 provenance 卡是同一个机制，不是两套。

### T4 深究 ANALYZE
- **何时出**：用户已看过基础答案（第二轮及以后）
- **生成**：预置分析框架（转录里「框死掉，不然他有发散性思维就无法无天了」那个思路）
- 优先级最低，**先不做**

---

## 为什么必须是类型而不是自由文本

现在 `decisionFollowups` 是三个硬编码问句，对每个 scenario 都一样。后果：

1. 追问质量取决于写它的人当时想到什么
2. 新增一个 tool 就要重新想一遍三句话
3. **它不可能知道这次答案缺了什么** —— 只拿到 `scenario` 字符串

类型化之后，追问是**从这次答案的结构里算出来的**，不是预先写好的。

---

## 回路怎么自我推进

```
第 1 轮：给数 + 限定语 + T2「补 X 能算 Y」
   ↓ 他补了 X
第 2 轮：Y 能算了，provenance 从 ESTIMATED 变 MEASURED，限定语自动消失
   ↓ 归因往下走
第 3 轮：走到无痕层 → T3「这天有没有做活动」
   ↓ 他答了
第 4 轮：事件入库，下次同类归因可以引用
```

每一轮的产出变成下一轮的输入。这是转录里那句
「就是推导让他去做…**不好意思不是我不好是你不给**」的机制化。

---

## 边界与优先级

- 按钮数量有上限：前端 `normalizeFollowUpActions` 拼完四路来源后 `.slice(0, 4)`
- **类型间优先级：T2 > T3 > T1 > T4**
  理由：缺数据是阻塞项、无痕是阻塞项，下钻只是锦上添花
- ⛔ 转录里的「让你修改一下提示词」**不做**。
  暴露 prompt = 暴露内部实现（违反「维度这些东西他看不着」）+ 绕开路由与权限。
  替代做法是**改问法**：把 plan spec 的槽位翻译成人话让他确认，
  例如「我理解成：全部门店 · 最近 30 天 · 毛利 [改成某一家][改成本月][改成营收]」——
  改的是已有的结构化槽位，输出契约不变，且顺带能让用户自己纠正上下文继承错误。

## 🔴 T1 的前置：resolver 词汇与 registry 词汇是两份，已经漂了（2026-08-13 实测）

T1 的生成规则是「registry 反查 **当前 metric × 未使用的 dimension**」，
所以它要能从答案里读出「已经用了哪个维度」。`rows` 投影（PR#2548）让答案有了
结构化数据，但**有结构不等于有共同语言**：

| 投影里的值（prod 实测） | registry 里 | 结果 |
|---|---|---|
| `type: "dish"` | `DIMENSIONS` 有 `product`（label=菜品），**没有 `dish`** | ❌ |
| `sales_volume` | `METRICS` 是 `sales_qty` | ❌ |
| `bill_count` | `METRICS` 里没有这个概念 | ❌ |
| `revenue` | ✅ 在 `METRICS` 里 | ✅ |

**四个字段只有一个对得上。**

⚠️ 这不是意外漂移，是**两代实现并存**：registry 是新的声明式抽象，
resolver 是 601 条那个年代的手写世界。形态 D（同一个东西有两份，它一定会漂）。

### 三条路，选第三条（**本卡不做，做 T1 时再动**）

1. **改 resolver 字段名对齐 registry** —— ⛔ 不行。`bill_count` 在 registry 里
   **根本没有对应键**，不能改名成一个不存在的东西；而且改名会破坏现有消费者，
   要先做一次「601 条」那样的消费者清单才敢动。
2. **投影层由 registry 反向推导归一** —— ⛔ 做不到。registry 里 `label`/`asks`
   都是中文，resolver 字段名是英文键，中间**没有可推导的桥**，最后一定退化成
   手写表 —— 而手写表正是本卡明令禁止的。
3. ✅ **resolver 自声明 + 闸钉住完整性**。每个 resolver 声明自己的输出字段对应
   哪些 registry 键，声明写在 **resolver 自己身上（一处）**，不是中央映射表。
   闸：任何 resolver 的输出字段**没有声明就红**。

   它与手写映射表的区别**不在映射写在哪，在于漏了能不能被发现** ——
   中央表漏一条是静默的，自声明漏一条被闸抓住。
   而且它天然处理 `bill_count` 那种情况：声明可以显式写
   「此字段不入 registry 域，不参与下钻」，改字段名做不到这个。

⛔ **这是 T1 的前置，不是 P0 的前置。** T2（补数据开价）全程在 registry 内部，
   不碰这个岔口 —— 所以 P0 先做 T2。

## 📌 挂账：粒度（grain）没有默认机制（**通用问答的改进，不是 P0 前置**）

⚠️ **不要因为 `restaurant_intent_service:322` 那句文案改漂亮了，就以为这块处理好了。**
文案改的是「怎么问」，没改「该不该问」。

2026-08-13 prod 实测：「今天赚多少」「今天毛利多少」「今天生意怎么样」
「打烊了，今天怎么样」**四句全部 `kind=clarification`**，回的是
「你是想看某道菜、某家门店，还是全店合计？」

而店长问「今天赚多少」**显然就是全店合计**，不需要问。

### 三件事写清楚

1. **判据与时间窗口那条完全一样**：默认 + 明示 + 可改。
   owner 2026-08-13 裁定时间窗口的三条理由（禁止降级处理防的是编数据不是防选默认 /
   反问把负担推回给不知道怎么问的人 / 人审同向）**对 grain 一字不改地成立**。
   落地形状：
   ```
   今天全店毛利 X 元
   （默认按全店合计；想看单店或单菜可以直接说）
   按钮：看各门店 / 看各菜品
   ```

2. **卡点在 `_execution_mismatch`（`restaurant_intent_service.py:284`），承重不能碰**。
   它的语义是「不许在执行期重新解释一个不可变的 v2 计划」。
   ⇒ 粒度默认**必须发生在计划生成时**（与时间/门店同一个位置），
   不能靠在这道校验上开口子。

3. **是新建，不是接线**。实测：
   ```
   time_range_defaulted   : 15 处
   store_scope_defaulted  :  9 处
   grain_defaulted        :  0
   aggregation_defaulted  :  0
   dimension_defaulted    :  0
   ```
   `RestaurantQuerySpec` 上只有两个 `*_defaulted` 字段，粒度这一层一个都没有。
   **工作量与「照抄时间那条」差一个量级** —— 别默认是后者。

### ⛔ 为什么它不是 P0 的前置

P0 的主体是**一个固定形态的日结报表**：粒度写死全店、时间写死当日，
**根本不经过 planner**，也就不会撞上那道一致性校验。
所以 grain 默认是通用问答的改进，P0 不等它。

## 📌 挂账：面向用户的串收敛到一处定义（P0 之后做，**现在不动**）

黑话闸目前用「有没有中文标点」当「面向用户」的**代理判据**，2026-08-13 实测
它两个方向同时失效：

- **假阳性**：扩面后报出 9 条，6 条是给模型的 prompt / SQL / 正则 / 开发者断言消息
- **假阴性**：prod 上**天天在发**的那句「查询维度超出计划 resolver 的能力范围」
  **不在清单里** —— 它没有中文标点

⛔ **不要靠不断加启发式去逼近**。静态分析判不出「这个串会走到用户面前」，
   加下去只会做出一个更复杂、误报更多、仍然漏 f-string 的东西。

**唯一的修法**：把面向用户的串**收敛到一处定义**，闸扫那一处。
`customer_text.py` 已有先例（`NO_SUBSTITUTION` / `PLANNER_UNAVAILABLE` 那批常量）。

⚠️ 这是个真重构，规模与「601 条」同级 —— 要先做一次消费者清单才敢动。
   **排在 P0 之后。** 在那之前闸保持 `ENFORCE_JARGON_GATE = False`（只报不拦）。

## 📌 挂账：成本覆盖率没接进限定语（**机制已经在，只是没接上**）

**2026-08-13 实测**：`provenance.qualifier()` 已经接受 `coverage_ratio`，覆盖不足时
会在限定语前面加一句「其中 X% 的营收没有配方成本，」；`provenance.coverage_ratio()`
也写好了。**而 `generic_answer.render()` 传的是 `coverage_ratio=None`** —— 那两样
今天是死代码。

**为什么这件事有实害**：`food_cost` 的表达式是

```
SUM(i.qty * COALESCE(c.food_cost, 0))
```

⛔ **没有成本卡的菜按 0 成本计入**。覆盖率 40% 的租户，毛利会被抬高一大截，
而限定语只说「按成本卡的理论用量估算」，**不说这个估只覆盖了四成**。
店长看到的是一个偏高的毛利 + 一句听起来已经解释过了的限定语。

**为什么今天没做**：
1. 接它要在执行器里多跑一次「有成本的营收 ÷ 全部营收」，属 P0 之外的改动；
2. **今天在 prod 上量不出来** —— MOCK_REST 的覆盖率是 **100.0%**
   （10 个在售菜品全部有成本卡，2026-08-12 营收 ¥749,009 全额覆盖）。
   这是「平租户让闸恒绿」的又一例：在这个租户上接不接，读数完全一样。

**做的时候的判据**：先找一个覆盖率明显不足的租户（或构造），
证明限定语里那句百分比**跟着覆盖率变**；再补一条变异对照——
把覆盖率强改成 100%，那句话必须消失。

## 📌 挂账：「没营业」和「数据没落库」在事实表上是同一个长相

**2026-08-13 实测**：打烊日结要判「今天有没有东西可推」。我原来的判据是
「`orders` 分得清（`0` vs `None`）」—— **错的**。`orders` 是 `COUNT(...)`，
空集上返回 **0 而不是 NULL**。拿一个根本不存在的租户跑，得到的是 `no_business`。

⛔ 更根本的一层：**没有行**这件事，既可能是今天没营业，也可能是 ETL 今天没落数。
从事实表本身推不出区别。

**要分清需要外部信号**，两条路：
- 门店营业日历（今天本来就该关门）
- ETL 水位表（今天这张表最后写入是什么时候）

在此之前，日结对这两种情况都是「不推、不告警」。**这是有意的**：宁可漏推一天，
也不要每周一给一家周一休息的店发一条假告警。

真正可达的 rc=2 只有一个：**一个租户都没轮到**（名单为空）。已构造验证：
`DAILY CLOSE INSTRUMENT DEAD 2026-08-13 06:05:55`。

## 🔴 挂账（阻塞真实门店）：同一屏上两个数字用了两个营收口径，毛利没扣折扣

**2026-08-13 体检结论。** owner 问：营收 71.8 万、毛利 50.7 万、毛利率 70.6%，
而中餐一般 60% 左右 —— 是覆盖率算漏了，还是 demo 数据本来如此？

**都不是。是口径混用。**

### 实测（prod / MOCK_REST / 2026-08-12）

`revenue` 在登记表里有**两个粒度的表达式**：

```python
exprs={"txn": "SUM(t.net_amount)", "item": "SUM(i.amount)"}
```

| 段 | 走哪个粒度 | 值 |
|---|---|---|
| 营收 | `txn` = `SUM(t.net_amount)`（**扣了折扣**） | 717,883.41 |
| 毛利 | `item` = `SUM(i.amount)` − 食材成本（**没扣折扣**） | 749,009.00 − 242,259.58 = **506,749.42** |

506,749.42 与界面显示的毛利**逐分一致** —— 机制确认。

两个口径的差 = **31,125.59**，正是折扣额。

### 为什么这是缺陷不是口径选择

- 店长拿屏上两个数相除得 **70.6%**；内部自洽的是 506,749/749,009 = **67.7%**
- 更要紧的：**毛利没有扣折扣**，被高估了 31,125.59（约 6.5%）。
  一家靠满减跑量的店，折扣越多毛利虚高越多 —— 而这正是老板要看的那个数

### 覆盖率是清白的

同日实测：7913 行 item 明细**无一缺成本卡**，覆盖率 **100.0%**，
食材成本率 **32.3%**（逐菜 10.7%~41.4%，鲈鱼 37.4% / 水煮牛肉 41.4% / 红糖糍粑 10.7%）。
成本卡数据本身合理。⛔ 所以不要去改成本卡，问题不在那里。

### 为什么没有顺手修

改 `revenue` 在 item 粒度的语义会影响**整条问答读路径**，不只是日结。
这是承重改动，等 owner 定方向。两条候选：

1. 毛利改用 txn 口径营收（`SUM(t.net_amount) − 食材成本` = 475,623.83）——
   数字变小但与营收段自洽
2. 明细行按比例摊掉交易级折扣，两个粒度都拿到扣折扣后的营收

## 🛑 前置 3 调查结论：不是「缺 grain 默认」，是 `all` 被当成了分组维度

**2026-08-13 prod 实测。** owner 让先查「planner 判据是不是太严」，查完了 —— **是**，
但成因和预想的不同：**planner 根本没有不肯定粒度，它正确地给出了 `all`。**

### 实测（deployed 代码 / prod 库 / 逐题清缓存）

| 问句 | 结果 | spec.dimensions | resolver 声明支持 | 差集 |
|---|---|---|---|---|
| 今天赚多少 | clarification | `('all',)` | `{store}` | `{all}` |
| 今天营业额多少 | clarification | `('all',)` | `{store}` | `{all}` |
| 今天多少单 | clarification | `('all',)` | `{store}` | `{all}` |

三题**同一个形状**。拦截点是 `_execution_mismatch` 里那句子集判断：

```python
if not set(_canonical_dimensions(spec.dimensions)).issubset(supported_dimensions):
    return "我不确定你要看的是哪一层的数"
```

### 为什么这是范畴错误

- `all` 在登记表里的定义是「**不分组**，整体汇总」（`Dimension.group_expr = None`）
- `_RESOLVER_DIMENSIONS` 列的是每个 resolver **能按什么分组**
- ⇒ `all` 不在任何一个 resolver 的集合里，**也不可能在** —— 它根本不是一种分组

所以 `{'all'} ⊆ {'store'}` 恒不成立。**任何「全店合计」类问句都会被拒**，
与指标无关、与 resolver 无关。这不是能力缺口，是拿「不分组」去比「分组清单」。

旁证：`RESTAURANT_OPS_SALES_SUMMARY` 自己的注释写着它返回
「a real per-store Top-N table **in addition to the chain aggregate**」——
chain aggregate 正是 `all` 要的东西，它一直都能出。
`AGGREGATIONS["summary"].needs_dimension` 也早就是 `False`。

### ⛔ 为什么没有动手

修法落点在 `_execution_mismatch`（或能力表）内部 —— owner 划的红线：
**不许动 `_execution_mismatch`，它是承重的**；且属「必须问我」的 B 类。
**已停下，等裁定。**

⚠️ 顺带排除了一个可能的回归：本轮给 registry 加 `caveat` 字段**没有**进指纹
（`_plan_semantics_materials` 只读 `_REQUEST_METRIC_RULES` / `sorted(_INTENT_DESCRIPTIONS)` /
`_REQUISITION_SPEND_RE`，都是纯字符串），HEAD 上算出的完整指纹 `fd5508a3` 与
今晨 02:25 那轮一致。
