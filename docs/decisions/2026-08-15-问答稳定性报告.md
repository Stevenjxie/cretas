## 结论一句话

**三个「非确定性」里，只有一个是真的。**

| # | 原判 | 实测 |
|---|---|---|
| ① 闸在槽位相同时翻转 1/10 | 闸不稳定 | ❌ **闸是确定的**。抖的是喂给它的 `dimensions` 一个字段 |
| ② 空 spec 1/10 且照样给答案 | 有回退路径在答 | ❌ **不复现**。空 spec 真实存在（LLM 超时），但**全部 fail-closed 成反问** |
| ③ 上下文串 | 从没真正量过 | ✅ **真的**。有效分母 13，真串 **3/13 = 23%** |

⚠️ ① 和 ② 的原判**都建立在我自己仪器的缺陷上**：我先 `parse_restaurant_query()`
记 spec、再 `ask()` 记 kind，中间清了缓存 ⇒ **那是两次独立编译**。
把 spec 换成 `res["spec"]`（同一次调用返回的那份）之后，两个现象都消失。

## ② 空 spec —— 成因是 LLM 超时，且它**不会**给出答案

### 成因（原文）

```
[restaurant-intent] T3 LLM parse failed/timed out: [llm_router] All providers
exhausted for review: aistore/DeepSeek-V4-Flash-A: ReadTimeout; tencent/deepseek-v4-flash-20…
```

32 次调用里出现 **3 次**（`全店本月毛利多少` 不带 / `最近30天按日期看毛利` 带 /
`上个月呢` 不带）。

### 🔴 2026-08-15 订正（接手复核，两处）

**(a) 这段引文出自探针进程，不是服务进程 —— 但支撑它的理由换了。**

⚠️ 复核第一版给的理由是「`ReadTimeout` 不是路由器产出的」。**那是错的。**
路由器有两条超时出口，**两条都会写**：

```
llm_router.py:1953  errors.append(f"{account}/{model}: timeout")
                    ← asyncio.TimeoutError 分支
llm_router.py:1962  errors.append(f"{account}/{model}: {type(e).__name__}")
                    ← 通用 except；httpx.ReadTimeout 走这条，写出来正是 "ReadTimeout"
```

⇒ 换一条**不依赖「谁写的」**的证据：`ReadTimeout` 在服务日志里出现 **0 次**
（`/www/wwwroot/cretas/python-prod.log`，窗口 `2026-08-10 03:34` →
`2026-08-15 16:11`，覆盖本轮探针时段）。它既然是路由器**会**写的串，
而服务进程一次都没写过 ⇒ 这 3 次不是服务进程产生的 ⇒ 出自探针进程，
stdout 已随终端消失。

▎**那 3 次的每跳耗时无法追认。** ⛔ 不要为此再跑一轮。

**(b) 两类超时不是同一件事，读数必须标明是哪一类。**

| | 出口 / 标签 | 触发 | 服务日志实测 |
|---|---|---|---|
| asyncio 超时 | 1953 行 · `timeout` | `asyncio.wait_for(..., request_timeout)` | 08-15 `04:41:31` / `04:44:16` **两次都是这一类** |
| httpx 读超时 | 1962 行 · `ReadTimeout` | `httpx.Timeout(request_timeout)` 的 read 阶段 | 本窗口 **0 次** |

⇒ 「单跳吃掉 `min(6.0s, 剩余)`、两跳吃满 12s 总预算」那套算术是按 **asyncio
那条**算的，对 `04:41` / `04:44` 两次成立。⛔ 不要把它套到 `ReadTimeout` 那类上：
httpx 的 connect / read / write 是**各自独立**的预算、**不相加**
（见 `llm_router.py:1858-1865` 的注释，那里专门订正过一次相反的说法）。

⚠️ **不受本条订正影响**的三件（它们是配额状态与到达与否，与超时属于哪一类无关）：

```
② tencent/deepseek-v4-flash-202605        : quota 402   欠费
③ ark/doubao-seed-2-0-code-preview-260215 : quota 429   限流
⑤ zhipu/glm-4.5-air                       : 从未出现在 errors 里
```

⚠️ ⑤ 的读法要小心：`call_chain` 在 `remaining <= 0` 时 `break`
（`llm_router.py:1795-1796`），**break 之后的候选根本不会进 `errors`**。
所以「不在错误串里」≠「不在链里」—— 判链长要读
`tests/golden/llm_router_chains.txt`，那里 `review` 链 `len=5`，zhipu 是第 5 跳。

⇒ 结论不变：**REVIEW 链名义深度 5，实际可用深度 2** —— 两个能跑的跳各
`min(6.0s, 剩余)`，正好吃满 12s 总预算（`_SEMANTIC_TOTAL_TIMEOUT_SECONDS`），
中间两跳配额直拒不耗时也不产出，第 5 跳**永远够不着**。

⛔ **不要从这里推出「付费给 tencent / ark 就能把有效深度 2→4」**（organizer
2026-08-15 自行收回）。单跳 6.0s、总预算 12.0s ⇒ **无论有几个健康候选，
12s 只够 2 次真尝试**。付费改变的是「哪两个被试」，⛔ 不是「试几次」。

**(c) 根因：`thinking` 字段**被照办**了 —— 它不是这 9% 的成因。**

假设是「DeepSeek V4 Flash 默认开 thinking，思考超过单跳预算 ⇒ 超时」。
代码本来就在发那个字段（`llm_router.py:1388 / 1431` × `SLOT.REVIEW` 的
`enable_thinking: False`，三条件全真），所以真正要问的是**发了有没有被照办**。

A/B 实测（2026-08-15，prod，`aistore/DeepSeek-V4-Flash-A`，同一个真 T3 prompt，
两侧都过生产的 `_apply_slot_params`，**唯一差别是删掉 `thinking` 键**）：

```
### A 带 thinking:disabled          ### B 不带(对照)
  HTTP              200               HTTP              200
  耗时              1.71s             耗时              5.69s
  completion_tokens 141               completion_tokens 580
  reasoning_tokens  null              reasoning_tokens  402
```

⚠️ 判读表里「`reasoning_tokens` 非 0 ⇒ 字段没被照办」指的是 **A 侧**。
**B 侧的 402 是阳性对照** —— 它证明 ① 这个模型默认真的会思考
② `usage` 通道真的会把 `reasoning_tokens` 填出来。⇒ A 侧读到 null
才能读作「没思考」，而不是「没量到」（硬约束 9）。

⇒ **字段被照办，机制也被证明**（402 → null，5.69s → 1.71s）。
   A 侧 1.71s 远在 6.0s 单跳预算之内 ⇒ **thinking 不是那 9% 的成因**，
   ⛔ 别再去「补」那个字段。

**(d) 替代解释（⚠️ 待验假设，本轮⛔ 不量）**

链首之所以是 `aistore/DeepSeek-V4-Flash-A`，来自：

```
llm_router.py:353  ("aistore", "DeepSeek-V4-Flash-A"): (1.0, 3.0)
llm_router.py:476  p50 = measured[1]
llm_router.py:477  if p50 <= _FAST_LATENCY_SECONDS(=5.0): return 0   # 「实测快」→ 排链首
```

而那个 `3.0` 的来源是 `llm_capability_rank.py:153`
`statistics.median(latencies)` —— **6 个真实餐饮样本的中位数**
（注释原文 `six real restaurant cases, 2026-08-13`）。

▎**量到的是中位，用起来当成了上界** —— 本仓形态 A。
6 个样本的中位框不住 p95，而超时打的正是尾部。这能解释「平时 1.7s、
偶尔撞穿 6s 单跳预算」的 9%。

⚠️ **只是待验假设**，⛔ 本轮不量 p95（那属于「LLM 超时」那条挂账）。
⚠️ 订正一处描述：`(1.0, 3.0)` **不是**「min/max」，第二个数是 **p50 中位数**
（`_latency_band` 的局部变量就叫 `p50`）。结论不变，但理由要写对。

### 🔑 阳性对照二：那几个槽位**自己会不会抖**（不带 history 跑 8 次）

单次 A/B 判「串」默认了「不带 history 那侧是确定的」。⛔ 那个默认要验。

