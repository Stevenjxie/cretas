# 门店简称消解 —— 三个选项、代价、裁定

**日期**: 2026-08-18
**缺口**: 架构定稿 #3（实体向量检索）+ #16（模糊命中走确认式反问，⛔ 不静默丢弃）
**改动范围**: `smartbi/canonical/entity_resolution/shortlist.py`（新）、
`smartbi/gold/restaurant/restaurant_intent.py`

---

## 一句话

老板说「宝山店」，库里叫「模拟·宝山大场社区店」。
改动前**三种模型输出形态全部静默丢弃**这个槽位，老板拿到一句通用反问；
改动后唯一命中直接归一（抬头用库里的全名），多条命中列候选反问，零条走原路。

## 一、现状读数（⛔ 不从注释推断，全部 prod 实测）

### 1.1 两条真实在用的匹配路径，在真实实体上的命中率

📏 租户 MOCK_REST，`dim_store` 的 10 家**真实门店**，简称由真名**机械派生**
（去前缀 / 头两字+店 / 头三字+店 / 去店字 / 尾两字+店，⛔ 不是我挑的），
n=50。菜品 `dim_product` 10 道，n=8。

| 路径 | 在哪 | 门店 n=50 | 菜品 n=8 |
|---|---|---|---|
| `name not in available`（精确集合成员） | `_validated_llm_store_names` | **0 (0.0%)** | **0 (0.0%)** |
| SQL LIKE 双向包含 | `_canonicalize_store_mention` | 含正确 30 (60.0%)<br>唯一正确 26 (52.0%)<br>**零候选 20 (40%)** | 8 (100%) |

**那 20 条零候选全部落在「头两字 + 店」「头三字 + 店」**——
宝山店 / 徐汇店 / 浦东店 / 陆家嘴店…… 正是人最常用的说法。

- 阳性对照：库里的全名本身，两条路都命中（`exact=True` / `like_n=1`）✅
- 阴性对照：「量子纠缠火箭发射器」，两条路都不命中（`exact=False` / `like_n=0`）✅

⚠️ **菜品侧在 MOCK_REST 上量不出缺陷**：菜名都是 3~4 字（凉拌木耳 / 水煮牛肉），
去一个字仍是真子串 ⇒ LIKE 必过。
▎这是「让闸不可能红」的验收环境，⛔ 不能据此说菜品侧没问题。

### 1.2 改动能覆盖多少租户（**这是本卡最重要的边界**）

📏 `dim_store` **全表 10 行**，全部属于 MOCK_REST。

判据用的是**与 RLS 无关**的统计量（`ANALYZE` 后 `pg_class.reltuples` = 10，
`pg_stat_user_tables.n_live_tup` = 10，`schemaname='public'` 限定），
以及逐租户 `set_config` + 无 WHERE 的 RLS 可见行数：

```
MOCK_REST 10 | RES_3101_009 0 | QHJ_PROD 0 | DEMO_REST 0
R_XMX_CHAIN 0 | R_GML_DEMO 0 | __不存在的租户__ 0（阴性对照）
```

⇒ **今天只有 MOCK_REST 走得到这条路。** 其余租户 `available_stores` 为空元组，
本改动的第一行就 `return None`，行为与改动前逐字相同（有阴性对照钉着）。

🔴 **顺带发现一条过期读数（另一条线的账，本轮不动）**：
`restaurant_ops_router.py:2202-2204` 有一条 **2026-08-17** 的注释写着
「RES_3101_009 38 家 / DEMO_REST 27 / R_XMX_CHAIN 1 / R_GML_DEMO 132 = 198 个真店名」，
它在 `smartbi_prod_db` 上**今天已经不成立**。那条注释正在支撑一条现行的判据设计。

## 二、`entity_resolution/` 能不能接（跑一次让它自己说，⛔ 不读注释下结论）

### 2.1 能接，而且效果是决定性的

📏 prod 直接调 `EmbeddingAgent.resolve`，对 §1.1 那 **20 条 LIKE 零候选**：

```
top-1 正确 20/20 (100.0%)      单次墙钟 中位 10ms / 最大 142ms（冷）
正确命中 cosine   0.608 ~ 0.796
正确命中的次优    0.421 ~ 0.642
阴性对照「量子纠缠火箭发射器」 top1 sim=0.232, matched_entity_id=None ✅
embedding 服务    768 维, 首次 172ms / 再次 10ms（服务侧有缓存）
```

### 2.2 ⛔ 但**不能整链接** `make_default_orchestrator` —— 三条结构性理由

1. **`EmbeddingAgent.ship_threshold = 0.90`，而实测正确命中最高 0.796 ——
   一条都到不了**。整条链会一路降到 `admin_queue`，**一次都不会 ship**。（实测）
2. `EntityResolutionOrchestrator.resolve()` 会往 `entity_resolution_history` 和
   `entity_resolution_admin_queue` **写行**。那是数据治理的审计链路，
   ⛔ 不该挂在一次问答的读路径上（每问一句写一行待人工审核）。（读代码）
3. 它按 `dim_<entity>` 自己查库；而读路径**手上已经有**候选清单
   （`_load_store_options` 刚读出来的）。再查一次是第二份来源。（读代码）

⇒ **复用零件、不复用编排**：`EmbeddingAgent._cosine` / `EmbeddingCache` /
`normalize_for_dim` 三样都是 import 过来的，⛔ 没有第二份实现。

## 三、三个选项

| | 做法 | 门店简称 n=20 | owner 定稿原文 n=2 | 代价 |
|---|---|---|---|---|
| **A** | 确定性：去尾缀 + 归一 + 双向包含 | **20/20 唯一** | 1/2 | 纯字符串，0ms，零依赖 |
| **B** | 向量：embedding 余弦 top-1 | 20/20 | **2/2** | 冷 172ms / 热 10ms；依赖 9090 gRPC |
| **C** | **A 先行，A 零候选才走 B** | 20/20 | 2/2 | A 覆盖的不付 B 的钱 |

**owner 定稿原文那两组**（逐字照抄，⛔ 不是我编的）：

```
'山川店'         vs '山川蒙湖店'         A ✅        B ✅ sim=0.841 margin=0.339
'青花椒二人套餐'  vs '鲜花椒大人二人套餐'  A 🔴 0 候选  B ✅ sim=0.860 margin=0.375
```

第二组**与候选没有任何子串关系** —— A 从原理上做不了，只有向量能。
反过来，A 能覆盖的那 20 条不该去付向量的钱。

### 裁定：**C**

理由，按取舍顺序（能不能决定 > 数字准不准 > 覆盖得全不全）：

1. **只做 A 会漏掉 owner 亲自举的那一类**（同音/近义改写）。那一类没有替代解法。
2. **只做 B 是过度工程**：实测 20/20 都被 A 接住，B 一次都用不上；
   而 B 依赖一个会挂的外部服务（挂了就是零候选，见 §五 未做）。
3. **C 与 `entity_resolution` 自己的链形一致**（deterministic → embedding），
   ⛔ 不是新发明的形状。

## 四、判据从哪来（⛔ 不是拍的），以及能让它红的对照

```
SIM_FLOOR  = 0.55   落在「最低正确 0.608」与「最高无关 0.232」之间的空隙里
SIM_MARGIN = 0.08   分「唯一」和「多条」
```

⚠️ **`SIM_MARGIN` 在实测样本上一次都没被触发过** —— 批 1 的 20 条全被 A 段接住，
批 2 两条 margin 都 > 0.33。它是**保守侧设定，没有实测支撑**。
这句话必须写在这里，否则下一个人会以为它也是量出来的。

**能让每条判据红的对照**（14 条变异，逐条见 PR 描述的变异表）：

| 判据 | 让它红的对照 |
|---|---|
| `SIM_MARGIN` | `test_two_equally_close_candidates_ask`（构造两个同样近的候选） |
| `SIM_FLOOR` | `test_scores_below_the_floor_decide_nothing` + `M5 下界形同虚设` |
| 多条要反问 | `M18 歧义时也直接归一(替老板挑一家)` → 打红 4 条 |
| 明说全店不许收窄 | `M16` → 打红 `test_an_explicit_all_store_scope_is_never_narrowed_to_one_store` |
| 接线真的在跑 | `M2 生产入口不再计算消解(整段删掉)` → 打红 5 条 |

⚠️ 「多条命中」这一态**有真实数据支撑**，⛔ 不是构造的：MOCK_REST 上
「社区店」对上 **4 家**（实测 `like_n=4`），prod 端到端已跑通反问原文。

## 五、prod 真跑（老板会看到的原文）

代码经旁路目录 `importlib` 加载，⛔ 未部署、⛔ 未覆盖线上文件。
自检三行贴出模块来源 + 真跑一次消解函数（找到标记 ≠ 它能跑）。

```
[简称-唯一] 宝山店最近30天营收多少
  → **模拟·宝山大场社区店最近30天销售情况：** 模拟·宝山大场社区店 — 营收 ¥2,211,579.00
[简称-唯一] 徐汇店 → 模拟·徐汇美罗城店 — 营收 ¥2,222,858.00
[简称-唯一] 浦东店 ×3 → 模拟·浦东金桥社区店 — 营收 ¥2,182,434.00（三次一致）
[简称-唯一] 长宁店 → 模拟·长宁龙之梦店 — 营收 ¥2,197,893.00
[简称-多条] 社区店 → 你说的「社区店」，我这边有 4 家对得上：
             模拟·宝山大场社区店、模拟·普陀真如社区店、模拟·浦东金桥社区店、
             模拟·闵行莘庄社区店。你要看哪一家？
[阳性-全名] 模拟·宝山大场社区店 → 同一个数 ¥2,211,579.00 ✅
[阴性-无关] 量子纠缠火箭发射器 → 不落任何门店槽 ✅
```

**判据 9/9 绿。** 抬头用的是**库里的全名**，⛔ 不是老板打的字。
简称问出来的数与全名问出来的数**逐字相同**（¥2,211,579.00）——
这是「归一到了对的那家店」最硬的旁证。

🔴 **「浦东店」连跑 3 次是有理由的，⛔ 不是凑数**：
真 LLM 对同一条问句实测跑出过**三种**输出形状，而第三种曾经让这条问句
从 ✅ 变 🔴。▎一次绿证明不了「接住了」，只证明这次抽到的是好那一种。

## 六、真正的缺口比我一开始读的更深（⚠️ 值得单独记）

owner 定稿写的是「**归一（最高频）：LLM 顺手改写了名字 → 查库查不到**」。
我一开始把它读成「模型不会归一」，于是单测的桩喂了 `store: "宝山店"`。
**单测全绿，prod 端到端 3/3 全红。**

prod 打出的原始 plan 是：

```
Q: 宝山店最近30天营收多少
   store = "模拟·宝山大场社区店"     ← 模型看得到门店清单, 自己归一好了
   store_scope = "single"  clarification_needed = false
```

⇒ 丢它的不是「查不到」，是 **`_verbatim_entity` 反幻觉守卫**：
那个**完全正确**的全名不是问句原文子串，当场被丢。

同一条问句实测跑出**三种**模型输出，三种都让 `_validated_llm_store_names`
返回空：

| # | 模型给的 | 被谁丢的 |
|---|---|---|
| ① | `store="模拟·浦东金桥社区店"` | `_verbatim_entity`（不是原文子串） |
| ② | `store="浦东店"` | `name not in available` |
| ③ | `store=null` + `missing_fields=["store_scope"]` | 模型没提名 → 补默认全店 → 下游口径闸拦下 |

⇒ 归一**只写一处**（`_semantic_spec_from_t3` 里那一格），三种形态一格全接住。

⚠️ 我第一版为 ① ② 各写了一条分支，**变异对照当场证明它们不红** ——
加了 ③ 那一格之后前两条成了同一个判据的第二、第三份（形态 D）。已删。
▎变异不红先证明变异生效了；生效了还不红，那才是「这段代码没在守东西」。

## 七、未做，显式登记（⛔ 不是豁免，是留痕）

| # | 未做的 | 为什么 | 什么条件下再做 |
|---|---|---|---|
| 1 | **两句消歧措辞没合成一句** | 仓里**已有一份**消歧（`_build_spec` 的 `ambiguous_partial_store`，措辞「请问您指的是哪家「X」？」）。两份触发条件不同（它要求 `llm_store_scope=="single"` 且模型一家没选），本轮做成**既有那份先行**，我的只补它够不着的。合并要改 `tests/test_restaurant_intent_clarification.py` 里钉着字面量的断言，不在本轮范围内 | 下一轮碰那个测试文件时，把措辞收敛到 `store_ambiguity_question` 一处（模板已抽出为 `_PARTIAL_STORE_ALIAS_TEMPLATE`），并把「先行」那道判据删掉 |
| 2 | **菜品侧没接** | MOCK_REST 菜名 3~4 字，LIKE 100% 命中 ⇒ 量不出缺陷。为一个不复现的形状做工程 = 反目标 | 拿到一个菜名够长/够脏的租户（`dim_canonical_dish` 今天全库 0 行），先按 §1.1 同样的机械派生法量一次命中率 |
| 3 | **归一后模型仍要求澄清时，没有清掉它** | prod 9 次里出现 1 次（「浦东店#3」门店已归一，模型自己又问「你想看哪家浦东的门店？」）。样本 1/9，且清 clarification 会成为第四个「补默认」载体 | 观测到 ≥3/10 且能证明模型的 `missing_fields` 只剩门店时 |
| 4 | **LLM 归一到一个与老板原话不一致的门店时，没有交叉反问** | 实测 3/3 两侧一致，没有分歧样本。为只有想象支撑的形状建检测器 = 反目标 | 生产日志里出现「模型给的全名 ∉ 我消解出的候选」时 |
| 5 | **embedding 服务挂了没有单独告警** | 挂了 = 零候选 = 走今天的路（fail-open），不会答错 | 若将来把向量段变成承重路径（例如菜品侧接上），要按三态 rc 加「没量到」告警 |
| 6 | **候选 > 60 家的租户不做向量段** | 一次问答要为每个候选算一次 embedding。⛔ 不截断后照算 —— 截断会把「他要的那家排在上限之外」变成看不见的错答 | 有 >60 家门店的租户真的走到这条路时，改成 pgvector 侧检索而不是逐个 embed |
