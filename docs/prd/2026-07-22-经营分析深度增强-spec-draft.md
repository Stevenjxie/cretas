## 客户原话（需求本质）

> 当前能根据已有数据分析原因、回答解决该问题的大方向……部分场景下的回答比较初级，只能告诉决策者：这里出了问题。如果能在互联网检索类似问题的解决方案、引用权威专家的方法论、计算分析各种措施的有效性以及置信度、推演各种措施落地后的结果，将解决方法呈现在决策者面前供其挑选，白垩纪AI就有重大意义。**需要避免客户复制这块的结论去粘贴在其他 AI 上询问解决方法**——那样系统就只是个数据库。

## 问题定义

现状：诊断层（"毛利率 51%，损耗点在活鱼边角"）已达标；处方层（"具体怎么办、哪个方案期望收益多大、置信度多少"）缺失。客户明确把处方层视为产品护城河。

## 方案分层（按投入递增，可独立交付）

### L1 — 方法论知识库注入（~1-2 周）
- 建 `restaurant_playbook` 知识表（问题模式 → 行业标准打法 → 适用前提 → 风险 → 验证方式），内容由公开餐饮管理方法论人工整理（30-50 条核心 playbook 起步），走现有 food_kb 的 RAG 基建（pgvector 已就绪）。
- 诊断回答命中问题模式时，追加「行业参考做法」段落，标注出处与适用前提。
- **不引入外网实时检索**，规避可控性与合规问题；知识库内容可审计。

### L2 — 措施效果量化（~2-3 周，依赖 L1）
- 对 playbook 中可量化的措施（如"高毛利小食搭套餐"），用租户自身历史数据回测：套餐带动系数、毛利弹性等，输出「预期区间 + 数据支撑度（高/中/低）」。
- 硬约束：数据不足时明确说"该措施在您的数据里无法回测"，沿用现有 fail-closed 风格；推测部分显著标识（呼应 Sheet「推测部分必须醒目标识」）。

### L3 — 措施推演沙盘（~4 周+，独立立项）
- What-if 引擎（backend/python/smartbi/api/whatif.py 已有雏形）接入经营分析：选定措施 → 参数化假设 → 推演营收/毛利曲线 → 对比呈现供决策者挑选。

## 非目标
- 不做开放互联网实时检索（结论不可审计、延迟不可控、有引用合规风险）。
- 不替代决策者：所有处方标注前提与风险，保留人拍板。
