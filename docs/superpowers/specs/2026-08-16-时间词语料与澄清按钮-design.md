**日期**: 2026-08-16
**状态**: 设计已批准（owner），待写实现计划
**触发**: 生产日志实测到「另一条对话的计划被当成你的答案」

## 一 · 问题（全部为实测，⛔ 无推断）

### 现象

2026-08-16 生产日志：

```
17:12:48  判定「没答到」, 已逐出计划缓存: query=本月
17:13:10  zero-token plan-cache hit: authority=validated_plan_cache
          intent=RESTAURANT_OPS_WASTAGE_TOP  clarification=False  query=本月
```

一条链问「损耗」→ 点「本月」→ 计划以字符串 `本月` 为键写入缓存；
另一条链问「门店排名」→ 点「本月」→ **命中前一条链的计划**。

### 「本月」从哪来 —— 它是**产品自己发的按钮**

`restaurant_intent_service._clarification_followups`：

```python
if spec.clarification_question == TIME_CLARIFICATION_QUESTION:
    return [{"label": window, "question": window}          # ← question 就是那两个字
            for window in ("本月", "上个月", "最近7天", "最近30天")]
```

⇒ 这 4 个串**每次时间澄清都会产生一个**，是全系统最高频的缓存键；
而它们每一个的含义**完全取决于上一轮在澄清什么**。

▎**最容易被缓存的那批串，恰好是最不该被缓存的那批。**

### 为什么现有守卫拦不住

计划缓存键：

```python
def _semantic_plan_cache_key(factory_id, query):
    return (factory_id, _normalize_exact_phrase(query), version)   # ⛔ 不含会话
```

写入侧只有一道守卫：

```python
and not _plan_time_slot_came_from_history(parsed, norm_query, history)
```

它的 docstring 自己写明了假设：

> Entities are safe by construction（`_verbatim_entity` 强制菜名/门店是问句字面子串）
> **TIME is the exposed slot**

⇒ 作者**枚举了暴露的槽位**。实测 18 个计划槽位里：

```
✅ 有守卫  4 个：dish / store / stores（字面）+ time_range
🔴 无守卫 14 个：intent · requested_metrics · dimensions · analysis_action ·
                aggregation · comparison · store_scope · wants_margin …
```

「本月」泄漏的是 **`intent`** —— 既不是实体也不是时间，三道守卫一道都不管。

⚠️ **同一失败形状在那份 docstring 里已经写过一次**（换的是 time 槽）：

> A asks "上个月怎么样" then "营收怎么样" → plan cached under the bare sentence
> "营收怎么样" → B, in a brand-new session, **silently gets LAST MONTH**

上一次的修法是「给那个槽加一道守卫」⇒ 它在下一个槽上又长了出来。**这是第二次。**

### 这个缓存值多少（实测，决定取舍）

```
标称 TTL              6 小时
进程存活中位          0.48 小时 = 29 分钟   (8-09~8-14, 116 次重启, ⛔ 不含当日部署)
活过 6 小时的比例      5/115 = 4%
workers               2  ⇒ 缓存每 worker 一份
实测命中率            2.9%   (电池负载, cache_hits 6 / fresh_parses 201, **偏高估计**)
T3 编译耗时           REVIEW 2.09s / MAPPER 2.14s 中位 (prod 各 3 次)
```

⇒ 期望收益 ≈ `2.1s × 2.9% ≈ 每次问答 60 毫秒`。

⚠️ **一格没量到**：真实用户句子复现率 —— `smart_bi_chat_session` 0 行
（会话在 Java 侧），⛔ 不用推断顶替。故 2.9% 只能当上界。

## 二 · 设计（owner 裁定的三段式）

```
① 确定性规则识别时间词
   ├─ 识别到 ──────────────────────────► 直接进后续 LLM 完整句子理解
   └─ 没识别到
        ② 交 LLM double check
           ├─ LLM 认出来 → 规范化 → **写入时间词语料库** ──► 进后续理解
           │                              └─(人工晋升)──► 确定性规则词表
           └─ LLM 也没认出 ⇒ 这句话确实没有时间词
                ③ 给按钮 → 点击/自定义 → **合成完整句子** ──► 进后续处理
```

### ①② 今天已经在跑，⛔ 不需要改

时间澄清的触发条件本身就是「两层都说没有」：

```python
and not time_phrase                                    # LLM 没认出
and _resolve_sales_date_range(query)[1] == "全部历史"   # 确定性层也没认出
and not clarification_needed
and not time_range_defaulted
⇒ clarification_question = TIME_CLARIFICATION_QUESTION
```

LLM 的规范化也已存在（`_parse_t3_time_range`）：

```
{'type':'relative','unit':'day','count':30} → '最近30天'
{'type':'named','value':'this_month'}       → '本月'
```

⇒ **缺的只有两件**：②的后半（语料库 + 晋升）、③的合成。

## 三 · 要做的三件

### 件 1 · 澄清按钮发完整句子

```python
# 现在
{"label": window, "question": window}                    # "本月"
# 改后
{"label": window, "question": f"{window}{seed}"}         # "本月米饭的销量是多少"
```

`seed` = `tiered_answer` 的 `query` 参数（**已在作用域内，只是没用**）。
门店那组同理：`{"label": "全部门店", "question": f"全部门店{seed}"}`。

**为什么前置是安全的**：走到时间澄清的前提就是「两层都没认出时间词」
⇒ seed 里按定义没有时间段要替换，⛔ 不需要 `_split_time_scope` 定位。

### 🔴 本卡最大的一个洞（最终评审抓到，Critical）

**这张卡从头到尾只写了产出侧，没有一个字提到谁消费这些按钮。**
grep「continuation / 延续 / APPROVED_TIME_ANSWERS」在设计卡和计划里 = **0 hits**。

而接收侧是**精确相等**匹配：

```python
# restaurant_intent.py:4331
if answer_normalized in {_normalize_exact_phrase(w) for w in _APPROVED_TIME_ANSWERS}:
    return matched_code          # ← 零 LLM 确定性延续
```

实测（带阳性对照，原问句取自 `_APPROVED_EXACT_ROUTES`）：

```
旧行为 answer='本月'            →  4/4 HIT      零 token 直接答
新行为 answer='本月哪个菜卖得好'   →  0/4 None     每次点击退回 T3 编译 ~2.1s
                                              LLM 挂掉时整条链断
```

▎**为省 60 毫秒的缓存命中，换来每次点击 2.1 秒 —— 净效果是负的。**

⇒ 件 1 的范围必须扩到**三个消费点**：`_approved_exact_continuation_route`、
`_trusted_named_dish_button_continuation`、`_parse_continuation` 的拼接。
解法是一个共用的 `_button_answer_fragment(original_query, answer)`，
判之前把合成句还原成片段（⛔ 不在三处各写一遍 —— 那是形态 D）。

⚠️ 同一个洞的第二半在**前端**：`mobile-rest-ai/src/api.ts` 的
`normalizeFollowups` 取 `rec.question ?? rec.text ?? rec.label`，
按钮上显示的就是 `question` ⇒ 我在后端断言了一路的「`label` 不变」，
**在真实载体上不成立**，按钮文字会变成整句。

**判据（写给下一次）**：**改一个东西「发什么」之前，先找出谁按精确相等消费它。**
`grep` 那个值的**字面量**，而不是 grep 函数名 —— 消费方不会提到产出方的名字。

实测（16/16 正例）：

```
'米饭的销量是多少' + 本月    → '本月米饭的销量是多少'      自足 ✅ 窗口='本月'
'哪个菜卖得好'   + 最近30天  → '最近30天哪个菜卖得好'      自足 ✅
两轮澄清: 时间→门店         → '全部门店本月米饭的销量是多少' 自足 ✅
   （门店段在时间段之前，与 `_time_window_switch_followups` 的
     `{store}{time}{body}` 顺序一致）
```

**准入（两条，任一不过就退回现在的行为，⛔ 不发一个更坏的串）**：

1. `seed` 非空 —— 否则合成句退化成光秃秃的词（实测：`seed=''` 时自足性检查会放行，
   因为「本月」确实解得出窗口，所以这一条**不能靠自足性检查兜**）
2. 合成句自足 —— 🔴 **按钮种类不同，检查的东西不同**：

   | 按钮 | 检查 |
   |---|---|
   | 时间 | `_resolve_sales_date_range(合成句)[1] != "全部历史"` |
   | 门店 | `_split_store_scope(合成句, spec.store_options)[0] == 那个前缀` |

   ⚠️ **本卡第一版把「解得出窗口」写成了通用准入 —— 那是错的**，写计划时实测发现：

   ```
   '全部门店米饭的销量是多少'          窗口='全部历史'
   '青花椒南方百联店米饭的销量是多少'    窗口='全部历史'
   ⇒ 照第一版写, **每一个门店合成句**都被判不自足 → 全部退回光秃秃的词
   ⇒ 门店那组等于没改, 而我会以为改好了
   ```

   ⚠️ 时间那条在**现有 4 个按钮词**下恒真（`本月`/`上个月`/`最近7天`/`最近30天`
   拼上任何 seed 都解得出窗口）。它**不是**恒真式 —— `第三季度末` / `某个月`
   实测解出「全部历史」⇒ 它守的是「将来往按钮词表里加了解析器不认识的词」。
   ⇒ 测试**必须**用那种词让它红一次，否则这条准入没被验证过。

⛔ **不加**「合成句里只能有一个时间段」那条 —— 理由**不是**「那种 seed 到不了」
（实测 `最近损耗怎么样` 在确定性层就是 `全部历史`，若 LLM 也没认出「最近」，
它**到得了**），而是**到了也无害**：

```
seed='最近损耗怎么样'  点「本月」 → '本月最近损耗怎么样'  窗口='本月'   ← 实测
```

两层都没认出「最近」⇒ 系统对它的判定就是「不是时间词」⇒ 合成句解出的
正是用户点的那个窗口。⚠️ 反过来说，只要有任一层认出「最近」，
时间澄清压根不触发 —— **两条路都不产生坏结果**。

### 件 2 · 时间词语料库

**记什么**：确定性层没认出、而 LLM 认出了时间的那些轮次。

| 字段 | 说明 |
|---|---|
**表结构照抄 `ai_promoted_routes` 的形状**（`V20261030_01`，已核实），
⛔ 不另发明一套：

| 字段 | 说明 |
|---|---|
| `domain` VARCHAR(32) | 与 `ai_promoted_routes` 同名同义，留出多业态 |
| `normalized_phrase` TEXT | 归一化后的原问句；与 `domain` 组成 **PK**（同句只一行） |
| `factory_id` | 哪个租户遇到的（首次） |
| `raw_query` TEXT | 原问句原文（**人工晋升时靠它认出是哪个词**） |
| `llm_phrase` VARCHAR(64) | LLM 规范化后的短语（`最近30天` / `本月`…） |
| `llm_time_range` JSONB | LLM 原始结构，留证 |
| `hit_count` BIGINT | 同一句重复只累加，⛔ 不重复插行（与既有表同名同义） |
| `created_at` / `last_seen_at` TIMESTAMPTZ | |
| `reviewed_by` VARCHAR(64) / `promoted_at` TIMESTAMPTZ / `promoted_note` TEXT | 人工晋升后回填；`promoted_at IS NULL` 即「积压」 |

⚠️ **⛔ 不记 LLM 认出的字面 span** —— T3 契约里没有这个字段，加它要改 prompt
（本仓有先例：改 named 词表导致模型降级）。人工晋升时读 `raw_query` 就能认出是哪个词。

**写在哪一步**：`restaurant_intent.py:2261` 那一支 —— 它**已经**在做这个判别，
⛔ 不需要新增条件（已核实原文）：

```python
if time_phrase and _resolve_sales_date_range(query)[1] == "全部历史":
    effective_query = f"{query} {time_phrase}".strip()
    # 走到这里 = 用户原话解不出窗口, 窗口是 `time_phrase` 给的。
```

▎「用户原话解不出窗口，而 LLM 给出了窗口」—— **正是语料的入库条件**。
⚠️ 写库**必须 fail-open**：记语料失败 ⛔ 不许让一次问答失败，但**要打 warning**
—— 否则「语料一直是空的」会长得和「没有这类问句」一模一样。

### 件 3 · 人工晋升 + 积压告警

**晋升 = 产出代码补丁，人 review 后合并**（owner 选的 B）。

- CLI 挂在既有的 `scripts/restaurant-intent-promote.py` 下（`--list-time-phrases` /
  `--mark-promoted <id>`），与整句晋升同一个入口
- 晋升动作本身是**人改 `restaurant_ops_router` 的时间词表 + 补测试**，
  CLI 只负责「告诉你该加哪些词」和「记下已处理」

**为什么是 B 不是「写库运行时查」**（实测支撑）：

```
404 条真实问句: 规则解得出时间 301 (75%) / 解不出 103 (25%)
而那 103 条**逐条读下来绝大多数根本没有时间词**
（「哪个菜卖得好」「加权毛利率是多少」「员工排班情况」「你们能做什么」）
⇒ 真正「有时间词但规则没认出」的只有寥寥几类（最近 / 全月 …）
```

⇒ 时间词是**封闭语法 + 少量格式变体**，会饱和。B 的发版成本是一次性的；
而「运行时查库」会让 `_resolve_sales_date_range` 从纯函数变成
「取决于哪台机器的表」，刚建的日历半年 / 今天到现在那几条闸**当场失去意义**。

**失败模式对比**（这是选 B 的第二个理由）：

| | 没人管的后果 |
|---|---|
| B | 语料堆着、规则不动 → **LLM 照样答对**，只多花一次调用 ⇒ 优雅降级 |
| 查库 | 有人加错一个词 → 所有含它的句子**立刻**在生产上解错窗口，无 review、无闸 ⇒ 静默且面广 |

**积压告警**（B 的前提是「有人真的会去晋升」，而本仓有反例：
`ai_promoted_routes` 从 7-27 至今**只有 8 条**，且是 seed + 一次批量补）：

- **单独一个 `scripts/cron/time-phrase-backlog-daily.sh`** —— `scripts/cron/` 下现有
  8 个脚本，每个只管一件事（已核实），⛔ 不塞进 provider 健康那个
- `promoted_at IS NULL` 的条目 **> 20 条** ⇒ 告警（owner 定，2026-08-16）
- ⚠️ 三态 rc（硬约束 4）：`rc=2` = 查不到语料表（**没量到**），
  措辞必须与 `rc=1`（有积压）不同

## 四 · 这三件各自解决什么

| | 缓存串话题 | 语料价值 | LLM 成本 |
|---|---|---|---|
| 件 1 按钮发完整句 | ✅ 根治（不再有「本月」这种键） | ✅ 记的是完整自足句 | — |
| 件 2 语料库 | — | ✅ 积累时间词 | — |
| 件 3 晋升 | — | — | ✅ 词进规则后不用再调 LLM |

⚠️ **件 1 是唯一解决今天那个缺陷的**，件 2/3 是 owner 要的长期语料能力。

⇒ **拆成两个实现计划，⛔ 不合并**：

| 计划 | 内容 | 为什么单独 |
|---|---|---|
| **计划 1** | 件 1（改一个函数 + 闸） | 纯 Python、零迁移、可当天上线，**今天那个缺陷等不起** |
| **计划 2** | 件 2 + 件 3（建表 + 写入 + CLI + 跑批） | 带 DB 迁移，节奏不同；且它**不依赖**计划 1 |

两者无先后依赖，但**计划 1 先上** —— 它同时改善计划 2 的语料质量
（进语料的将是完整自足句，⛔ 不是「本月」这种串）。

## 五 · 测试与判据

### 件 1

| 断言 | 变异（必须红） |
|---|---|
| 澄清按钮的 `question` 是完整句 | 改回发光秃秃的词 |
| 合成句自足 | 把 seed 拼到时间词**后面**（语序坏掉） |
| `seed` 为空 ⇒ 退回旧行为 | 去掉非空检查 |
| 门店按钮同样合成 | 只改时间那组 |
| **AST 守调用点** —— 合成结果真的进了 `question` | 算了但没用上 |

⚠️ 阳性对照：正常 seed 下**确实**产出了完整句（否则「不再有光秃秃的词」
在「按钮压根没生成」时也成立）。

### 件 2

- 规则没认出 + LLM 认出 ⇒ **写一行**；⚠️ 阴性对照：规则认出时 ⛔ 不写
- 同一句重复 ⇒ `hit_count` 累加，⛔ 不新增行
- 写库抛异常 ⇒ 问答**不失败** 且 **打 warning**（变异：把 warning 去掉 ⇒ 闸红）

### 件 3

- 积压 > 阈值 ⇒ 告警；⚠️ 阴性对照：积压为 0 时 ⛔ 不喊
- `rc=2`（表查不到）**主动构造一次** —— 三态的价值全在第三态，
  而第三态平时永远不会自然发生

### 全局

照抄 CI 的 pytest 命令跑全量；⛔ 不自拟目录。
**所有承重断言写在 `tests/` 下** —— 本轮实测过：手工探针里的断言
CI 抓到率只有 1/8。

## 六 · 明确不做

- ⛔ **不删计划缓存** —— 它与飞轮语料是**两套东西**（前者进程内 29 分钟，
  后者数据库永久+人工晋升）。件 1 之后进缓存的都是自足整句，风险已除
- ⛔ **不给 `_split_time_scope` 加词** —— 那是维护第二份时间词定义（形态 D）。
  时间词的唯一权威是「确定性规则词表 + LLM 兜底」这条链
- ⛔ **不改 TTL** —— owner 已裁定「29 分钟够了」；且实测 TTL 不是绑定约束
  （进程活不到 6 小时的占 96%）
- ⛔ **不让 LLM 返回时间词的字面 span** —— 要改 T3 契约，本仓有先例（改 named
  词表导致模型降级成 relative，「上个季度」5/5 答错窗口）

## 七 · 已知盲区（登记，⛔ 非豁免）

1. **真实用户句子复现率没量到**（会话表 0 行）⇒ 缓存命中率 2.9% 只是上界
2. **件 1 只覆盖时间 / 门店两组按钮，⛔ 不动 `clarification_options`**（LLM 自撰选项）。
   ⚠️ 本卡第一版写的是「先按同一条准入处理」—— 写计划时发现那句话**没有内容**：
   自撰选项是「先看营收」这种任意短语，**不存在**对应的自足性概念，
