**日期**: 2026-05-31
**作者**: Steve + Claude (brainstorming + 28-agent 对抗审计)
**状态**: 设计待审
**环境**: prod F006 (叮咚卤味厂真实数据)

---

## 0. 一句话

出成率数学**早已验证可算**(猪舌 998kg→382.08kg 累计出成率 **0.3828**,人工算+已验证,见 `project_2026_05_29_f006_production_traceability_test`)。本设计**不碰算法**,只解决**报工体系**:让"投入/产出"数据能被采上来、喂给算法、进看板。

---

## 1. 背景与问题(问题在报工体系,不在算法)

prod F006 全链路走查 + 后端深挖确认,Cretas 有**三套互不连通的报工体系**,导致出成率有数学没数据:

| 体系 | 现状 | 致命缺陷 |
|---|---|---|
| ① `WorkProcessTask`(工序任务状态机) | 有工序链模板/spawn/processOrder/状态机,卤猪舌已配 7 道 | **只记 `actualQuantity`(产出),无投入字段** → 单工序出成率无数据源 |
| ② `process-tasks`(累计报工) | RN 前端在用 `/process-work-reporting/normal`,累计产出+审批 | 无投入、无良品 |
| ③ `ProcessingStageRecord`(加工环节) | 有 `inputWeight`/`outputWeight` | `@PrePersist` 强制反算 `lossRate` **覆盖出成率,且 yield>1(保水)被压成负损耗**;独立手工录入,工人用不了 |

**RN 现状**:工人 `operator` 角色只能扫批次条码报整批,**看不到逐道工序报工**;逐道报工只有车间主任(三步报工代报)能用。

**根因**:三套都不是"采集投入+产出双量喂给出成率"而设计的,且工人角色被锁在最弱的一套。

---

## 2. 设计原则(经 28-agent 对抗审计修正)

审计推翻了最初"全新三层、三套全废、大爆炸"的方案(4/5 lens REWORK,16/23 验证为真:重复造已有 `ProductWorkProcess`/`WorkProcessTask`、carryover 双计、kg→盒量纲、大爆炸打断 RN/AI工具/Traceability、工人填双量违背防呆)。修正后原则:

1. **复用不重造**:配置层用现有 `WorkProcess`+`ProductWorkProcess`(已数据驱动,卤猪舌 7 道现成);任务层用现有 `WorkProcessTask`(状态机/spawn/processOrder)。**只新建 1 个实体:`ProductionReport`(报工事实层)**。
2. **角色分工调和"张权要全数据" vs "工人防呆"**(已与 Steve 确认):
   - **仓库/班长** 在**领料环节**记 `出库量`+`投料量`(张权 A1 双量,"每个数据都需要")
   - **产线工人** 在**报工环节**只报**每道产出量**(防呆:"就告诉他这步收多少就行")
   - **系统**自动算 单工序/整批出成率 + 每日结清 + carryover
3. **出成率直接存双向值**:`yieldRate = 产出/投入`,允许 >1(滚揉保水 1.35)和 <1(损耗)。**绝不用 lossRate 反算**(绕开 `ProcessingStageRecord` @PrePersist 坑)。
4. **配置即数据**:工序链是实体+API,手动/Canvas/AI 写同一套底座(战略要求)。
5. **不大爆炸迁移**:`ProductionReport` 与老三套**并存**,老的继续转(RN/AI工具/Traceability 不断),新数据逐步接,验证后再逐步废老的。
6. **回写挂现有路径**:批次产出回写挂现有 `SupplyChainOrchestrator.onBatchCompleted`,不新造。

## 3. Phase A — 详细设计(本 spec 实施范围)

Phase A = **报工事实层 `ProductionReport` + 角色分工数据流 + 出成率派生 + carryover/每日结清 + 回写挂钩 + API**。后端为主,API 可独立验证。

### 3.1 数据模型

**复用(不动,仅加可选列)**:
- `WorkProcess`(工序定义):加可选列 `standard_yield_min` / `standard_yield_max`(标准出成率区间,张权 A7 越界告警用)、`needs_input`(该工序是否需投入量)、`output_unit`(产出单位,处理 kg→盒)。
- `ProductWorkProcess`(产品工序链):不动(已是配置层)。
- `WorkProcessTask`(工序任务):不动(任务状态机)。

**新建唯一实体 `ProductionReport`(报工事实,append-only)**:

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String(36) UUID | |
| factory_id | varchar(50) | |
| production_batch_id | Long | 所属批次 |
| work_process_task_id | Long | 对应工序任务(关联任务层) |
| process_order | Integer | 工序序(冗余,便于按序聚合) |
| product_type_id | varchar | |
| input_quantity | NUMERIC(14,3) | **投入量**(来自领料环节/上游,见 3.3) |
| input_unit | varchar(16) | |
| output_quantity | NUMERIC(14,3) | **产出量**(工人报) |
| output_unit | varchar(16) | 可能 ≠ input_unit(kg→盒) |
| carryover_quantity | NUMERIC(14,3) | 本道余料结转(张权 A2b),系统算 |
| source_batch_refs | jsonb | 跨批料来源批+用量(张权 A3 双标注) |
| operator_id | Long | 报工人 |
| work_minutes | NUMERIC(8,2) | 工时(选填) |
| qc_pass | Boolean | 质检(选填,needs_qc 工序必填) |
| labels | jsonb | 标签字段(温度/盐度等,配置驱动) |
| settled | Boolean | 是否已结清(每日结清打标) |
| settled_at | timestamp | |
| reported_at | timestamp | append-only 时间戳 |
| created_at/updated_at/deleted_at | | BaseEntity |

**关键**:`yieldRate` **不存**(派生:读时 `output/input`),避免 ProcessingStageRecord 那个 @PrePersist 反算坑 + 避免双计。一道工序可 **N 条** report(分次报工),per-step yield = `Σoutput / Σinput`。

### 3.2 出成率派生算法(不存,读时算)

- **单工序出成率** = `Σ(该工序所有 report.output) / Σ(该工序 report.input)`。允许 >1 / <1。
- **整批累计出成率** = `末道工序总产出 / 首道工序总投入`(猪舌:382.08/998 = 0.3828,跟金标准对上)。
- **kg→盒 量纲**:跨单位工序(装盒 kg→盒)的出成率标记为 `不可比`(`output_unit != input_unit`),只在同单位段算出成率;整批端到端用"首投 kg → 末产盒×标准克重 折算 kg"算(克重来自产品标准,配置项)。**审计抓的量纲 bug 在此显式处理**。
- **carryover**:`本道 carryover = 上道总产出 − 本道总投入`(若 >0 = 余料结转;<0 = 靠前期结转补,张权 A2b)。carryover 只在 `ProductionReport.carryover_quantity` 记一次,**不进 WIP 库存表**(避免双计;WIP 实体是 Phase B)。

### 3.3 角色分工数据流

```
[领料环节] 仓库/班长 → 记 出库量 + 投料量
   数据源: 复用现有 /processing/batches/{id}/material-consumption (已存在)
   或首道工序报工时班长填 input_quantity (needs_input=true 的首道)
        ↓ input_quantity 落到首道 ProductionReport
[报工环节] 产线工人(operator) → 每道只报 output_quantity (防呆: 一个数)
   下道 input = 上道 output (系统带默认值, 班长可在领料环节修正为实际投料量)
        ↓ N 条 append-only ProductionReport
[系统自动] 单工序/整批出成率派生 + carryover 算 + 每日结清快照
        ↓ 末道产出汇总
[回写] 挂 SupplyChainOrchestrator.onBatchCompleted → batch.actualQuantity → 入成品库(已通)
```

### 3.4 每日结清(张权 A2/A2b)

- **触发**:人工标记优先 + 原料用完自动(张权 A2b)。
  - 人工标记结清 API:`POST /production/batches/{id}/settle-day`,把当日该批未结清的 `ProductionReport` 打 `settled=true`+快照;若原料没用完,剩余记 carryover,批次仍按人工标记结清。
  - 原料用完自动:领料量全部消耗 → 自动结清。
- **结清快照**:当日该批 投入合计/产出合计/出成率/carryover,供看板按天看(Phase E 消费)。

### 3.5 超收容差(张权 A4)

报工 output 超过"理论可产"(上道产出 × 标准出成率上限)→ **软告警 + 可强制提交,容差默认 30% 可配**(工厂级配置项)。不硬拦(防呆 Rule 1 预先显示边界,但允许强制)。

### 3.6 工序批次命名(张权 A6)

半成品/工序批次号规则:`{产品码}-{批次日期}-{工序序}-{流水}`,人易读 + 机器易统计 + 跨 SKU 唯一。系统生成,防重复。

### 3.7 API(Phase A)

| 端点 | 角色 | 说明 |
|---|---|---|
| `POST /production/batches/{id}/reports` | operator | 工人报一道工序产出(append ProductionReport) |
| `PUT /production/batches/{id}/material-input` | warehouse/foreman | 领料环节记出库量+投料量 |
| `GET /production/batches/{id}/yield` | all | 派生出成率(单工序+整批+carryover) |
| `POST /production/batches/{id}/settle-day` | foreman | 人工标记每日结清 |
| `GET /production/batches/{id}/reports` | all | 报工流水(append-only) |

权限:报工 API 对 `operator` 开放(修复"工人角色看不到逐道报工");结清/领料对 foreman/warehouse。报工是否需审批 = 工厂级配置(默认免审,张权防呆;严格厂可开)。

### 3.8 回写(挂现有,不新造)

末道工序结清 → 发 `BatchReportsSettledEvent` → 现有 `SupplyChainOrchestrator` 监听 → 汇总末道产出写 `batch.actualQuantity/goodQuantity` → 现有 `onBatchCompleted` → 入成品库(已验证通)。

## 6. 迁移策略(不大爆炸 — 审计 blocker)

- `ProductionReport` 新表与老三套**并存**。
- 老 `WorkProcessTask`/`process-tasks`/`ProcessingStageRecord` **不立即废**(RN 7 屏、4 个 AI 工具、TraceabilityService 仍依赖)。
- 新报工走 `ProductionReport`;老报工继续转。
- prod flyway 迁移:加 `production_reports` 表 + `WorkProcess` 几个可选列(版本号 > 当前 prod max,out-of-order=false)。
- 验证 Phase A+D 真能用后,再分批把 RN/AI工具/Traceability 切到 ProductionReport,最后废老表。
