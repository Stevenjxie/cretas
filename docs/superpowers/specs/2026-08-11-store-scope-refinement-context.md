# 门店范围 refinement context —— 让「先答后收窄」成立

**日期**: 2026-08-11
**状态**: spec，待实施
**前身**: PR #2368 / #2370（已合并的**半成品**）、2026-08-07 撤回记录（`HANDOFF-2026-08-07-restaurant-ai-round.md`「🔴 撤回的那条」）
**Owner 拍板**: 「账号是单店的还是总部的，如果是总部的话就走乙（默认全部门店 + 显式声明）」

---

## 1. 要解决什么

多店租户问「米饭的销量是多少」，系统该**直接答全部门店并声明范围**，而不是先反问
「哪一组门店」。

Owner 的规则按账号范围分两半：

| 账号范围 | 处置 | 现状 |
|---|---|---|
| 单店 | 范围唯一确定，直接用那家店 | ✅ **已实现**：`_apply_store_scope_guard` 里 `if len(names) == 1` 直接推断 |
| 总部/多店 | 默认全部门店 + 显式声明 | ⛔ 现在是「反问」，且**是否反问由模型的 `missing_fields` 自述决定** |

⚠️ 查证（2026-08-11，prod）：
- `users` 表**没有** store 绑定列（只有 `factory_id / department / position / role_code / level`）
- 餐饮租户**没有一个是单店**：R_SSW_DEMO 5 家、MOCK_REST 10 家、R_GML_DEMO 132 家
- MOCK_REST 的账号全是总部级角色（`factory_super_admin` / `restaurant_manager` / …）

**所以按 owner 的规则，今天所有真实账号都落在「总部」这一格 → 一律走乙。**
单店那一半是为将来的店长账号预留的（届时需要 `users` 加一列门店绑定，属另一件事）。

## 2. 为什么不能直接翻默认（这条已经被撤回过一次）

2026-08-07 实测过：首轮默认全部门店，「反问」类归宿从 12 条降到 9 条，方向是对的。
撤回的原因是**代价出现在第二轮**：

> 首轮默认之后，用户再说店名收窄就得**重走一次 T3**。

而 goal 的 hard criterion 明写「多轮 agentic tool-calling 视为设计失败」——
**在一条原本确定性的路径上新增 LLM 调用，是直接违反判据**。

判据（撤回记录原话）: **半成品在这里是净亏。**

## 3. 为什么不能复用 `restaurant_pending_clarifications`

两者的**语义相反**：

| | pending clarification | refinement context |
|---|---|---|
| 何时写 | 我**问了**你一句 | 我**答了**你，但范围是我替你选的 |
| 下一句是什么 | 一定是答案 | **可能**是收窄，也可能是全新问题 |
| 消费方式 | **无条件**拼接 `original + " " + new` | **有条件**：只在能确定性判定为收窄时 |

复用 pending 的后果（撤回记录已经写明）：给「已答完」的问题登记 pending，
**下一个不相关的新问题会被拼到旧问句后面**。

## 4. 设计

### 4.1 载体

新表 `restaurant_scope_refinements`（与 pending 同库同形，独立一张）：

```
factory_id, session_key, resolver_query_seed, created_at
```

- `resolver_query_seed`：产生上一轮答案的**密封问句**（已含菜品/时间/指标）
- TTL 与 pending 一致，`DELETE ... RETURNING` 原子弹出
- ⛔ 不复用 pending 表加一个 `kind` 列：两者消费语义相反，同表会诱使下一个人
  写出「顺手也 pop 一下另一种」的代码

### 4.2 写入时机

答案发出且 `store_scope_defaulted is True` 时写一行。
⛔ 范围是用户自己说的（`store_scope` 非空且非默认）时**不写** —— 那不需要收窄提示。

### 4.3 消费条件（关键：确定性，零 LLM）

下一轮同 session 且**没有 pending**（pending 优先，它是真正的待答问题）时：

```
收窄 := 本轮问句去掉范围词后为空
        且 extract_store_mentions(本轮问句) 能解析出已知门店
           或 本轮问句 ∈ {"全部门店", "所有门店", …}
```

- 命中 → `query = seed + " " + 本轮问句`，走**既有确定性路径**（显式槽位编译），
  **不调 T3**
- 未命中 → 当作全新问句，refinement 行丢弃

⚠️ 「去掉范围词后为空」这一条不能省：「模拟·长宁龙之梦店的毛利率」是**新问题**
（它自带指标），不是对上一问的收窄。少了它就退化成 pending 那种无条件拼接。

### 4.4 默认翻转

`_apply_store_scope_guard` 的多店分支：反问 → `store_scope="all"` +
`store_scope_defaulted=True`（披露走既有的 `_store_scope_disclosure`）。

⛔ 延续轮（`is_clarification_continuation`）**不翻**：那一轮用户正在回答我们问的槽位，
替他答就是抢答（撤回记录里 20 条红压到 8 条时验过这一点）。

## 5. 闸（每条都要能变红）

1. **收窄不重走 T3** —— 变异：让收窄路径调一次 T3 → 断言必须红。
   这是撤回那次的**唯一**技术阻塞，它必须有闸守住。
2. **不相关的新问题不被拼接** —— 「米饭的销量」答完后问「今天天气怎么样」，
   断言 resolver 收到的 query 里**没有**「米饭」。
3. **单店租户行为不变** —— `len(names) == 1` 那条路一个字不改，断言仍然直接推断。
4. **默认必被披露** —— `store_scope_defaulted` 为真时答案含范围声明；
   ⚠️ 披露文案要引用**实际范围**，不是写死常量（同 08-11 `_time_range_disclosure`
   踩过的「说的窗口与算的窗口不同源」）。
5. **延续轮不被翻默认** —— 断言澄清延续轮仍然反问。

## 6. 电池期望要跟着改

现在期望「哪一组门店」的用例（`dish` / `dish_named_store` 链的第 2 轮等）改成
期望**答案 + 范围声明**。

⚠️ 判据（08-07 实测）：一批问句的归宿分布**对措辞极其敏感**，报改善必须与基线用
**逐字相同**的问句集。改期望的同时要跑基线对照，不能只看总分。

## 7. 不在本次范围

- `users` 加门店绑定列（店长账号）—— 另立
- 时间槽的同类问题（`time_phrase` 由 T3 自述、planner 编的窗口不披露）——
  同一形状，但独立一条，见 2026-08-11 对话记录
