# 副产品产出与盘点抵扣 — 设计

**日期**: 2026-07-31
**需求来源**: Steve（触发：客户一对多 workflow 生效被「副产品缺少单位可变现净值」拦住）
**状态**: 设计待评审

---

## 1. 起点：系统里已经有副产，别当成从零建

> ⚠️ 本节是 2026-07-31 写计划前查证后**改写**的。初稿写的「没有任何地方能声明副产，
> 也无处记录副产的产出量与价值」**是错的** —— 没验就写了。以下为线上实际情况。

| 已有能力 | 载体 | 线上数据 |
|---|---|---|
| 工序**预先声明**预期副产 | `work_processes.expected_byproducts` | **4 个工序已声明** |
| 报工**录副产**（名/量/单位/单价） | `production_reports.byproducts` | **15 条已录**，如 `{"name":"肥油","unit":"kg","quantity":36,"unitPrice":8}`<br>⚠️ **全部在 `DEMO_FACTORY`**，非真实工厂数据（2026-07-31 Task 7 实测；真实工厂 F006 共 13 条报工，0 条带副产） |
| 副产**成本冲减**（含上游 WIP 链传播） | `OrderCostBreakdownService.upstreamByproductCredit` | 在用 |
| BOM 侧 **NRV 抵扣** | `bom_recipes.byproduct_nrv_unit_price` + `recomputeFamilyCosts` | 🔴 **有实现、有录入界面、线上 0 行使用**<br>（2026-07-31 Task 7 实测：`bom_recipes` 61 行，`byproduct_nrv_unit_price` **有值 0 行**。初稿此处写「在用」是错的 —— 正是这句话让 Task 7 去追一个并不存在的「两套单价合并」。详见 `docs/dispatch/2026-07-31-byproduct-price-source-audit.md`） |

### 1.1 真正缺的四样

1. 副产是**自由文本 name**（"肥油"、"副产"），不是原料字典 SKU → **不能被当原料再投入**
2. **不落 `material_batches`** → 不进生产仓，**盘点盘不到它**
3. 单价在**报工时**填 → 要挪到**盘点时**确认
4. **单价有两个权威来源**（见下）

### 1.2 两套机制：不是重复计算，但单价来源要并

两者算的是**不同的成本对象**，并存本身不是 bug：

| | 成本对象 | 副产单价来源 |
|---|---|---|
| `recomputeFamilyCosts` → `BomRecipe.totalMaterialCost` | **BOM 标准成本**（配方层面的计划成本） | `bom_recipes.byproduct_nrv_unit_price` |
| `OrderCostBreakdownService` | **订单级单盒实际成本**（沿实际消耗边回溯） | 报工 `byproducts[].unitPrice` |

问题在于**同一个副产的单价维护在两处**，会各说各话。

> 🔴 **2026-07-31 Task 7 实测修正**：这个「两处」在线上**并不成立** —— BOM 侧
> `byproduct_nrv_unit_price` **0 行有值**，只有报工侧在用。所以不存在「跨两侧取值不同」，
> 也没有任何既有 BOM 标准成本会因收敛而改变（没有值可迁移）。
> 真正存在的分歧在**报工侧内部**：同一个「料头」在 3 条记录里填了 5 / 3 / 3，
> 另有 2 条根本没填单价 —— 这反而印证了「单价收敛到 SKU、确认挪到盘点」是对的。
> 完整取证见 `docs/dispatch/2026-07-31-byproduct-price-source-audit.md`。

**并法（Steve 2026-07-31 拍板「并成一套」，以报工侧为准）：**

- **单价的唯一权威链**：SKU 上的**参考单价** → 盘点时**确认单价**（落在副产批次上）
- **BOM 标准成本**继续用参考单价估（标注为估计值），**不再**每配方维护一份
  `byproduct_nrv_unit_price`
- **订单实际成本**用盘点确认单价
- 两个成本对象各取所需，但**单价只有一条来源链**

> 🔴 这是本设计里唯一一处「改既有计算输入」的地方。BOM 标准成本的副产单价从
> 「每配方一个值」变成「SKU 参考价」—— 若两者原本不等，标准成本会变。
> 实现时**先出存量对比**（现有 `byproduct_nrv_unit_price` 与拟用的 SKU 参考价差多少），
> 再决定是迁移还是保留覆盖位。

本设计补的是这条链：**SKU 化 → 落生产仓 → 盘点确认单价 → 抵扣后成本与利润**。

## 2. 不做什么（YAGNI）

- **不做会计意义上的副产品成本抵扣自动化**。抵扣只发生在盘点，由人确认单价触发。
- **不改多产出的成本分摊口径**。主产品之间的分摊仍在报工时按「比例 / 重量 / 数量」算
  （`ProcessSheetServiceImpl` 那套**从头到尾没读过 `outputRole`**）。副产不参与该分摊。
- **不做副产的再加工链路**。副产要加工就另建 workflow + 生产计划，走既有正常流程。
- **不自动创建副产 SKU**。SKU 由人在原料字典里先建好（自动生成的主数据没人维护）。

## 3. 数据落点（复用既有模型，不新建库存体系）

关键事实：**报工产出本来就落在 `material_batches`**（`ProcessSheetServiceImpl` 里
`materialBatchRepo.save(wip)`，带 `warehouseId` + `sourceDocType`）。

所以副产产出 = 这张表里的一条记录：

| 字段 | 值 |
|---|---|
| `materialTypeId` | 副产对应的**原料字典 SKU** |
| `warehouseId` | **生产仓**（它是生产出来的，不是采购入的原料仓） |
| `sourceDocType` | 新增一种，标识「来自报工的副产」 |
| `quantity` / `quantityUnit` | 本次实际产出重量 |

**不需要新表存副产库存**。副产此后就是一个普通的原料批次，能被别的 workflow 正常投入。

### 3.1 副产 SKU 放哪个字典 —— 原料字典（有实证，非拍板）

**结论：放 `raw_material_types`（原料字典）。**

依据不是"副产像原料"，而是**系统里同类东西已经这么做**。prod 实测
`material_batches` 按来源统计 `material_type_id` 指向哪张字典：

| 来源 | 条数 | 在原料字典 | 在成品字典 |
|---|---|---|---|
| `PRODUCTION_BATCH`（**生产出来的 WIP 半成品**） | 255 | **249** | **0** |
| `MATERIAL_REQUISITION`（领料） | 24 | 24 | 0 |
| `OPENING` / `MANUAL_ADJUST` / 空 | 616 | 616 | 0 |

WIP 半成品与副产是同一类东西——**产出物 + 可再投入**——它已经用原料字典 249 条。
副产另起炉灶会变成第二套"产出物字典"，正是要避免的。

### 3.2 但必须把「产出的副产」与「买来的原料」分开

原料字典大半字段是**采购属性**：`unitPrice` / `taxIncludedUnitPrice` /
`taxExemptionReason` / `movingAvgPrice` / `minStock` / `maxStock` / `associatedCustomerId`。
副产没有采购来源，这些字段对它全是空的。

**做法：用 `category` 打「副产」大类。** 前端 `utils/materialCategory.ts` 已有
「先选大类再筛物料」的两级筛选（客户张权 2026-07-02 提的，因为"物料下拉太乱"），
大类桶从 `原料/辅料/调料/包材/其他` 加一个「副产」即可 —— **筛选逻辑不用改**。

已核过的边界：

- ✅ **低库存告警天然安全**：`InventoryLowStockEventPublisher` 在
  `minStock == null || <= 0` 时直接跳过，副产不配 `minStock` 就不会告警。
- ⚠️ **采购下拉需要显式排除副产** —— 未找到明确的筛选点，实现时确认（见待确认）。

## 4. 录入位置（两处，各管一件事）

### 4.1 Workflow 配置：声明结构

产出 Cell 上勾「这是副产」。声明的是**哪道工序会出副产**——结构信息，进入不可变快照。

### 4.2 BOM 配方内容：填具体 SKU 与预计产出

配方内容从 `原料 / 辅料 / 包材` 三类扩为**四类**，新增「副产」，配一个
**「添加副产」按钮**（与现有「添加原料」并排、同样的交互）。每行填：

- 副产对应的**原料字典 SKU**（必填，从原料字典选）
- **预计产出量 + 单位**（用于报工时预填与偏差提示）
- **参考单价**（可选，作为盘点时的默认值）

### 4.3 报工：记录实际产出

报工时副产行按 BOM 预填，操作员改成**本次实际重量**。保存即落 `material_batches`。

> 🔴 副产**不参与主产品的成本分摊**，也不进入「多产出必须填分摊比例」那道校验。

## 5. 盘点：确认价值并抵扣

**关联系统已知**——Workflow 已声明副产来自哪道工序、哪个主产品，不需要人工绑定。
盘点只做一件事：**确认价值**。

- 盘点单上，副产批次显示：来源主产品、产出重量、参考单价（来自 SKU 或 BOM）
- 人工确认/修改**单价**，系统 `单价 × 盘点实际重量 = 抵扣额`
- 抵扣额从对应主产品的成本中扣减 → 展示**抵扣后成本**与**利润**

### 为什么是单价而不是总额

单价可以沉淀成 SKU 的历史默认值，下次盘点只改例外；重量变了也不用重新拍数。
总额每次都得重算，且无法沉淀。

### 诚实边界

- 未确认单价的副产批次：抵扣额记 **null**，主产品成本显示「未抵扣」，**不臆造 0**。
  （与既有 `collectionStatus` / 「未归集」同一套诚实语义。）
- 单价为 0 需要显式确认，与「没填」区分开。

## 6. 影响面

| 模块 | 改动 |
|---|---|
| Workflow 配置 | 产出 Cell 增「是否副产」标记，进快照 |
| BOM 配方 | 第四类 + 「添加副产」按钮；`bom_recipe_items` 增副产类别或新表 |
| 报工 | 副产行录入；落 `material_batches`；排除出多产出分摊校验 |
| 盘点 | 副产批次的单价确认 + 抵扣计算 + 抵扣后成本/利润展示 |
| 原料字典 | 无改动（SKU 由人先建好） |

**`getOutputRole()` 的消费者只在 BOM 域内部**（`BomWorkflowRevisionService` /
`BomRecipeServiceImpl`），报工/库存链路一处都没有 —— 改动面比看起来小。

## 7. 测试要点

- 副产声明进入不可变快照，且 slot re-keying 时能正确对上
- 报工落库：`warehouseId` = 生产仓、`materialTypeId` = 副产 SKU、重量正确
- 副产**不**参与主产品分摊：多产出分摊比例校验不把副产算进「计量维度」
- 盘点抵扣：单价 × 重量；**未确认单价 → 抵扣 null 且成本标「未抵扣」**（禁降级）
- 副产批次能被别的 workflow 当原料正常投入（端到端）

## 8. 已定的四件（Steve 2026-07-31）

### 8.1 算法已经有了 —— 要做的是补展示

`recomputeFamilyCosts` **已实现净变现价值法**，见既有用例
`byProductNrvCreditsOnlyItsSharedPathAndPreservesTotalInputCost`：

```
共享原料 100（主产+副产共担） + 副产专属包材 5   =  总成本 105
副产 NRV = 单价 10 × 产出 2 = 20
→ 主产成本 85 ／ 副产成本 20 ／ 合计仍 105（总额守恒）
```

副产的"成本"被记成它的变现价值，主产承担剩余。**本设计不改这个算法**，
只是把「单价」的确认时机挪到盘点，并把结果展示出来。

### 8.2 成本报表：单列一行抵扣

沿用标准成本计算单格式：

```
生产成本合计          105.00
  减：副产品变现价值   ( 20.00)
主产品成本             85.00
```

不并入主产品成本行的三个理由：**可追溯**（审计要看到扣了多少、按什么单价）；
副产变现价值是**估计值**，与实际发生成本性质不同，混行会掩盖估计成分；
单价一改，抵扣额变化能直接看出来。

### 8.3 一主多副：汇总一行 + 明细可展开

主表一行「减：副产品变现价值 合计 xx」，展开看各副产分列。

两头都要顾：副产多了主表会碎；但每个副产的单价**确认时间与来源不同**，
缺哪个必须看得出来 —— 尤其「未确认单价」那种，合并成一个数就把它藏了。

### 8.4 盘点重量 ≠ 报工重量 → 按**盘点实际**

与盘点语义一致（盘点就是以实物为准）。报工记录的重量保留，差异可查。

### 8.5 采购下拉排除 `category=副产`

副产没有采购来源，出现在采购单/补货建议里会让人误以为可以买。
实现时**逐个入口确认**（未找到统一的筛选点）。

已核过的相邻边界：低库存告警天然安全（`minStock` 未配置即跳过）。
