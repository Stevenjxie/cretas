## 一、要解决的问题（客户原话 → 实测）

客户说：**「上工序不报工，下工序就没有库存，而且经常漏报工。」**

2026-08-16 在 F006 受控走查实测后，定性要改：**不是漏报的问题。**

| 实测 | 说明 |
|---|---|
| 一次产量报工把**整个批次**置 `COMPLETED` | 批次 `10759` `planned_quantity=0`，报 3 盒后 w2/w3 仍 `PENDING` 却再也报不了工（409）|
| 报工产出**不进半成品库存** | 报工成功后 `semi_finished_inventory_transactions` 仍 0 行 |
| 领用**即时扣**、产出**等审批** | 料没了、下一道仍领不到，最难自查 |
| **小结完全不读 App 报工** | `InterimSettleServiceImpl` 里 `production_reports` 引用 **0** 次 |

⇒ **就算他们一次不漏报，这条链现在也走不通。**

### 两条互不相通的路（形态 D）

```
路 A   App 报工 ──→ production_reports ──→【网页审批】──→ SFI ✅
路 B   文员网页录 ──→ process_sheet_rows ──→【点小结】──→ SFI ✅
```

客户描述的「App 报工 → 文员网页检查 → 点小结」**横跨两条路**，所以走不通。

### 生产存量（决定了改动时机）

| | 线上行数 |
|---|---|
| `production_reports` | **0** |
| `process_sheet_rows` | **2**（F006，8-15）|
| `semi_finished_inventory` | 1 |
| `semi_finished_inventory_transactions` | 0 |

⇒ **现在是动这个架构代价最低的时刻**，没有存量要迁移。
⚠️ 反面：**两条通道都没经过真实使用检验**，没有真实数据能提前告诉我们哪里会疼。上线头几天必须有人盯。

## 二、UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

**操作员/工人** — 低技术素养，年纪偏大，车间现场戴手套、手可能是湿的、环境嘈杂 —
干完一道工序，在手机上报「我做完了第②道卤制，出了 4.5 公斤」，希望下一道的人马上能领到料。

**文员** — 网页端，两个身份叠加：**代工人录**（工人不用 App 时）+ **审核调整**（工人报错了改）。日终点小结核对。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|---|---|---|---|
| 1 | 今天该干的工序列表，每条带**产品名 + 批次号 + 第几道 + 工序名** | 点进「卤猪蹄 · 第②道 卤制」 | 不用回想自己是哪道 |
| 2 | **可领的半成品名称 + 数量**（例：猪蹄碎肉 可领 6.0 kg），投入框预填 | 确认或改投入量 | 领超了当场拦住，不是提交后报错 |
| 3 | 产出框（大字号）+ 本道标准出成率区间 | 填 4.5 | 明显偏离当场提示 |
| 4 | 唯一主按钮「提交报工」 | 点一次 | 提交即**入库**，不等任何人批 |
| 5 | 成功页：「第②道完成，产出 4.5kg **已入半成品库**」 | 无需再操作 | 看得见自己这一报的下游后果 |
| 6 | 批次进度条 ①✅ ②✅ ③⏳ | — | 知道整批还没完 |
| 7 | （文员网页）当天报工清单，可改数量 | 改 4.5 → 4.2 | 库存同步调整并留痕 |
| 8 | （文员网页）日终小结 | 点小结 | **核对差异**，⛔ 不是入库时机 |

### 摩擦点清单

| # | 摩擦点 | 严重 | 来源 |
|---|---|---|---|
| F1 | 同一个「报工」动作**两块屏两条路**，走错那条不进库存 | HIGH | Rule 5 / 信息密度 |
| F2 | 报一次工**整批被关**，后续工序 409；界面事先无提示 | HIGH | Rule 1 |
| F3 | 报工不带工序 | HIGH | Rule 2 |
| F4 | **文员代报把产量/工时记在文员名下**（`workerId` 被忽略）→ 计件工资错 | HIGH | Rule 2（责任人）|
| F5 | 产出等审批才入库，工人报完看不到下游有料 | HIGH | Rule 5 |
| F6 | **领用即时扣、产出等审批**的不对称 | HIGH | Rule 1 |
| F7 | 「批次**已已**完成」重复字，且无下一步 | MED | 铁律 a/d |
| F8 | 上道可领多少，报工屏没预先显示 | MED | Rule 1 |
| F9 | 文员改了报工，库存怎么变两边都看不到 | MED | Rule 2 |
| F10 | 半成品行锚在 (计划,产品类型)，工人语言里没有这个概念 | LOW | Rule 2 |
| **F11** | **网络差/提交失败时工人以为报上了**，下一道空等 | **HIGH** | Rule 4 + 铁律 d |
| **F12** | **文员想改报工，却被「下游已领用」挡死**——而这正是核对场景 | **HIGH** | Rule 5 |

> F11/F12 是 2026-08-16 对抗性审计新增的。原始 UX 分析对离线**零覆盖**，
> 且把逃生门设计成了一个**必然成立的拦截条件**（同形态在 memory 里记过一次）。

### 每个摩擦点的设计回应

- **F1** → 报工只留**一条**路（带工序那条）。文员网页不再是独立通道，而是同一条路的**代录**入口。⛔ 不给旧路补字段（那会变成两份都「对」的实现）。
- **F2** → 收口**按工序**：报完第②道只关第②道。批次完工 = **所有工序完成**。报工屏常驻进度条。
- **F3** → 报工必带 `workProcessTaskId`，从工序列表带入，工人不需要选。
- **F4** → `workerId` 必须生效；代录时界面显示**「代 张三 报工」**，产量/工时归张三，操作人另记。
- **F5 / F6** → **报工即入库，取消审批门**；产出与领用**同一事务**。
- **F7** → 修重复字；文案给下一步 + 跳转。
- **F8** → 打开即拉可领量，投入框 `max` 绑它，超限 disable 提交。
- **F9** → 改完回显「库存已同步调整 4.5 → 4.2（−0.3）」并写反向流水。
- **F10** → 工人侧一律说**半成品名称**（「猪蹄碎肉 可领 4.5kg」），⛔ 不说「第②道产出的」，也不出现 `CLK-SEMI-…`。
- **F11** → **离线可存草稿，⛔ 不可离线入库**。无网络时提交按钮禁用并明说「报工未提交，料**没有**扣」。提交幂等（客户端 `requestId`）。⛔ 不做乐观提交。
- **F12** → 拦截判据从「下游有没有领用」改成「**下游有没有出厂**」。厂内 → **级联预览 + 一次确认 + 一个事务改完**；已发货/已开票 → 拦住并跳转退货/差异流程。

## 三、职责重划

```
                 ┌──────────────────────────────────────────┐
   工人 App ───→ │  报工（唯一入口，必带 workProcessTaskId）  │
   文员网页 ───→ │  录入者可以是本人或代录，写同一张表         │
                 └───────────────┬──────────────────────────┘
                                 │ 同一事务
                    ┌────────────┼────────────┐
                    ↓            ↓            ↓
              扣上道料      产出进 SFI    只关本道工序
```

| 角色 | 现在 | 改后 |
|---|---|---|
| 报工 | 两条路，一条不带工序还会关整批 | **唯一入口**；即时扣料 + 即时入库 + 只关本道 |
| 审批 | 产出要等审批才入库 | **取消** |
| 小结 | 唯一入库时机 | **核对与差异处理**：重算应有余额 → 比对 → 列差异 |
| 文员网页录入 | 独立通道 `process_sheet_rows` | 退役为独立通道，改为报工的**代录**入口 |
| 批次完工 | 按数量猜 | **所有工序完成** |

### 三条硬约束

1. **`workerId` 必须生效** —— 否则计件工资算错。
2. ~~**「待小结投料」语义必须彻底归零**~~ —— 🔴 **这条是错的，2026-08-17 实施时订正。**

   **原文（错误）**：实时化后延迟扣减窗口消失，所以半成品盘点里那段
   `PendingInterimFeedService` 补偿要删掉，否则双重扣减。

   **实测订正**：`PendingInterimFeedServiceImpl` 读的是 **`ProcessSheetRow`**
   （文员网页流水单，由 `interim_settled_at IS NULL` 界定），**不是**
   `production_reports`（App 报工）；而 yield 栈**根本不写** `process_sheet_rows`。

   ⇒ **报工实时化既不制造也不消除待小结投料。** 文员那条路**仍然是延迟扣减**
   （小结未改），所以那段补偿**仍然必要**。

   ⛔ **按原文删掉它 = 亲手制造它注释里写的那个 bug**：仓管诚实数少 → **假盘亏**
   → **假凭证（借6602/贷1405）**，且随后小结二次扣减 → 库存虚低。

   ✅ **正确的约束**：只要还存在延迟扣减的录入路径，盘点就必须继续减待小结投料；
   两端**同生共死**。由 `DeferredDeductionCompensationContractTest` 钉住
   （成对判据 —— 只断言「补偿还在」会变成一道永远不许删的闸，挡住将来正当的清理）。

   📌 **真正归零的时机**：文员路也实时化、`PendingInterimFeedService` 整体退役时。
   那时这道闸会红，**那个红是对的**，把闸和补偿一起清掉。
3. **瞬态 WIP 规则取消** —— 中间道产出进出各一笔。

## 四、事务边界与差异处理

**一次报工 = 一个事务，四件事同生共死：**

```
① 扣上道料(SFI OUT)  ② 产出入库(SFI IN)  ③ 本道工序置完成  ④ 写报工记录
```

任何一步失败四件全回滚。⛔ 不允许「料扣了、产出没进」——那正是现在断链的样子。

### 文员改报工（日终核对）

| 场景 | 处理 |
|---|---|
| 改产量 4.5 → 4.2，下游**未出厂** | **级联预览**：算出受影响的下游链并展示（「第③道领用 4.5→4.2，产出 3.0→2.8」）→ 文员确认 → **一个事务全改 + 各写反向流水**。⛔ 不改原记录（留痕）|
| 下游**已出厂**（已发货/已开票）| 拦住，明确说明 + 跳转退货/差异流程（Rule 5）|
| 改到账面为负 | 拦住 |

> 判据是「**下游有没有出厂**」，⛔ 不是「下游有没有领用」——后者在核对场景下必然成立，
> 用它当拦截条件等于把逃生门锁死。

**小结**：重算当日应有余额 → 与实际比对 → **只列差异**；零差异安静通过。
⛔ 小结不再产生任何库存变动。

## 五、怎么证明它是对的

| 要证明什么 | 判据 |
|---|---|
| **数量余额没变**（承重墙）| 同一批数据，新路重算余额 == 旧路（小结）余额，逐 `productType` 比 |
| **总成本守恒** | 新旧两路总成本相等 |
| ⚠️ **单位成本** | SFI 是**移动加权平均**，路径依赖 ⇒ **只断言模型一致 + 总额守恒**，⛔ **不得断言 `unitCost` 逐位相同**（那条会红且红得没道理）|
| ~~「待小结投料」归零~~ | 🔴 **判据作废**（见硬约束 2 的订正）。改为：**延迟扣减路径与盘点补偿同生共死** —— `DeferredDeductionCompensationContractTest`，变异实测（删掉盘点补偿 → 红）|
| 代录归属正确 | 文员代 A 报工 → `worker_id = A`，操作人 = 文员。变异：把 `workerId` 改回忽略 → 必须红 |
| 只关本道 | 报第②道 → 只有 w2 `COMPLETED`，w1/w3 原样，批次仍 `IN_PROGRESS` |
| 下游立刻可领 | 报完第②道立即查可领量 = 本道产出。⛔ 中间不插审批/小结 |
| 事务原子 | 注入产出失败 → 上道料**没有被扣** |
| 幂等 | 同一 `requestId` 提交三次 → 一条报工、一笔库存 |

每条都要有会红的断言，**且变异实测红过一次**。
