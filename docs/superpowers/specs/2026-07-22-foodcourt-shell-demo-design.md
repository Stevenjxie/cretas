# 美食广场「跳转壳」Demo — 设计文档

**日期**: 2026-07-22
**客户**: 天物书岛食集（美食广场，10 个独立档口）
**交付形态**: 静态 H5 Demo，部署到 139 网关 `:8089`，IP 直访
**需求来源**: 客户微信语音 9 分钟（转录见 `platform/foodcourt/assets/source/requirement-voice-transcript.txt`）+ 现状小程序截图 6 张 + 桌牌照片 1 张

---

## 1. 背景：客户现状与痛点

天物书岛食集是一个美食广场，场内有 10 个独立经营的档口，共用一套堂食扫码点餐。桌上贴桌牌二维码（如 `A01`），扫码进入客如云（客户如云）小程序「天物书岛食集」。

现状实现方式：把小程序的**菜品大类导航**改造成了**门店切换**——左侧竖栏塞下 10 个档口 logo，顶部才是真正的菜品分类。

### 1.1 体验层痛点（截图坐实）

| # | 痛点 | 证据 |
|---|---|---|
| 1 | 10 个彩色 logo 挤在左侧一条竖栏，红绿蓝黄互相打架，看不清 | 全部 6 张截图左栏 |
| 2 | 门店名与菜品分类混在同一屏，信息层级错乱 | 左栏=门店，顶栏=分类 |
| 3 | 菜品只有小方图，点击展不开大图，只能 `+` 加减或「选规格」 | 全部截图菜品列表 |
| 4 | 单个档口打烊时，**点进去才**弹「本店已打烊，仅可浏览菜单／您也可以尝试切换到其他门店进行点单」 | 6 张截图底部黑条 |
| 5 | 菜品图加载慢，出现「加载中…」转圈 | 青岛鲜啤截图 |

### 1.2 结算层痛点（客户核心诉求）

现状是**聚合收款**：顾客付的钱 100% 进总部账户，第二天总部再手工分 90% 给各档口，自留 10%。

- **已连续 4 个月没分过账** — 手工分账不可持续
- **税务风险** — 税务按 100% 收入认定总部，分出去的 90% 还需各档口回开发票，流程冗长

---

## 2. 解决方案：外面套一层「跳转壳」

**核心思路：不接入、不改造客如云内部系统，只在最外层套一个壳。**

```
桌牌二维码（A01）
      ↓ 扫码
┌─────────────────────────┐
│  跳转壳（总部小程序）      │   ← 我们做的，只有 10 个按钮，没有任何菜品/收银逻辑
│  显示桌号 A01 + 10 个档口 │
└─────────────────────────┘
      ↓ 点「磊子川菜」，桌号 A01 随之带入
┌─────────────────────────┐
│ 磊子川菜的独立点餐小程序    │   ← 客如云原有，各档口独立账号、独立收款
└─────────────────────────┘
      ↓ 顾客直接付给该档口
   钱进磊子川菜自己的账户，总部次日抽 10%
```

### 2.1 这样解决了什么

| 原痛点 | 解法 |
|---|---|
| 手工分账 4 个月没做 | 各档口独立收款，钱本来就在自己账上，**无需分账** |
| 税务按 100% 认定总部 | 总部只收 10% 抽成，只对 10% 计税 |
| 10 个 logo 挤一条竖栏 | 壳首页两列大卡，每家一张，留白充分 |
| 点进去才知道打烊 | **进店之前**就在卡片上标「已打烊」并置灰 |
| 图片展不开 | 档口页菜品大图，点击全屏展开 |

### 2.2 已明确接受的取舍

- **一次只能在一家档口下单**。想吃三家＝下三笔单。跨档口合并购物车需打通各档口收银，不在本方案范围内，客户已认可。
- 壳内**不做**任何菜品、库存、收银、订单逻辑，纯跳转。

### 2.3 桌号对齐（关键约束）

10 家档口必须共享同一套桌号。1 号桌扫码后跳进任何一家，该档口都必须知道这单来自 1 号桌，否则菜送不到桌。壳负责把桌号从扫码入口一路透传到跳转链接。

## 3. Demo 范围

本次交付的是**给客户看的高保真 H5 原型**，不是上线的小程序。目的：让客户在手机上真扫真点，认可方案后再走客如云授权、小程序开发、审核。

### 3.1 做什么

- 扫码落地页（壳首页）：桌号 + 10 个档口卡片
- 档口页（模拟）：真实菜名价格、大图可展开、桌号常驻
- 3 张演示桌牌二维码：A01 / A05 / B02
- 部署到 139:8089

### 3.2 不做什么

- 不做真实跳转（链接未拿到，跳转位置显示说明条）
- 不做购物车、下单、支付、订单
- 不做分账看板（分账由「各档口独立收款」天然解决，无需系统）
- 不做微信小程序（授权未到位，属下一阶段）

## 4. 技术方案

### 4.1 选型

纯静态 H5：单个 `index.html` + `config.json` + 图片资源，vanilla JS 做两屏切换。

**理由**：两屏体量，零构建零依赖当天可上；客户后续要改档口名/链接，直接改 `config.json` 即可，无需重新构建部署。

已否决方案：
- Vue + Vite SPA — 为两屏上完整构建链路过重，且改档口名要重新 build
- 直接做微信小程序 — 需客如云总账号授权 + appid + 审核，均未到位，属下一阶段

### 4.2 目录结构

```
platform/foodcourt/                    # 本地源
├── index.html                         # 单文件页面（两屏，hash 切换）
├── config.json                        # 唯一需要改的：档口名/图/跳转链接
├── assets/
│   ├── logo/                          # 10 个档口 logo（截图裁切）
│   ├── dish/                          # 菜品图
│   └── source/                        # 原始素材（截图、桌牌、语音转录）
├── qr/                                # A01.png / A05.png / B02.png 演示桌牌
└── tools/
    └── make_qr.py                     # 桌牌二维码生成脚本
```

部署目标：`139:/www/wwwroot/foodcourt/`（`assets/source/` 与 `tools/` 不上传）

### 4.3 nginx

139 端口现状：8086=web-admin，8087=client-request，8088=prototype，**8089 空闲且安全组已放行 0.0.0.0/0**。

新增 `/www/server/panel/vhost/nginx/foodcourt.conf`：

```nginx
server {
    listen 8089;
    server_name 139.196.165.140;
    root /www/wwwroot/foodcourt;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }
}
```

`nginx -t` 通过后 reload。**不修改任何现有配置文件**（139 是网关，承载 API 反代，不可影响）。

访问：`http://139.196.165.140:8089/?table=A01`

## 7. config.json 契约

```json
{
  "brand": {
    "name": "天物书岛食集",
    "tagline": "FOOD IS NEW FASHION"
  },
  "defaultTable": "A01",
  "stalls": [
    {
      "id": "leizi",
      "name": "磊子川菜",
      "tag": "川菜·小炒",
      "logo": "assets/logo/leizi.png",
      "open": true,
      "url": "https://客如云给的链接?tableNo={table}",
      "dishes": [
        { "name": "水煮牛肉", "price": "¥58", "img": "assets/dish/leizi-1.jpg" }
      ]
    }
  ]
}
```

### 7.1 跳转链接的两种形态（都必须支持）

档口跳转链接尚未拿到，其形态存在两种可能，代码需同时兼容：

| 形态 | config 写法 | 说明 |
|---|---|---|
| A. 链接可带桌号参数 | `"url": "https://...?tableNo={table}"` | `{table}` 运行时替换为当前桌号 |
| B. 一店一桌一码（每家每桌各一固定链接） | `"urlByTable": { "A01": "https://...", "A05": "https://..." }` | 按当前桌号查表 |

优先读 `urlByTable`，缺失则回落 `url` 并做 `{table}` 替换。因此链接未到手不阻塞开发。
