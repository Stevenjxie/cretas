## 2. `smart_bi_finance_data` target schema

From `database/create_smart_bi_finance_data_pg.sql` + JPA entity `SmartBiFinanceData.java`:

```sql
CREATE TABLE smart_bi_finance_data (
    id BIGSERIAL PRIMARY KEY,
    factory_id VARCHAR(50) NOT NULL,
    upload_id BIGINT,                  -- nullable; ETL-generated rows set NULL or sentinel
    record_date DATE NOT NULL,
    record_type VARCHAR(20) NOT NULL,  -- COST, AR, AP, BUDGET, REVENUE (per enum)
    department VARCHAR(100),
    category VARCHAR(100),             -- 必填语义 keyword (per RestaurantFinancialMetricsFetcher.sumRevenueCategory)
    customer_name VARCHAR(200),
    supplier_name VARCHAR(200),
    material_cost NUMERIC(15,2) DEFAULT 0,
    labor_cost NUMERIC(15,2) DEFAULT 0,
    overhead_cost NUMERIC(15,2) DEFAULT 0,
    total_cost NUMERIC(15,2) DEFAULT 0,   -- RestaurantFinancialMetricsFetcher.sumCostByKeywords reads this first, falls back to actualAmount
    receivable_amount NUMERIC(15,2) DEFAULT 0,
    collection_amount NUMERIC(15,2) DEFAULT 0,
    aging_days INTEGER DEFAULT 0,
    payable_amount NUMERIC(15,2) DEFAULT 0,
    payment_amount NUMERIC(15,2) DEFAULT 0,
    budget_amount NUMERIC(15,2) DEFAULT 0,
    actual_amount NUMERIC(15,2) DEFAULT 0,   -- RestaurantFinancialMetricsFetcher.sumRevenueCategory reads this for REVENUE rows
    variance_amount NUMERIC(15,2) DEFAULT 0,
    due_date DATE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    deleted_at TIMESTAMP
);
```

**Critical contract** (per `RestaurantFinancialMetricsFetcher.java:256-272`):

For REVENUE rows:
- `category` MUST contain **"收入"** (matched by `sumRevenueCategory("收入")`) OR **"净利"** for derived net_profit
- value goes into `actual_amount`

For COST rows:
- `category` MUST contain keywords: **食材/原材料/食品/饮料/酒水/菜品** → food_cost
- OR **人工/工资/薪/员工/劳务** → labor_cost
- OR **租金/房租/店租/场地** → rent
- value goes into `total_cost` (preferred) OR `actual_amount` (fallback)
- `.abs()` applied at read time (defensive — sign-neutral)

**Latest-upload filter** (per `filterToLatestUpload` lines 239-254):
- Multiple uploads for same date keep only the max `upload_id` rows. ETL-generated rows can use **a sentinel `upload_id`** (e.g. `9999999999` reserved for ETL) to ensure they win OR set `upload_id = NULL` and modify the fetcher (RISKY — touches PR #225 code).

**Recommended**: Reserve `upload_id = -1` as the "ETL-generated" sentinel. Fetcher already uses `Comparator.naturalOrder()` so NULL is filtered out (`Objects::nonNull`), and -1 < any positive upload_id. **However**, if a real Excel upload exists for same period, it wins (correct: operator data > ETL imputed).

Actually re-reading lines 243-249: the fetcher computes `maxUpload = max(upload_id)` ignoring nulls, then keeps only `maxUpload.equals(r.getUploadId())`. If `upload_id IS NULL`, the row is FILTERED OUT (max() returns positive, equals(null) = false). So **ETL rows must use a positive sentinel upload_id**.

**Decision**: Use `upload_id = 1_000_000_000_000L` (1 trillion) as ETL sentinel — far larger than any natural sequence value so ETL always wins when present. Operators can override by re-uploading Excel (then natural upload_id ≪ sentinel, ETL keeps winning — **BUG**). Reverse: use `upload_id = 0L` so any operator upload wins. **Recommended**: `upload_id = 0L` (operator upload always wins). Risk: if upload_id sequence happens to be 0 in legacy data → won't happen, BIGSERIAL starts at 1.

## 3. ETL design

### 3.1 Source → Transform → Target mapping

#### REVENUE row generation (from `fact_pos_transaction`)

```sql
INSERT INTO smart_bi_finance_data (
    factory_id, upload_id, record_date, record_type, category, actual_amount
)
SELECT
    factory_id,
    0::bigint AS upload_id,             -- ETL sentinel (lowest, operator upload wins)
    date AS record_date,
    'REVENUE' AS record_type,
    '营业收入' AS category,              -- triggers RestaurantFinancialMetricsFetcher.sumRevenueCategory("收入")
    SUM(net_amount)::numeric(15,2) AS actual_amount
FROM fact_pos_transaction
WHERE factory_id = $1::varchar
  AND date BETWEEN $2::date AND $3::date
GROUP BY factory_id, date
ON CONFLICT (factory_id, upload_id, record_date, record_type, category)
DO UPDATE SET
    actual_amount = EXCLUDED.actual_amount,
    updated_at = NOW();
-- NB: requires ON CONFLICT requires UNIQUE INDEX (see §3.6)
```

Daily POS aggregation gives ~365 REVENUE rows per RES_3101_009 for 2025 (verified date range 2025-01-01 to 2025-12-31).

#### COST row generation (food cost — from wastage)

```sql
INSERT INTO smart_bi_finance_data (
    factory_id, upload_id, record_date, record_type, category, total_cost, actual_amount
)
SELECT
    factory_id,
    0::bigint,
    date,
    'COST',
    '食材损耗' AS category,
    SUM(estimated_cost)::numeric(15,2),
    SUM(estimated_cost)::numeric(15,2)
FROM fact_restaurant_wastage
WHERE factory_id = $1::varchar
  AND date BETWEEN $2::date AND $3::date
  AND status = 'APPROVED'
GROUP BY factory_id, date
ON CONFLICT (factory_id, upload_id, record_date, record_type, category) DO UPDATE
SET total_cost = EXCLUDED.total_cost, actual_amount = EXCLUDED.actual_amount, updated_at = NOW();
```

Only 6 rows for RES_3101_009 today (verified). This gives 6 食材-bucket COST rows.

#### COST row generation (food cost — from POS × recipe-derived COGS)

The REAL food cost is `(qty_sold × recipe_food_cost)` for each dish. Compute by joining `fact_pos_item` → `agg_restaurant_product_cost`:

```sql
INSERT INTO smart_bi_finance_data (
    factory_id, upload_id, record_date, record_type, category, total_cost, actual_amount
)
SELECT
    pt.factory_id,
    0::bigint,
    pt.date AS record_date,
    'COST',
    '食材成本' AS category,  -- triggers FOOD_KEYWORDS = {"食材", ...}
    SUM(pi.qty * COALESCE(pc.food_cost, 0))::numeric(15,2),
    SUM(pi.qty * COALESCE(pc.food_cost, 0))::numeric(15,2)
FROM fact_pos_transaction pt
JOIN fact_pos_item pi ON pi.transaction_id = pt.id AND pi.factory_id = pt.factory_id
LEFT JOIN agg_restaurant_product_cost pc
       ON pc.factory_id = pt.factory_id
      AND pc.product_id = pi.product_id
WHERE pt.factory_id = $1::varchar
  AND pt.date BETWEEN $2::date AND $3::date
  AND pi.product_id IS NOT NULL
GROUP BY pt.factory_id, pt.date
ON CONFLICT (...) DO UPDATE SET ...;
```

**Caveat**: Many `fact_pos_item` rows have `product_id IS NULL` (unresolved per `idx_fact_pos_item_unresolved` index hint). Aggregated cost only covers resolved items — this is a known data quality gap. Phase B' accepts this; Phase C+ should run a `product_name → product_id` resolution backfill.

#### NET_PROFIT row generation (DERIVED — optional)

`RestaurantFinancialMetricsFetcher.java:117-122` falls back to `revenue - totalCost` if no `净利` category exists. So we **don't need to emit NET_PROFIT** rows — the fetcher derives it. **Skip this**.

#### LABOR / RENT / OTHER cost

No source data exists for RES_3101_009 (verified: 0 rows in payroll_records / payment_records / expense_requests). **Skip these** — the fetcher will return `null` for those buckets and the Composite Tool's narrative layer should handle null gracefully (verify in Phase D smoke test — if narrative breaks, file Sprint 12 bug).

### 3.2 Target shape summary

For each (factory_id, date) in scope, emit:
- **1 REVENUE row** (category=营业收入, actual_amount=sum of net_amount from POS)
- **0-1 COST food rows** from wastage (category=食材损耗, total_cost=wastage cost)
- **0-1 COST food rows** from POS×recipe COGS (category=食材成本, total_cost=derived COGS)
- **0 labor/rent/other rows** for Phase B' (no source data)

Estimated row count for RES_3101_009 backfill: 365 days × ~2 rows = **~730 rows** for 2025. Plus 6-18 rows for wastage period. Very small payload.

### 3.3 Frequency / scheduling

**Backfill (one-time)**:
- Run for RES_3101_009 covering 2025-01-01 to 2025-12-31 (POS data range)
- Run via admin trigger endpoint: `POST /api/restaurant-etl/trigger {factoryId: "RES_3101_009"}` — extend existing endpoint
- Expected runtime: <30s (POS data aggregation, ~140K row scan, 365 daily groups)

**Ongoing (nightly cron)**:
- Trigger via Java `@Scheduled(cron = "0 30 2 * * ?")` (2:30 AM daily) — pattern exists in `IntentMetricsScheduler.java` per memory
- Run for each restaurant factory_id in catalog
- Re-process last 30 days (idempotent upsert covers late-arriving POS data)

**Alternative: on-demand trigger from Composite Tool**:
- When `RestaurantFinancialMetricsFetcher.fetch()` returns Optional.empty() AND it's been >24h since last ETL run for this factory, trigger ETL job + retry fetch after 60s
- More complex; defer to Sprint 12

**Decision**: Phase B' uses **one-time backfill + nightly cron**. Add on-demand trigger in Sprint 12.

### 3.6 Schema requirement (new UNIQUE INDEX)

Current `smart_bi_finance_data` has NO unique constraint usable for `ON CONFLICT`. To enable idempotent upsert, add:

```sql
-- Flyway migration V20260524_01__smart_bi_finance_data_etl_uniq.sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_smart_bi_finance_data_etl
    ON smart_bi_finance_data (factory_id, upload_id, record_date, record_type, category)
    WHERE deleted_at IS NULL;
```

Partial index (excludes soft-deleted rows). Existing rows: 0, so no constraint violation risk.

**WARNING**: The existing Excel-upload path (`tryExtractAndSaveFinanceData`) does NOT use upsert — it `saveAll(entities)`. If two uploads for same date produce same category, you'd get duplicate rows. Today this works (rows are differentiated by upload_id). Our migration adds (upload_id, category) to the UNIQUE key, so Excel path still works (each upload_id is unique). **No breaking change**.

## 5. Risks + open questions

### R1: B2B factory_type drift (HIGH)

Brief says "餐饮 factory finance data". But `RestaurantFinancialMetricsFetcher` is invoked by Composite Tool for the user's factory_id. If user is F006 (B2B factory_type, per P0-3 evidence), this ETL won't help — F006 has `sales_orders` data (5 rows), not POS data. Should we generalize ETL to also work from `sales_orders` for B2B-type restaurants?

**Recommendation**: Phase B' scope = RES_3101_009 only. F006 stays as P0-3 mealclaw chat decision. If F006 needs same path, file Sprint 12.

### R2: Latest-upload filter semantics (MEDIUM)

`RestaurantFinancialMetricsFetcher.filterToLatestUpload()` keeps only `maxUpload` rows. If an operator later uploads Excel for the same period:
- Excel upload_id = e.g. 5234
- ETL sentinel upload_id = 0
- `maxUpload = 5234`, ETL rows dropped ✓ (operator wins, correct semantics)

But if there's NEVER an Excel upload, max = 0 (our ETL rows), our rows kept ✓.

Edge case: existing legacy upload with upload_id = 100, we add ETL with upload_id = 0 → max = 100, ETL rows dropped, FALLBACK to old (potentially stale) Excel data. Acceptable.

### R3: `fact_pos_item.product_id NULL` (MEDIUM)

The COGS calculation joins on `product_id`. Many POS items have unresolved `product_id IS NULL` (per existing index `idx_fact_pos_item_unresolved`). Those items contribute 0 to COGS → understated food_cost.

**Mitigation**: log + report in ETL stats. Phase C+ run product_name resolution backfill.

### R4: Period selection mismatch (HIGH for demo)

Fetcher defaults to "上月" (today=2026-05-23 → 2026-04). But POS data is 2025. Customer demo asks "上月损益" → returns Optional.empty() **even after ETL**.

**Mitigation**: Phase F mealclaw brief update — demo script asks "2025年12月损益" explicitly. Risk: feels stale to customer.
