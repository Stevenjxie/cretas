# 物流调度 MVP 模块化工作台设计

## 1. 目标

把当前单页超长的“智能排班看板”拆成清晰的物流业务模块，同时保留一次排线所需的连续上下文。

设计原则：

1. 低频资料独立维护，高频排线集中完成。
2. 地图是核心业务画布，不是装饰背景。
3. 一条线路必须连接该车辆实际配送的多个不同门店，并显示配送顺序。
4. 客户界面只显示业务信息，不出现“会议讲法、Demo、MVP、后续接入”等内部文字。
5. 当前版本继续使用前端 mock 数据，不暗示已经完成真实地图 SDK、实时 GPS 或成熟算法。

## 2. 转录依据

### 2.1 明确需求

- `[00:22-00:56]`：按模板导入订单，在地图显示全部点位，设置装载率，自动排线，并允许人工调整。
- `[01:56-02:13]`：当天约 200 家门店全部显示；门店包含件、箱、重量、体积；车辆按约 10 方容量规划。
- `[03:05-03:09]`：客户明确确认业务属于多点运输。
- `[04:35-04:46]`：车辆容量约 10 方，超过容量自动分配到下一辆车。
- `[06:31-06:34]`：客户明确不需要实时 GPS 位置。
- `[07:51-08:05]`：点击点位查看门店货量；一车装多个点；线路输出第一家、第二家、第三家。
- `[08:24-08:31]`：线路每天随订单变化，是每日动态生成，不是固定线路。
- `[08:50-09:07]`：一条线路可包含约 5 家门店，并输出该车总公里数。
- `[09:38-09:51]`：导出门店顺序；从第一家到第二家、第二家到第三家直到最后；输出车辆当日总公里数。
- `[09:51-10:00]`：首期一家门店由一辆车送完，不拆给多辆车。
- `[12:22-12:47]`：先交付地图点位和排线框架，成熟算法后续再迭代。

### 2.2 明确不应误读的内容

- “实时线路”指每天订单不同、线路动态生成，不是实时车辆轨迹。
- 客户明确需要线路总公里数，但没有明确要求主界面常驻显示每一段公里数；分段距离放在线路详情中。
- 多点运输是主要模式，但不能强制每条线路至少两个门店；偏远或大体积门店可能单独成线。
- 路线颜色、行政区命名、固定 4 辆车和固定仓库起终点属于产品设计或 mock 数据，不是客户已经确认的业务规则。

## 3. 信息架构

物流租户左侧“物流调度”下拆成四个入口：

### 3.1 排线工作台

每日高频核心页面，一次完成：

`导入订单 → 地图排线 → 人工确认 → 确认导出`

地图、推荐线路和人工调整属于同一次排线决策，不拆成独立菜单页。

### 3.2 调度记录

简版 mock 列表，展示：

- 调度日期和批次号
- 门店数、车辆数、总公里数
- 草稿、待确认、已确认状态
- 查看详情、再次导出

不包含审批流、费用结算和 GPS 轨迹。

### 3.3 门店与订单

简版 mock 页面，展示：

- 模板下载和订单导入
- 门店编码、门店名称、地址
- 件、箱、重量、体积
- 地址校验和导入状态

不实现真实地址解析和完整门店 CRUD。

### 3.4 车辆与司机

简版 mock 页面，展示：

- 车牌、容量、载重、双温车型
- 自有车、外协车
- 主司机、替班司机、一车多司机
- 固定区域和班次

不实现司机端、工资计算和完整排班 CRUD。

## 4. 排线工作台

### 4.1 四步结构

#### 步骤 1：导入订单

- 下载模板
- 导入订单
- 显示成功、异常地址和字段缺失
- 显示今日门店数、总方数、总重量
- 本步骤不显示大地图和推荐线路

#### 步骤 2：地图排线

- 详细苏州地图
- 全部门店点位及门店名称标签
- 目标装载率
- 生成推荐线路
- 右侧推荐线路列表
- 条件异常提示

#### 步骤 3：人工确认

- 当前线路配送顺序
- 车辆和司机
- 主司机、替班司机、固定区域和班次
- 上下移动或拖拽调整顺序
- 超载门店自动顺延下一车次
- 调整后同步更新地图节点顺序和公里数

#### 步骤 4：确认导出

- 最终线路结果表
- 线路、车辆、司机、门店顺序
- 总方数、装载率、总公里数
- 确认排线和 CSV 导出

本步骤不再显示大地图。

## 5. 地图详细设计

### 5.1 视觉基准

使用客户提供的苏州地图截图作为当前 mock 视觉基准：

- 保留真实道路、水系、区县、地名和高速信息。
- 同屏展示密集门店点位和门店名称标签。
- 地图至少占工作台主体宽度的 70%，高度不低于 500px。
- 门店名称使用高对比度文本和白色标签底，不能使用低对比度浅灰字。

客户原图包含完整门店分布和名称，只作为设计参考，不得原样提交到 public GitHub。实现时创建脱敏后的本地高细节底图：保留苏州道路、水系、区县和公共地名，只显示当前 13 个 mock 门店；资源不依赖外部 URL。

地图和覆盖层使用同一个固定坐标系：

- 原图坐标系固定为 `1917 × 1165`。
- 地图容器保持 `1917 / 1165` 宽高比，禁止使用会裁剪图片的 `object-fit: cover`。
- SVG 使用 `viewBox="0 0 1917 1165"`，门店点、路线节点和道路段都保存原图像素坐标。
- 每个门店必须定义唯一 `mapAnchor: { x, y }`；实现前逐店核对锚点是否落在客户参考图对应门店上。
- 响应式缩放只缩放整张图片和 SVG，不重新计算或裁剪坐标。

### 5.2 地图状态

#### 订单点位状态

订单导入后：

- 显示当天全部门店点位。
- 默认显示门店名称。
- 点击门店打开详情抽屉，显示件、箱、重量、体积和时间窗。
- 未生成线路时不显示路线。

#### 全部线路状态

生成线路后：

- 默认显示当天全部线路。
- 不同线路使用不同颜色。
- 每条线路经过自己实际分配的门店节点。
- 一家门店只能归属一条线路。
- 路线必须使用多段道路形态折线，禁止从仓库向区域直接画粗直线。
- 所有路线使用白色外描边和细色线，避免压住地图道路。

#### 当前线路状态

点击右侧线路卡片后：

- 当前线路加粗。
- 其他线路降低亮度但仍保持可见。
- 当前线路节点显示 `1、2、3……最后`。
- 地图节点顺序与右侧门店顺序完全一致。
- 显示路线方向，不显示实时车辆位置。

### 5.3 多点线路不变量

对于每条 `RoutePlan`：

1. `storeIds` 是有序且不重复的门店 ID 列表。
2. 不同线路之间的 `storeIds` 不得重复。
3. 已分配门店集合与当日可配送订单门店集合一致，溢出门店必须明确进入下一车次或待处理集合。
4. 地图路线 geometry 必须依次经过 `storeIds` 对应的节点。
5. 右侧顺序、地图编号和导出顺序来自同一个 `storeIds` 数据源。
6. 人工调序后，上述三处同时更新。
7. 分段距离之和等于线路总公里数。

### 5.4 当前 mock 的路线 geometry

当前版本不接真实地图 SDK，采用预先维护的拟真道路 geometry：

- 每条线路保存经过多个道路转折点的 polyline。
- polyline 必须连接该线路的所有门店节点。
- 路线不得穿过太湖、阳澄湖或明显不可行区域。
- 当前版本的公里数明确来自 mock 数据，但该说明写在项目文档，不写进调度员界面。

为支持人工调序，mock 数据不只保存整条线路，还要保存“节点对 → 道路段”的查找表：

- 每个可调整的相邻节点对都有预先维护的 `geometry` 和 `distanceKm`。
- 调整顺序后，按新的相邻节点对重新拼接道路段，并汇总分段公里数。
- 如果新的节点对没有道路段数据，界面阻止确认并提示“当前顺序缺少路线数据”。
- 禁止用两点直线作为缺失道路段的降级结果。

客户参考图本身包含大量蓝色门店点位和标签。制作脱敏底图时先移除这些客户点位和标签，再由 `StoreOrder.mapAnchor` 统一绘制当前 13 个 mock 门店；当前线路的顺序编号作为额外覆盖层。

未来接入真实地图时，用路径规划 API 返回的 geometry 和里程替换该字段，页面组件和数据契约保持不变。

## 6. 推荐线路卡片

每张卡片展示：

- 线路名称
- 车辆和司机
- 门店数量
- 完整配送顺序摘要
- 装载率
- 总公里数
- 待确认、需处理、已确认状态

可读性要求：

- 线路名使用深色正文。
- 车辆和里程使用正常深灰。
- 只有状态使用绿色、橙色或红色。
- 禁止整张卡片使用浅灰文本。

## 7. 条件提示

地图下方不常驻显示“防呆提示”。只有出现下列情况时显示简短业务提示：

- 超过车辆容量
- 地址无法定位
- 门店未分配车辆
- 司机或车辆冲突

界面文案只写“需要处理”及具体原因，不出现“防呆”内部术语。

## 8. 页面与组件边界

建议目录：

```text
web-admin/src/views/scheduling/logistics/
├── types.ts
├── mockData.ts
├── useLogisticsDemoState.ts
├── components/
│   ├── LogisticsStepBar.vue
│   ├── LogisticsMap.vue
│   ├── RouteCards.vue
│   ├── StoreDetailDrawer.vue
│   ├── OrderImportStep.vue
│   ├── ManualConfirmStep.vue
│   └── ExportConfirmStep.vue
├── workbench/index.vue
├── records/index.vue
├── orders/index.vue
└── resources/index.vue
```

共享状态由 `useLogisticsDemoState.ts` 提供，四个页面读取同一组 mock 订单、车辆、司机、线路和调度记录，避免各页面数据互相矛盾。

### 8.1 核心数据契约

```ts
interface MapPoint {
  x: number;
  y: number;
}

interface RoadSegment {
  fromId: 'DEPOT' | string;
  toId: 'DEPOT' | string;
  geometry: MapPoint[];
  distanceKm: number;
}

interface RouteTrip {
  id: string;
  routeGroupId: string;
  tripNo: number;
  vehicleId: string | null;
  driverId: string | null;
  storeIds: string[];
  segmentKeys: string[];
  geometry: MapPoint[];
  segmentDistances: number[];
  totalDistanceKm: number;
  totalVolumeCbm: number;
  loadRate: number;
  status: 'draft' | 'needs_vehicle' | 'needs_route_data' | 'confirmed';
}

interface ScheduleResult {
  trips: RouteTrip[];
  unassignedStoreIds: string[];
  assignedVehicleCount: number;
  additionalVehicleCount: number;
}
```

页面、线路卡片、地图和导出都读取 `RouteTrip[]`，不再各自计算另一套线路状态。

### 8.2 超载和下一车次

超出容量不能只进入一个仅供展示的 `overflow[]`：

1. 当前车次达到软目标或硬容量后，创建新的 `RouteTrip`。
2. 优先匹配同区域、容量足够且尚未占用的车辆。
3. 没有可用车辆时，仍创建下一车次，但 `vehicleId = null`、状态为 `needs_vehicle`。
4. 原车次的 `storeIds`、门店数、方数和导出数据不得包含已顺延门店。
5. 顶部同时显示“已匹配车辆数”和“待补车辆数”，不把待补车辆伪装成已存在车辆。

### 8.3 目标装载率规则

目标装载率必须真实影响车次生成：

- `hardCap = vehicle.capacityCbm`，任何车次都不得超过硬容量。
- `targetCap = hardCap × targetLoadPct / 100`。
- 按区域和固定司机优先级取得候选门店后，按确定顺序贪心装车。
- 当前车次已有门店时，如果加入下一家会超过 `targetCap`，关闭当前车次并创建下一车次。
- 单家门店体积超过 `targetCap` 但不超过 `hardCap` 时，允许该门店单独成车次。
- 单家门店体积超过 `hardCap` 时进入 `unassignedStoreIds`，阻止确认并提示需要拆单或更大车辆。
- 调整目标装载率后必须重新生成 `RouteTrip[]`；至少一组测试数据要证明 70%、88%、98% 得到不同车次结果。

固定区域是候选门店分组条件，不等于固定四辆车或固定四条线路。推荐车辆数来自生成后的 `ScheduleResult`。

## 9. 数据流

```text
导入订单
  → 校验门店和货量
  → 显示全部地图点位
  → 按容量/区域生成 RoutePlan[]
  → 为每条线路产生有序 storeIds + geometry + segmentDistances
  → 人工调整 storeIds
  → 重算 geometry/segmentDistances/totalDistance
  → 确认结果
  → 写入 mock 调度记录
  → 导出 CSV
```

## 10. 错误与边界处理

- 门店重复分配：阻止确认，并显示重复门店名称。
- 门店未分配：显示待处理数量，不能静默丢弃。
- 容量超限：超出部分进入下一车次或待处理集合。
- 地址无坐标：保留在订单列表，地图显示“无法定位”，不能伪造坐标。
- 路线 geometry 缺失：线路卡片显示异常，不能退化为一条穿地图直线。
- 空订单：显示明确空状态，不生成空线路。

## 11. 测试与验收

### 11.1 单元测试

- 所有当日门店恰好分配一次。
- 每条线路的门店顺序唯一。
- 路线 geometry 依次经过所有门店节点。
- 分段公里数之和等于总公里数。
- 人工调序同时更新地图、卡片和导出顺序。
- 容量超限产生下一车次或待处理门店。
- 原车次和导出数据不再包含已顺延门店。
- `neededVehicles` 来源于实际车次和待补车辆，不来源于固定模板数量。
- 70%、88%、98% 目标装载率生成不同的车次结果。
- 所有门店 `mapAnchor` 位于 `1917 × 1165` 坐标范围内。
- 每条线路允许的全部调序组合都能找到对应的双向道路段；缺失时测试必须失败。

### 11.2 页面验收

- 左侧显示四个物流模块且均可进入。
- 排线工作台不再是一张超长页面。
- 地图具有客户参考图级别的道路、水系、地名和门店标签细节。
- 生成后默认显示全部线路。
- 至少三条演示线路包含多个不同门店节点。
- 点击线路后节点编号与右侧顺序一致。
- 线路卡片文字清晰可读。
- 正常状态不显示异常提示。
- 页面中不存在“会议讲法、Demo、MVP、后续接入”等内部词语。
- CSV 导出包含线路、车辆、司机、门店顺序、装载率和总公里数。

### 11.3 浏览器验证

使用 headed 浏览器完成：

1. 物流演示登录并进入排线工作台。
2. 导入订单并确认全部门店点位出现。
3. 生成线路并确认全部线路可见。
4. 逐条点击，确认不同线路拥有不同门店节点。
5. 调整顺序，确认地图编号、公里数和导出预览同步变化。
6. 切换到调度记录、门店与订单、车辆与司机页面。
7. 截图保存关键状态。

### 11.4 测试深度声明

- `smoke`：页面、菜单、地图和四个模块能够打开。
- `medium`：完成订单导入、生成线路、切换线路、调序、确认和 CSV 下载，并核对页面状态变化。
- 本轮不声明 `deep`：当前无后端持久化、刷新后读回和下游模块真实回读。

构建通过不等于业务测试通过；交付总结必须分别报告单元测试、组件测试、smoke 和 medium 数量。

## 12. 演示数据标识

- 删除页面中的会议讲法、产品路线图和“后续接入”等内部说明。
- 物流演示租户的全局顶部区域保留低干扰“演示数据”标识，避免 mock 公里数被误认成真实路径规划结果。
- 标识只说明数据性质，不展示 GPS、算法或商业范围解释。

## 13. 非目标

本轮不实现：

- 真实高德/腾讯/百度地图 SDK
- 实时 GPS、车辆轨迹和偏航告警
- 成熟 VRP 路径优化算法
- 司机端 App
- 财务结算和司机工资
- 完整门店、车辆、司机 CRUD
- 后端 API 和数据库表
