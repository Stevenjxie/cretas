## 0. 本轮要立的三条原则（Steve 拍板）

1. **确定性层只能「认得」，不能「猜」。** 认不出来就往下传，最后由 LLM 猜。
   ⇒ 黑名单（对无限世界的枚举）必须退役；闭集白名单（我们自己定义的契约）保留。
2. **置信度不作为晋升门槛。** 一段长话里只差「高/低」一个字，置信度照样很高——
   它和向量相似度是同一种失效：连续的数、不可证伪。
   ⇒ 门槛只留「次数 >= 2」当筛子，**真正的闸是人审，且人必须看到当时的真实回答**。
3. **配额耗尽时整体封闭 AI 入口，不许降级到非 LLM 能力。**
   部分可用比完全不可用更危险——用户无法判断此刻答案的可信度。

## 1. 动手前的查证结果（**两处推翻了原计划**）

### 🔴 1.1 「会话配置」这一层不存在，需要新建

- 全仓 grep `user_store` / `store_permission` / `accessibleStores`：**Python 与 Java 均零命中**。
- ⇒ 优先级链的第 1 层（会话配置/门店权限）**不是接线问题，是要建的新能力**。

### 🔴 1.2 没有单店租户；两个高频真实租户的门店目录是空的

| 租户 | `dim_store` 行数 | 捕获提问数 |
|---|---|---|
| R_GML_DEMO | 132 | 168 |
| RES_3101_009（青花椒） | 38 | 1,600 |
| DEMO_REST | 27 | 11,176 |
| MOCK_REST | 10 | 1,433 |
| **RES_GML_001** | **0** | **1,303** |
| **R_XMX_FRESH（鲜行者）** | **0** | **1,285** |

- **「单店租户直接定死门店」这个简化不存在**（最小 10 家）。
- 🔴 **2026-08-07 晚订正：这一条我写错了。** 继续查证后发现
  `R_XMX_FRESH` / `RES_GML_001` 的 `dim_store`、`fact_pos_transaction`、
  `agg_restaurant_daily_totals` **三张表全空**，而它们的提问**确实有真实答案**

  按 `template_code` 一查就清楚了：这两个租户的 `RESTAURANT_OPS%` 命中数是 **0** ——

  数据在别的地方。

  ⇒ **实施顺序第 5 条「门店目录补数据」作废**：不存在「餐饮租户缺门店目录」这件事。
  真正在用餐饮 AI 的租户（MOCK_REST 10 家 / RES_3101_009 38 家 / DEMO_REST 27 家 /
  R_GML_DEMO 132 家）门店目录都是全的。

  🔑 判据（我这轮第二次栽在同一形状上）：**「某表 0 行」不等于「这个能力缺数据」——
  先确认这个租户走不走这条路。** 我此前只看了行数就断言「数据问题卡住 L1」，
  而它们连餐饮意图都没命中过一次。

### 1.3 计划缓存有指纹保护，晋升表没有（不对称）

```python
key = (factory_id, 归一化问句, f"{_PLAN_VERSION}#{_routing_rules_fingerprint()}")
```
注释记着真实事故：`#2043` 改了指标编译规则但没人改手写版本号，
**部署几小时后仍在重放修复前的计划**。于是加了路由规则指纹，规则一变缓存全失效。

**`ai_promoted_routes` 没有这个指纹**，只过滤「resolver 已退役」（`_VALID_CODES`）。
⇒ 规则改了，晋升行照旧回放 —— 这就是「晋升冻结」，且比缓存严重（永久、跨重启）。

## 2. 槽位优先级链

### 2.1 链

```
1. 会话配置    该用户的门店权限 / 租户默认时间口径     ← 🔴 需新建（见 1.1）
2. 上下文      上一轮问的是哪家店、哪个时间           ← 已有（澄清延续 + trusted context repair）
3. 默认        全部门店 / 最近30天 + **显式披露**      ← 已有（2026-08-07 上线）
4. 反问        前三层都空才问                         ← 已有
```

⚠️ **今天上线的「补默认」只实现了第 3 层**，且是无条件的。第 1、2 层没接进来。
这也是为什么放宽第 3 层会撞坏 5 个澄清链测试——**那些链就是第 2 层**，
不该被默认值绕过。判据：**第 3 层只能在第 1、2 层都空时才生效。**

### 2.2 哪些槽位可以有默认（按 spec 字段全量盘点）

| 槽位 | 能否默认 | 默认来源 |
|---|---|---|
| `store_scope` / `store_slots` | ✅ | 用户门店权限 → 上下文 → 全部门店 |
| `date_range` / `window_label` | ✅ | 租户口径 → 上下文 → 最近30天 |
| `ranking_limit` 前几名 | ✅ | 固定 Top 5（**现在每次由 T3 决定，本该是配置**） |
| `ranking_direction` 升/降序 | ✅ | 由问法定（最好/最高→降序，最差/最低→升序）——**闭集，不是猜** |
| `output_preference` 表格/文字 | ✅ | 由渠道定（web→表格，手机→文字） |
| `comparison` 对比基准 | ⚠️ | 环比可默认；同比/自定义必须问 |
| `metrics` 指标 | ❌ | **无无歧义默认**，缺了必须问 |
| `dish_slot` 具体菜 | ❌ | 没点名 = 全店，不是「默认某道菜」 |

🔑 **判据：能默认的是「范围类」槽位，不能默认的是「问什么」本身。**

## 3. 晋升审核台

### 3.1 门槛改造

| | 现状 | 改后 |
|---|---|---|
| 筛子 | 次数>=2 **或** 置信>=0.85 | **次数>=2**（去掉置信度） |
| 冲突 | 多 code 冲突则拒 | 不变 |
| 真正的闸 | 人审（但看不到回答） | **人审，且必须看到当时的真实回答** |

### 3.2 `--list` 要补的证据（现在给不出）

```
问句：       本月哪个店营业额最高
问过：       3 个租户 / 7 次
模型给的计划：STORE_MARGIN + dimensions=[store] + window=本月
**当时的真实回答**：（从 smart_bi_llm_fallback_log.answer 调出）
数字回查：   与库一致 ✓ / ✗
```

### 3.3 纯 LLM 辅助审核（人机结合）

一个**独立的全量模型**，不进生产链路，只在审核台上对每条候选独立判「这个回答对不对」，
给人第二意见。⛔ **它不授权，只是意见** —— 与「向量不授权」同一条原则。

### 3.4 晋升表补路由规则指纹

写入时记下 `_routing_rules_fingerprint()`；读取时指纹不一致 → **标记为待复审**
（不是直接失效，因为它是人审过的；但要让人知道规则变了）。

## 4. 配额耗尽整体封闭

- 依据 `llm_router` 现有的 `cb_open` / `quota_skip` 状态判定「AI 可用性」。
- **入口处**返回明确的「当前额度不足，AI 暂不可用」，不进任何层。
- ⛔ 不许降级到 B 轨继续跑。

**待 Steve 确认的边界**：缺口前置（「供应商报价还没有数据」，纯查表）与域外拒答
（「天气不在范围」）——这两条不依赖 LLM 且零风险，**是否也一起关**？
计划按「一起关」实施（用户分不清哪些答案可信），如需保留请在实施前说。

---

## 5. 措辞：多套模板轮换（不让 LLM 碰）

- **数据必须一样，措辞可以不一样。**
- 秒回类（今日营业额 / 这道菜毛利率 / 这道菜销量）：**模板池轮换**，零延迟零 token。
- 复杂追问、下钻：可用 LLM 措辞，数字仍来自确定性层（同 ④ 行动建议的形态）。
- 模板池像飞轮一样**批量人工构造**——「一个人能想到的常用说法」先写进去。

## 7. 验收判据

- **不许出现新的黑名单词**。任何「这些词不是 X」的枚举都算违规。
- 每条晋升必须有：真实回答证据 + 人审记录 + 路由规则指纹。
- 优先级链的第 3 层（默认值）**必须能被第 1、2 层抢占**，且有测试证明。
- 配额耗尽时，**任何层都不产出答案**，只产出「AI 暂不可用」。
- 措辞轮换后**同一问句的数字逐字相同**（数据一样、措辞不一样）。
