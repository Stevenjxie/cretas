# Android 新签名同包名迁移（2026-08-09）

## 决策与边界

- Android 包名继续使用 `com.cretas.foodtrace`。
- 1.0.4 起改用新的正式签名证书；由于旧私钥不可恢复，1.0.3 及更早版本不能原位覆盖安装 1.0.4。
- 本次只完成正式 APK、下载页和版本门禁迁移；不改变 RN 角色权限、业务操作或生产数据。
- APK 和下载页先上线，最低版本暂时保持 1.0.0。何时将最低版本提升到 1.0.4 属于产品发布决策，必须在用户确认后执行。

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

操作员、仓管、质检员及普通管理人员 — Android 安装经验不一，部分用户不理解“签名冲突”或系统安装器错误 — 需要在旧 App 被强制更新时独立完成一次卸载重装。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | App 提示当前版本已不支持，并提供更新按钮 | 点击更新按钮 | 浏览器打开官方迁移下载页，而不是直接进入安装器死路 |
| 2 | 页面突出提示“这次不能直接覆盖”，主按钮为下载 1.0.4 | 先下载 APK | 安装包完整保留在浏览器下载记录或“文件管理 > 下载” |
| 3 | 页面按顺序提示卸载旧版 | 卸载手机里的旧 App | 清除旧签名应用，为同包名新签名安装让路 |
| 4 | 页面提示从下载记录重新打开安装包 | 打开 `cretas-v1.0.4.apk` 并允许未知来源安装 | 1.0.4 安装成功 |
| 5 | 新 App 登录页 | 重新登录 | 恢复使用已同步到服务器的业务数据 |

### 摩擦点清单

| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 旧签名 App 直接安装新 APK 会被 Android 拒绝，用户看不懂签名冲突 | HIGH | fool-proof Rule 1 |
| F2 | 先卸载再找不到下载地址，会形成无法继续的死路 | HIGH | fool-proof Rule 5 |
| F3 | 用户可能误以为卸载会删除服务器业务数据，或忽略本机未同步内容会丢失 | HIGH | fool-proof Rule 2 / 错误恢复 |
| F4 | 新用户和旧用户共用下载页，步骤必须区分且不能出现多个竞争主操作 | MED | 信息密度 / 主操作唯一 |
| F5 | 版本门禁若在迁移页上线前强制，会把现有用户立即锁住 | HIGH | fool-proof Rule 1 |

### 每个摩擦点的设计回应

- F1 → 页面明确写“1.0.3 及更早版本不能直接覆盖”，不暴露“证书指纹”等技术术语。
- F2 → 固定顺序为“先下载 → 再卸载 → 从下载记录安装”，强制更新按钮最终指向迁移页而非 APK 直链。
- F3 → 同时说明“账号及已同步到服务器的数据保留”和“本机登录状态、未同步内容会清除”。
- F4 → 页面只保留一个 52px 高主下载按钮；首次安装用户直接安装，旧用户按下方四步操作。
- F5 → 先发布并回验 APK 与迁移页，最低版本保持 1.0.0；取得产品确认后再把最低版本提升至 1.0.4，并同步把 Android 下载地址切到迁移页。

## 发布与验证

1. 在 clean、exact `origin/main` 的工作树构建 1.0.4（versionCode 15）release APK。
2. 验证包名、版本号、APK SHA-256、新证书 SHA-256 与唯一 signer。
3. 发布版本化 APK 和下载页，公网回下载后再次验证字节数、SHA-256 与 signer。
4. 上线阶段只更新 latest/file size，minimum 仍为 1.0.0。
5. 产品确认强制时机后，将 minimum 提升至 1.0.4，并让 App 内更新按钮打开 `https://download.cretaceousfuture.com/`。
