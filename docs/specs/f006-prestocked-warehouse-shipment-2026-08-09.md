# F006 客户已有库存正式出库

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

仓管员 — 低技术素养、熟悉实物但不应理解销售预留台账或批次分配算法 — 在装车前核对销售交来的发货任务、填写实际装车数量并完成出库。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 待确认发货单，带发货单号、客户、销售订单和计划数量 | 打开一张待确认单 | 系统显示品名、计划数量、单位和默认实发数量 |
| 2 | 明确提示“客户已有库存会自动匹配销售订单预留批次” | 核对或修改实发数量 | 输入保留，负数在提交前被阻止 |
| 3 | 唯一主操作“确认并出库” | 点击一次 | 后端完整匹配预留批次后扣库存；匹配不足则整单不扣并给出解决办法 |
| 4 | 成功消息和刷新后的待办列表 | 无需回销售模块 | 发货单变为已发货、预留释放、批次已发数量增加 |

### 摩擦点清单

| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 仓管被要求返回销售订单手工分配批次，跨模块且容易选错客户库存 | HIGH | fool-proof Rule 3 / Rule 5 |
| F2 | 销售详情同时提供“确认发货”，职责边界不唯一，可绕过仓管 | HIGH | fool-proof Rule 2 / Rule 4 |
| F3 | PRESTOCKED 销售订单被误提示“缺客供料需求”，与已有成品库存语义相反 | HIGH | fool-proof Rule 2 |
| F4 | 仓管看不到本次要核对的品名、计划量与单位时容易输错 | MED | fool-proof Rule 1 / Rule 2 |
| F5 | 预留不足若在扣库中途才发现，会造成部分写入风险 | HIGH | fool-proof Rule 1 / 错误恢复 |

### 每个摩擦点的设计回应

- F1 → PRESTOCKED 在仓库确认事务内按当前销售订单 ACTIVE 预留自动生成精确批次分配；普通订单保留原批次规划方式。
- F2 → 销售端只建发货任务；旧销售直接发货 API 固定返回 410，界面只引导去“仓储管理 → 出货管理”。
- F3 → ORDER_DRIVEN 才显示客供原料收货进度；PRESTOCKED 改为显示客户已有成品库存及精确预留批次。
- F4 → 确认弹窗逐行展示品名、计划量、实发量和单位；主操作统一为“确认并出库”。
- F5 → 自动推荐数量必须先完整覆盖每个发货行才写分配；任何不足抛出带下一步的业务错误，事务回滚，不扣库存。
