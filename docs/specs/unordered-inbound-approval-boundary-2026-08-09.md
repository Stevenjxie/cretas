# 无订单入库申请与仓储任务边界

用户确认的单一业务真值：“无订单入库申请”只处理申请和审批；审批通过后才进入“入库任务与批次”，实际收货、库存增加和批次生成始终属于仓储任务域。

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

运营协调员 / 仓储审批人 / 仓管员 — 熟悉到货业务但不应记忆系统状态码和跨页规则 — 经常在手机或仓库电脑上快速登记无订单到货，需要系统明确告知当前只能申请、何时才能去收货。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 独立“无订单入库申请”入口和责任边界 | 点击“发起申请” | 仅打开申请所需的来源、客户、预计时间和说明 |
| 2 | 申请单号、归属和待审批状态 | 提交或撤回 | 未审批前不产生仓储待收货任务，不写库存 |
| 3 | 同一申请的身份信息与审批上下文 | 仓储通过或驳回 | 通过才交接任务；驳回必须留原因 |
| 4 | “已交接到入库任务与批次” | 进入关联任务 | 系统精确筛选到源申请，仓管再核对实物、数量和仓库 |

### 摩擦点清单

| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 申请与收货在同页，用户误以为提交即可入库 | HIGH | fool-proof Rule 1 |
| F2 | 审批操作缺少申请单号上下文 | HIGH | fool-proof Rule 2 |
| F3 | 驳回可不填原因，无法恢复 | MED | fool-proof Rule 3 |
| F4 | 移动端仍把新申请称为“待收货”，并在提交后将其隐藏 | HIGH | 信息密度 / 错误恢复 |
| F5 | 审批通过后仍要手工在入库列表查找 | MED | fool-proof Rule 5 |

### 每个摩擦点的设计回应

- F1 → 独立侧边栏页面，申请页不导入物料、数量、仓库或收货 API；后端以 `PENDING_APPROVAL` 和可收货状态集双重防线隔离。
- F2 → 审批对话框始终显示申请单号，列表同屏显示原因、归属和预计到达。
- F3 → 驳回原因前后端必填；审批意见和审批人/时间持久化。
- F4 → RN 统一为“待审批 / 审批通过 / 已驳回 / 已撤回”，待审批筛选从全部申请本地精确筛选，不再调用仓储可收货语义的 `openOnly` 过滤。
- F5 → Web 审批通过行提供“查看关联任务”，携带 `sourceType + arrivalNoticeId` 精确进入入库任务与批次。
