# RN 多设备登录与标签质检并发保护

## 目标

同一个工厂手机号账号允许在多台 RN 设备同时登录并保持独立会话。不同设备可并行处理不同标签质检任务；若误开同一任务，服务端必须保证只有第一份有效提交落库，禁止后提交覆盖，同时允许同一设备在网络超时后安全重试同一请求。

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像

质检员 — 设备操作熟练度不一，可能多人临时共用同一工厂账号 — 两台手机同时处理不同照片或任务，偶尔会误点同一任务。

### 用户旅程

| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 正常登录页 | 两台设备登录同一手机号 | 两台都保持在线，后登录不踢前设备 |
| 2 | 待审核任务列表 | 分别打开任务 | 不同任务可并行处理 |
| 3 | 同一任务被两台打开 | 两边分别编辑后提交 | 第一台提交成功并原子锁定结果 |
| 4 | 第二台提交旧结果 | 明确的已处理提示 | 不覆盖结果；点击按钮返回刷新后的待审核列表 |
| 5 | 第一台因网络超时重试 | 原提交页面仍保留 | 相同请求幂等返回既有结果，不重复写入 |

### 摩擦点清单

| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 后登录或单设备退出导致其他设备掉线 | HIGH | 内联错误恢复 / fool-proof Rule 5 |
| F2 | 两台设备提交同一任务产生后提交覆盖 | HIGH | fool-proof Rule 4 |
| F3 | 冲突只显示 409/500 等技术错误 | HIGH | 错误四位一体 |
| F4 | 网络超时重试导致同一设备重复写入 | HIGH | fool-proof Rule 4 |

### 每个摩擦点的设计回应

- F1 → 每次签发的访问令牌和刷新令牌带唯一会话标识；退出仅撤销当前令牌，不撤销该用户其他设备会话。
- F2 → 审核请求携带任务版本，服务端对任务加写锁并比较版本；第一份提交成功后，其他请求不可覆盖。
- F3 → RN 将并发冲突转成“这条质检已在另一台设备或页面完成”，提供唯一主操作“返回待审核列表”。
- F4 → 每次审核提交携带稳定的 `reviewRequestId`；相同请求重试直接返回已完成结果，不重复保存标注。

## 后端契约

- JWT access/refresh token 必须有随机 `jti`，同一账号连续登录两次也产生不同 token。
- `logout` 仅拉黑当前 access token，并仅撤销与当前 token 对应的历史 session 记录。
- 标签 QC 详情返回 `version`。
- 审核请求新增：
  - `expectedVersion`：打开任务时的服务端版本。
  - `reviewRequestId`：本次提交的客户端幂等键。
- 已完成任务：
  - `reviewRequestId` 相同：返回既有结果，视为幂等重试。
  - `reviewRequestId` 不同：返回业务冲突 `LABEL_QC_ALREADY_REVIEWED`。
- 版本不一致：返回业务冲突 `LABEL_QC_REVIEW_STALE`。
- 旧版 RN/Web 未携带新字段时，服务端按审核人和完整审核载荷生成稳定请求指纹；相同载荷重试幂等，不同载荷仍执行先提交者生效，避免发布时破坏旧客户端。

## RN 行为

- 打开任务时保存详情版本。
- 本次页面生命周期内生成并复用同一个 `reviewRequestId`。
- 冲突时不清空本地标注；显示发生了什么及下一步按钮，用户确认后返回并刷新待审核列表。

## 验收

- 同一手机号连续两次登录得到不同 access token 和 refresh token，两个 access token 均可独立通过认证。
- 设备 A 退出后，设备 B token 仍有效。
- 两个事务并发审核同一任务时只允许一个结果落库。
- 同一 `reviewRequestId` 重试不产生重复人工标注。
- 不同任务可由同一账号的不同设备并行审核。
- 真实 JPA Context、Java 目标测试、RN API/model/screen 目标测试和字段契约检查通过。
- `NOT_DEPLOYED`。
