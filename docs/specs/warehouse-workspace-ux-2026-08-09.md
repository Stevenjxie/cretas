# 仓储入库工作区与多任务导航 UX 规格

## UX Flow Analysis（ux-flow 门控产出，不可删除）

### 用户画像
仓管员与仓储主管 — 日常更关注当前应处理事项，技术素养差异较大 — 需要快速区分待收货、处理中、部分入库和已生成批次，并避免把“申请审批”误认为“已经入库”。

### 用户旅程
| 步骤 | 用户看到 | 用户操作 | 期望结果 |
|------|---------|---------|---------|
| 1 | 左侧菜单真实待办红点 | 点击“入库任务与批次”或“无订单入库申请” | 进入对应待办，不需要先打开列表判断是否有事 |
| 2 | 入库任务生命周期页签 | 选择待收货、收货中或部分入库 | 只显示当前阶段的真实任务，并保留清晰的主操作 |
| 3 | 已入库批次页签 | 切换批次明细或物料汇总 | 查询已生成的真实库存批次，不与审批状态混杂 |
| 4 | 顶部多任务标签 | 切换已打开页面 | 返回原页面时保留搜索、分页和未提交表单状态 |
| 5 | 拖动任务标签到右侧 | 松开标签 | 右侧以只读方式展示参考页，左侧当前任务不被覆盖 |

### 摩擦点清单
| # | 摩擦点描述 | 严重程度 | 来源规则 |
|---|-----------|---------|---------|
| F1 | 审批、收货任务和库存批次混在同一长页，用户无法判断当前处理阶段 | HIGH | fool-proof Rule 2 |
| F2 | 菜单没有待办数量，只能逐页打开确认 | HIGH | 内联 UX 规则：信息密度 |
| F3 | 查询历史价格或库存时离开当前表单，返回后可能丢失上下文 | HIGH | fool-proof Rule 5 |
| F4 | 同一任务同时出现多个状态口径，分类可能重叠 | MED | fool-proof Rule 1 |
| F5 | 红点接口失败时显示 0，会误导用户认为没有待办 | HIGH | 跨规则铁律 |

### 每个摩擦点的设计回应
- F1 → 无订单入库页只负责申请与审批；入库页第一层使用互斥生命周期页签，批次作为“已入库”阶段展示。
- F2 → 菜单红点只统计真实、可处理的待办；处理成功后通过统一事件立即刷新，并保留 60 秒低频兜底刷新。
- F3 → 全局任务标签使用 keep-alive 保留页面实例；拖到右侧后通过同源只读参考框展示，禁止指针交互。
- F4 → 状态优先级固定为“部分入库 > 收货中 > 待收货”，每个开放任务只进入一个分类。
- F5 → 单个计数请求失败时隐藏该红点并保留其他成功计数，不用 0 伪装成功。

## 交互与数据边界

- 菜单计数不是历史总数：销售订单排除已完成/已关闭，无订单入库只统计待审批，入库任务统计开放收货任务。
- “已入库”数量来自现有 material-batches 分页总数；不把批次数冒充任务数。
- 只读参考页不允许鼠标和键盘业务操作，不扩大生产写入面。
- 本批不修改 Entity、Repository、Flyway 或仓储写服务。
