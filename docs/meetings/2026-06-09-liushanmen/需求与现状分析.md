# A · 一物一码 & 主数据编码体系

> Gap 分析 — 2026-06-09 六扇门需求 vs 现有 Cretas 系统。
> 代码证据基于: `RawMaterialType`/`ProductType` 实体, `RawMaterialTypeServiceImpl`/`ProductTypeServiceImpl`, `web-admin/src/views/warehouse/material-types/list.vue`, `system/products/index.vue`, `MaterialBatch` 实体。

---

**A1 · 物料主数据字典(原料/成品/辅料/蔬菜)** [partial · web-admin+backend · M · P0-半月上线]
— 原料/辅料/蔬菜 = `RawMaterialType`(category 区分), 成品/SKU = `ProductType`。CRUD + 软删 + 工厂内 code 唯一 + 抄码品标记齐全。
现状: `RawMaterialType`(code/name/category/unit/unitPrice/storageType/shelfLife/min-maxStock/isAbacaPackaging) + `ProductType`(productCategory: FINISHED_PRODUCT/RAW_MATERIAL/PACKAGING/SEASONING/CUSTOMER_MATERIAL); web-admin `warehouse/material-types/list.vue` + `system/products/index.vue` 已建; 防呆建档(必填极简 + 名称自动匹配填充)已 ship。
缺口: 客户"五大项(原料/成品/辅料/蔬菜/BOM)"中蔬菜目前靠 category 标识无独立校验; "采购原料登记 vs 入库登记"两步分离需确认是否清晰; 逐个录入 UX 优化。
依赖: 无(地基)。

**A2 · 物料编码自动生成(前缀+流水)** [partial · backend · M · P0-半月上线]
— 创建时不传 code, 后端按 category 选前缀 + 扫描最大序号 +1 零填充3位生成, 防手敲重码。
现状: `RawMaterialTypeServiceImpl.getMaterialCategoryPrefix`(原料→YL/肉类→RL/包材→BC/其他→WL) + `generateNextCode` 扫 `findCodesByFactoryIdAndCodePrefix` 取 max+1 `%03d`; 创建时不传 code 自动生成; 唯一性 existsBy 兜底; 客户名拼音首字母前缀(ProductType)。
缺口: **不满足客户要求的 16 位分段结构**(前10位固定段不可改 + 后6位流水); 缺"逐级下拉级联生成"(选类型→自动001→选部位→001的001); 前缀分类映射(001=原料/002=包材/003=辅料 vs 当前 YL/RL/BC)需与客户最终编码方案对齐; 仅英文+数字约束已满足。
依赖: A1。

**A3 · 16位分段编码体系 + BOM主编码关联** [missing · backend+web-admin · L · P1-近期]
— 编码=16位: 前10位固定段(级联选类型/部位/品类自动拼, 用户不手敲) + 后6位系统流水; BOM 只关联前三位主编码(部位/品类), 实现"扫编码自动弹出对应物料"全关联。
现状: 无。当前编码是扁平 prefix+3位序号, 无分段语义, 无主编码层级, BOM 关联走 `materialTypeId`(UUID)非编码前三位。
缺口: 全新设计 — 编码分段定义表(类型/部位/品类字典) + 级联下拉 UI + 16位生成器 + BOM 主编码(前三位)关联键; 是客户编码体系的核心诉求, 但客户也说"编码规则怎样都无所谓能搜到即可", 需先与客户敲定到底要 16 位结构还是当前扁平方案够用。
依赖: A1, A2(替换/扩展现有生成器), B流 BOM。

**A4 · 原料厂号/产地字段(批次属性)** [missing · backend+web-admin+RN · M · P0-半月上线]
— 同一原料一个编码, 不同厂号/产地作为批次属性区分, 避免"同供应商品牌多厂号串货"; 厂号≠供应商, 独立字段; 暂不做匹配校验; 录入时厂号录清楚, 生产人员领料/报工时可选实际厂号。
现状: **无独立字段**。`MaterialBatch` 仅有 supplierId + 通用 `customFields`(jsonb) + 注释提到产地可作 customer-configured 字段; `material-types/list.vue` 无厂号/产地输入。
缺口: `MaterialBatch` 加 `factory_number`(厂号) + `origin_place`(产地)两列(或 RawMaterialType 层标记需采集); 入库录入 UI(web + RN)采集厂号; 领料/报工时按厂号选实际批次(关联 C流报工)。这是客户"一物一码防出错料"的实际落点。
依赖: A1, F流 入库。

**A5 · 一物一码 / 批次条码标签(防出错料)** [partial · backend+web-admin · L · P0-半月上线]
— 最紧迫: 物料多仓库可能出错料, 要一瓶一码/一物一码; 后期扫编码自动弹出对应物料(全关联), 显示编码/厂号/重量。
现状: `Label` 实体(label_code/label_type/二维码内容URL)提供追溯标签/条码基础设施(成品追溯层); `SalesOrderItem`/`EmployeeProcessSegment` 有 barcode 字段。
缺口: 原料/批次级一物一码标签生成 + 打印模板 + 扫码弹出物料(编码/厂号/重量)的查询端点 + RN/web 扫码交互未落到原料批次场景; 当前 Label 偏成品追溯非原料防错料。需确认客户是要"打印贴标签扫码"还是"系统内唯一编码搜索"(客户口径在两者间摆动)。
依赖: A1, A2/A3, A4(扫码显示厂号/重量)。

**A6 · SKU 组装模型(模板+SKU+规格自动拼+名称推导)** [exists · web-admin+backend · S · P0-半月上线]
— 一个产品=一个SKU, 模板/SKU 两级(template_id 区分); 规格由结构化字段(克重+二级单位+装箱系数+一级单位)自动拼; 基础名称从"产品名-客户前缀-规格后缀"自动推导; 创建SKU自动识别规格; 智能填充(LCS 历史匹配)。
现状: `ProductType.templateId`/`recipeVersion` SKU 组装模型; `assemble-sku` 端点; `suggestDefaults`(LCS 历史记忆带入温区/规格/克重/出成率/基础名) 阈值 0.34; `system/products/index.vue` 规格自动拼(T153) + 基础名推导(T153 Fix B1) + 客户前缀剥离; 关联客户/产品图片/温区齐全。
缺口: 基本完整。客户"创建SKU每个产品签编号一二三"的级联编号若走 A3 需联动。
依赖: A1, A2。

**A7 · 两级单位换算(框/盒/袋, SKU + 原料)** [exists · web-admin+backend · S · P0-半月上线]
— 1框=10盒级别换算; SKU 一级/二级单位; 原料包装层级二级/三级内联换算。
现状: `ProductType.level1Unit` + `boxConversionCoefficient` + `gramsPerUnit`(T123); `material-types/list.vue` 二级/三级换算内联行 + live preview; `MaterialUomConverter` 服务(kg称重/装箱口径); RN MaterialBatchPicker。
缺口: 基本完整。需确认成品(份/盒→kg)与原料(称重 kg)口径在报工/成本链路一致(已有 UoM 模型, project_uom_unit_model 记录)。
依赖: A6。

**A8 · 价格/税率口径(成本价/销售价/含税未税)** [partial · backend+web-admin · M · P0-半月上线]
— 产品维护成本价+销售价两价; 含税率字段(9点/13点, 税由工厂承担, 成本核算用未税价); 建SKU 时不需价格, 价格在创建销售订单时填。
现状: `ProductType.unitPrice`(@PriceSensitive) + `taxIncludedUnitPrice`(含税单价) + `settlementMethod`; `RawMaterialType.unitPrice`/`movingAvgPrice`(移动均价雏形); @PriceSensitive 价格脱敏。
缺口: 缺显式税率字段(9%/13% 枚举)+ 含税↔未税自动换算; 缺成本价 vs 销售价并列维护(当前 unitPrice 单价语义模糊); 三价体系(BOM价/销售价/实际成本价对比)属 B 流。
依赖: A6; B流(成本算法)。

**A9 · 包材建档(生产/厂长建, 跟随生产, BC/BFF前缀, 关联客户)** [partial · web-admin+backend · M · P1-近期]
— 包材跟随生产流程建档(生产/厂长建, 客户只引用); 建档与建项(检验)分离; 编码 BFF/BC 前缀顺序递增; 必填极简(名称+箱数+规格); 可关联固定客户(非必填); 同款不同规格/客户建多条(前缀字母区分客户); 在 SKU 模块建档。
现状: 包材作为 `productCategory=PACKAGING`(ProductType)或 category=包材(RawMaterialType, 前缀 BC)管理; SKU 组装模型 + 关联客户(customerId/relatedCustomer)已支持; 防呆极简建档已 ship。
缺口: 缺"包材跟随生产建档 vs 客户预建"的权限/入口约束; BFF 前缀(当前只有 BC); 客户前缀字母区分同款多条规则; 建档与检验建项分离的明确边界; 扫编码自动弹出对应包材(同 A5 全关联)。
依赖: A1, A2, A5。

**A10 · 测试批 vs 实际生产批边界(供单单厂号 vs 实际多厂号)** [missing · backend+RN · M · P2-后续]
— 供单理论绑单厂号但实际投料可能跨厂号(如 50CL 321厂/411厂), 需支持生产人员在领料/报工时选实际厂号, 否则成本追溯失真; 测试采购建多编码污染 BOM 的边界。
现状: 无。报工/领料按 `materialTypeId` + 批次, 但批次无厂号维度(见 A4)。
缺口: 依赖 A4 厂号落地后, 报工/领料 UI 支持选实际厂号; 测试编码隔离(不污染正常品 BOM)机制。客户也说"批次不去管它", 优先级低。
依赖: A4, C流 报工/领料。

# B · BOM(5大项) & 三价成本 — Gap 分析

> 流 B: BOM 配方建模 + 三价(标准BOM价/销售价/实际成本) + 出成率 + 半成品成本卷积 + 人工成本口径。
> 探测基准: `BomRecipe`/`BomRecipeItem`/`CostRollupUtil`/`BomCostSummaryDTO`/`FinanceCostBreakdown`/`SemiFinishedInventory`/`WipInventoryServiceImpl`/`BomYieldEstimateService`/`LaborCostConfig`/`OverheadCostConfig` + web-admin `production/bom/index.vue` + RN `factory/bom/*`。

---

**B1 · BOM 配方主数据 & 版本管理** [exists · backend+web-admin+RN-app · M · P0-半月上线] — BOM 配方头(产品/版本/is_current/出成率/单份产出克数/状态机 DRAFT→ACTIVE→ARCHIVED)+ 配方子项(原料硬外键防手写/标准用量/出成率/单价/分类 RAW·AUXILIARY·PACKAGING/可选项/替代分组)。
现状: `entity/bom/BomRecipe.java` + `BomRecipeItem.java` (硬外键 `material_type_id→raw_material_types` ON DELETE RESTRICT, 禁手写)。`BomRecipeServiceImpl` 全 CRUD+clone+activate(同产品其余 is_current 置 false)+softDelete。`recipe_code` 自动生成 `BOM-YYYYMMDD-NNN`。web-admin `production/bom/index.vue` 原辅料/人工/均摊三栏 + RN `factory/bom/BomEditorScreen.tsx`/`BomConfigScreen.tsx`。`ECNServiceImpl`/`BomVersionServiceImpl` 工程变更/版本审批。
缺口: 客户「编码前三位主编码=BOM 关联键」(流 A 编码体系)尚未接入 BomRecipeItem 关联逻辑; 半成品作为配方项(半成品当原料用)的嵌套引用尚未建模(见 B6)。
依赖: A(原料/SKU 主数据编码)。

**B2 · 出成率折算 & 成本卷算(原辅料成本)** [exists · backend+web-admin · S · P0-半月上线] — 出成率折算公式 `actualQty = stdQty/(yieldRate/100)` + 单项成本 `actualQty×unitPrice` + 配方总料成本聚合(任一项无价→总价诚实 null 不显 0)。
现状: `service/shared/CostRollupUtil.java` (factory BOM 与餐饮菜品成本单一事实源, scale-6 数量/scale-4 成本/HALF_UP)。`BomRecipeItem.calculateActualQuantity()`/`computeItemCost()` + `recomputeMaterialCost()` (hasNullPrice→totalMaterialCost null)。`BomRecipeItemTest`/`CostRollupUtilTest` 覆盖。
缺口: 无(料成本核算完整)。注: 整产品级 overall_yield_rate 与 item 级 yield_rate 并存, UI 口径需确认。
依赖: B1。

**B3 · 三价体系(标准BOM价 vs 销售价 vs 实际成本)对比** [partial · backend+web-admin+RN-app · L · P0-半月上线] — 客户核心诉求: BOM 标准成本(爆末理论价) vs 销售价 vs 最终实际成本三价齐全, 财审/事后分析对比, 超支(>5块)报警。
现状: 三价字段齐全 — `BomRecipe.standardSalePrice`(标准售价) + `total_cost`(标准BOM成本) + `SalesOrder.estimatedCost/estimatedProfit`(预估) + `SalesOrderItem.costUnitPrice`(实际成本回填)。`SalesServiceImpl.getFinanceCostBreakdown()` 已产出 `FinanceCostBreakdown`(`bomStandardCost`/`currentEstimatedCost`/`actualCost`+预估·实际利润率+行级对比+缺失诚实 null+dataSourceHint)。web-admin `sales/finance-review/detail.vue` 展示。`@PriceSensitive` 全字段脱敏。`SalesServiceImplCostBreakdownB2Test` 覆盖。
缺口: **(1) 超支阈值报警未实现** — 客户「标准成本18 vs 实际成本9, 差5块触发报警」, 现仅展示对比无阈值告警/通知; (2) **偏差及时反馈研发/销售** 的回流通知缺; (3) 三价对比目前只在销售订单财审视图, 缺产品(SKU)级三价看板(研发维护视角)。
依赖: B1, B2, C(实际成本来自报工)。

**B4 · 人工成本 & 均摊费用配置(标准BOM 人工口径)** [partial · backend+web-admin · M · P1-近期] — BOM 含人工费(研发预估口径=元/kg成品) + 均摊费用; 与财务实际人工(按工序工时×人数)两个口径并存对比。
现状: `entity/bom/LaborCostConfig.java`/`OverheadCostConfig.java` + `BomCostSummaryDTO`(materialCostTotal+laborCostTotal+overheadCostTotal+totalCost 三段式) + web-admin BOM 页人工/均摊两栏。`BomRecipe.total_labor_cost`/`total_overhead_cost` 字段在位。
缺口: **(1) 研发预估人工口径"元/kg成品"** 与现有按工序 unitPrice 配置口径需对齐(客户明确排除按件/按小时); **(2) 预估人工 vs 实际人工(I 流人效)对比** 未打通(衔接点, 算法待定); (3) 客户「成本核算确认范围=人工+包材+辅料, 排除能源水电」需在 totalCost 口径文档化约束。
依赖: B1, I(实际人工采集已在报工层 workerCount/workMinutes)。

**B5 · 出成率自学习(报工迭代滚动更新)** [exists · backend+web-admin · M · P1-近期] — 未生产过先手填预估出成率; 报工后系统按已完成批次 cumulativeYieldRate 反算建议出成率, 下批领料用上批基准(滚动迭代)。
现状: `service/bom/BomYieldEstimateService` 三端点 — 单产品评估(近10批 P50 中位数, 样本≥3)/批量预览(当前vs建议)/确认后批量写入(写 BomChangeLog)。web-admin BOM 页 `bomYieldEstimateApi` + `RecalculatePreview`/`RecalculateApply` + `MagicStick` 重算按钮。
缺口: 客户「每天产量对应实际出成率统计/各产品建实际出成率看板」的可视化统计页可补; 自学习已是 pull(用户触发重算)而非每批 push 自动更新, 客户可接受但需确认。
依赖: B1, C(报工 cumulativeYieldRate)。

**B6 · 半成品成本核算(单库多 SKU code + 混合加权计价)** [partial · backend · XL · P1-近期] — 半成品按重量挂账并核算价格; 单库多 code 承载多价格(否决建多库); **核心算法: 半成品 + 新原料同步投入时的加权价格**(今淋1吨用500kg剩500kg, 下批500kg旧+新淋1吨同步投, 一吨一价格 → 加权混合计价)。
现状: `entity/SemiFinishedInventory.java`(WIP 余额库: produced/consumed/available + accumulatedCost + unitCost + 乐观锁 + jsonb 溯源)。`service/wip/WipInventoryServiceImpl`: 报工产出 upsert WIP(跨天累加同 task)+下道领用扣减 + `unitCost = accumulatedCost/produced` 滚动。半成品当原料用(sourceWipNo 领用)已支持。
缺口: **(1) 混合加权计价算法缺** — 现 unitCost 是单 task 滚动均价, 客户要的是"旧批半成品库存价 + 新投原料价 按量加权"的混合计价(唯一具体规格算法, 转录 [27:45]-[28:25]), 需新算法层; **(2) 半成品多状态多价格(焯水/熟制两个半成品两个价)用同库不同 code 区分** — SemiFinishedInventory 按 task/intermediateBatchNo 区分, 但与"半成品作为带 code 商品(SKU)管理"的主数据建模未完全打通。

## 关键判定说明

- **付款 + 进项票是 D 流真正缺口**: 单据层(订单/入库/审批/退货/供应商/询价)已相当完整, 但客户最在意的"付款申请替代钉钉 + 出纳 + 进项票催票核销"几乎全缺。现有 InvoiceRecord/PaymentRecord 均为**销售侧**(customerId/salesOrderId), 不可直接复用为采购进项。
- **AR/AP 台账 ≠ 付款工作流**: ArApController 是记账冲减台账, 客户要的是 申请→审批→出纳 业务流, 需新建。
- **超收防呆已有但非"异常单"模型**: 当前是 30% cap 硬拦截(fool-proof), 客户要的是"生成异常单退回采购人判断退/入"的分支流, 属增强。
- **审批引擎可复用**: PurchaseOrderApprovalRule + canvas workflow 已支撑采购审批, 付款审批流可在此之上扩展, 降低 L 工作量。
