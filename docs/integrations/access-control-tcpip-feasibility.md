## 2. 架构：设备主动外连（这是本方案成立的地基）

协议支持两种模式，包内 Java demo 用的是第二种：

> 「控制器 web 界面-网络界面上，通信模式需要选择**"设备作为客户端"**，且服务器端口修改为和 demo 中一致。默认为 8001。」

即 **工厂的门禁控制器主动拨号连我们的服务器**，我们只需监听一个 TCP 端口。

带来的直接好处：

- 不需要 VPN / 内网穿透
- 不需要在工厂路由器做端口映射
- 不需要我们的服务器能访问工厂内网
- 工厂侧只需在控制器 web 页面填我们的服务器地址

配合下面的「拉指令」，**权限下发也走同一条入站连接**，全程零反向通道。这比海康 ISAPI / 大华那种「我们主动去连设备」的模式省掉了整类网络工程问题。

## 3. 协议要点

### 3.1 帧结构

```
STX(0x02) | Rand | Command | Address | Door | LenL | LenH | Data... | CS | ETX(0x03)
CS = 从 STX 起到 CS 前一字节的逐字节异或
```

样例（心跳）：
```
02 AA 56 00 00 00 15 00 09 08 18 0C 07 0A 00 00 00 00 00 00 00 00 00 00 00 50 00 00 A3 03
```

⚠️ 长度字段**不是固定值**，协议明确要求「接收方需要忽略掉后面多出来的部分」——解析必须按长度+校验走，不能按固定偏移硬解。

### 3.2 设备 → 我们（主动上传，必须应答）

| Cmd | 内容 | 频率 |
|---|---|---|
| `0x56` 心跳/状态 | 序列号(6B)、控制器 RTC、4 门开关状态、门磁/按钮/防拆/火警输入、型号、固件版本、上次拉指令序号+结果 | 每 5–6 秒；状态变化立即发 |
| `0x53` 刷卡记录 | **卡号(4B) + 时间(6B) + 类型(低7位=事件码, 最高位=进0/出1) + 门号 + 是否还有记录 + 流水号** | 有记录时约每 3 秒一条 |
| `0x54` 报警记录 | 时间 + 事件码 + 门号 + 流水号 | 同上 |
| `0x52` 卡状态 | 防潜返用，同区域多控制器状态同步 | 同上 |

**应答契约**: 记录类必须回流水号；「如果不应答，或者应答错误，控制器会重复发送同一条记录」。心跳不应答 → 「超过 10 秒后控制器会断开连接」。

### 3.3 我们 → 设备

开门 `0x2C` / 常开 `0x2D` / 关门 `0x2E` / 锁门 `0x2F`、时间同步 `0x07`、增删改卡 `0x62`、批量加卡 `0x88`、开放时间段 `0x0D`、假日 `0x09`、清空卡 `0x17`、门参数 `0x61`、控制器参数 `0x63`、复位 `0x04`、报警/火警继电器 `0x18`/`0x19`、禁止读卡 `0x5A`、改 IP `0x08`。

### 3.4 拉指令（Pull Command）

固件 2018-08-17 之后支持。机制：

> 服务器备好指令列表 → 心跳到达时，应答里**搭一条指令 + 4 字节随机序号** → 控制器执行后立即再发一个心跳带回该序号与成功/失败 → 服务器比对序号确认，再发下一条。序号为 0 表示无指令或出错。

约束：
- **单个心跳应答包 ≤ 512 字节**
- 支持「除批量下载卡以外的全部通讯指令」（`0x88` 走不了）

厂商另提供 B 方案：不碰协议，第三方往门禁软件的 `TPullCmd` 表插指令，由厂商软件负责与设备通讯。字段：`Priority / ControlID / DoorAddress / Command / CmdHex`（红色必填）。**如果客户已在跑厂商门禁软件且我们能访问其 SQL Server，这条路一期开发量小得多**——待确认。

### 3.5 设备发现

UDP 广播，控制器监听 9000，回包也发 9000。搜索指令 `02 A0 99 00 00 00 00 3B 03`。
型号值：`1` 单门 / `2` 双门 / `3` 四门 / `6` 电梯 / `11` 闸机。

### 3.6 事件码（`事件类型.xlsx`，103 条）

考勤相关：`0` 单卡识别、`10` 出门、`11` 进门、`12` 卡加密码、`13` 双卡开门、`26/27` 自由进出、`62/63` 多人进/出。

异常/安防：`1` 无效卡号、`2/3` 时区错误、`16/17` 无效卡进/出、`18/19` 黑名单、`39` 读卡器防拆、`47` 胁持、`48` 防拆、`49` 潜返、`56` 门报警、`57` 开门时间太长、`58` 门没锁、`72` 火警、`75` 控制器启动。

## 4. 与 Cretas 现有能力的对接

### 4.1 已有的部分（本仓已实现，无需新建）

| 能力 | 位置 |
|---|---|
| 员工 NFC 卡（手机当读卡器） | `frontend/CretasFoodTrace/src/utils/nfcUtils.ts`、`NfcCheckinScreen.tsx`、`NfcTagManagementScreen.tsx`；`react-native-nfc-manager@3.17.2`；标签格式 `CRETAS:EMP:{employeeId}:{factoryId}`（NTAG213），无 NFC 时降级 QR |
| 考勤打卡 | `entity/TimeClockRecord.java`（上下班/休息/`work_duration`/`attendance_status`/位置/设备/GPS/HR 手改审计）、`TimeClockService`、`TimeClockController` |
| 工序时段 | `entity/workreport/EmployeeProcessSegment.java`（一天多条 segment，`ACTIVE → CLOSED_NORMAL / CLOSED_EARLY 欠退 / CLOSED_SWITCH 换岗`） |
| 考勤异常 | `service/hr/impl/AttendanceExceptionServiceImpl.java` |
| AI 工具 | `ClockInTool` / `ClockOutTool` / `AttendanceStatsTool` / `WorkerRealtimeCountTool` / `OnlineStaffCountTool` |
| 硬件对接先例 | `client/isapi/IsapiClient.java`（海康 ISAPI + Digest）、`client/dahua/DahuaClient.java`（大华）——目前用于摄像机 |

### 4.2 门禁能给 / 不能给

| 客户要的 | 门禁能否给 | 结论 |
|---|---|---|
| **工作时间** | ✅ 能 | 刷卡记录带 `卡号+时间+进出+门号`，直接映射 `TimeClockRecord`。工人不用再手动打卡 |
| **在哪个车间** | ✅ 能（有条件） | 控制器有 1/2/4 门型号。**每个车间一道门**时可自动定位，与 `EmployeeProcessSegment` 的换岗语义天然对齐 |
| **工作效果** | ❌ 不能 | 门禁只知「谁几点进了哪个门」，不知产量/良品率。**必须继续走现有报工链路** |

**组合口径（给客户讲这个）**:

```
门禁进出时间 = 在岗工时（分母，自动采集，工人无感）
报工产量     = 产出（分子，现有能力）
                    ↓
              人效 / 工时成本
```

⚠️ 沟通要点：不能让客户以为「装了门禁就能看到人效」。门禁解决「人在不在、在哪儿」，报工解决「干了什么」。

### 4.3 反向控制（客户说的「据此做门禁」）

- 员工离职 → 系统停用，下一个心跳即删卡（不用管理员去门禁软件里操作）
- **排班联动**：只有今天排到班的人能进车间门（开放时间段 `0x0D` + 权限位）
- 无证上岗拦截：质检员证书过期 → 自动收回质检间权限
- 临时工/外包：用卡片有效期功能（精确到年月日时分）自动到期

## 5. 硬约束与坑（必须在设计阶段解决）

### 5.1 卡编号不能用 employeeId ⛔

> 「卡编号必须从 0 开始，不得间断，不得重复，不得超出控制器的卡容量（约 3-6 万）。软件删除一个卡的时候只是空出该编号。增加一个卡的时候，需要先使用前面被删除的编号。」

我们的 `employeeId` 是 Long 且不连续，直接当卡编号会瞬间超容量。
**必须建每控制器的槽位分配表**：`controllerSerial + cardIndex → employeeId`，删人时回收槽位供复用。
删除语义 = 用卡号 0 覆盖该 index（「删除、添加、修改都是一样的」）。

### 5.2 心跳 5 秒内必须应答 ⛔

TCP server **不能与业务逻辑同步耦合**——心跳处理线程里不能查库、等锁、调 Python 服务。必须「立即 ACK + 异步落库」。

当前后端是 `spring-boot-starter-web`（Tomcat），pom 中**无 netty**。方案二选一：加 netty 依赖，或独立进程跑这个 TCP 服务。

### 5.3 事件是 at-least-once，必须幂等 ⛔

不应答就重发同一条。且**流水号只有 1 字节（0-255）会绕回**，不能单独当唯一键。
去重键建议：`controllerSerial + 卡号 + 事件时间 + 门号 + 事件码`。

### 5.4 时间来自控制器 RTC，会漂

时间戳是设备本地时钟（年份需 +2000）。断电/晶振漂移会让考勤时间错乱。
**必须定期 `0x07` 同步**：建议每次连上 + 每天一次。

### 5.5 安全：明文、无认证 ⚠️ 最需要决策的一点

协议明文 TCP，设备身份**只靠 6 字节序列号**，无密钥、无签名、无 TLS。
知道我们 IP+端口的任何人可伪造序列号 → 伪造考勤、伪造报警、耗尽连接。

缓解手段（按强度）：
1. 白名单：只接受已登记序列号 + 来源 IP 段
2. 走内网/专线，不暴露公网端口
3. 前置自研 TCP 网关做认证转发

另有 **OEM 客户代码**字段：心跳应答必须回正确值，设备才认。**该值需向供应商索取**。

### 5.6 文档质量

协议文档的字段表在 Word 里是表格，转文本后被压成一行，可读性差。
**实现时以 Java demo 代码为准**（`StandTCPCmd.java` 448 行 / `StandTCPCmdBase.java` 444 行 / `TCPCmdStruct.java` / `TCPController.java` 563 行），文档仅作参考。

## 6. 结论与粗估

**结论：可实现，且是较易接入的一类设备协议。**

理由：① 设备主动外连，绕过内网穿透这一整类问题；② 拉指令让下发复用同一连接；③ 有完整 Java+Netty 服务端 demo，与我们的 Java 21 / Spring Boot 3.2.12 栈同源；④ 考勤/工时/工序数据模型已存在，门禁事件基本是往现成表里灌。

**粗估：1 人 3–4 周**（基础版，不含排班联动与人效打通）

| 模块 | 估时 |
|---|---|
| 协议编解码 + Netty server + 心跳应答（移植 demo） | 3–5 天 |
| 事件落库 + 幂等去重 + 映射 `TimeClockRecord` | 3 天 |
| 卡槽位分配 + 拉指令队列 + 权限下发 | 5 天 |
| web-admin 设备管理界面（控制器列表/在线状态/发卡/开门） | 5 天 |
| 真机联调 + 压测 | 5 天 |

二期（增值点）：排班联动门禁权限、门禁工时 × 报工产量 = 人效、异常事件（防拆/胁持/无效卡）接告警。

## 7. 待客户确认（阻塞立项）

1. **控制器型号与固件日期** — 单门/双门/四门/闸机？固件是否 2018-08-17 之后（决定能否用拉指令，这是方案地基）
2. **OEM 客户代码 + 设备序列号** — 心跳应答要用，缺则设备不认我们
3. **买了几台、几个门、装在哪** — 只有大门口一道门 → 只能做考勤，做不了「在哪个车间」
4. **网络环境** — 设备能否访问公网；我们需新开一个 TCP 端口（demo 默认 8001），阿里云安全组需放行；端口号待定
5. **是否同时买了厂商门禁软件** — 若已在跑且我们能访问其 SQL Server，`TPullCmd` 表对接可作为开发量小得多的一期方案
6. **卡片规格** — 门禁卡通常 Mifare/EM ID，与我们现有 NTAG213 NFC 员工卡不是一回事；是否一卡两用需先定
7. **考勤合规口径** — 工时上限、加班计算规则，会反向影响数据模型
