# 多批次出成率 + 成本反算 — 正确算法规格 + 现有数据适配评估

**日期**: 2026-06-20
**背景**: 客户提出"多批次出成率 + 人工成本反向卷积"方案（半成品做熟制时用多个半成品批次，"无法计算只能加权平均"）。superpowers 对抗式审计（6 维度 × 找反例 × 逐条证伪）发现客户那版公式有 **5 个会算错钱的硬伤**。本文给正确算法，并评估白垩纪系统现有数据够不够支撑。

---

## 0. 客户方案的 5 个硬伤（审计确认，都带反例）

| # | 硬伤 | 方向 | 反例（客户自己的数） | 严重度 |
|---|------|------|------|------|
| ① | 人工卷积上游分子口径错：三道都用固定分子(下游存活量50)÷各道自己产出(90/85/80) | 系统性**少算**上游人工，越上游/越损耗越严重；各道人工加起来 < 总人工（漏入虚空） | B链 修油 280×(10/95)=29.47 vs 正确 280×(10/40)=70 → **−58%** | HIGH |
| ② | 一单多熟制时盒数按(订单+熟制批次)去重 → 盒数翻倍 | 每盒成本**腰斩** | 200盒来自2熟制→算400盒→¥10/盒 vs ¥20 = **−50%** | HIGH |
| ③ | 支链跳工序时 `链式率连乘 + 原料=成品÷链式率` 把某道损耗套到没经过它的物料 | 系统性**高估**原料 | 反推129.6kg vs 真实120kg = **+8%**（注水链 +24%） | HIGH |
| ④ | 工序间有未记录的物料增减（掺外购半成品/解冻吸水）时，反推"原料"混入非原料质量 | 口径错配 | 掺20kg外购→反推122kg vs 真实100kg = **+22%** | MEDIUM |
| ⑤ | 多源混批 + 异质成本：split（每源投了多少）不可观测时，"卷积"和"加权平均"是**同一个缺失数据**，换算法不提精度 | 静默偏置成本 | A链8元/kg B链30元/kg，真实50:10=11.67 vs 估计78:22=12.84 = **+10%**（两法误差相同） | HIGH |

> 注：审计同时**推翻**了一个常见误解——"对出成率做加权平均是数学错误"。客户的 `calcByOrder` 综合出成率其实是 `Σ产出/Σ投入`（分子分母分别累加），这是**正确**的；78:22 是用来拆成本的，不是出成率权重。链式率连乘本身在质量守恒（每道总产出=下道总投入）下也是**精确**的——错只在"支链跳工序"破坏了这个守恒（硬伤③）。

## 1. 数据模型：生产 = 批次级有向无环图（DAG）

```
原料批次(叶) ──consume──> 修油批次 ──consume──> 滚揉批次 ──consume──> 焯水批次 ──consume──> 熟制批次 ──consume──> 气调成品订单(根)
                                                              (多源汇入: 熟制可同时吃多个焯水/滚揉批次)
```

- **节点 = 一个批次**（一道工序的产出）；带 `inputWeight / outputWeight / lossWeight / lossRate / durationMinutes / passCount / failCount / reworkCount`（`ProcessingStageRecord`），及 `outputQuantity / laborCost / materialCost`（`ProductionReport`）、`yieldRate`（`ProductionBatch`）。
- **边 = `MaterialConsumption`**（持久化）：`productionBatchId`(本批) + `batchId`(上游源批) + `quantity`(实测领用量) + `sourceType`(RAW_MATERIAL / SEMI_FINISHED) + `unitPrice / totalCost`。**这就是 split 的实测值**——多源汇入 = 多条 consumption 行，每行带 quantity。
- **叶子** = 原料批次（`sourceType=RAW_MATERIAL` → `MaterialBatch`）；**根** = 成品订单批次（QD），带盒数 + 净重。

## 2. 正确算法

### 2.1 反推原料 + 成本：逐路径物料平衡（**不要**率连乘反推）

从成品订单批次出发，沿 `MaterialConsumption` 边**逆向遍历到原料叶子**。每条边带**实测 quantity** → 直接累加绝对质量。

```
原料总量(本订单) = Σ over 叶子原料批次 ( 该原料批次被本订单链路实际占用的 quantity )
原料成本(本订单) = Σ ( 占用 quantity × 该原料批次 unitPrice )
```

- 每条支链只走它**真正经过的**工序，套它**自己**的投入产出 → 修正硬伤③。
- 外购半成品/吸水作为**独立的边/质量**进入图，不并入"原料"口径 → 修正硬伤④。
- 因为用实测 quantity 沿边累加，**根本不需要"链式率连乘 ÷"**——率只用于展示。

### 2.2 人工分摊：守恒分摊（gross-up 到本道产出口径）

每道工序人工按"**本订单实际占用该道产出的质量 ÷ 该道总产出**"分摊：

```
本订单对道k的分摊 = 道k总人工 × ( 本订单占用道k产出量 / 道k总产出量 )
本订单占用道k产出量 = 沿边逆推回道k产出口径的实测质量   （≠ 固定的下游存活量）
```

- **校验不变量**：对每道工序，`Σ(各订单分摊) == 该道总人工`（产出全消耗时）。任何工序出现 `Σ分摊 < 总人工` 即口径错 → 修正硬伤①。

### 2.3 出成率：展示用 `Σ产出 / Σ投入`（保留客户的正确做法）

每道综合出成率 = `Σ该道产出 / Σ该道投入`（多批次分别累加分子分母再相除）。**仅用于展示/预警**，不参与 §2.1 的成本/原料反推。

### 2.4 盒数 / 成品重量：按**订单**去重一次

盒数、成品净重是成品订单（QD）的固有属性 → 按 **QD 批次**去重一次；熟制及上游批次**只**参与成本拆分，不参与盒数计数 → 修正硬伤②。

### 2.5 混批成本：实测 split，并对"不可观测"显式披露

- 若混料点逐源 quantity **有实测**（见 §3）→ 直接用，硬伤⑤消失。
- 若某混料点确实只有总量没有逐源量 → 误差下界 ≈ `Δsplit × (源链成本差)`；**显式告诉客户这个误差**，而不是误以为"换成加权平均/卷积"能提精度。

## 3. 现有数据适配评估（够不够）

| 正确算法需要 | 现有载体 | 评估 |
|---|---|---|
| 批次→上游批次 的边 + 实测数量 | `MaterialConsumption`(batchId, quantity, sourceType, 成本)，结单时 `appendConsumptionLines(...,SEMI_FINISHED,...)` 落库 | ✅ **已有且可遍历** |
| 多源半成品 split（78:22 那种） | `ProductionSettlementRequest.semiFinishedConsumptions`(List，每笔 batch+quantity) → 落 `MaterialConsumption` | ✅ **实测，非估计** |
| 逐道投入/产出/损耗/合格/返工/工时 | `ProcessingStageRecord`(inputWeight/outputWeight/lossRate/passRate/reworkCount/durationMinutes) | ✅ 已有 |
| 每道人工 | `ProductionReport.laborCost / laborSegments`，`ProcessingStageRecord.durationMinutes` × 工价 | ✅ 已有 |
| 原料叶子 + 单价 | `MaterialBatch`(sourceType=RAW_MATERIAL) + `unitPrice` | ✅ 已有 |
| 成品盒数 + 净重 | `ProductionReport.outputQuantity / goodQuantity / warehouseOutQuantity` | ⚠️ 见待确认 3 |

### ⚠️ 开发前必须确认的 3 点

1. **批次粒度 vs 工序粒度（最关键）**：客户截图是"**每道工序开一个新批次**"（XY-001→GR-001→CS-002→SZ-002→QD-002，靠 `MaterialConsumption` 串边）。但系统里 `ProcessingStageRecord` 是"**一个批次内多道 stageOrder**"。两种表示必须对齐——六扇门到底是哪种？这决定 DAG 怎么遍历（跨批次走 consumption 边，还是批次内走 stageOrder）。**大概率是多批次串边**（符合截图 + 两点报工"半成品产出/投入"模型），但要核实。
2. **操作工报工是否真逐源选批次+填量**（WipBatchPicker / `semiFinishedConsumptions`）——split 准不准、硬伤⑤救不救得了，全取决于此。若实际只报总量、不报逐源，则混批节点要加"逐源称重/选批"采集。
3. **成品盒数 + 净重的权威字段口径**（盒 vs kg）——出成率链全程用 **kg**，盒数只用于最终"每盒成本 = 总成本 ÷ 盒数"。明确哪个字段是净重 kg、哪个是盒数，避免硬伤②类的单位混。

---

## 4. 落地建议

1. **不要**按客户那版"反向卷积/链式率连乘"公式直接开发——①②③ 都会进定价和毛利红线，是系统性错账。
2. 按 §2：**逐路径物料平衡（实测 quantity 累加）+ 守恒人工分摊 + 出成率仅展示 + 盒数按订单去重**。
3. 大头逻辑**可复用**已有 `MaterialConsumption` 图 + `ProcessingStageRecord` + 成本字段，不是从零造。
4. 开发前先敲定 §3 的 3 个待确认点。
5. 单元测试必含：跳工序支链、一单多熟制、一熟制多单、混批异质成本、注水(出成率>100%)——这些正是客户公式翻车的场景。
