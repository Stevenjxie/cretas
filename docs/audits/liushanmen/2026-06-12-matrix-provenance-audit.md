## 四、诚实边界(Ambiguous Items)

以下功能点在客户证据和spec之间存在合理模糊，不做硬性判定：

### 4.1 WorkflowEngine vs 简单审批状态机
**客户说了什么**: "系统需设置审批流"(付款)、"报损审批"、"撤回需加审批" — **有审批业务需求**

**判断边界**: 用简单3状态机(pending→approved→rejected)实现审批 = CUSTOMER-CORE；用WorkflowEngine + workflowInstanceId + 可配置流程图 = SPEC-ONLY  
**建议**: 简单状态机满足客户需求；WorkflowEngine对P0来说是gold-plating，现在已是dead code

### 4.2 16位分段编码严格实现
**客户说了什么**: 两段信息矛盾 — 一方设计了16位结构(行4192)；老板收敛"能搜到即可"(行4228)  
**判断边界**: 前3位主编码前缀 = CUSTOMER-CORE；完整16位层级字典管理 = CUSTOMER-ADJACENT偏SPEC-ONLY  
**建议**: 决策3已拍板"小补，16位列P1"；分段字典管理UI是P1 not P0

### 4.3 @RequirePermission细粒度权限注解
**客户说了什么**: "权限按模块交叉配置"、角色清单、"明确否决给全权限" — CUSTOMER-CORE业务需求  
**什么是模糊的**: @RequirePermission注解的粒度设计(模块级 vs 操作级 vs 数据级)  
**建议**: 注解本身是合理工程实现；但涌现出的细粒度扩展(>5种角色细分)超出客户描述范围

### 4.4 RN报工三阶段时序
**客户说了什么**: 现场看到一小时一报(六扇门微信群照片证)；需要投入+产出分开  
**什么是模糊的**: 三阶段状态机(投入→时段→产出)是spec推导，还是客户明确要求  
**判断**: 基于真实操作场景spec推导，属CUSTOMER-ADJACENT；客户原话未明说三阶段，但实地场景自然导出
