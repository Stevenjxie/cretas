# Cretas 产品能力 × 邓总餐饮数字化流程契合分析

> **核心问题**: 我们的产品能帮到邓总流程的哪些部分?
> **一句话结论**: 邓总流程的「进销存 → 财务 → 数据分析」三段,我们**已建好底盘 (STRONG)**,可以直接接;「数字化加速/稳定」这段不是产品功能问题,而是**组织落地问题**——而这恰好是我们三大差异化武器 (定制积木箱 / 设计级防呆 / AI对话语音OCR) 最能发力、也最能让邓总避免「金毛范囊式死亡」的地方。真正的 GAP 集中在 **3 个具体引擎** (取数自动化 OCR/语音、价格异常威慑、成本卡自动反推) 和 **1 个机制** (价值可视化回馈)。

## 2. 逐段能力契合 (痛点 → 已有能力+真实代码 → 差异化价值 → 缺口)

### 第 1 段 · 进销存全流程 — **STRONG**

**邓总痛点**: 验货→入库→对账→付款→盘点全靠人工单据流转,「拍照、下一家、贴历史单」操作地狱;元辉类供应商手写单录入麻烦;现金流被超额采购拖垮。

**我们已有能力 + 真实代码案例**:
- **采购下单一键防呆** — `ProcurementOrderCreateTool.java` (已核实代码):
  - R1: 数量上限 = 历史 PO 90 天均用量 × 3,preview 显 `"采购数量 X 超过上限 Y (月均 Z × 3 月 buffer)"` (代码 L205-212, L298)
  - R2: preview 必显物料名 + 推荐供应商 + 期望到货日 (L42)
  - R3: 供应商 ranking top3 (按 last-PO + 价格,L256)
  - R4: businessKey = materialId+supplierId+5min 窗口 → 重复下单返 409 + existingPoId + actionHint (L44, L238)
- **入库验收** — `PurchaseReceiveRecord.java`,带 `warehouse_id` 预留 + `aiInvocationMetadata` 来源追踪,为对账留接口
- **质检** — 16 个质检工具覆盖感官/物理/化学/微生物
- **电子秤 AI 识别** — `ScaleAddDeviceVisionTool.java`,拍照自动提品牌/型号/规格
- **调拨/出货/退货** — `TransferCreateTool` / `ShipmentCreateTool` (Issue #740 销售推送发货单待确认队列) / `ReturnOrderCreateTool`
- **真实 E2E 实证**: 六扇门 F006 已跑通「叮咚日报订单 → 逐道生产报工 → 成品入库 FG-AUTO → 出货 shipped」完整链路 (memory 多条 prod E2E 闭环记录)

**差异化价值**: 进销存底盘已是**生产级跑通的真实系统**,不是 demo。邓总不需要我们重建,只要接数据。防呆 R1-R4 直接缓解「超额采购拖垮现金流」「拿错供应商」「重复下单」。

**缺口**: ⚠️**取数自动化 (第一道防线,最高优先级)** — OCR 供应商手写单 / 语音补录还没接进采购入库主链路;目前仍是「拿单 → 手工录」。这是邓总最痛的点,也是我们最该先打的 (见 §5)。

### 第 2 段 · 财务 / 成本 / P&L / 成本卡 — **STRONG**

**邓总痛点**: 成本卡手工填「搞了一两个人不想干」;月结时间压力 (30 号对账 → 想 1-3 号出报表留 20 天调整);损耗次日要可见但责任不清。

**我们已有能力 + 真实代码案例**:
- **完整 P&L** — `IncomeStatementService.java`: 期间凭证按科目自动分桶 (REVENUE/COST/EXPENSE) → 毛利/营业利润/净利,含期末平衡检验 (diff ≤ 0.01)
- **资产负债表 / AR/AP** — `BalanceSheetService` + `ArApService` (账龄分段 0-30/31-60/61-90/90+,逾期率/回款率)
- **成本卡自动化 (超预期)** — `BomRecipe` + `BomRecipeItem`: 材料/人工/制造费用三分量自动算 + 出成率折算;`BomRecipeCreateFromTextTool` 从文本 (「麻辣牛肉 → 牛肉200g+花椒10g」) AI 生成成本卡 → **直接解决「手工地狱」**
- **配方版本管理** — `BomVersion`: DRAFT→PENDING→APPROVED→OBSOLETE 审批链 + 生效日期
- **损耗 + 盘点** — `RestaurantWastageRecordTool` (EXPIRED/DAMAGED/SPOILED 枚举约束 + 自动单号 WST-YYYYMMDD-NNN);`StocktakingRecord` 支持 10/20/30 号三次盘点,系统账面 vs 实盘自动算差异 (盘盈/盘亏)
- **F006 逐道成本实证** (memory): WorkProcess.standardHourlyRate × 人数 × 工时 + 领料折价 + WIP unitCost 滚动 → 逐道出成率 + 总人工成本,prod 真实跑通

**差异化价值**: 成本卡从「手工填」变「AI 文本/采购单反推自动生成」是**对邓总最直接的惊喜点**——这正是他说「搞了一两个人不想干」的痛点。P&L 无需改动即可对接邓总现有金蝶数据出月度报表。

**缺口**:
- 🟡 **损耗未绑档口/人** — `WastageRecord` 缺 `operator_id` / `section_code`,无法支持「今天损耗明天屌你」的按人责任制
- 🟡 **成本卡自动反推链不完整** — 有 BOM + 采购单价,缺「出菜数据 → 食材消耗」反推 (需打通 Kitchen 出单日志)
- 🟡 **月结自动闭环未实现** — 支持报表查询,缺「1-3 号自动期末结账 → 留 20 天调整窗口」的 AccountingPeriodService 编排

### 第 3 段 · 数据分析 / BI / AI 问答 / 体检诊断 — **PARTIAL → 偏 STRONG**

**邓总痛点**: 50 个品种逐行找品类的「查询地狱」;要「损耗明天可见 + 给方案不是给问题」;代运营渠道想做 AI 体检表 (体检报告→指出超标→给处方)。

**我们已有能力 + 真实代码案例**:
- **诊断引擎 + 结构化处方 (核心武器)** — `diagnostics_engine.py` + YAML 注册 (已核实):
  - `diagnostics_registry.yaml` 已注册 **11 个指标** (food_cost_ratio / labor_cost_ratio / cost_rigidity 等)
  - `cost_rigidity_high.yaml` 已有 **9 个 RxAction 结构化处方** (已核实): 如 `CR-A01` 带 `owner:店长 / timeframe:本周内 / priority:P0 / effort:low / expected_impact:人工成本 -¥3.2K/月, cost_rigidity 0.561→0.68`,还有 `expected_savings_formula` 算月度可节省金额
  - **这就是邓总要的「体检→指出超标→给处方」**,而且处方带责任人+时限+预估省钱金额
- **NL2SQL 自然语言问数** — `nl_to_sql.py` (LRU 512 条缓存),中文直接问「胡萝卜单价」「食材成本率趋势」→ 直解 50 品种查询地狱
- **Gold 层日级 KPI** — `gold_reads.py` (<100ms 响应),`GoldDashboardBuilder.java` 总营收/账单/客单价/门店数 → 对标邓总「5 号对账 → 想 1-3 号出报表」时间线
- **餐饮运营分析** — `RestaurantEconomicsAnalysisTool` 编排 3 子工具 (单店 P&L 一页纸 + 档口损溢根因 + 成本刚性诊断),**任一子工具失败标注「X 数据不可用」不编故事** (诚实底线)
- **代运营 SaaS 化支撑** — `restaurant_ops_gold` ETL 有 `format=llm` 返回白名单结构化数据 (防元数据泄露) 直接喂 LLM 生成诊断报告
- **真实 prod 实证** (memory): qhj 餐饮分析侧 16 问答接 gold 层,headed E2E 实测真数据 + 图表渲染

**差异化价值**: 我们的诊断不是「丢一堆图表给老板自己看」,而是「YAML 积木注册指标 + 自动对标 benchmark + 输出带责任人/省钱金额的处方」——这正是邓总代运营 AI 体检表的产品原型,**已经有真实落地的 playbook**。

**缺口**:
- 🟡 **诊断信号缺几个邓总关键指标**: 外卖依赖度/渠道毛利率 (需 BOM Layer 2 数据)、充卡赠送依赖度 (已注册无 playbook)、固定成本占营收比 (未注册 metric)
- 🟡 **BOM 精度待升** — 现状 Layer 1 (±15%),cost_rigidity playbook 要求 Layer 2 (±8%) 才精准诊断
- ❌ **价值可视化回馈缺失** — 诊断输出处方,但没有「这样做省了多少钱」自动反馈给门店/档口 (见 §4 金毛范囊死因)

---

### 第 4-5 段 · 数字化加速 / 稳定 — **PARTIAL,但这是机制问题不是功能问题**

**邓总痛点**: 数字化推不动会像金毛范囊一样死——采购没养成习惯、门店看不到价值、老板没指引;目标拆分 (年3000万→月→周→日) 缺实时 vs 计划预警;CRM 生命周期 + 阶梯提成无联动。

**我们已有的底子**: `SalesPlan` / `SalesPlanTrackTool` 实体框架、`PerformanceRule` + `PieceworkConfig` 绩效框架、AI Intent 自学习 (KeywordLearner/ExpressionLearner 渐进学邓总团队术语如「档口」「实财占比」)。

**这一段的真相**: 加速/稳定不靠新功能,靠 §3 的三大差异化武器 + §4 的价值可视化机制。GAP 见 §5。

## 3. 我们的三大差异化武器 (每个配真实落地案例作证)

### 武器一 · 高度定制化积木箱 — 「不要什么直接抱 0 来码」的低成本定制

**是什么**: 528+ 个 Java Tool + 51 个领域包 (restaurant 包 36 个 Tool) + 16 个内置 Skill,加上 Python 侧 **YAML 注册式诊断积木** (`diagnostics_registry.yaml` 加指标 + `playbooks/*.yaml` 加处方,**不用改 Python 代码**)。

**真实作证**:
- `cost_rigidity_high.yaml` (已核实): 一个 YAML 文件就定义了完整的「成本刚性诊断 + 9 条带责任人的处方 + 省钱公式」,新增一个邓总专属诊断 (如「青菜价格异常」) = 加一个 YAML,不动引擎代码。
- `SkillComposeTool.java`: 把多个已有 Tool 编排成新 Skill,**月结闭环只需组合 Invoice+Payment+Reconciliation 三个已有 Tool**,0.5 天。

**对邓总的话术**: 「你的每个特殊规则——价格异常容限、档口分摊、阶梯提成档位——都是往积木箱加一块,不是重新开发一套系统。定制成本被我们的积木架构压到平民价。」

### 武器二 · 设计级防呆 — 让文化素质低的员工也不会做错

**是什么**: `.claude/rules/fool-proof-design.md` (已核实) 5 大规则强制落地:Rule1 预先显边界 (不事后报错)、Rule2 上下文带身份信息、Rule3 自由文本改约束选择、Rule4 写操作幂等防重复、Rule5 dead-end 改导航 + 4 位一体错误处理 (response.message=UI 文案=sticky 显示+next action)。

**真实作证**:
- 客户原话证据 (rule 内): 六扇门 F006 仓管员张权「做仓管的年纪都比较大文化素质很低,你不能太依赖他们,最好的方法就是告诉他这个东西你要收多少就行了」——**这条防呆规范的起源就是真实仓管场景**,跟邓总「文化素质低员工也能用」诉求同源。
- `ProcurementOrderCreateTool` R1-R4 (已核实代码) 就是防呆 5 规则的标准实现。
- `RestaurantWastageRecordTool` 枚举约束 + 自动单号 + `StocktakingRecord` 自动读系统账面只让用户录实盘数。

**对邓总的话术**: 「金蝶/用友对仓管员不友好是它们 UI 复杂度太高。我们的设计哲学是『在用户犯错前阻止』而不是『犯错后报错』——这是我们跟传统 ERP 的核心差异,也是你说『文盲也能操作』的产品保证。」

### 武器三 · 便捷使用 (AI 对话 + 语音 + OCR) — 90% 操作零文本输入

**是什么**: AI Intent 7 层识别管道 + 563+ Tool 对话执行;讯飞语音 (`IFlytekVoiceService`) + AI 对话语音助手;DashScope Vision OCR (`DashScopeVisionClient`,品牌别名映射/铭牌标签解析);发票 OCR 自动核对 (`V20260606_03__invoice_ocr_columns`,带置信度+原始JSON+debug)。

**真实作证**:
- `FormAssistantService.java`: 自然语言 → 表单字段,DashScope 思考模式直连。
- `MaterialBatchCreateTool.java`: 正则提取「500公斤/300kg/100斤/吨」自动单位转换。
- `SkuVoiceDialog.tsx`: 全屏语音对话累积配置 SKU。
- 意图层 **W0 写护栏已 ship prod** (memory): 置信度无关的写操作确认门,「删除这个订单」会先确认不静默执行——AI 便捷的同时安全可控。

**对邓总的话术**: 「采购员说一句话/拍一张供应商单,系统自动建采购单 + 提取数量单位 + 推荐供应商。这就是把『拍照、下一家、贴历史单』的操作地狱变成对话。」

## 4. 数字化「加速且稳定」的故事: 我们如何让邓总不像金毛范囊那样死

**金毛范囊死因 (邓总自己诊断的)**: ① 采购员没养成习惯 ② 门店看不到价值 ③ 老板没指引。这三条**没有一条是『功能不够』,全是『落地机制缺失』**。我们用四个机制对症:

| 金毛范囊死因 | 我们的对症武器 | 真实落地 |
|---|---|---|
| **① 采购员没养成习惯** | 防呆 + AI对话/语音/OCR 把操作门槛降到「说一句话/拍一张照」 | `ProcurementOrderCreateTool` 防呆 R1-R4 + `FormAssistantService` 自然语言建单。习惯养不成往往是因为「太难用」,我们把难用消灭掉。 |
| **② 门店看不到价值** | **价值可视化回馈** (这是 GAP,必须补) — 把诊断处方的「省钱金额」自动算出反馈给一线 | `cost_rigidity_high.yaml` 已有 `expected_savings_formula` 和 `CR-A01: 人工成本 -¥3.2K/月` 这种带金额的处方。**底子已在,缺的是把它推送到门店/档口的回馈回路** (见 §5 GAP)。 |
| **③ 老板没指引** | 诊断引擎给的是**带责任人+时限+优先级的处方**,不是一堆图表 | `RxAction` 结构 (owner/timeframe/priority/effort/impact) = 直接告诉老板「谁、什么时候、做什么、能省多少」。诊断子工具失败诚实标注不编故事,老板信得过数据。 |
| **数据准确性 (邓总执念)** | 数据血缘 + 软删除 + 审计时间戳 + 诚实底线 | `PurchaseReceiveRecord.aiInvocationMetadata` 追踪来源;实体解析人工确认会写回 history 当金标准 (memory #389);P&L 期末平衡检验 diff≤0.01;Gold 层脱敏防营收泄露。**数据可信是数字化不死的地基**。 |

**故事一句话**: 邓总的数字化「加速」靠我们的便捷使用 (降门槛 → 习惯养成),「稳定不死」靠价值可视化 (门店看见省钱 → 自觉) + 诊断处方 (老板有指引) + 数据血缘 (信得过)。我们已经有了前 3 个的底子,**唯一必须补的是「价值可视化回馈回路」**——把已经算出来的省钱金额主动推给一线,而不是埋在诊断报告里。

## 5. 给 Steve 的落地建议

### 先打哪段最能体现差异化价值 (按优先级)

**P0 — 取数自动化 (OCR 供应商单 + 语音补录) 接进采购入库主链路**
- **为什么先打**: 这是邓总最痛的「第一道防线」,也是三大武器里「便捷使用」最直观的演示。底子已有 (`DashScopeVisionClient` OCR + `IFlytekVoiceService` 语音 + `FormAssistantService` 文本解析 + `V20260606_03` 发票 OCR),**缺的是把它们串进采购/入库的端到端工作流**,不是从零开发。
- **演示效果**: 拍一张元辉类手写供应商单 → 自动出采购入库单 → 这一个 demo 就能让邓总相信我们不一样。

**P1 — 成本卡自动反推 + 损耗按人/档口责任制**
- **为什么**: 直击邓总「成本卡手工地狱」+「今天损耗明天屌你」两大执念。`BomRecipeCreateFromTextTool` 已能从文本生成成本卡 (已超预期),只需补「Kitchen 出菜数据 → 食材消耗」反推 + 给 `WastageRecord` 加 `operator_id`/`section_code`。
- **演示效果**: 「冷餐间今天用了多少钱、跟谁的绩效挂钩」——按人透明化是组织变革的杠杆。

**P2 — 价格异常威慑引擎 (差异化护城河)**
- **为什么**: 邓总案例「青菜2.5→2、洗洁精110→150」「连续三次跟我这样玩」。`SupplierPriceComparisonTool` 已有价格对比,缺的是**时序规则**:同类物料相邻采购单价异常 (容限 ε~5%) → 报警 → 记录趋势 → 连续 N 次标高风险。**威慑化而非处罚化**重塑供应商话语权,这是金蝶/用友没有的差异点。开发量小 (1 Tool + 1 Rule,~2 天)。

### 哪些是真 GAP 要补 (诚实清单)

### 一句话给 Steve

**别想「补功能」,要想「接底盘 + 打三个引擎」**。进销存/财务/分析三段我们已经是 prod 跑通的真实系统 (F006/qhj 都有 E2E 实证),邓总不用我们重建。先用 **OCR/语音取数 (P0)** 做一个让邓总「哇」的演示,再用 **成本卡反推 + 损耗按人 (P1)** 兑现他的两大执念,最后用 **价格异常威慑 (P2)** 建差异化护城河。而数字化「不死」的真正答案不在功能列表里,在「价值可视化回馈」这个机制——我们已经把省钱金额算出来了 (playbook 里就有),只差把它推到门店/档口/员工面前,这是金毛范囊死、而我们活的分水岭。
